# EVEngine 模块 API 单元测试覆盖

> 状态：已讨论确认（方案：人工维护 Markdown 覆盖矩阵 + 约定驱动补测）。  
> 范围约定：以 **C++ 公开头文件 API** 为准；达标标准 = **happy-path + 主要错误/边界路径**。  
> 本轮样板模块：`data`、`filesystem`。其余模块先列入总表，API 明细后续展开。  
> 相关模块清单见 [模块设计.md](./模块设计.md)。测试框架见 [zeroerr 设计](./superpowers/specs/2026-08-04-zeroerr-test-framework-design.md)。

## 1. 目标与非目标

### 1.1 目标

- 建立跨模块 C++ API 单测规范（zeroerr + 现有 `test/`）
- 维护本文档作为长期进度表：模块总表 + API 明细（可分多轮推进）
- 本轮落地样板：`data`、`filesystem`（清单展开 + 缺口补测至达标标准）

### 1.2 非目标

- 不测脚本绑定层（Squirrel / `.nut` 冒烟不计入本矩阵）
- 不引入覆盖率工具或 YAML/JSON 自动化清单
- 不为本轮补齐未实现模块的实现与测试
- 不改模块公共 API 语义（仅补测；发现 bug 另开修复）

## 2. 覆盖矩阵约定

### 2.1 模块总表列

| 列 | 含义 |
|---|---|
| 模块 | 如 `data`、`filesystem` |
| 头文件入口 | 主公开头文件路径 |
| 实现状态 | 与模块设计对齐：`可用` / `部分` / `未实现` |
| API 展开 | `已展开` / `待展开` / `N/A` |
| 覆盖进度 | `x/y 已覆盖`；未展开为 `-` |
| 备注 | 依赖设备、阻塞项等 |

### 2.2 API 明细表列

| 列 | 含义 |
|---|---|
| API | `Class::method` 或自由函数（重载写清签名要点） |
| 头文件 | 声明所在文件 |
| 状态 | `未测` / `部分` / `已覆盖` / `N/A` |
| 用例 | `TEST_CASE` 全名（可多条，逗号分隔） |
| 缺口 | 缺的 happy / 错误 / 边界说明 |

### 2.3 状态判定

| 状态 | 含义 |
|---|---|
| **已覆盖** | 至少 1 条 happy-path，且覆盖该 API 主要错误/边界（非法参数、空输入、失败返回等，按语义） |
| **部分** | 有用例触及，但未达上述标准 |
| **未测** | 无对应用例 |
| **N/A** | 未实现、无可独立测点、或仅平台桩（本机跳过并在备注说明） |

### 2.4 清单来源

- 以公开头文件中的 public 方法 / 自由函数为准
- 不含 `private`、匿名命名空间、`Module_REG` 宏细节
- 构造/析构/赋值：仅当行为有契约（所有权、空对象、clone）时单独成行；平凡默认析构可不列
- 后端特化类（如 `physfs::Filesystem`）不单独列行；测抽象接口（如 `Filesystem`）即可
- 全模块进总表；未实现模块 API 展开为 `N/A`，不展开方法级明细，直至模块可用

## 3. 测试约定

### 3.1 框架与布局

- 使用 zeroerr：`TEST_CASE` / `CHECK` / `REQUIRE`
- C++ API 测放在 `test/<module>.cpp`（可按子域拆文件，并登记进 `test/CMakeLists.txt`）
- 现有 `.nut` 脚本冒烟可保留，**不计入**本覆盖矩阵

### 3.2 命名

格式：`Module.Subject.behavior`

示例：

- `data.ByteData.roundTrip`
- `data.JsonDocument.decodeInvalid`
- `filesystem.mount.missingArchiveReturnsFalse`

覆盖表「用例」列填完整 `TEST_CASE` 名，便于：

```text
unit_test --testcase=^data\.ByteData\.
```

### 3.3 Fixture

- **data**：直接构造 `DataModule` / 相关类型，避免不必要的全局单例
- **filesystem**：每用例独立 `init` + 临时 identity/source（或测试夹具目录）；写路径测后清理；失败路径用不存在路径 / 未 setup 写目录

### 3.4 本轮交付

1. 本文档：规范 + 全模块总表 + `data` / `filesystem` API 展开与现状标注
2. 按表补齐 `data`、`filesystem` 缺口至「已覆盖」
3. 本地跑通相关 `unit_test` / CTest

### 3.5 后续轮次

按总表优先级展开下一模块 API → 补测 → 更新本文档进度。不要求一轮完成全部模块。

## 4. 错误处理与维护流程

- **断言失败**：按 API 契约区分返回空指针 / 抛异常 / 返回 false；用例应对准真实契约，不为迁就测试改 API
- **发现实现 bug**：先记入该 API「缺口」或备注；修复与补测可同 PR，也可分 PR
- **新增公开 API**：合并前在对应明细表增加一行，状态 `未测`，并尽量同批补测
- **废弃 / 未实现**：标 `N/A` 并写明原因，勿静默删行（保留历史可见性）
- **进度更新**：补测合并时同步更新「状态 / 用例 / 覆盖进度」列
