> 状态：设计草案
> 日期：2026-08-23
> 相关文档：[模块编排与裁剪架构](./模块编排与裁剪架构.md)、
> [模块设计](./模块设计.md)、[API 使用约定](./API-CONVENTIONS.md)、
> [载具与武器组件 PR #207](https://github.com/EVEngine/EVEngine/pull/207)

## 一、愿景

EVEngine 不为开发者规定一种固定的游戏类型，也不内置一套不可拆分的“RTS Core”、
“RPG Core”或“经营模拟 Core”。引擎提供的是一组高性能、可裁剪、可反射、可被
Squirrel 组合的游戏机制组件。开发者使用这些组件描述事实、施加规则、订阅事件，
从而构造自己的游戏类型。

同一批组件应当能够组合出传统 RTS，也能够组合出带行政、将领、派系、忠诚与叛乱的
政治 RTS，还可以用于城市经营、舰队模拟、战棋、塔防或尚未命名的新玩法。

本文的核心原则是：

> **引擎负责通用事实、高成本计算、生命周期、数据验证和跨模块接缝；脚本负责规则、
> 策略、组合和具体游戏语义。**

### 1.1 目标

- 游戏模块可以独立使用，也可以通过统一契约组合。
- 游戏规则主要在 Squirrel 中实现，无需修改或重新编译引擎。
- 常见行为有开箱即用的默认策略，但默认策略必须可以关闭、替换或叠加。
- 高成本、批量、确定性敏感的计算可以下沉到 C++，同时保留脚本控制面。
- 编辑器可以从运行时 schema 和反射信息生成，而不需要引擎内置某一种编辑器产品。
- 模块之间保持可裁剪和单向依赖，不因新玩法产生向上 include 或依赖环。
- 同一份数据和规则可以运行于有渲染客户端、无头模拟、测试和编辑器预览环境。

### 1.2 非目标

- 不提供固定的 RTS 胜负规则、科技树、阵营或 AI。
- 不规定属性必须是生命、攻击、防御，也不规定关系必须是外交或忠诚。
- 不把“将领”“行政”“叛乱”等具体题材概念写入底层通用模块。
- 不要求每一种扩展都在逐实体、逐帧脚本回调中执行。
- 不让通用模块直接依赖 UI、编辑器或具体表现资源。

## 二、统一概念模型

组合式玩法由六类对象组成：定义、实体、组件、系统、策略和事件。

### 2.1 Definition：静态定义

Definition 是版本化、可验证、可热重载的静态数据，例如坦克模板、武器模板、官职模板、
资源类型或生产配方。Definition 使用稳定字符串 ID，运行时实体只引用 ID 或稳定句柄。

```squirrel
definitions.register("rank", {
    id = "rank.general",
    displayName = "General",
    authority = ["command_army", "govern_base"],
    commandCapacity = 8
});
```

Definition 不保存一局游戏中的可变状态。升官后的当前军衔、武器剩余弹药和基地当前库存
都属于运行时组件。

### 2.2 Entity：身份与生命周期

Entity 表示游戏世界中的一个稳定身份。将领、坦克、基地、经济点、阵营、编队、政策和
生产任务都可以是 Entity。实体类型不决定其全部行为；行为来自它拥有的组件和参与的系统。

每个需要持久化或跨模块引用的实体必须拥有稳定 ID。运行时句柄可以高效，但不能成为存档、
网络消息或 Definition 中的长期标识。

### 2.3 Component：事实状态

Component 只描述事实，不解释事实的游戏意义。例如：

- `Attributes`：实体有哪些基础值和最终值。
- `Ownership`：谁拥有实体。
- `Assignments`：谁以什么角色被分配给谁。
- `Relations`：两个实体之间存在何种有向关系和权重。
- `Orders`：当前排队等待执行的命令。
- `VehicleMotion`：载具的位置、朝向、速度与到达状态。
- `WeaponState`：弹药、冷却、装填和瞄准状态。

“忠诚低于 20 会叛乱”不是 Component；这是脚本规则。

### 2.4 System：通用状态转换

System 批量读取组件、执行通用算法并写回结果。例如：

- Pathfinder 根据可行走网格生成路径或 Flow Field。
- Steering 根据路径、邻居和约束计算期望速度。
- WeaponSystem 推进冷却、装填和挂点转向。
- ProductionQueue 推进有持续时间的任务。
- ModifierSystem 聚合属性或通道修饰器。

System 不应偷偷决定题材规则。生产队列可以完成一个任务，但不应自行决定完成任务意味着
生成坦克、通过法案还是训练将领。

### 2.5 Policy：可替换决策

Policy 解释“遇到这种情况应该怎么做”。它可以是内置 C++ 策略、Squirrel 回调、批量脚本
System 或若干 modifier 的组合。

```squirrel
production.setCompletionPolicy("spawn_unit", function(task, context) {
    return units.spawn(task.getProductId(), context.spawnPoint);
});
```

所有带明显游戏语义的默认行为都应被视为 Policy。例如 `vehicle` 中的默认 RTS 命令处理、
自动索敌和自动开火可以开箱即用，但必须允许脚本关闭或替换。

### 2.6 Event：已经发生的事实

Event 用于模块间的松耦合协作。事件描述已经发生的事实，而不是要求所有监听者执行某个
固定动作。

```text
order_completed      salary_unpaid       ownership_changed
weapon_fired         general_assigned    faction_created
resource_depleted    task_completed      entity_destroyed
```

行政系统可以监听 `salary_unpaid` 并降低将领忠诚；叛乱规则可以监听属性变化；外交 UI 可以
监听 `faction_created`。事件发布者不需要知道这些监听者是否存在。

## 三、模块关系全景

模块按照“越往下越通用、越往上越接近具体组合”的方向组织。下层不能 include 上层；可选的
反向协作通过 `eve::cap::provide/query`、listener、开放式 scene link 或事件完成。

```text
游戏脚本 / 项目规则
  行政、将领、叛乱、科技树、战役、胜负、AI 战略
                              │
组合与决策组件                │ 解释事实、选择策略
  state / blackboard / utility / influence / triggers
                              │
行动与流程组件                │ 推进可复用流程
  orders / production / weapon / vehicle / building / economy / rpg
                              │
社会与数值组件                │ 保存关系和规则输入
  attributes / modifiers / ownership / authority / assignment /
  relations / faction
                              │
世界与查询组件                │ 提供空间事实和高成本算法
  scene / map / grid / spatial / physics / sensing / animation
                              │
运行时与数据基础
  ECS / event / data / filesystem / schema / serialization /
  timer / thread / math / capability
                              │
表现与工具（旁路消费者）
  graphics / audio / particles / ui / editor / devtools
```

表现与工具不是玩法依赖链的顶点。它们观察玩法状态和事件，或通过开放式 link 绑定运行时对象；
无头模拟裁掉表现模块后，玩法仍应正确运行。

## 四、现有模块在架构中的位置

### 4.1 可直接作为底座的模块

| 领域 | 现有模块 | 组合职责 |
|---|---|---|
| 实体与层级 | `common/ECS`、`scene` | 运行时实体、组件查询、场景节点、开放式 link |
| 数据与持久化 | `data`、`database`、`filesystem` | JSON/二进制数据、SQLite、资源访问与热重载 |
| 地图与空间 | `grid`、`map`、`spatial` | 投影、A*/Flow Field/FoW、空间索引 |
| 仿真 | `physics`、`timer`、`thread` | 物理、时间和异步任务 |
| 数值与物品 | `rpg`、`inventory`、`economy` | 属性/效果雏形、容器、资源账本与采集 |
| 建筑 | `building`、`buildingfx` | 占格、校验、放置会话与可选表现桥 |
| 载具与战斗 | `vehicle`、`weapon` | 移动模型、命令适配、挂点、弹药、伤害和座位 |
| 表现 | `graphics`、`animation`、`particles`、`audio` | 视觉、动画、特效和声音 |
| 工具构件 | `ui`、`editor`、`devtools` | Inspector、Dock、History、Gizmo、调试接入 |

`rpg` 已经包含属性和 modifier 思想，但其 API 和命名更接近角色战斗。后续应评估是把其中的
通用数值内核提取成较低层的 `attributes`，还是扩展 `rpg` 使其能够作为任意实体的通用属性
服务。无论选择哪条路线，都不应复制两套不兼容的 modifier 语义。

### 4.2 建议补充的通用模块

| 建议模块 | 保存的事实或算法 | 不负责的具体语义 |
|---|---|---|
| `schema` | 字段元数据、约束、引用、继承、版本迁移 | 不生成某一种固定编辑器 |
| `attributes` | 基础值、最终值、modifier、依赖失效 | 不解释统率、忠诚或攻击力 |
| `ownership` | owner、controller、权限和能力查询 | 不决定为何转移所有权 |
| `assignment` | 带角色的实体到实体分配及反向查询 | 不定义将领、工人或市长 |
| `relations` | 有向标签边、数值关系、关系索引 | 不定义外交或好感规则 |
| `faction` | 阵营身份、成员、关系矩阵、共享控制 | 不提供固定胜负条件 |
| `orders` | 通用命令队列、中断、优先级、完成/失败 | 不规定 attack_move 的含义 |
| `production` | 有时长任务、槽位、暂停、取消和进度 | 不负责扣款或生成产品 |
| `sensing` | 批量空间查询、阵营/tag/可见性过滤 | 不决定目标价值 |
| `steering` | seek/arrive/path follow/separation/avoidance | 不提供完整 RTS 单位控制器 |
| `decision` | FSM、Blackboard、Utility、Influence Map | 不内置敌人战略 AI |
| `serialization` | 稳定 ID、组件快照、dirty tracking、迁移 | 不规定存档槽或联机协议 |

这些名字是职责边界，不要求每项都立即成为独立目录。若实现较小，可以先作为 `common` 能力
或现有模块内的子组件；只有当职责、依赖或裁剪需求足够独立时才声明新模块。禁止用一个
`gameplay` 大模块重新制造 God Module。

## 五、核心组合契约

### 5.1 属性与修饰器

属性系统面向任意实体和任意字符串/稳定键，不限制为角色战斗属性。

```squirrel
attributes.setBase(general, "command", 72.0);
attributes.setBase(general, "administration", 81.0);
attributes.setBase(general, "loyalty", 48.0);

attributes.addModifier(general, {
    id = "salary_unpaid:turn_42",
    attribute = "loyalty",
    operation = "add",
    value = -10.0,
    source = treasury,
    tags = ["politics", "temporary"]
});

local loyalty = attributes.getFinal(general, "loyalty");
```

modifier 至少支持稳定实例 ID、来源实体、标签、优先级、叠加规则和可选生命周期。系统应按
脏标记重算，不要求每帧遍历全部属性。其他模块读取最终值或订阅变化，不直接 include
`attributes` 的具体实现；跨层消费可以走轻量查询接口。

### 5.2 所有权、控制权与权限

所有权和控制权必须分离：基地可以属于国家，但由将领管理；军队可以属于阵营，但暂时由玩家
或 AI 控制。

```squirrel
ownership.setOwner(base, faction);
ownership.setController(base, general);
authority.grant(general, base, "manage_economy");
authority.grant(general, army, "issue_orders");
```

权限查询只回答“当前能否做”，不决定 UI 是否显示按钮，也不自动执行行为。

### 5.3 Assignment：带角色的任命图

Assignment 表达“实体 A 以角色 R 被分配给实体 B”。边必须可反向查询，并允许携带起始时间、
优先级、容量占用和自定义属性。

```squirrel
assignment.assign(general, "governor", base);
assignment.assign(general, "commander", army);
assignment.assign(officer, "subordinate", general);

local governors = assignment.assigneesOf(base, "governor");
local commands = assignment.targetsOf(general, "commander");
```

同一机制可表达工人岗位、英雄驻守、科研负责人、舰队司令和任务护送关系。

### 5.4 Relations：通用关系图

Relations 是有向、多类型、可带权重的实体关系图。

```squirrel
relations.set(general, ruler, "loyalty", 48.0);
relations.add(general, ruler, "resentment", 12.0);
relations.link(officer, general, "subordinate");
relations.link(general, faction, "member");
```

需要按起点、终点、关系类型和阈值建立索引，避免脚本扫描全部实体。外交、家族、派系、贸易、
上下级与仇恨都使用同一事实图，但各自的规则由脚本解释。

### 5.5 通用命令队列

`vehicle.moveTo` 等便捷方法可以保留，但底层命令应能用于步兵、飞机、建筑、将领和 UI 工作流。

```squirrel
orders.replace(tank, "move", { x=400, y=260 });
orders.append(tank, "attack", { targetId=enemyId });
orders.interrupt(tank, "retreat", { x=baseX, y=baseY }, 100);

local order = orders.current(tank);
orders.complete(tank, order.id);
orders.fail(tank, order.id, "unreachable");
```

引擎负责队列、优先级、中断、状态、超时、序列化和事件；Policy 负责把命令翻译成移动、瞄准、
生产或政治动作。`vehicle` 可以提供 `default_rts` OrderAdapter，但不得垄断命令语义。

### 5.6 生产与持续任务

Production 本质是有持续时间、槽位和生命周期的任务队列。它可以用于生产坦克，也可以用于
研究、维修、训练、行政命令和外交谈判。

```squirrel
local task = production.enqueue(factory, {
    kind = "build_unit",
    product = "tank.medium",
    duration = 12.0,
    context = { spawnPoint="factory_exit" }
});
```

成本检查、资源预留和完成结果通过 Policy/事件连接 `economy`、`inventory` 与游戏脚本，避免
production 硬依赖任何一种经济模型。

### 5.7 空间感知与目标查询

空间索引已有 `spatial`，地图已有 FoW；仍需要一个面向玩法的批量查询组合器，把常见过滤在
C++ 中执行，避免脚本跨边界逐个检查。

```squirrel
local target = sensing.circle(x, y, range)
    .requireTag("unit")
    .excludeFaction(selfFaction)
    .requireVisible(fog, playerId)
    .sortBy("distance")
    .limit(1)
    .first();
```

查询器只返回候选事实。目标价值、是否追击和是否允许误伤属于脚本策略。

### 5.8 脚本策略注册

目前部分模块只允许 C++ 注册 mobility、weapon logic、driver、damage modifier 或 placement
rule。为实现脚本组合，需要统一三档扩展方式：

1. **内置 C++ 策略**：高性能默认路径。
2. **脚本单体策略**：少量特殊实体或原型验证。
3. **脚本批量 System**：面向数百实体，按 batch 跨越 C++/Squirrel 边界。

```squirrel
vehicle.registerMobilityPolicy("hover", hoverPolicy);
weapon.registerFirePolicy("chain_lightning", chainPolicy);
building.registerValidatePolicy("needs_governor", validateGovernor);
```

脚本回调必须有明确的输入快照、允许修改的输出、生命周期和错误语义。不得把裸 C++ 指针、
临时引用或内部容器暴露给脚本。

## 六、跨模块协作方式

模块之间按照以下优先顺序协作：

1. 同一模块内直接调用强类型 API。
2. 游戏脚本同时持有两个模块并显式编排。
3. 通过通用 ECS 组件和缓存 view 协作。
4. 通过事件传递已经发生的事实。
5. 通过 `Capability` 查询可选服务或注册多监听者。
6. 通过开放式 scene link 连接变换和表现对象。

只有在消费方没有合理的脚本编排位置、且协作属于稳定基础设施契约时，才新增 Capability。
不得为了少写几行脚本就在低层模块中 include 高层模块。

### 6.1 事件契约

组合式玩法需要比字符串消息更强的事件元数据。推荐的事件信封包括：

```text
sequence        全局单调序号
type            稳定事件类型
source          直接来源实体
subject         主要受影响实体
causation       导致本事件的前序事件/命令
correlation     同一事务或玩法链 ID
tick            仿真 tick
payload         schema 验证后的载荷
flags           cancellable / replayable / transient
```

事件分为三类：

- `before_*`：可取消或修改请求，仅用于明确的事务扩展点。
- `*_changed` / `*_completed`：已经提交的事实，不可被监听者撤销。
- `visual_*`：非持久表现提示，可以在无头环境丢弃。

事件监听器不得依赖未声明的执行顺序。确需顺序时使用优先级，并在文档中说明原因。

### 6.2 事务与所有权转移

叛乱、基地占领、交易等操作会同时影响多个组件，需要通用事务边界：先验证全部操作，再统一
提交，失败则不产生半完成状态。

```squirrel
local tx = world.beginTransaction("rebellion");
tx.transferOwnership(base, newFaction);
tx.transferOwnership(army, newFaction);
tx.assign(general, "leader", newFaction);
if (tx.validate()) tx.commit(); else tx.rollback();
```

第一阶段不必实现通用 ACID 数据库；至少要提供命令预检、延迟事件发布和批量提交能力。

## 七、贯穿案例：行政、将领与叛乱

### 7.1 数据组成

将领不是一个封闭的 `General` God Class，而是一个拥有多个组件的实体：

```text
General Entity
├─ Identity / DefinitionRef
├─ Attributes：command、administration、loyalty、ambition、prestige
├─ Rank：当前军衔/官职 Definition ID
├─ Ownership：所属阵营
├─ Assignments：governor、commander、subordinate
├─ Relations：trust、resentment、friend、rival
└─ Status/Modifiers：负伤、欠饷、胜利、政策效果
```

基地、经济点和军队同样是实体：

```text
Base      = Ownership + BuildingWorld + ProductionQueues + Inventory + Assignments
Economy   = Ownership + GatherNode/Region + Ledger link + Assignments
Army      = Ownership + UnitMembers + Orders + Assignments + Morale Attributes
Faction   = Ownership root + Relations + Ledger + Policies
```

### 7.2 行政加成

行政系统查询基地的 governor，然后把一个带来源的 modifier 写入基地生产或经济通道：

```squirrel
function refreshGovernorBonus(base) {
    modifiers.removeBySource(base, "governor_bonus");
    local governor = assignment.firstAssignee(base, "governor");
    if (governor == null) return;

    local admin = attributes.getFinal(governor, "administration");
    modifiers.add(base, {
        id = "governor_bonus",
        channel = "production_speed",
        operation = "multiply",
        value = 1.0 + admin * 0.005,
        source = governor
    });
}
```

Production 只读取 `production_speed` 最终通道值，不知道该值来自将领、科技、天气还是建筑。

### 7.3 编队与统率容量

将领通过 `commander` assignment 负责一个 Army。脚本根据 command 属性和 rank definition
计算容量，超过容量时向军队施加组织度或命令延迟 modifier。Vehicle、Weapon 和 Orders
无需认识将领，只消费最终参数和命令。

### 7.4 升官与降级

Rank Definition 声明能力和容量；晋升规则由脚本检查声望、战绩和政治条件。晋升完成后更新
DefinitionRef/Rank 组件、刷新 authority grant，并发布 `rank_changed`。UI、AI、行政加成和
任务系统分别监听该事件。

### 7.5 叛乱

叛乱是组合规则，不是底层模块：

```squirrel
function evaluateRebellion(general) {
    local loyalty = attributes.getFinal(general, "loyalty");
    local ambition = attributes.getFinal(general, "ambition");
    local support = politics.subordinateSupport(general);
    if (loyalty >= 20 || ambition <= 75 || support <= 0.6) return false;

    local newFaction = factions.createFromLeader(general);
    local tx = world.beginTransaction("rebellion");
    tx.transferOwnership(general, newFaction);

    foreach (local base in assignment.targetsOf(general, "governor"))
        tx.transferOwnership(base, newFaction);

    foreach (local army in assignment.targetsOf(general, "commander"))
        if (politics.armyWillFollow(army, general))
            tx.transferOwnership(army, newFaction);

    if (!tx.validate()) return false;
    tx.commit();
    diplomacy.setRelation(newFaction, oldFaction, "hostile");
    events.emit("rebellion_started", { leader=general, faction=newFaction });
    return true;
}
```

这里复用了 attributes、relations、assignment、ownership、faction、transaction 和 event。
传统 RTS 组件只会观察到 owner/controller 变化，随后更新可控制单位、生产权限、FoW revealer
和目标敌我过滤。没有任何模块需要加入 `if (rebellion)` 特判。

## 八、数据、反射与脚本编辑器

完整编辑器由项目脚本构造，但引擎必须提供足够的自描述信息：

- 字段名称、类型、默认值和说明。
- 数值范围、枚举和 bit flags。
- Definition 类型与引用目标类型。
- 资源路径类型及可接受扩展名。
- 数组、对象、variant 和可选字段。
- stable ID、schema version 和迁移函数。
- 只读、运行时可改、需要重建等编辑提示。
- validator 返回结构化错误路径和错误码。

```squirrel
schema.define("vehicle", {
    maxSpeed = field.float(100).range(0, 1000),
    mobility = field.enumFromRegistry("vehicle.mobility"),
    mounts = field.array(field.reference("weapon_mount")),
    visual = field.resource("model,image").optional()
});
```

项目可以用 `ui`、`editor` 和 schema 自动生成兵种、将领、官职、政策或建筑 Inspector。
运行时、编辑器和 CI validator 必须使用同一套 schema，避免“编辑器能保存但游戏不能加载”。

## 九、帧序与生命周期

组合系统需要稳定但不过度僵化的阶段：

```text
1. input        采集输入和外部消息
2. command      脚本把输入/AI 决策写成命令
3. pre_sim      处理事务、权限、订单切换和脏状态
4. simulate     路径、移动、物理、武器、生产等固定步长系统
5. resolve      伤害、所有权、任务完成和规则结算
6. event        发布已提交事件，脚本响应并形成下一轮命令
7. present      场景 link、动画、音效、UI 和渲染
```

模块在 manifest 中声明参与的阶段和局部顺序约束，而不是由 `main.nut` 维护越来越长的隐式调用
顺序。脚本仍可选择不启用某系统或手动驱动独立实例。

固定步长是可选运行模式，不代表引擎内置 RTS Core。它是物理、回放、无头测试和同步模拟都能
复用的时间组件。

## 十、性能模型

组合自由不能以逐对象跨语言调用为默认代价。脚本 API 同时提供三种粒度：

- 便利对象 API：原型、少量特殊对象和编辑器操作。
- 缓存 ECS view：常规脚本 System。
- Batch/Buffer API：大规模单位、关系和空间查询。

```squirrel
local view = eve.query()
    .all("Transform", "Ownership", "Orders")
    .changed("Orders")
    .compile();

view.forEachBatch(256, function(batch) {
    orderPolicy.updateBatch(batch, fixedDt);
});
```

热路径要求：

- Capability 在初始化时查询并缓存，不在逐实体循环中按字符串查找。
- 关系、assignment、ownership 和 sensing 必须有反向/过滤索引。
- 属性 modifier 使用脏标记和依赖失效，不每帧全量重算。
- 高频事件支持批量读取、按类型队列和帧末清理。
- 脚本回调失败应隔离到对应策略，并提供实体、策略和 tick 上下文。
- 所有批量 API 都需要无渲染基准测试。

## 十一、序列化、热重载与兼容性

每个可持久化组件声明：

- schema ID 和版本。
- 稳定字段 ID。
- entity reference 字段。
- transient/derived 字段。
- 默认值和迁移函数。
- 热重载时 patch、重建或拒绝策略。

Definition 热重载不能让运行时对象持有悬垂指针。建议使用稳定句柄或 registry generation；
重载后系统按 Definition ID 重新解析，并发布 `definition_reloaded`。

存档和网络不是各玩法模块的直接职责，但组件应提供快照和 dirty tracking，使游戏项目可以自行
选择全量存档、增量存档、权威服务器或命令同步。

## 十二、模块设计检查清单

新增或修改玩法模块时必须回答：

1. 它保存的是事实、执行的是算法，还是解释规则的策略？
2. 是否把某一种游戏类型的语义硬编码进了通用组件？
3. 默认行为能否关闭、替换或叠加？
4. 脚本能否注册策略；大规模使用时是否有批量路径？
5. 是否通过事件、ECS 或 Capability 协作，而不是新增向上 include？
6. 没有 graphics/ui/editor 时能否无头运行？
7. 数据是否有 schema、稳定 ID、验证、热重载和版本迁移？
8. 组件和事件是否可序列化；实体引用是否稳定？
9. 错误属于编程错误还是可恢复失败，是否符合 API 使用约定？
10. 模块关闭时消费方是否能优雅降级或在配置期得到明确错误？
11. 是否有组件级单测、脚本组合测试和无头批量基准？
12. 能否举出至少两种不同游戏类型复用该组件的例子？

如果第 12 项无法回答，该能力很可能属于示例或项目脚本，而不属于通用引擎模块。

## 十三、建议落地顺序

### Phase A：统一组合接缝

- 定义统一 Policy 注册和生命周期契约。
- 扩展 ECS 缓存 query、changed filter 和 batch API。
- 定义类型化事件信封、因果链和批量消费。
- 统一 Definition schema、validator 和稳定引用。

### Phase B：通用社会与流程组件

- 从现有 RPG 能力中收敛通用 attributes/modifiers 语义。
- 实现 ownership/authority、assignment 和 relations。
- 提取通用 orders，使 vehicle 的 RTS orders 成为可选适配器。
- 实现通用 production queue，并通过 Policy 连接 economy/building/inventory。

### Phase C：高成本计算组件

- 在 spatial/map 之上提供 sensing 查询组合器。
- 提供 path follower、arrive、separation、avoidance 等 steering 原语。
- 提供 Influence Map、Utility、Blackboard 等 decision 积木。
- 为上述系统建立无头批量基准与脚本 batch 接口。

### Phase D：组合示例验证

- 传统 RTS 最小组合：经济、建筑、生产、载具、武器、订单和 FoW。
- 行政 RTS 组合：将领属性、任命、基地加成、统率容量、升降级和叛乱。
- 非 RTS 组合：用同一套 assignment/relations/production 构造城市或舰队模拟。
- 用脚本实现项目专属 Inspector，验证 schema 能力足以构建编辑器而无需新增专用 C++ UI。

## 十四、验收标准

本架构是否成功，不以“内置了多少玩法”为标准，而以组合成本衡量：

- 一个新规则可以通过新增脚本 Policy/System 接入，而不是修改三个 C++ 模块。
- 一个实体可以同时参加经济、行政、战斗和政治系统，而无需创建新的 God Class。
- 所有权变化后，订单、FoW、生产、AI 和 UI 通过通用事实与事件响应，无题材特判。
- 同一模块可以在至少两类明显不同的游戏中复用。
- 大规模批量逻辑不因脚本组合而产生不可接受的跨语言开销。
- 裁掉任何未使用玩法或表现模块后，剩余依赖图仍是合法 DAG。
- 项目可以基于 schema 和反射构建自己的编辑器，而不是等待引擎增加专用 Studio。

最终，EVEngine 提供的不是一套预制游戏，而是一种构造游戏规则的语言：C++ 模块提供可靠、
高效的原语，Squirrel 脚本决定这些原语组合后意味着什么。

## 十五、当前基础实现

首批实现已经提供 `schema`、`attributes`、`orders` 和 `social`。第二批进一步加入：

- `tags`：保存分类标签和能力声明，支持集合条件与反向索引。
- `effects`：保存带来源、标签、持续时间和堆叠策略的通用效果实例。
- `eventstream`：保存类型化事件信封，提供独立消费游标、保留策略和确定性快照。
- `definitions`：保存版本化 Definition，并用 generation 识别热重载后的陈旧句柄。
- `transaction`：保存、验证并冻结跨组件操作计划及 correlation/causation 日志。
- `statepatch`：以 compare-and-set 批次原子修改通用 JSON 状态，冲突时不产生部分写入。
- `authority`：裁决 actor 在 scope 上是否拥有某项 capability，并提供可解释的胜出规则。
- `production`：推进任意 owner 的多槽持续任务，不解释成本或完成产物。
- `policyregistry`：保存可发现、可热重载的策略描述符，确定性选择策略但不持有回调。
- `sensing`：在 `spatial` 之上批量过滤位置、阵营、tag 与可见性事实，只返回候选集。
- `steering`：提供 seek、flee、arrive、path target、separation 与 avoidance 数学原语。
- `decision`：提供标量 Blackboard、显式触发 FSM、Utility 评分和二维 Influence Grid。

这些模块均位于低层，不互相 include，也不解释题材语义。一个典型组合链为：脚本根据
`social` 关系和 `attributes` 最终值作出判断，用 `effects` 表示持续原因，以 `orders` 表达
后续动作，再把已经提交的事实写入 `eventstream`；`tags` 负责快速筛选参与者和能力。

`examples/composable-rebellion` 提供了首个贯穿验证：基地治理加成、欠饷降低忠诚、部属支持度、
将领叛乱、资产转移和后续命令全部由 Squirrel 组合完成，没有新增 `General`、`Faction` 或
`Rebellion` C++ 类型。该示例同时作为自动化脚本组合测试运行。

事务职责被有意拆成两层：`transaction` 负责可审计的意图、校验结果和生命周期，`statepatch`
负责通用状态的原子 compare-and-set。具体模块的适配执行仍由脚本或项目 System 完成，底层事务
不会反向依赖 Social、Economy 或其他玩法组件。示例将原子状态仓库作为所有权事实来源，只在
批次成功后更新 Social 查询投影并发布事件；冲突测试验证失败时不会转移一部分资产。

行政叛乱示例进一步验证了三项边界：治理加成必须同时满足 governor assignment 与
`govern_base` authority；Policy Registry 只选择 `governor_bonus` 名称，具体计算仍位于脚本；
同一 ProductionQueue 同时完成 `build_unit/tank.medium` 和
`issue_decree/decree.tax_reform`，证明持续任务模块不理解单位生产或行政命令的题材差异。

同一示例现在还包含一条完全由脚本编排的 AI 链：`sensing` 筛出可见敌军候选，脚本把候选
转换成 Utility considerations，`decision` 选择 attack 并推进显式 FSM，`steering` 只计算
arrive 期望速度。三个组件都不知道“敌人”“防御基地”或“攻击命令”的含义，因此同样能够
服务野生动物、交通工具、NPC 日程或政治代理人。
