# Tactics 模块设计：回合 / 棋盘 / 行动 / 反应

日期：2026-08-28
状态：v1 已实现（正式 GCC 构建仍需具备仓库工具链的环境验收）

## 1. 定位

`tactics` 是与 `rts` 同级的 **L5 domain composition profile**，用于搭建回合制战棋、策略 RPG、
小队战术和回合制小规模冲突。它负责“何时轮到谁、能做什么、在哪些格子做、
行动如何被插入或取消”，不负责具体数值战斗、显示或输入。

脚本入口：

```nut
local created = eve.Tactics().newBattle(
    "00000000-0000-0000-0000-000000001000", 42);
if (!created.ok) throw created.status.summary;
local battle = created.value;
```

模块设计优先满足以下目标：

1. **确定性**：同一初始状态和命令序列必须得到同一结果，便于录像、AI 模拟和联机同步。
2. **可组合**：像 `rts` 一样复用 `action` 生命周期、`attributes` 数值、`effects` 事实、
   `authority` 权限、`orders` 命令和 `transaction` 原子提交，
   但不强制任何一种角色或战斗模型。
3. **可解释**：行动被拒绝时返回稳定的 reason code 和上下文，供 UI、AI 和测试共用。
4. **无渲染依赖**：核心仿真可以在无 `graphics` / `map` / `scene` 的进程中运行。

## 2. 边界

### 2.1 模块负责

- 战局生命周期：`setup -> running -> ended` 。
- 回合、轮次与阶段推进，支持队伍交替和单位行动条两种策略。
- 战棋单位的战局身份、阵营、占位、朝向、行动资源与存活状态。
- 格子占用、邻接、移动成本、可达范围和确定性路径查询。
- 行动的提交、预检、消耗、执行、反应窗口与完成。
- 战局事件和可重放命令记录。
- 胜负条件的可插拔评估。

### 2.2 模块不负责

- 生命、攻防、技能、Buff 和伤害公式：使用 `rpg` 或游戏自定义系统。
- 地图素材、地形绘制和坐标投影：使用 `map` / `grid` / `hd2d` / 游戏表现层。
- 动画、镜头、特效、选格和 HUD：使用 `animation` / `camera` / `particles` / `ui`。
- AI 搜索算法：模块只提供可 clone 的快照和可枚举的合法行动。
- 网络传输和持久化容器：对外提供确定性命令与快照数据即可。

## 3. 分层与依赖

`tactics` 应与 `rts` 一样是 L5 的纯 CPU 领域组合模块。它提供战棋语义的短根实体、
适配器和系统调度，不复制底层 provider 的实现。首版显式依赖：

```cmake
eve_declare_module(NAME tactics LAYER 5 SCRIPT Tactics SLOT tactics
                   DEPS action attributes authority effects game_event grid
                        orders settlement statepatch transaction
                   GROUP 2d 3d web)
```

> 这是设计上限，不是要一次性加入的依赖清单。Slice A 实施时只声明实际 include 到的模块，
> 并用 `scripts/module_depgraph.py --check` 保持 manifest 与 include 图一致。`rpg` 不是直接依赖；战棋 RPG
> 通过 shared protocols 或游戏编排层连接，不让两个 L5 profile 互相 include。

运行时关系：

```text
Game / Squirrel
  ├─ tactics       回合、站位、合法性、行动与反应
  ├─ rpg           可选的角色战斗 profile，与 tactics 经共享协议组合
  └─ presentation  把仿真事件转成动画 / UI 意图

tactics
  ├─ grid          网格拓扑与投影值类型（不依赖 map 渲染）
  ├─ action        共享 ActionRuntime，tactics 只做领域 adapter
  ├─ attributes    通用属性权威，不在 tactics 内复制 modifier
  ├─ effects       通用效果实例生命周期
  ├─ authority     “谁在此阶段能做什么”
  ├─ orders        命令排队、中断与终态
  ├─ settlement    攻击/技能的可组合结算边界
  ├─ statepatch    结果 patch 表达
  ├─ transaction   资源与状态的原子提交
  └─ game_event    类型化的领域事件 schema
```

这一结构刻意对齐 `src/modules/rts/` 的方向：profile 拥有领域根实体和 adapter，provider
仍是唯一真值来源，跨领域关系使用强类型 Link/Handle，不长期保存 provider 裸指针。

## 4. 核心模型

### 4.1 稳定标识和格坐标

跨帧引用全部使用稳定 ID，不在命令、事件或快照中保存裸指针。

```cpp
using ActionId = LogicalId;

struct Cell {
    int x = 0;
    int y = 0;
    int layer = 0;
    auto operator<=>(const Cell&) const = default;
};
```

`Battle` / `TacticalUnit` / `TacticalSide` 的持久跨域身份使用 `SubjectRef`，定义与行动类型使用
`LogicalId`，本地 ECS 关系使用 generation-checked `ecs::EntityHandle`。不再另造一套字符串
BattleId/UnitId 作为并行身份系统。

`Cell` 是逻辑坐标；正方形、六边形、等距投影只改变邻接与世界坐标转换，
不改变行动协议。对六边形建议对外统一使用 axial `(q, r)`，不在 API 中混用 offset 坐标。

### 4.2 BattleState

```text
BattleState
  SubjectRef identity, seed, SimulationTick, round
  status: setup | running | ended
  phase: battle_start | round_start | turn_start | acting |
         reaction | turn_end | round_end | battle_end
  activeSide, activeUnit
  TurnPolicy
  BoardState
  UnitState[]
  ActionStack
  ObjectiveState[]
```

`Battle` 是战棋领域短根 ECS 实体，`TacticalUnit` 和 `TacticalSide` 是同领域的独立短根，
不继承 `rts::Unit` 或 `RPGActor`。它们之间通过强类型 Link 关联；稳定的游戏项目类型
可以在这些短根下派生。`Battle` facade 是唯一高层写入入口；查询对象只读。
一个战局拥有自己的计数器、随机源、
事件流和注册表，避免进程级单例导致多战局串扰。

### 4.3 BoardState

`BoardState` 只保存战术语义：

- topology：`square4 | square8 | hex` 或注册的自定义拓扑名。
- cell facts：是否存在、标签、高度、基础移动成本。
- occupancy：单位 -> 格子与格子 -> 单位的双向索引。
- edge facts：可通行性、额外成本、墙/门/放逐边等标签。

占位修改必须通过 `placeUnit / moveUnit / removeUnit`，不允许两份索引分别写入。
多格单位与同格多层占用不在 v1 中实现，但占位检查应通过 `OccupancyPolicy`，
避免把“每格最多一人”写死到路径算法。

### 4.4 UnitState

```cpp
struct UnitState {
    SubjectRef  identity;
    ecs::EntityHandle side;
    Cell        cell;
    int         facing = 0;
    bool        alive = true;
    int         actionPoints = 0;
    int         movePoints = 0;
    int         reactionPoints = 0;
    int         initiative = 0;
    std::vector<std::string> tags;
};
```

这里的点数是战棋回合资源，不是 RPG 属性的副本。它们由回合规则重置、被行动预留和消耗。
战斗数值以 `SubjectRef` 为公共键，由 `attributes` / `effects` 作为权威 provider；项目也可通过
强类型 link 关联 `RPGActor` 或其他领域实体，但战棋组件不长期保存它们的裸指针。

## 5. 回合调度

### 5.1 TurnPolicy

回合顺序不应写死在 `Battle::update`。内建两种 policy：

- `side_alternating`：阵营回合；一方单位在其 side turn 中行动。
- `initiative`：单位轮次；按 initiative 降序、`SubjectRef` 的 canonical key 升序打破平局。

扩展接口概念：

```cpp
class ITurnPolicy {
public:
    virtual void beginRound(BattleState&) = 0;
    virtual std::optional<SubjectRef> nextUnit(const BattleState&) = 0;
    virtual bool mayAct(const BattleState&, const SubjectRef&) const = 0;
};
```

第三方 policy 在 C++ 注册，数据中只存稳定字符串 ID。不允许 policy 直接播放动画或修改
RPG 属性。

### 5.2 显式状态机

每次调用 `advance()` 最多完成一个可观测迁移并发出事件；不使用一个无界 `while`
跳过多个阶段。这使 UI 、重放器和网络层都能在阶段边界停下。

```text
battle_start
    -> round_start
    -> turn_start
    -> acting <---------------------------+
         | submit action                  |
         v                                |
       reaction --(reaction stack empty)--+
         |
         +--(unit done)--> turn_end
                            | more units -> turn_start
                            v
                         round_end
                            | objectives unresolved -> round_start
                            v
                         battle_end
```

## 6. 行动协议

### 6.1 ActionCommand

```cpp
struct ActionCommand {
    LogicalId   definition;
    SubjectRef  actor;
    LogicalId   kind;          // move, attack, skill, wait, interact, custom.*
    Cell        targetCell;
    SubjectRef  targetUnit;
    std::string payloadJson;
    uint64_t    expectedRevision = 0;
};
```

`expectedRevision` 用于拒绝针对旧状态做出的命令。命令中不传入“最终伤害”或“必然命中”等结果，
结果必须由执行时规则产生。

### 6.2 处理管线

```text
submit
  -> normalize     补齐 ID，解析 payload
  -> authorize     是否轮到 actor，是否拥有行动权
  -> validate      目标、范围、路径、占位、资源
  -> reserve       预留 AP / MP / RP，防止反应期重复使用
  -> declare       发出 action.declared，打开反应窗口
  -> resolve       调用具名 ActionResolver
  -> commit        原子提交状态 patch
  -> complete      发出 action.completed / action.failed
```

查询和执行必须共用同一套 validator，避免 UI 显示可点但提交后被另一套规则拒绝。

```cpp
struct ValidationResult {
    bool ok = false;
    std::string reason;       // not_your_turn, occupied, out_of_range, no_ap ...
    std::string detailsJson;
};
```

不对外暴露翻译后的报错文字；UI 使用 reason code 做 i18n。

### 6.3 Resolver 和原子提交

内建 resolver：

- `move`：沿经验证路径产生一系列 `unit.moved` 事件。
- `wait`：结束当前单位激活。
- `face`：改变朝向。
- `custom.*`：由游戏注册。`attack` / `skill` 可以作为官方适配器，但不把 RPG 强绑到核心。

resolver 不直接写入 `BattleState`，而是生成 `StatePatch + DomainEvent[]`。全部 patch 通过不变式检查
后一次提交；失败则回滚预留资源，不留下半步移动或半次扣费。

## 7. 反应系统

反击、机会攻击、护卫、拦截和限时打断使用统一反应栈：

```text
ReactionWindow
  triggerEvent
  eligibleReactors[]     按 priority desc, initiative desc, SubjectRef canonical key asc 排序
  acceptedReaction
  depth
```

规则：

- 触发器只产生候选反应，不在扫描时立即修改状态。
- 每个反应仍是普通 `ActionCommand`，因此复用验证、资源和事件机制。
- 反应深度设置硬上限，v1 默认 8；超限产生 `reaction.depth_exceeded`。
- 同一 trigger + reactor + reaction kind 默认只触发一次，防止环。
- “是否弹出询问玩家”属于控制器/UI policy，不属于仿真核心。

## 8. 路径、范围与视线

v1 提供三种纯查询：

- `reachable(unit, budget)`：Dijkstra，返回每格最小成本及前驱。
- `path(unit, target)`：A* 或从 reachable 前驱表回溯，结果包含起点与终点。
- `cellsInRange(origin, min, max, metric)`：按 Manhattan / Chebyshev / hex distance 枚举。

确定性规则：相同 cost 时按 `(estimatedTotal, cost, y, x, layer)` 排序；不依赖
`unordered_map` 的迭代顺序。路径成本使用定点整数，不在同步逻辑中累加浮点数。

视线和掩体建议在 v2 以 `ILineOfSightPolicy` / `ICoverPolicy` 加入。v1 可先由游戏侧 validator
读取 cell/edge tags 实现，避免过早锁定 2D、2.5D 或 3D 的几何语义。

## 9. 与 RPG 的集成

`tactics` 管“行动机会”，`rpg` 管“行动结果的数值计算”。推荐由游戏层编排：

```text
tactics: action.declared(kind=attack, actor=A, target=B)
    -> game adapter: rpg.canCastSkill / runSettlement
    -> rpg: damage/status/cast events
    -> game adapter: tactics.applyOutcome(...)
    -> tactics: unit.defeated / objective.updated / action.completed
```

`applyOutcome` 只接受战术结果，例如 `defeatUnit`、`displaceUnit`、`grantActionPoints`、
`addTacticalTag`；不复制 HP 或 Buff 数据。如果未来多个高层模块都需要驱动 RPG，
再在 consumer 侧声明 `IRpgCombat` capability，由 RPG provider 注册；不添加向上 include。

## 10. 事件、快照与重放

所有状态变化产生带单调 sequence 的事件，事件类型使用点分字符串：

```text
battle.started, round.started, turn.started, phase.changed
action.declared, action.rejected, action.committed, action.completed
unit.placed, unit.moved, unit.facing_changed, unit.defeated
reaction.opened, reaction.accepted, reaction.closed
objective.updated, battle.ended
```

事件的 `causationCommand` 指向直接命令 sequence，`correlationCommand` 指向根命令 sequence，
反应链因此可追踪且能在恢复时验证引用完整性。

存档分为：

- `snapshotJson()`：完整持久状态、当前 revision、随机源状态和各稳定 ID 计数器。
- `commandLogJson(fromRevision)`：已接受命令序列，用于回放和联机调试。

`restoreJson()` 必须先在临时对象中解析并检查不变式，成功后再交换，禁止失败后留下半个战局。

## 11. 随机性

- 战局拥有显式 seed 和可序列化 PRNG 状态。
- 随机数只能在 action resolver 的 commit 路径上消耗；预览、UI 查询和 AI 枚举不能推进 PRNG。
- 事件记录随机结果和 roll index，但不以记录值替代重放时的状态一致性检查。
- 命中率、暴击等概率公式仍属于 RPG/游戏 resolver，不在 tactics 内置固定公式。

## 12. 脚本 API

```nut
local created = eve.Tactics().newBattle(
    "00000000-0000-0000-0000-000000001000", 42);
if (!created.ok) throw created.status.summary;
local b = created.value;
b.setTopology("square4");
b.addCell(0, 0, 0, 100);             // x, y, layer, moveCostFixed
b.addSide("00000000-0000-0000-0000-000000001001");
b.addUnit("00000000-0000-0000-0000-000000001002",
          "00000000-0000-0000-0000-000000001001",
          "game:hero", 0, 0, 0, 1, 100, 1, 20);
b.start("initiative");
b.advance(1, 1);
b.advance(2, 1);
b.advance(3, 1);
local moved = b.move("00000000-0000-0000-0000-000000001002", 1, 0, 0);

for (local i = 0; i < b.eventCount(); ++i) {
    local e = b.eventAt(i);
    // e.type / e.sequence / e.subject / e.causationCommand / e.correlationCommand
}
```

Squirrel 绑定中浮点数使用 `float` 或 lambda 转换，不直接绑定 C++ `double`。
高频的 cell 查询应提供结构化方法；JSON 主要用于扩展 payload、命令记录和快照，
不应迫使每个鼠标悬停查询都做 JSON parse。

## 13. 建议源码结构

```text
src/modules/tactics/
  Tactics.h / Tactics.cpp             Module facade 与脚本绑定
  TacticsTypes.h                      Cell / UnitState / command / event 值类型
  Battle.h / Battle.cpp               战局状态机与唯一写入入口
  Board.h / Board.cpp                 占位、邻接、cell/edge facts
  TurnPolicy.h / TurnPolicy.cpp       内建回合策略与注册表
  Action.h / Action.cpp               validator / resolver / patch / reservation
  Reaction.h / Reaction.cpp           反应栈与防环检查
  PathQuery.h / PathQuery.cpp         reachable / path / range 纯查询
  Objective.h / Objective.cpp         胜负条件注册与评估

```

单文件接近 1000 行时继续按职责拆分，不把所有脚本绑定和仿真逻辑堆入 `Tactics.cpp`。

## 14. v1 实施分片

### Slice A：战局核心

- `Cell` / `Board` / `UnitState` / `Battle`。
- setup、start、阶段迁移和两种 TurnPolicy。
- 事件序列与基本快照。
- 不接 RPG，不接渲染。

### Slice B：移动和行动

- reachable / path / range。
- `move` / `face` / `wait` resolver。
- validator、资源预留、revision 检查和原子 patch。

### Slice C：反应与胜负

- 候选反应、排序、递归深度和防环。
- eliminate / survive-rounds / occupy-cells 三个内建 objective。
- 战局结束后拒绝新行动。

### Slice D：脚本与 RPG 示例桥

- `eve.Tactics` 脚本绑定与 `docs/usr/modules/tactics.md`。
- `examples/tactics/`：最小方格战棋，脚本侧把 `attack` 事件接到 `rpg` 结算。
- 无窗口纯模拟测试作为主验收，渲染 smoke 只验证示例桥。

## 15. 测试与验收

新测试按子系统放入独立文件：

- `test/tactics_board.cpp`：占位双向不变式、方格/六边形邻接、不可通行边。
- `test/tactics_path.cpp`：可达成本、并列路径确定性、阻挡、超出 budget。
- `test/tactics_turn.cpp`：两种 policy、平局打破、跳过阵亡单位、回合资源重置。
- `test/tactics_action.cpp`：预检与执行一致、旧 revision、原子回滚、稳定 reason code。
- `test/tactics_reaction.cpp`：反应优先级、嵌套、深度上限、同触发器防环。
- `test/tactics_replay.cpp`：命令回放后快照字节级相同；中途恢复后继续模拟仍一致。
- `test/tactics_rpg_integration.cpp`：攻击 -> RPG 结算 -> 阵亡 -> objective -> battle end 的端到端链路。

必须满足的核心不变式：

1. 每个存活单位有且只有一个合法占位；占位双向索引始终一致。
2. 同一 Battle revision 内，一个行动的预检成本与提交成本一致。
3. 任何失败行动都不改变持久战局状态或 PRNG 状态。
4. 事件 sequence 严格递增，同一命令的 causation/correlation 链完整。
5. 快照恢复、命令重放和直接运行的最终持久状态相同。

## 16. v1 非目标

- 多格单位、飞行层和同格堆叠。
- 完整 3D 视线、弹道物理与可破坏掩体。
- 内置特定游戏的命中、暴击、夹击、背刺或高地加成公式。
- 动画锁和真实时间计时；仿真以离散命令与逻辑 tick 为准。
- 让 Squirrel 函数作为底层 pathfinding 或每节点 validator 回调；高频核心规则保持 C++ 实现。
- 网络 lockstep / rollback 协议本身；首版只保证它们所需的确定性和快照能力。

## 17. v1 已锁定的产品决策

1. 方格四向、方格八向与 axial 六边格同时提供。
2. 阵营交替与单位 initiative 都是内建 policy。
3. 反应窗口暂停并由调用方明确 accept/decline；候选排序保持确定性。
4. 首个示例为纯无渲染确定性模拟，图形表现由项目层组合。
