# EVEngine 重构代码质量与系统完整性规范

日期：2026-08-26
状态：已确认的架构要求
适用范围：新增模块、公共 API、跨模块整合、存量系统重构与 agent 实施工作。

## 目的

重构不能只做到“编译通过”和“局部测试通过”。每次修改还必须回答：失败如何表达、状态由谁拥有、对象能活多久、结果是否确定、跨线程是否安全、数据能否迁移、可选模块裁剪后是否仍成立。

本规范与以下文档共同构成重构约束：

- `领域短根继承与跨域组合架构.md`
- `Result检查与不得丢弃返回值规范.md`
- `2026-08-26-architecture-consolidation-checklist.md`
- `模块编排与裁剪架构.md`

## 1. API 语义

- 禁止新增语义含混的 `bool` 返回值。查询真假可返回 `bool`；可能失败的操作返回 `Result<T>`；需要表达是否发生变化时返回强类型 `Change::Changed/Unchanged`；按契约必定完成且无需结果时返回 `void`。
- 禁止新增 `nullptr/false + lastError` 公共接口。兼容层可以投影旧接口，但内部真源必须是结构化 `Result/Error/Diagnostic`。
- 可能失败、产生身份、转移所有权或建立生命周期责任的返回值，必须依照 `Result检查与不得丢弃返回值规范.md` 标记 `[[nodiscard]]`。
- 输出参数只用于有测量依据的性能敏感路径；普通 API 返回值或返回 owning value，避免输入、输出和部分修改语义混杂。
- 公共 API 不直接暴露内部容器的可变引用、迭代器或实现相关布局；返回 view、span、快照或领域操作。
- 每个指针、引用、view、span 和 handle 必须能从类型或 Doxygen 文档判断 `Owned/Borrowed/Observed`、可空性、有效期和失效条件。
- Public header 中的接口必须具有完整 Doxygen 契约，包括失败、线程、重入、所有权和失效语义。

## 2. 生命周期、所有权与 Link

### 2.1 返回类型选择规则

返回类型由语义决定，不允许把裸指针、`optional` 和 handle 当作可互换的个人风格：

| 语义 | 统一返回类型 | 适用条件 |
| --- | --- | --- |
| 必然存在、仅在当前同步作用域借用 | `T&` / `const T&` | 调用期间 owner 与地址稳定；不存在属于调用方违约或内部不变量；以基类引用返回时保留动态派发 |
| 可以正常不存在、仅在当前同步作用域借用 | `OptionalRef<T>` | `optional<reference_wrapper<T>>` 的统一词汇类型；“没有”是正常查询结果，不需要携带失败原因 |
| 可以失败且调用方需要原因、成功时借用 | `ResultRef<T>` | `Result<reference_wrapper<T>>` 的统一词汇类型；需要区分 `NotFound`、`StaleHandle`、`Unsupported`、权限或其他失败 |
| 小型或自然拥有的数据快照 | `T` / `std::optional<T>` / `Result<T>` | 返回值独立拥有数据，不依赖被查询对象的地址和生命周期 |
| ECS 对象身份可能跨帧、跨结构变更或进入队列 | `ecs::EntityHandle` | 解析时必须通过 world 的 generation/stale 检查；不得缓存 component/entity 地址 |
| 非 ECS registry 对象身份可能跨帧或热替换 | `RuntimeHandle<Tag>` 或领域强类型 handle | registry 是唯一解析入口并校验 generation；不得退化成整数 ID 或地址 |
| 唯一所有权转移 | `std::unique_ptr<T>` 或领域 owning value | 返回即明确把销毁责任交给调用方；多态所有权使用 `unique_ptr<Base>` 且基类具有 virtual destructor |
| 真实共享所有权 | `std::shared_ptr<T>` | 仅当多个 owner 的生命周期确实不可嵌套；不得为了避免设计 owner 而使用 |
| 连续只读数据借用 | `std::span<const T>` / 明确 view | owner 和失效边界明确；不得跨 mutation、异步或下一帧保存 |
| C ABI、第三方 ABI 或局部实现细节 | `T*` | 仅限边界或函数内部的即时 observer；公共 C++ 领域 API 默认不使用 |

补充判定规则：

- `optional` 只表达“值可能没有”，不表达错误。只要调用方需要知道为什么没有，就必须使用 `Result`。
- 公共 API 使用 `eve::OptionalRef<T>` / `eve::ResultRef<T>`，避免重复展开模板。它们只是借用语义的统一词汇，不延长生命周期，也不提供线程安全；禁止再包一层模拟指针操作的 owning-looking 类。
- handle 表达稳定身份，不表达对象当前一定存在。每次解析都可能返回 `StaleHandle` 或 `NotFound`；handle accessor 不得偷偷返回长期有效的裸指针。
- 引用表达非空的即时借用。`reference_wrapper` 只是让引用进入 `optional/Result`，不会延长生命周期，也不能跨 mutation 保存。
- 裸指针不作为“可空引用”的项目默认写法。允许的例外必须是 ABI、外部库接口、性能已测量的内部热路径，或严格局限于单个同步函数体，并在边界立即投影为上述类型。
- owning pointer 与 observer 不得使用同一种无标记类型表达；所有权转移禁止返回裸指针。
- public API 评审必须依次回答：谁拥有、能否正常不存在、是否需要失败原因、地址是否稳定、是否跨帧/异步/热重载。答案唯一决定上表中的类型。
- public API 还必须回答调用方是否需要动态类型。多态不会改变所有权规则：即时借用返回接口/短根基类引用；可空或可失败借用在该引用外包 `optional/Result`；跨帧保存领域 handle 并在解析时取得基类引用；所有权转移使用 `unique_ptr<Base>`。禁止按值返回多态基类、依赖对象切片，或以裸指针作为多态机制。

### 2.2 多态边界

- 稳定的“是什么”使用领域短根基类或最小接口；正交能力仍使用组件/组合，不因需要动态派发而恢复统一 `GameObject` 大根类。
- 查询一批同类对象时，优先由 ECS 的类型闭包/View 完成批量多态；不要构造一批 `Base*` 作为第二套对象索引。
- registry/provider 的开放扩展点可返回 `Interface&`、`optional<reference_wrapper<Interface>>` 或 `Result<reference_wrapper<Interface>>`。接口 owner 必须比本次调用活得更久；跨卸载边界改用 generation handle 或 capability lease。
- 需要在 variant 的封闭类型集合与 virtual interface 的开放类型集合之间做明确选择：玩法协议中可穷举且需要序列化的类型优先 tagged enum/variant；第三方 backend、策略或插件扩展优先窄接口动态派发。
- `dynamic_cast` 只能用于明确的边界适配或诊断，不作为日常领域分发。业务分发优先虚函数、visitor、variant 或 ECS query；反复向下转型说明基类契约不足或边界错误。
- handle 自身不负责多态派发；handle 解析器负责验证类型与 generation，并返回最窄的所需接口引用。错误类型必须返回 `TypeMismatch`/结构化 Diagnostic，不得返回空裸指针。

### 2.3 `Value` 与强类型领域对象

`eve::Value` 解决“数据形状在编译期未知或需要跨通用边界传递”，不解决对象身份、生命周期或运行时多态。它是 owning data tree，不是 `GameObject`、`any` 指针或 handle 的替代品。

使用 `Value`：

- schema 驱动、插件扩展字段、编辑器属性、脚本参数、配置/JSON、事件 payload、patch、通用 snapshot/artifact metadata 等形状由数据或协议决定的边界；
- common 层无法依赖具体玩法模块，但必须传递可拥有、可复制/移动、可验证和可序列化的数据；
- 不同 frontend/backend 之间需要一个 canonical dynamic representation，并在边界通过 codec 转成领域类型；
- 未知字段需要按 schema 策略保留或转发，而编译期 struct 无法表达这些扩展字段。

不使用 `Value`：

- 编译期已经稳定已知的核心玩法状态、热循环组件、物理 solver 数据和渲染提交数据；这些继续使用强类型 struct/component；
- 表达对象身份或跨帧引用；使用 `PersistentId`、`ecs::EntityHandle`、`RuntimeHandle<Tag>` 或领域 handle；
- 表达开放运行时行为或 backend 多态；使用窄接口/短根基类；
- 仅为了避免定义类型、绕过模块契约或把字段名字符串化；这会把编译错误推迟为运行时错误；
- 同时把 typed object 与 `Value` 都作为可变权威状态。`Value` 应是边界输入、输出、不可变 payload 或可重建投影，领域对象仍只有一个 canonical owner。

转换规则：

- 外部输入先解析为 owning `Value`，再做 schema/codec 验证，成功后一次性构造强类型领域对象；验证失败不得部分修改领域状态。
- 领域对象对外发布时通过唯一 codec 生成 `Value`；JSON、Squirrel、Editor、Network 复用该 codec，不各自复制映射规则。
- 已知字段读取失败需要诊断时返回 `Result<T>`；合法可缺失字段使用 `optional<T>`。不要让 `Value*`/空值同时承担缺失、类型错误和生命周期三种语义。
- 高频路径不得反复在 `Value` 与强类型之间转换；转换放在 admission、publication、serialization 或 inspector 边界。

生命周期规则：

- 一个根 `Value` 递归拥有其 string、array、object 和全部子 `Value`；复制产生独立深值，移动转移整棵树的所有权。发布到异步队列时按值移动或复制，不发布子节点地址。
- 对子节点、string、array 或 object 的引用/view 只是根 `Value` 的即时借用；根被销毁、移动、重新赋值、改变 active kind 或进行可能重排/替换节点的结构修改后全部视为失效。
- `Value` 不保存 native pointer、引用、ECS component、VM object、backend 对象或 `RuntimeHandle`。它保存的是数据，不是活对象。
- 需要描述另一个持久对象时，`Value` 中只编码 canonical `PersistentId`/`LogicalId`/URI 及可选 type discriminator，由边界 codec 解析；不得序列化地址、slot index 或进程内 generation handle。
- 仅进程内的命令/事件若确实需要对象身份，身份放在强类型 envelope 字段中，payload 仍可为 `Value`；不要把 handle 偷塞成无类型整数或字符串。
- snapshot/event/artifact 中的 `Value` 默认不可变发布。若 consumer 需要修改，先取得自己的副本或通过受控 patch/transaction 修改唯一权威状态。
- 从 `Value` 构造出的领域对象拥有自己的强类型数据，不得长期引用源树中的 string 或子节点；codec 完成后源 `Value` 可以安全销毁。

### 2.4 字符串 API

字符串类型同样由所有权、可空性和边界决定；`const char*` 不作为公共 C++ API 的默认字符串类型：

| 语义 | 统一类型 |
| --- | --- |
| 不保留的 UTF-8 文本输入 | `std::string_view` |
| 编译期/进程期静态名称（enum、kind、诊断 code） | `std::string_view` |
| 生成、拼接、解码或需要独立保存的输出 | `std::string` / `Result<std::string>` |
| 正常可缺失的 owning 文本 | `std::optional<std::string>` |
| 正常可缺失的即时只读借用 | `std::optional<std::string_view>` |
| 可失败的即时只读借用 | `Result<std::string_view>`，且 owner/失效条件必须明确 |
| 二进制缓冲区 | `std::span<const std::byte>` / `std::span<std::byte>`，不得冒充 C string |
| C ABI、第三方 API、printf/GL/Vulkan 等要求 NUL 结尾的边界 | `const char*`，在最窄边界使用 `.c_str()` |

- `string_view` 不拥有数据，也不保证 NUL 结尾；不得保存到下一帧、异步任务或 owner mutation 之后。需要保存就复制为 `std::string`。
- 返回局部 `std::string` 的 `string_view` 是悬垂错误；返回容器内部文本的 view 必须说明 mutation、rehash、replace 和 owner destruction 的失效条件。
- enum/kind 名称函数返回静态 literal 对应的 `std::string_view`；协议名称必须与 enum 定义或统一 codec 同处维护，不另建散落字符串表。
- `const std::string&` 只用于对象必有成员的同步 getter，且生命周期明显受 `*this` 约束；registry、热更或容器元素查询优先 owning string、可选 view 或结构化 Result。
- 可空性不得由 `const char* == nullptr` 表达；使用 `optional<string_view>` 或 `optional<string>`。空字符串是一个存在的值，不等于缺失。
- API 内部若需要传给 C 函数，先保证 owning `std::string` 在整个调用期间存活，再调用 `.c_str()`；禁止保存临时 `.c_str()`。
- 文件路径、URI、资源名和用户可见文本不是同一领域类型；跨模块稳定协议优先使用对应强类型（如 URI/LogicalId），只在解析/展示边界转换为字符串。

### 2.5 用类型状态证明数据与步骤已完成

网络、用户输入、文件、资源、插件和存档均属于不可信边界。数据刚进入进程时只能处于 unchecked/untrusted 状态；解析成功不等于业务有效，验证成功也不等于引用已解析或事务已提交。

推荐流水线：

```text
UntrustedBytes<Source>
  -> Result<Parsed<Value, Format>>
  -> Result<Validated<DomainInput, Contract>>
  -> Result<Resolved<DomainInput, WorldEpoch>>
  -> Result<Prepared<Operation>>
  -> Result<Committed<Receipt>>
```

设计规则：

- `Unchecked<T, SourceTag>`、`Parsed<T, FormatTag>`、`Validated<T, ContractTag>` 等类型必须带来源/契约 tag；禁止只有无语义的全局 `Checked<T>`，否则不同 schema、权限和版本会被误认为等价。
- 未验证 wrapper 不向普通业务代码暴露 `T&`、`operator->`、隐式转换或 public `take()`。只有指定 parser/validator 能消费它；否则只是给不安全数据换了名字。
- 状态转换消费旧值（通常接收 `&&`、类型 move-only），成功返回 `Result<NextState>`。失败保留结构化 Diagnostic，并且不得发布部分状态。
- `Validated<T, Contract>` 构造函数私有，仅 validator/factory 能创建；不得允许调用方通过 aggregate initialization、公开 tag 构造或 `static_cast` 伪造证明。
- 解析、schema 验证、领域不变量、权限/引用解析是不同阶段，不得把“JSON 能 parse”当作“可进入系统”。每个阶段只证明其类型名声明的事实。
- validation contract 必须包含版本或策略身份，例如 `Validated<PlayerCommand, ProtocolV3>`、`Validated<Definition, VehicleSchemaV1>`；热更新 contract 后旧 validated 值不能自动获得新证明。
- `Resolved<T, Epoch>` 中的运行时引用只在对应 world/registry epoch 有效；跨帧保存仍使用 handle。typestate 不能替代 generation/stale 检查。
- 步骤性工作使用有领域含义的状态类型，例如 `DecodedImage -> UploadedTexture`、`PreparedTransaction -> CommittedReceipt`、`GeneratedMesh -> ValidatedMesh -> PublishedArtifact`；避免难读且可误接的通用 `Step<1>/Step<2>`。
- 可回滚操作把 prepare 与 commit 分开：prepare 产生 owning candidate，不改变可观察状态；commit 消费 candidate 并一次发布。析构不得暗中完成 commit。
- 类型状态只用于有真实错误代价、顺序依赖或安全边界的流程。普通局部两步计算不应为了形式增加 wrapper；必须能指出它阻止的具体非法状态。
- 跨 Squirrel/C ABI/网络边界无法保留 C++ typestate 时，在边界 adapter 中重新建立证明，不接受外部传入“已验证”标志。

验收要求：针对每条 typestate 流程增加编译期/API-shape 测试与运行时失败测试，证明未完成前无法调用后续 API、失败不发布状态、旧 contract/epoch 的证明不能越界复用。

典型示例：

- Inspector 保存 UI ECS 对象：保存并返回 `UIHostHandle`，使用时解析，不保存 `UIHost*`。
- registry 按名称即时查询定义：正常缺失用 `optional<reference_wrapper<const Definition>>`；缺失需要诊断则用 `Result<reference_wrapper<const Definition>>`。
- `UISystem` 的必备 backend：安装使用 `UIBackend&`，拆卸使用独立 `clearBackend()`；可选查询使用 `optional<reference_wrapper<UIBackend>>`。
- viewport 查询：正常不存在使用可选引用；创建可能失败则使用 `Result<reference_wrapper<ViewportState>>`。

- 禁止把临时裸指针或借用引用保存到下一帧、异步任务、回调队列或模块卸载边界；跨帧身份使用 owning value、`ecs::EntityHandle` 或带 generation 的强类型 handle。
- 每种跨域 `Link` 必须定义：谁创建、谁拥有、谁销毁、源先销毁、目标先销毁、restore/hot reload 后如何重建，以及 stale 如何被检测。
- 析构函数不得执行可能失败的业务提交、网络/磁盘持久化或需要调用方处理错误的操作。析构只做 noexcept 资源释放；显式 `close/commit/shutdown` 返回 Result。
- 仅在真实共享生命周期时使用 `shared_ptr`；默认使用 value、`unique_ptr`、handle 或 observer。
- 一份可变业务状态只能有一个权威 owner。其他模块保存引用、缓存或投影，并明确同步和失效协议；禁止 Physics、ECS、Render、Script 各自维护无法判定真源的副本。

## 3. ECS 使用规则

- 新增或重构 ECS System 前，先声明：Entity 类型范围、组件 View、读取组件、写入组件、结构变化、发布事件、依赖服务和执行阶段。
- 类型继承只表达稳定的“是什么”，组件表达正交能力和批量数据，跨领域关系使用 Link/Handle；不得引入统一 GameObject/GameplaySubject 大根类。
- 每个组件应标注其类别：hot/cold、authoritative/derived、persistent/transient、replicated/local、owned/linked。分类决定布局、序列化和同步策略。
- 遍历 View 时的 create/destroy/add/remove component 必须通过现有 deferred mutation 机制，除非 API 明确证明当前操作安全。
- 派生实体加入基类查询闭包前，必须满足基类所有系统的不变量；基类组件是行为承诺，不只是内存复用。
- Solver、渲染图、procgen 中间网格等专用密集数据结构不得为了“统一”而逐元素 ECS 化。

## 4. 时间、随机性与确定性

- Gameplay、procgen、physics 仿真不得直接读取 wall clock；统一由 scheduler/context 注入 `SimulationTick`、`Duration/dt` 和 time source。
- 随机数必须由显式 seed/context 注入。子系统使用稳定、命名的 RNG stream 派生规则，禁止依赖调用顺序偶然共享全局 RNG。
- 需要 replay、存档恢复、网络同步或 CPU/GPU 后端互换的系统，必须记录确定性等级：bit-exact、tolerance-bounded 或 explicitly nondeterministic。
- 浮点、并行归约和 GPU backend 必须定义容差及可观察结果，不得用“看起来接近”代替契约。

## 5. 线程、异步与回调

- 非线程安全 API 必须标明 thread affinity（main/render/simulation/worker）；线程安全 API 必须说明并发读写保证。
- Worker 任务返回 owning CPU data、ID 或消息，不返回指向 engine/world 临时对象的裸指针。
- 回调必须声明是否允许重入、是否允许取消自身/其他订阅，以及调用发生在哪个线程。
- 禁止持锁调用未知外部 callback、脚本、事件订阅者或 capability provider；先复制必要状态或排队，释放锁后派发。
- 异步 API 分开表达启动失败和完成失败；TaskHandle 的 cancel/detach/join 生命周期不得由隐式析构猜测。

## 6. Schema、序列化与恢复

- 所有持久化或跨进程格式必须具有稳定 schema id 和 schema version，并给出兼容性与 migration 策略。
- 存档默认支持当前版本和前一个已发布 schema 版本；窗口外交给显式离线迁移工具，未知新版本必须拒绝。
- 每种格式必须明确未知字段政策：保留、忽略或拒绝；禁止不同 backend 默默采用不同策略。
- restore/import/apply patch 默认具有强事务保证：验证或构建失败时，原有可观察状态保持不变。
- 同一领域对象只保留一个 canonical serializer；JSON、Squirrel、Editor、网络和 snapshot 通过 adapter 投影，不各自维护独立真源。
- 确定性 hash 只包含规范化业务状态，不包含 wall-clock、地址、容器偶然顺序或 backend 临时数据。

## 7. 模块边界与可裁剪性

### 7.1 模块存在性与组织规则

每个独立 module 必须用证据回答以下问题；不能仅因目录、作者或概念名称不同而拆分：

- 它是否拥有单一、可描述的职责和权威状态？
- 它是否有独立生命周期、初始化/关闭顺序或线程亲和性？
- 它是否能在至少一个受支持 profile 中被独立裁剪，并且裁剪后依赖闭包有实际收益？
- 它的公共契约是否比内部实现边界稳定，且 consumer 不需要同时依赖其“配套模块”才能完成每次操作？
- 它是否避免循环依赖和上下层反向 include，而不是通过拆 module 把循环隐藏到 capability/global singleton？
- 至少两个真实 consumer 是否使用其稳定契约；若只有一个 provider/consumer 对且永远同步演进，优先同 module 子目录或 private component。

组织决策：

- 职责相同、生命周期相同、总是共同启用、存在大量双向调用或重复类型的模块应合并；不得用 adapter 掩盖永久的一对一耦合。
- 职责不同但名称相近的模块应重命名为实际语义，不让调用方通过历史知识猜边界。
- 一个公共体验可以由 facade 组合多个 module，但 facade 不得成为第二权威状态；core、adapter、presentation 仍保持可验证依赖方向。
- 大 module 只在存在真实裁剪、后端替换或生命周期边界时拆分；仅为缩短文件或并行开发应拆 translation unit/子目录，不自动升级成 module。
- 小 module 若只有类型别名、转发 facade、单 consumer 或没有独立测试/profile，应触发“合并回 owner”评审。
- module 名称使用职责名而不是过宽领域名。`event`、`system`、`data`、`common` 等宽泛名称必须有清晰二级边界，新增宽泛 module 禁止进入 manifest。

`event`/`game_event` 当前整改结论：

- 现 `event` 是 transient platform event loop/message queue：SDL pump、platform sink、window/input dispatch、worker-to-main wakeup；不承诺持久化、replay、schema 或领域因果关系。
- 现 `game_event` 是 deterministic domain event log：稳定 EventId、stream sequence、causation/correlation、schema、retention、snapshot/restore；不负责 OS 输入泵或主线程唤醒。
- 两者职责、生命周期和裁剪价值不同，不应为“统一名称”直接合并。固定重命名为 `platform_event` 与 `game_event`；前者服务平台循环，后者是玩法事件公共入口，其持久序列组件命名为 `GameEventLog`。
- `platform_event::Message` 不作为通用 gameplay event；`game_event::GameEventEnvelope` 不用于每帧输入和临时回调。需要把平台输入记录进 replay 时，由明确 adapter 从 validated input command 投影成 typed `GameEventLog` entry。
- `GameCommand` 表达尚未执行的请求，`GameEvent` 表达已经发生并通过领域验证的事实；禁止把 command 直接追加成“已发生事件”，也禁止用 event log 代替 command queue。
- 只有 replay、同步、存档、审计或跨领域事实传播需要的事件进入 `GameEventLog`；局部临时 callback、UI 点击和渲染通知留在各自 owner 内。
- 重命名必须一次更新 manifest、模块类、namespace、bindings、provider、consumer、测试与文档；不永久保留两套 module 名或双注册入口。

`presentation` 当前整改结论：

- 当前模块只包含动态属性 schema、校验和跨来源读写/观察端口，并不拥有渲染、UI 呈现或 simulation-to-view 投影职责；`presentation` 与 `PropertyModel` 都会误导其真实角色。
- 固定重命名为 `property_access`；其稳定领域命名空间使用 `eve::property_access`，核心端口命名为 `IPropertyAccess`，诊断码使用 `property_access.*`。不得保留永久的 `presentation`/`property_model` 兼容 module、namespace 或双注册入口。
- `IPropertyAccess` 仅在 consumer 必须运行时多态地消费不同 authority 时使用。目前真实 provider 是 Squirrel reflection adapter 与 editor transaction/revision adapter；UI 是共同 consumer。单一反射调用链应直接使用 reflection API，不得被迫套一层 adapter。
- `Value`、`Result`、`Subscription`、`OptionalRef` 等无属性领域语义的机制属于 common；`PropertySchema`、`PropertyDescriptor`、属性约束校验和 `IPropertyAccess` 属于 `property_access`。
- 删除仅为别名存在的 `presentation/Value.h`，`property_access` 直接依赖 `common/Value.h`。common 不得吸收属性编辑 flags、presenter hints、schema 或访问端口状态。
- 当前公开 `DynamicPropertyModel` 只有测试 consumer，不满足落地原则；若找不到生产 authority，删除公共实现并用 test fixture 测试契约，不得以“未来可能使用”保留。
- `scriptmodel` 是 Squirrel/reflection adapter；editor 是事务 adapter；UI 与 automation 是 consumer。各层不得复制 property kind、enum、finite、range 或 read-only 校验。
- `IPropertyAccess` 只暴露 owner 明确声明在 `PropertySchema` 中的字段，不允许借此向任意对象临时挂接数据，也不得成为第二权威状态。动态附加数据若确有需求，应另行评审 `PropertyBag`/`ExtensionSet`；ECS 对象优先使用显式 component。

- 跨模块调用遵循 consumer-owned interface 和 capability provider；禁止新增向上 include 或通过公共 header 泄漏重依赖。
- 公共 header 应使用 forward declaration、Pimpl 或稳定 value type 控制依赖扇出；新增依赖必须通过 module dependency graph 检查。
- 声称 optional 的依赖必须在“存在”和“不存在”两种构建/运行配置中测试。缺失时应返回 `Unsupported` 或使用有文档的等价 backend。
- capability 查询集中在 composition root、adapter 或明确边界，不得在业务逻辑中散落 `if (graphics)`、`if (physics)` 分支。
- 公共 facade 可以保持模块整体体验，但内部 core、adapter、presentation 的职责和依赖方向必须可验证。

## 8. Error、日志与降级

- Error/Diagnostic 使用稳定 code；message 面向人类，可本地化且不得成为程序分支依据。
- 日志不能替代错误传播。调用方需要决策的失败必须返回 Result、事件或任务完成状态。
- 禁止静默 fallback。每个 fallback 必须分类为：预期等价、能力降级、仅开发环境或禁止；并记录触发原因和可观测状态。
- 可恢复业务失败不得触发 invariant assert；参数违约、stale handle 和内部不变量不得被包装成普通“失败后继续”。

## 9. 测试与 CI 门禁

- 修复缺陷前先建立最小回归测试；重构公共协议时同时更新接口、所有 provider、所有 consumer 和契约测试。
- 同一接口的多个 backend/provider 必须运行共享 contract test suite，不能只测试各自 happy path。
- 必须为关键事务与生命周期加入 failure injection：分配失败、provider 缺失、restore 中断、callback 重入、stale handle 和 backend 切换。
- soft skip 必须结构化上报原因、owner 和计数。CI 对新增 skip、allowlist 和 fallback 设预算，禁止无提示增长。
- 跨模块重构至少增加一条端到端组合路径，并覆盖相关裁剪 profile；局部单元测试不能替代整合验证。
- 涉及 replay/serialization 的修改应具有 round-trip、旧版本 migration、未知新版本拒绝和确定性 hash 测试。

## 10. 复杂度与技术债

- 大文件不继续堆叠职责；约 1000 行以上 `.cpp` 按稳定边界拆分后再扩展。类或函数同时承担注册、解析、执行、上传、绑定等多种职责时应触发拆分评审。
- 新增 `TODO/HACK/FALLBACK/ALLOWLIST` 必须附带 issue、owner、原因和移除条件或期限。
- 废弃 API 必须提供 replacement、迁移窗口、调用点清单和删除条件；禁止永久保留双真源。
- 不以抽象层数量衡量质量。公共抽象至少由两个真实 consumer 验证，并应减少重复契约或依赖，而非只转移代码。

## 11. 设计必须进入真实系统

- 新系统、新抽象和新协议必须指出至少一个恰当的生产调用边界，并在同一轮整改中接入；只有定义、注册接口或单元测试，不等于系统已经完成。
- 接入新系统时必须删除、收敛或明确迁移原有重复实现。禁止新旧两套权威路径长期并存，也禁止只增加一层 facade 而不改变真实数据流。
- 每项设计验收必须提供“使用证据”：真实 producer、真实 consumer、调用入口、失败如何传播，以及至少一条覆盖该生产路径的集成测试。
- 若尚无合理调用点，设计应保持为实验性提案或私有实现，不进入稳定公共 API，不为预想需求扩展能力。
- 不以“未来可能使用”为过度设计辩护。抽象的复杂度必须由当前明确需求、重复消除或边界隔离收益支撑。

## Agent 重构交付清单

执行重构的 agent 在提交结果前必须逐项确认，并在最终报告中说明适用项：

- [ ] 没有新增含混 `bool`、`nullptr + lastError` 或可被静默丢弃的关键返回值。
- [ ] 裸指针、引用、`optional`、`Result`、owning pointer 与 handle 均按 2.1 的语义矩阵选择，没有用类型风格掩盖生命周期或失败。
- [ ] 所有权、句柄有效期、Link 销毁顺序和唯一权威状态已经定义。
- [ ] ECS System 的 query/read/write/structural mutation 契约明确。
- [ ] 时间、RNG、线程和回调语义不依赖隐式全局状态。
- [ ] 持久数据具有 schema/version/migration，恢复失败不留下部分状态。
- [ ] optional dependency 在 present/absent 下均有定义和测试。
- [ ] backend/provider 共享契约测试，关键失败路径具有注入测试。
- [ ] 新系统已接入恰当的生产边界，替代重复路径，并有真实 producer、consumer 与集成测试证据。
- [ ] 没有新增无 owner/expiry 的 skip、fallback、allowlist 或临时兼容层。
- [ ] 公共 header、模块依赖图、裁剪构建和至少一条组合路径已验证。
- [ ] 文档、实现、bindings 和调用方在同一次变更中保持一致。
