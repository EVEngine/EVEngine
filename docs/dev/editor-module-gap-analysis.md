# Editor module gap analysis

This document tracks authoring support by *domain capability*, rather than by
hard-coded editor window. A domain counts as supported only when project code can
discover/edit its stable data, route mutations through editor transactions, persist
an authoring document, and obtain diagnostics or preview data where applicable.

## Priority model

- **P0** blocks the basic level-authoring loop or risks destructive/non-reversible edits.
- **P1** is required for common content production but has a runtime API workaround.
- **P2** improves specialist workflows or scale after the main content loop works.

## Delivery order

1. Complete the scene authoring loop: hierarchy/TRS operations, live-world adapter,
   multi-selection properties, then prefab semantics.
2. Add asset document domains shared by most projects: material, animation, and UI.
3. Add simulation/content domains: particles, physics, audio, dialogue, and definition assets.
4. Add specialist overlays and scale tooling without embedding project-specific panels
   in the engine.

## Acceptance criteria for each domain

A domain increment is complete only when it provides:

1. stable target/document identity and capability discovery;
2. immutable reads and revision tracking;
3. planned reversible mutations through `DomainOperation`/transactions;
4. schema/property metadata usable by both developer and runtime presenters;
5. persistence with conflict-safe revision handling for asset-backed content;
6. structured validation/preview diagnostics;
7. focused tests for apply, rejection, undo, redo, stale revision and serialization.

Project-specific layout and art/game policy stay outside engine modules. The engine
supplies domain adapters, operations, metadata and preview contracts that arbitrary
workspaces can compose.
