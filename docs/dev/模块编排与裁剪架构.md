# 模块编排与裁剪架构

> 目标：让 EVEngine 的 51 个模块**分层清晰、互联互通**，同时**任何未使用的模块都能被裁掉**。
> 本文是对当前代码（`main` @ `0af8e7e`）的实测分析 + 目标架构 + 落地路线，不引入任何行为变更。

口径说明：`src/modules/` 下有 **51 个模块目录**，向脚本暴露 **53 个 `eve.*` 模块类**
（`filesystem` 额外暴露 `HotReload`，`Cmdline` 来自 `engine/cmdline`；`data` 的类名是
`DataModule`，`tensor` 的类名是 `TF`）。下文一律以**模块目录**为单位计数。

相关文档：[整体架构](./整体架构.md)、[模块设计](./模块设计.md)、[依赖项](./依赖项.md)、[用户模块手册](../usr/MODULES.md)

---

## 摘要

当前引擎的状态可以用一句话概括：**"互联互通"已经做得相当好，"可裁剪"基本没做。**

- **协作**：`ModuleManager` 字符串注册表 + 全局 ECS + `scene` 的 Link 系统 + 统一帧序，
  已经形成了一套自洽的协作范式，51 个模块几乎全部可以在一个脚本里协同工作。
- **裁剪**：只有**一条硬编码的裁剪轴**——Emscripten/WASM。它靠 `EVENGINE_WEBGPU_TRIM`
  一个内部变量、20 多处 `if(NOT ...)`、一份手写的 `EVELIBS` 删除列表和**一份分叉的启动脚本**
  （`load_web.nut`）拼出来。桌面端**没有任何**按模块裁剪的开关。
- **根因不是模块太多，而是缺三样东西**：① 分层契约（依赖方向没有约束，已产生 26 个依赖环）；
  ② 可选依赖的表达方式（跨模块协作一律用硬 `#include` + 直接符号引用）；
  ③ 构建期与启动期的一致配置源（CMake 链接表和 `load.nut` 各写各的）。

好消息是**修正成本远比看上去低**：全部 26 个依赖环只来自 **9 个文件**，
而 Poco 这个最大的"裁不掉的重依赖"里有 **一半以上的引用点只是在解析 JSON**。

## 一、模块全景：实测出来的 7 层

下面的分层不是设计意图，而是**从 `#include` 关系反推**出来的：
去掉 §3.2 那 16 条反向边后，依赖图是一个干净的 7 层 DAG，层号 = 到叶子的最长路径。
（`python3 scripts/module_depgraph.py`，方法见附录 A。）

```
L6  sceneloader  dialogue
L5  avatar  particles  procgen  scene  tensor  virtualgeometry
L4  animation  camera  card  daynight  demo  gpgpu  housegen  map
    physics  spritestack  stylize  ui  voxel  weather
L3  graphics                                        ← 唯一枢纽
L2  audio  font
L1  building  i18n  image  inventory  keyboard  model3d  mouse
    network  rpg  rx  sound
L0  data  database  editor  event  filesystem  ik  joystick  math
    plugins  spatial  system  thread  timer  touch  window
      + engine/common（Module / Runtime / ECS / Object / Data，非模块）
```

两点需要注意，它们本身就是结论：

- **`event` / `filesystem` / `window` / `system` / `thread` 落在 L0**，是因为它们的
  上行依赖全被算作反向边扣掉了。换句话说，这几个模块**本应是最底层**，
  今天却在反向依赖 `graphics` / `ui` / `map` / `particles`——这正是 §3.2 要处理的债。
- **`rpg` / `inventory` / `building` 落在 L1**（只依赖 `data`），
  `card` / `housegen` 在 L4 也仅因为顺带用了 `graphics`。
  玩法框架在依赖图上**极浅**，却全部无条件编入桌面版——这是最容易拿到的裁剪收益。

按职责再横切一刀，51 个模块可归为 **6 个功能域**（与上面的计算层号正交）：

| 功能域 | 模块（51） | 说明 |
|--------|------|------|
| **运行时内核**（5） | `plugins`、`thread`、`timer`、`system`、`math` | 线程、时间、系统查询、数学；`engine/common` 的注册表 / 脚本运行时 / ECS 不算模块 |
| **平台与输入**（7） | `window`、`event`、`keyboard`、`mouse`、`touch`、`joystick`、`rx` | SDL 之上的窗口/事件/输入；`rx` 是事件的响应式包装 |
| **数据与 I/O**（10） | `filesystem`、`data`、`image`、`sound`、`audio`、`font`、`model3d`、`network`、`database`、`i18n` | 解码、播放与持久化 |
| **渲染与计算**（12） | `graphics`、`camera`、`gpgpu`、`tensor`、`ui`、`stylize`、`daynight`、`weather`、`voxel`、`virtualgeometry`、`spritestack`、`particles` | 以 `graphics` 为唯一枢纽 |
| **世界与仿真**（9） | `scene`、`sceneloader`、`map`、`physics`、`animation`、`ik`、`spatial`、`procgen`、`housegen` | 场景树、地图、物理、动画 |
| **玩法框架**（8） | `rpg`、`inventory`、`building`、`card`、`avatar`、`dialogue`、`editor`、`demo` | 纯数据驱动、几乎不碰渲染 |

## 二、现有的协作机制盘点

引擎已经有 6 个"接缝"，质量参差不齐。这是评估的基线：

| # | 机制 | 位置 | 支持可选性？ | 评价 |
|---|------|------|--------------|------|
| 1 | **`ModuleManager` 字符串注册表** | `common/Module.h` | ⚠️ 部分 | 静态注册 + 字符串查找。`getInstance()` 对未链接模块返回 `nullptr`——**这是全引擎最好的软依赖原语**，但全仓只有 97 处调用点在用 |
| 2 | **全局 ECS** | `common/ECS.h` + `ECS.hpp` | ✅ | 各模块自注册组件管理器；`ecs::current()->getManager<T>()` 判空是标准防御写法。天然松耦合 |
| 3 | **`scene` Link 系统** | `scene/SceneHost.h` | ❌ | 节点 ↔ 外部对象的通用挂点，`void* target` 已经类型擦除，但 `LinkKind` 是**闭合枚举**、API 是**硬类型**的 6 个方法 |
| 4 | **`IRenderTracer`** | `common/RenderTrace.h` | ✅ | 未安装时全部 inline no-op。DevTools 与 Graphics 解耦的范本 |
| 5 | **`registerPostEcsHook` / `registerCppEntityView`** | `common/ECS.cpp` | ✅ | 模块向脚本 ECS 追加绑定的正确姿势（`scene` 在用） |
| 6 | **`plugins` + `expose_pending()`** | `plugins/Plugins.cpp` | ✅ | `dlopen` 后补注册模块。可**新增**能力，但**不能替换**已静态链接的模块 |

**结论**：#1/#2/#4/#5/#6 都是可选性友好的设计，问题在于**它们不是主流写法**。
主流写法是直接 `#include "graphics/Graphics.h"` 然后调具体方法——这在链接期就把模块焊死了。
数量上：跨模块硬 include **202 处**，软查找（`getInstance` / `getModInst`）**97 处**。
而且即使走软查找，消费方仍要 include 对方头文件才能拿到完整类型，链接期依然耦合
（§5.2 要补的正是这一环）。

### 3.1 跨模块依赖图（出入度）

被依赖最多的 8 个模块：

| 模块 | 被 N 个模块依赖 | 角色 |
|------|-----------------|------|
| `graphics` | **24** | 唯一的渲染枢纽，合理但过重（21 207 行 / 71 文件，占模块总量 104 425 行的 20%） |
| `data` | 14 | 但它自己拖着 Poco（见 3.3） |
| `filesystem` | 13 | 合理 |
| `image` | 9 | 合理 |
| `event` | 5 | 合理 |
| `model3d` | 5 | 合理 |
| `window` | 4 | 合理 |
| `animation` / `gpgpu` | 3 | 合理 |

依赖最重的 4 个模块：`event`(8)、`sceneloader`(8)、`particles`(6)、`ui`(6)。

完全孤立（零跨模块依赖、也无人依赖）的模块只有 4 个：`database`、`editor`、`math`、`plugins`
——**这 4 个今天就能安全裁掉**，只差一个开关。

### 3.2 依赖环：26 个环，全部来自 9 个文件

这是本次分析最有价值的发现。当前依赖图有 **26 个环**，例如：

```
filesystem → graphics → font → image → filesystem
filesystem → particles → gpgpu → graphics → filesystem
event → ui → event
```

但它们不是 26 个独立问题。移除下面 **16 条反向边**后，剩余环数为 **0**，
而这 16 条边只分布在 **9 个文件**里：

| 文件 | 反向边 | 原因 |
|------|--------|------|
| `event/sdl/Event.cpp` | → `audio` `graphics` `joystick` `keyboard` `touch` `ui` `window` `filesystem`（8 条） | SDL 事件泵**主动推**给各消费者，而不是消费者订阅 |
| `filesystem/HotReload.cpp` | → `graphics` `map` `particles`（3 条） | 热重载分发器**内联**了各资源类型的重载逻辑 |
| `window/Window.cpp`、`window/sdl/Window.cpp` | → `graphics` `image`（2 条） | 窗口直接持有 Graphics 与图标 ImageData |
| `system/System.cpp` | → `graphics`（1 条） | 仅为 `getGPUName()` 等 5 个查询 |
| `thread/Thread.cpp`、`thread/ThreadPool.cpp` | → `event`（1 条） | `postMain` 跨线程投递 |
| `ui/EditorHost.cpp` | → `event`（1 条） | 无头编辑器宿主自己泵事件 |

**这 9 个文件是整个可裁剪化改造的杠杆点。**

### 3.3 Poco 的扩散：15 个模块，但一半只为 JSON

Poco 是桌面端最大的"裁不掉"的依赖（Foundation + JSON + XML + Net + Data + SQLite）。
实测 **15 个模块**引用它（`animation` `building` `card` `data` `database` `filesystem`
`housegen` `inventory` `map` `network` `particles` `rpg` `scene` `ui` `voxel`），
加上 `engine/` 下的 devtools / cmdline，共 **136 个 include 点**。按头文件归类：

| Poco 头 | 引用点 | 真实用途 |
|---------|--------|----------|
| `JSON/Object` + `JSON/Array` + `JSON/Parser` + `JSON/Stringifier` + `Dynamic/Var` | **79** | **纯 JSON 读写** |
| `Net/*` | 27 | 只有 `network` 真正需要 |
| `DOM/*` + `XML/*` | 4 | 只有 `data/XmlDocument` 需要 |
| `Data/*` + `Data/SQLite` | 3 | 只有 `database` 需要 |
| 其余（`Exception`、`Timespan`、`DirectoryWatcher`、`Path`、`File`、`AutoPtr`…） | 23 | 零散工具 |

也就是说 **58%（79/136）的 Poco 引用点只是在解析 JSON**。更直接的证据：

```
src/modules/rpg/JsonHelpers.h        74 行
src/modules/inventory/JsonHelpers.h  74 行   ← 与 rpg 逐行相同，仅 namespace 不同
src/modules/building/JsonHelpers.h  101 行   ← 同一份的扩展版
src/modules/data/JsonDocument.h      34 行
src/modules/i18n/I18n.cpp                    ← 又手写了一个不依赖 Poco 的 JSON 解析器
```

同一件事有 **5 份实现**，其中 4 份把 Poco 硬绑进了本可以零重依赖的玩法模块。

### 3.4 裁剪能力现状矩阵

| 目标 | 今天能做到吗 | 机制 |
|------|--------------|------|
| 关掉单元测试 | ✅ | `-DBUILD_TESTING=OFF` |
| 关掉 Demo 模块 | ✅ | `-DEVENGINE_BUILD_DEMO=OFF` |
| 关掉 DevTools | ⚠️ 仅移动端/WASM 自动关 | 平台判断硬编码，桌面无开关 |
| Vulkan ↔ WebGPU 后端切换 | ✅ | `EVENGINE_EXCLUDED_BACKEND_SUBDIRS` |
| WASM 裁掉 22 个模块 | ✅ | `EVENGINE_WEBGPU_TRIM`（内部变量，非用户开关） |
| **桌面端裁掉任意一个模块** | ❌ | **无开关**。需同时改 `src/modules/CMakeLists.txt`、`EVELIBS`、`ThirdParty`、`load.nut` |
| **裁掉模块后连带裁掉第三方** | ❌ | 桌面 `ThirdParty` 是**每平台一份写死的扁平列表**，与模块无关联 |
| 以库形式只集成部分模块 | ❌ | `install_sdk.cmake` 只安装整机宿主 + 固定头文件子集 |

**四个机械阻塞点**（按修复难度递增）：

1. **`load.nut` 无条件 `eve.Foo()` 约 30 次**（`src/scripts/load.nut:38-87`）。
   模块一旦不链接，脚本在绑定期直接抛异常。这是 WASM 必须分叉出 `load_web.nut` 的唯一原因。
2. **`EVELIBS` 是手写列表**（`src/engine/CMakeLists.txt:170-249`），
   Emscripten 靠一个 `list(REMOVE_ITEM)` 循环特判。
3. **`ThirdParty` 与模块无映射关系**（`src/engine/CMakeLists.txt:120-168`）。
   裁掉 `EVNetwork` 不会让 PocoNet 从链接行上消失。
4. **DevTools 编译期硬依赖业务模块**。`devtools/McpServer.cpp` 直接 include
   `graphics/`、`scene/`、`physics/`、`procgen/`、`audio/`、`ui/EditorHost.h`；
   `devtools/SceneInspect.cpp` 直接 include `graphics/` + `scene/`。
   运行时虽然都做了判空，但**链接期仍然要求这些模块存在**。

### 3.5 文档与协作面的缺口

51 个模块中，有 **9 个没有用户文档、也不在 `docs/usr/MODULES.md` 索引里**：

`avatar`、`camera`、`database`、`dialogue`、`housegen`、`sceneloader`、`stylize`、`virtualgeometry`、`voxel`

（其中 `dialogue`/`avatar`/`stylize`/`voxel`/`housegen`/`sceneloader` 在 `docs/dev/` 有设计文档，

这件事实际上没有落地，各模块各自为政。

## 四、七个结构性问题

按"阻碍可裁剪性"的严重程度排序：

| # | 问题 | 影响 | 证据 |
|---|------|------|------|
| **P1** | **启动脚本硬编码模块清单** | 任何裁剪都必须同步改脚本，否则运行期崩 | `load.nut:38-87`；`load_web.nut` 是被迫的分叉 |
| **P2** | **没有分层契约** | 26 个依赖环；底层模块反向依赖上层 | §3.2 的 9 个文件 |
| **P3** | **可选依赖只能用 `#include` 表达** | 跨模块协作 = 链接期焊死 | 硬 include 202 处 vs 软查找 97 处 |
| **P4** | **第三方依赖与模块解耦失败** | 裁模块省不下依赖体积，裁剪收益趋近于 0 | `ThirdParty` 扁平列表 |
| **P5** | **Poco 通过 `data`（L0）渗透全栈** | 最底层就绑死重依赖；5 份重复 JSON 实现 | §3.3 |
| **P6** | **`scene` Link 是闭合枚举** | 第三方/新模块无法挂进场景树，必须改 `SceneHost.h` | `LinkKind` 6 个值；`TransformSystem.cpp` 硬 `static_cast` |
| **P7** | **DevTools 编译期依赖业务模块** | DevTools 与模块裁剪互斥 | `McpServer.cpp`、`SceneInspect.cpp` |

补充（不阻碍裁剪，但影响"功能完整/互联互通"）：

- **P8** `ResourceManager` 空壳：没有统一资源缓存与热重载标记，`filesystem/HotReload.cpp`
  只能把 texture/tilemap/particle 三种类型硬编码进分发器（这也正是 P2 的来源之一）。
- **P9** 模块 expose 顺序是 `unordered_map` 遍历，**未定义**。目前没暴雷是因为没有模块争抢同名槽位，
  但没有依赖声明就意味着这个隐患一直在。
- **P10** 9 个模块缺用户文档（§3.5）。

## 五、目标架构

四条主线，彼此独立、可分别推进。

### 5.1 分层契约：把方向约束写进构建

定义 7 层（§一），规则只有一条：**只能向下依赖，同层需显式声明**。

护栏本文已随附：[`scripts/module_depgraph.py --check`](../../scripts/module_depgraph.py)
扫描 `#include` 并在出现白名单之外的反向边时 exit 1。现有 16 条已登记为白名单，
按 §六 的顺序逐条清空即可——既不阻塞开发，又能保证不再退化。
（层号本身由脚本从依赖图推导，不需要在 `create_module()` 里额外标注。）

### 5.2 能力注册表：把"可选依赖"变成一等公民

现状是二选一：要么硬 `#include`（不可裁），要么 `ModuleManager::getInstance` 判空
（可裁，但仍需要完整类型 → 仍需 include 头文件 → 链接期仍然耦合）。

补第三种：**面向接口的能力注册表**。接口定义在 `engine/common/`（零依赖），
提供方在自己的模块里注册实现，消费方只认接口：

```cpp
// engine/common/Capability.h（新增，仅依赖 std）
namespace eve::cap {
template <class I> void provide(I* impl);   // 提供方在模块 ctor 里调用
template <class I> I*   query();            // 消费方调用，缺失时返回 nullptr
}
```

这正是 `IRenderTracer`（`common/RenderTrace.h`）已经验证过的模式，只是把它一般化。
优先改造的 4 个接口，正好对应 §3.2 的 9 个文件：

| 新接口（置于 `common/`） | 提供方 | 消费方 | 消掉的反向边 |
|--------------------------|--------|--------|--------------|
| `IHotReloadHandler`（按扩展名/kind 注册重载器） | `graphics`、`map`、`particles` 各自注册 | `filesystem/HotReload.cpp` | 3 |
| `IEventSink`（输入/音频/图形订阅 SDL 事件） | `keyboard`、`mouse`、`touch`、`joystick`、`audio`、`graphics`、`ui`、`window` | `event/sdl/Event.cpp` | 8 |
| `IGpuInfo`（GPU 名称/厂商/显存） | `graphics` | `system` | 1 |
| `IMainThreadPost`（跨线程投递到主线程） | `event` | `thread` | 1 |

剩余 3 条（`window→graphics/image`、`ui→event`）按具体情况直接反转依赖方向即可。

**关键收益**：`IHotReloadHandler` 落地后，`filesystem` 不再认识 `graphics`，
`P8`（资源系统空壳）也有了正确的落点——`ResourceManager` 可以复活为
"URI → 缓存条目 + 重载器" 的注册中心，而不是一个 `if/else` 分发器。

### 5.3 开放式 Link：让场景树接纳任意模块

`SceneLink::target` 已经是 `void*`，只差把闭合枚举换成开放注册：

```cpp
// scene/SceneHost.h
struct LinkOps {
    const char* kind;                                    // "renderable3d" / "particles" / ...
    void (*writeWorld)(const SceneNode&, void* target);  // 节点 → 目标
    void (*readWorld)(SceneNode&, void* target);         // 目标 → 节点（可空）
    bool (*alive)(const void* target);
};
int registerLinkKind(const LinkOps&);   // 返回 kind id
bool link(const std::string& nodeId, int kindId, void* target, int syncMode = 0);
```

`graphics`、`physics`、`audio` 在各自模块里注册自己的 `LinkOps`。
于是 `scene` 从 L5（依赖 graphics/physics/audio/spatial）降到 **L1**，
并且 `particles`、`voxel`、`spritestack`、`avatar`、`weather` 这些今天挂不上场景树的模块
**不改 scene 一行代码**就能接进来——这是"互联互通"和"可裁剪"同时变好的一处。
现有 6 个 `linkXxx()` 方法保留为薄封装，脚本 API 不变。

### 5.4 构建期：per-module 开关 + 预设档位

**每个模块一个开关，由单一数据源生成**。把今天散落在
`src/modules/CMakeLists.txt` / `EVELIBS` / `ThirdParty` / `load.nut`
四处的信息收敛到一份清单（`cmake/modules.cmake`）：

```cmake
eve_declare_module(NAME map        LAYER 4 DEPS data filesystem graphics
                   THIRDPARTY Poco  SCRIPT Map      DEFAULT ON)
eve_declare_module(NAME database   LAYER 0 DEPS ""  THIRDPARTY PocoData PocoDataSQLite
                   SCRIPT Database DEFAULT OFF)
```

由它自动派生：`create_module()` 调用、`EVELIBS` 内容、`ThirdParty` 链接项（**并集，不再是固定表**）、
依赖闭包校验（开了 `particles` 就自动开 `gpgpu`/`animation`/`ik`）、以及 §5.5 的启动清单。
用户接口就一个：`-DEVENGINE_MODULE_<NAME>=ON|OFF`。

**预设档位**（`-DEVENGINE_PROFILE=`），覆盖绝大多数使用场景：

| 档位 | 内容 | 目标 |
|------|------|------|
| `minimal` | L0–L3 + `window`/`event`/输入 + `graphics` | 自绘引擎壳，第三方仅 SDL2 + Vulkan + squirrel + physfs |
| `2d` | `minimal` + `image`/`font`/`map`/`particles`/`ui`/`animation`/`physics`/`audio` | LÖVE 级 2D 游戏 |
| `3d` | `2d` + `model3d`/`scene`/`sceneloader`/`camera`/`gpgpu`/`stylize`/`daynight`/`weather` | 3D 游戏 |
| `full` | 全部（**当前唯一档位**，保持默认） | 现状不变 |
| `web` | 现有 WASM 集合 | 用 profile 表达，**删掉 `EVENGINE_WEBGPU_TRIM` 特判** |

注意 `web` 档：一旦 profile 机制到位，`EVENGINE_WEBGPU_TRIM`、
`src/modules/CMakeLists.txt` 里 20 多处 `if(NOT ...)`、
`EVELIBS` 的 `REMOVE_ITEM` 循环 **全部可以删除**——这是净减代码，不是净增。

### 5.5 启动期：数据驱动的 boot，删掉分叉脚本

`load.nut` 的 30 行 `xxx <- eve.Foo()` 换成按清单遍历，缺失即跳过：

```squirrel
// eve.moduleList 由构建期从 §5.4 的清单生成并嵌入
foreach (m in eve.moduleList) {          // [{ slot = "map", cls = "Map" }, ...]
    if (m.cls in eve) getroottable()[m.slot] <- eve[m.cls]();
}
```

帧循环里对可选模块同样加存在性判断（`if ("ui" in getroottable()) ui.dispatchEvents();`）。

**`load_web.nut` 随即可以删除**，`Run.cpp:95-100` 的 `#ifdef EVENGINE_WEBGPU` 分支也一并删除。
两份启动脚本的行为差异（WASM 用 `eve_frame()` 而非 `while` 循环）本来就该按平台能力判断，
而不是按模块集合分叉。

### 5.6 DevTools 解耦

`McpServer.cpp` / `SceneInspect.cpp` 里对业务模块的调用，改走 §5.2 的能力接口
（`ISceneQuery`、`IRenderCapture`、`IPhysicsQuery`），接口定义在 `common/`。
这样 DevTools 既能独立裁剪，也不再阻止别人裁 `scene`/`physics`/`procgen`。
顺带把桌面端的 DevTools 也变成显式开关 `-DEVENGINE_MODULE_DEVTOOLS=OFF`，
而不是今天这样"只有移动端和 WASM 才自动关"。

## 六、落地路线

六步，每步都能独立合入、独立验证，且**任何一步中断都不会让仓库处于半成品状态**。
排序原则：先立护栏、再降耦合、最后加开关——这样开关一旦加上就立刻可用。

| 步骤 | 内容 | 验收标准 | 风险 |
|------|------|----------|------|
| **S1 立护栏** | 把 `scripts/module_depgraph.py --check` 接进 CI（脚本与 16 条反向边白名单本文已随附） | CI 能在新增反向边时 fail；白名单即待办清单 | 无（纯新增） |
| **S2 收敛 JSON** | 把 `rpg`/`inventory`/`building` 的 3 份 `JsonHelpers.h` 与 `data/JsonDocument` 合成一个 `common/Json.h` 门面；后端可切 Poco 或 `i18n` 里那份自研解析器 | 6 个玩法模块不再直接 include `Poco/JSON/*`；测试全绿 | 低（纯重构，有测试覆盖） |
| **S3 引入能力注册表** | 加 `common/Capability.h`；落地 `IHotReloadHandler` / `IEventSink` / `IGpuInfo` / `IMainThreadPost`，清掉 13 条反向边 | 白名单从 16 降到 3；依赖环 0 | 中（触及 `event`/`filesystem` 主路径，需 `test/hotreload.cpp`、`test/event.cpp` 把关） |
| **S4 开放 Link** | §5.3；`scene` 层级 L5 → L1 | `scene` 不再 include `graphics`/`physics`/`audio`；`test/scene.cpp`、`test/sceneloader.cpp` 全绿 | 中（`TransformSystem` 是热路径，注意别引入间接调用开销——用函数指针表而非虚调用） |
| **S5 单一清单 + 开关** | §5.4；`cmake/modules.cmake` 生成 `EVELIBS`/`ThirdParty`/依赖闭包 | `-DEVENGINE_MODULE_DATABASE=OFF` 能编能跑；`full` 档产物与改造前逐字节可比 | 中（CMake 改动面大，但可先让生成结果与现状完全一致再开放开关） |
| **S6 数据驱动 boot** | §5.5；删 `load_web.nut` 与 `EVENGINE_WEBGPU_TRIM` | `minimal`/`2d`/`3d`/`web` 四档均能启动示例；WASM 构建产物行为不变 | 中（依赖 S5） |

**为什么是这个顺序**：S2 单独就有价值（消重 + 为 Poco 可选化铺路）；
S3 是 S6 的前置（不解耦 `event`/`filesystem`，输入和热重载模块就没法真正裁）；
S5 必须在 S6 之前（启动清单由构建清单生成）。S4 与 S3/S5 无依赖，可并行。

**可以立刻做、零风险的两件事**（不在上表，因为不涉及架构）：

- 给 §3.5 那 9 个模块补 `docs/usr/modules/*.md` 并挂进索引。
- 把 `database`、`editor`、`math`、`plugins` 这 4 个零耦合模块先加上开关——
  它们在依赖图上完全孤立，`-DEVENGINE_MODULE_X=OFF` 只需从 `EVELIBS` 摘掉即可，
  可作为 S5 的先导验证（`database` 还能直接省掉 PocoData + SQLite）。

## 七、需要明确的取舍

1. **`graphics` 要不要拆？** 它 21 207 行、被 24 个模块依赖，是唯一的枢纽。
   本文**不建议**现在拆——拆它的收益（更细的裁剪粒度）远小于风险（触及所有模块）。
   更划算的做法是先把 `daynight`/`weather`/`stylize`/`voxel`/`virtualgeometry`/`spritestack`
   这些"渲染扩展"保持在 `graphics` 之上并各自可裁，
   等 S1–S6 稳定后再评估是否把 `graphics` 内部的 2D/3D/后处理分成子目标。

2. **能力注册表 vs 直接 include 的性能。** 能力查询只应发生在初始化期（缓存指针），
   热路径（`TransformSystem` 的 link 同步、`RenderSystem` 的每帧遍历）必须用
   函数指针表 + 预取指针，不引入虚调用或每帧查表。S4 需要基准测试把关。

3. **裁剪粒度到模块为止。** 不建议做模块内的 feature flag（那会重演今天
   `#ifdef EVENGINE_WEBGPU` 散落 78 处的问题）。模块内部要么全有要么全无；
   粒度不够就说明该拆模块，而不是加宏。

4. **`full` 档必须保持默认且零行为变化。** 所有改造都以"现状即 `full` 档"为回归基线。

## 附录 A：分析方法

本文的依赖图由扫描 `src/modules/**/*.{cpp,h,hpp}` 的 `#include` 得到，规则：

- 只有**带子路径**的 include 才算跨模块依赖（`#include "map/Map.h"`）。
  裸 `#include <map>` / `<thread>` / `<filesystem>` 是标准库头，必须排除——
  否则会误报 `mouse→map`、`audio→thread` 等约 10 条不存在的边。
- 区分头文件中的 include（公开 API 泄漏，标 `*`）与仅 `.cpp` 中的 include（实现细节，更易解耦）。
- 分层由移除 §3.2 那 16 条反向边后的最长路径深度确定。

复现命令（脚本：[`scripts/module_depgraph.py`](../../scripts/module_depgraph.py)）：

```sh
python3 scripts/module_depgraph.py            # 分层 / 出入度 / 孤立模块
python3 scripts/module_depgraph.py --cycles   # 依赖环，及移除已知反向边后的残留
python3 scripts/module_depgraph.py --check    # 出现新反向边时 exit 1（S1 的护栏）
```

`--check` 已经可以直接接进 CI。脚本里的 `KNOWN_BACK_EDGES` 就是 §3.2 那 16 条边的
白名单兼待办清单：每修好一条就从表里删一条，`--check` 会把已修好却仍在表里的条目
标为 `stale` 提醒清理。
