# EVEngine 通用结算系统完整建设计划

> 日期：2026-09-21
> 范围：`settlement`、`effects`、`combat`、`rpg`、`rts`、`tactics`、`card` 及其脚本、持久化、回放和工具链
> 目标：把 Settlement 从统一伤害流水线建设为可承载 RPG、RTS、战棋、卡牌等玩法的通用、确定性、可解释、可扩展结算框架。

## 1. 目标与非目标

### 1.1 总体目标

系统最终应提供以下统一能力：

1. 玩法只拥有自己的权威状态，不复制生命、护盾、卡牌、单位或效果实例到 Settlement。
2. 所有数值和效果结算使用同一阶段协议、配置入口、错误模型、预演接口和审计结果。
3. Buff、Debuff、装备、地形、科技、卡牌与临时规则可投影为不可变规则快照。
4. 策划可直接编写受限条件字符串，加载时编译成强类型 AST，运行时不重复解析。
5. 支持多资源、多段、范围、触发链、免疫、驱散、吸血、反伤等常见复杂机制。
6. 预测、权威提交、回放和联网校验共享同一条执行路径。
7. 所有失败均返回结构化 `Result`，重要提交具备原子性和回滚能力。
8. 热路径避免脚本 VM、动态模块查询和逐次字符串解析。

### 1.2 非目标

- 不创建跨玩法的 `GameObject`、`Actor` 或统一战斗实体根类。
- 不让 Settlement 成为生命、护盾、状态、牌库或棋盘状态的第二所有者。
- 不允许条件表达式执行任意脚本、修改状态、读取墙钟或隐式使用随机数。
- 不强制所有玩法采用同一数值模型；差异由领域 `ISettlementPolicy` 保留。
- 不把编辑器、配置格式或脚本绑定作为核心运行时的硬依赖。

### 1.3 简洁性与复用硬约束

本计划不得以“通用”为理由扩张类型和框架层级。实现时遵守：

1. **先扩展现有类型，再考虑新增类型。** 优先复用 `SettlementRuleSet`、`SettlementContext`、`SettlementRequest`、`SettlementResult`、`Value`、`EffectContainer`、`ISettlementPolicy` 和现有领域 adapter。
2. **一种事实只有一种表示。** 不为编辑器、脚本、回放分别创建规则模型；它们都解码到同一个运行时规则结构。
3. **不为单一调用方创建接口。** 只有两个以上独立领域确实需要替换实现时，才提取虚接口；否则使用普通函数、值类型或现有 policy。
4. **不建立 AST 类层级。** 条件 AST 使用紧凑值类型、variant 或顺序指令表示，不创建每种运算符一个派生类。
5. **不重复建设注册表。** 字段和谓词尽量并入一份条件符号表；Tag、LogicalId、Value、Result 和身份类型直接复用公共实现。
6. **简单路径保持简单。** 只使用 kind/tag 的规则不构造复杂表达式执行器；单数值结算不强制包装成 Bundle。
7. **新增抽象必须删除重复。** 新类型若不能替代至少两处重复逻辑，或不能形成明确稳定边界，应留在调用方内部实现。
8. **代码体积是验收指标。** 每阶段评审新增公开类型、公开方法、模板实例和总代码行；只为未来假设服务的抽象立即删除。
9. **拒绝平行系统。** 不同时保留两套 parser、两套规则执行器、两套 Trace 或两套领域接入路径。
10. **按真实需求渐进。** 先实现已存在玩法能够验证的最小闭环，不预建尚无调用方的扩展点。

新增公开类型前必须回答：

- 哪两处以上现有重复由它统一？
- 为什么现有类型不能安全扩展？
- 它拥有哪项状态或不变量？
- 删除它后会出现什么实际问题？

任一问题没有具体答案，则不新增该类型。

## 2. 当前基线

当前已经具备：

- 固定阶段的 `SettlementPipeline`；
- 领域 `ISettlementPolicy`；
- `PreparedApply` 原子提交和回滚；
- `SettlementRuleSet` 声明式规则；
- kind/tag 过滤、叠层缩放、加法、乘法、固定/百分比减免、吸收、上限和暴击标记；
- RPG Battle 伤害与治疗接入；
- RTS 武器、投射物、技能、目标效果倍率与护盾接入；
- Card 即时护盾及周期伤害、治疗、护盾接入；
- Tactics 已提交能力回执到游戏状态 policy 的结算桥接；
- 完整无副作用 Combat 预演入口；
- 结构化阶段明细和确定性阶段排序。

当前主要缺口：

- 规则条件仍以简单 kind/tag 过滤为主；
- 活动 Effect/Status 到规则快照尚未自动投影；
- 缺少规则分组、独立乘区、互斥与唯一规则；
- 缺少正式触发链、递归保护和内部冷却；
- 单次结算仍以单一 magnitude 为主；
- 缺少统一的免疫、驱散和部分生效状态；
- 缺少完整配置 Schema、迁移、热重载和编辑器诊断；
- Trace、回放、联网验证和大规模性能能力仍需增强。

## 3. 目标架构

```text
配置 JSON / EveScript 字符串
             │
             ▼
规则配置编译函数
  ├─ Schema 校验
  ├─ 条件字符串词法/语法分析
  ├─ 类型检查与符号解析
  └─ 编译为 SettlementRuleSet 内部的不可变条件程序
             │
             ▼
Effect/Status/Equipment/Terrain Projection
             │
             ▼
SettlementRuleSet
             │
             ▼
SettlementRequest / SettlementBundle
             │
             ▼
SettlementPipeline
  Validate
  Eligibility
  SourceModifiers
  TargetMitigation
  ArmorShield
  Clamp
  Apply
  Event
  Trigger
             │
             ├─ SettlementResult
             ├─ SettlementTrace
             ├─ Follow-up triggers
             └─ Replay/network digest
```

核心层只负责顺序、规则解释、审计与事务协调。领域状态读取和写入继续由 RPG、RTS、Tactics、Card 等 policy 完成。

## 4. 条件表达式与 AST

### 4.1 用户体验

策划直接编写字符串：

```json
{
  "id": "execute.low-health",
  "stage": "source_modifiers",
  "operation": "multiply",
  "value": 1.5,
  "when": "kind == \"damage\" && target.hp_ratio < 0.3 && source.has_tag(\"class.assassin\")"
}
```

加载或热重载时执行：

```text
String → Tokens → Parsed AST → Typed AST → Bound Program
```

结算时只执行规则内部持有的已编译条件程序，不得再次解析字符串。

### 4.2 第一版语法

支持：

- 字面量：Bool、Number、String；
- 逻辑：`&&`、`||`、`!`；
- 比较：`==`、`!=`、`<`、`<=`、`>`、`>=`；
- 数值：`+`、`-`、`*`、`/`；
- 函数：`min`、`max`、`clamp`、`abs`；
- 请求字段：`kind`、`magnitude`、`tick`；
- 主体字段：`source.*`、`target.*`；
- 上下文字段：`context.<name>`；
- 查询：`has_tag`、`has_effect`、`has_trait`；
- 关系：`is_self`、`is_ally`、`is_enemy`；
- 空间：`distance(source, target)`，由明确 provider 提供。

第一版不支持：

- 赋值、循环、递归和用户函数；
- 任意对象访问；
- 任意脚本函数回调；
- 墙钟、文件、网络和全局状态；
- 隐式随机数。

### 4.3 类型系统

AST 节点必须带静态类型。类型枚举应作为条件实现的内部细节，不建立公开对象体系：

```cpp
enum class ConditionValueType {
    Boolean,
    Number,
    String,
    Subject,
    Tag,
};
```

编译阶段拒绝：

- `Number && String`；
- 字符串与数字的大小比较；
- 未注册字段或函数；
- 除零的常量表达式；
- 超出节点、嵌套或字符串长度限制的表达式。

诊断必须包含规则 id、配置路径、行列号、期望类型和实际类型。

### 4.4 字段与函数绑定

当前不新建字段注册表、descriptor 类型、scope 类层或读取虚接口。已有的
`kind` / `magnitude` / `tick` / `has_tag` 由编译器直接绑定；领域差异通过当次请求的
`context.<path>` 拥有型值表达。RPG、RTS、Tactics 和 Card 只负责生成自己需要的
context 快照，不向 Settlement 暴露玩法对象。

RPG 周期 Status 使用已有 `StatusTickEvent` 加一个普通请求构造函数完成显式交接：效果定义的
`extra["settlement.tick"]` 保存严格 JSON 请求模板，调用方提供其已经拥有的稳定 source/target
`SubjectRef` 和模拟 tick。这样 stack、tag、resource、context 可进入同一 Settlement 请求，同时不在
没有持久身份的 `RPGActor` 上建立第二份身份注册表，也不让 StatusSystem 隐式拥有 Vitals 提交。
`Battle::settleStatusTick` 复用普通行动的内部 `settleRequest`，因此双方活动 Status、触发链、VitalsEvent
和 BattleEvent 都走同一实现，不复制周期伤害公式。

只有在出现至少两个不能由 `context` 表达的真实读取器，且拷贝快照已由基准证明为瓶颈时，
才评估内部的 ID 绑定表。即使到时需要，也先使用模块私有的数组和普通函数，
不预设 `ConditionFieldDescriptor` / `ConditionSubjectScope` / `IFieldReader` 等公开类型。

不得把玩法对象裸指针保存在条件程序中。

### 4.5 编译与缓存

- `conditionSource` 用于编辑器、错误定位和持久化；
- 编译后的条件程序直接由 `SettlementRule`/`SettlementRuleSet` 拥有，不再增加独立生命周期对象；
- 缓存键至少包含源码、语言版本和字段注册表版本；
- 热重载先完整编译候选配置，全部成功后一次性替换；
- 旧程序由快照或共享所有权保持到在途结算结束。

## 5. 规则模型扩展

### 5.1 条件接入

仅向现有 `SettlementRule` 增加条件源文本：

```cpp
struct SettlementRule {
    std::string id;
    std::string source;
    StageKind stage;
    int priority;
    RuleOperation operation;
    double value;
    std::string when;
};
```

编译产物由 `SettlementRuleSet` 私有容器按规则索引保存，不再暴露
`BoundConditionProgram`、`ConditionCompiler` 或 AST 节点类型。简单 kind/tag filter
保留为快速路径；只有非空 `when` 进入 evaluator。

### 5.2 分组与堆叠

不一次性引入一整套堆叠类型。`EffectContainer` 继续拥有层数、上限、刷新、
替换和到期；`SettlementRule` 只接收已投影的 `stacks` 和计算操作数。
第一步只验证已有的 Add / Multiply 阶段顺序和稳定 priority。

当真实内容同时需要“取最高值”或“同源唯一”时，再在 `SettlementRule`
上增加一个小型枚举和一个 group key，不新建 `RuleStacking` 类。
`diminishingCurve`、独立乘区和按次消耗均延后到有真实玩法用例的阶段；
消耗会改变效果生命周期，必须由 effect/trigger 所有者提交，不放进纯计算规则。

固定计算顺序：

```text
基础值
→ 固定加减组
→ 同区百分比加成
→ 独立乘区
→ 减免/穿透
→ 护盾/护甲
→ 最终限制
```

所有分组和聚合结果进入 Trace。

### 5.3 Effect 自动投影

先在现有领域 adapter 中用普通函数遍历 `EffectContainer`，把当前
`EffectInstance` 的 magnitude、stackCount、priority、tags 和 payload 转为
`SettlementRule` 值。不新建 projector 类、虚接口或回调注册表。

当 RPG 和 Card 的首批接入稳定后，如果两者的遍历与校验代码确实重复，
再把重复部分提取为 `settlement` 内部的一个纯函数；领域 payload 解码仍留在领域侧。
只有出现多个需要运行时替换的实现时，才评估提取接口。

投影原则：

- EffectContainer 继续唯一拥有生命周期、层数和到期状态；
- 投影结果是单次结算使用的不可变拥有型值；
- 不保留 `EffectInstance*`；
- remove、expire、restore、热重载后下一次结算重新投影；
- 相同输入按稳定 effect identity 排序，保证确定性。

RPG Status、RTS Effect、Card Effect 最终复用同一经证明有必要的投影循环，
但不因为计划中有四种玩法就预先建立抽象。Tactics 不拥有第二个效果容器，
它继续通过 `AbilitySettlementRequest::context` 与游戏拥有的 policy 参与结算。

## 6. 结算数据模型

### 6.1 多资源 Delta

不新建与 `SettlementRequest` 重复的 `ResourceDelta`。一个 request 就是一个
资源通道：`kind` 表达 damage/heal/spend/gain 等语义，`resource` 表达
hp/mana/armor/fire 等领域 key，magnitude 是正数数量，tags/context 携带类型与领域数据。
```

一次结算可原子修改：

- HP、MP、怒气、行动点；
- 护盾、护甲、韧性；
- RTS 建筑耐久与资源；
- 卡牌费用、手牌、牌库；
- 自定义领域资源。

### 6.2 SettlementBundle

保留现有单 magnitude 低成本 API，另增显式批量入口，直接接收
`span<SettlementRequest>` 与对应 policy span，不再包一层只持有 vector 的 Bundle 类：

```cpp
settleAtomic(requests, policies, events) -> Result<vector<SettlementResult>>
settleIndependent(requests, policies, events) -> Result<vector<SettlementBatchItemResult>>
```

每个 request 可表示物理、火焰、毒素、治疗、护盾、资源支付等。
不得通过默认参数把单值和昂贵批量 API 混为一个接口。

### 6.3 多目标与事务模式

新增批量目标模式：

- `AtomicAll`：任一目标失败则全部回滚；
- `Independent`：逐目标提交并返回逐项结果；
- `BestEffort`：只跳过明确可忽略的失效目标。

目标必须按 `SubjectRef` 或请求提供的稳定序号排序。不得依赖容器地址或非确定性哈希遍历顺序。

## 7. 判定阶段

新增 Eligibility/Decision 概念，形成明确顺序：

```text
请求校验
→ 目标合法性
→ 命中
→ 闪避
→ 格挡/招架
→ 暴击
→ 来源修正
→ 目标减免
→ 护盾/护甲
→ Clamp
→ Apply
→ Event
→ Trigger
```

随机决策必须使用调用方注入的命名 RNG stream：

```cpp
struct SettlementRandomDecision {
    LogicalId stream;
    std::uint64_t sequence;
    double sample;
    double threshold;
    bool accepted;
};
```

预演可选择：

- 使用固定决策输入；
- 返回概率范围；
- 消费克隆的 RNG 状态，绝不推进权威 stream。

## 8. 免疫、抵抗与驱散

引入强状态而不是用零伤害模拟：

```cpp
enum class SettlementDisposition {
    Applied,
    NoOp,
    Immune,
    Resisted,
    PartiallyApplied,
    Blocked,
    InvalidTarget,
};
```

支持：

- 伤害类型免疫；
- 状态/控制免疫；
- 标签免疫；
- 部分抵抗与持续时间缩短；
- 驱散类别、强度、优先级和最大数量；
- 不可驱散效果；
- 控制递减和免疫窗口。

驱散必须通过 EffectContainer 的事务候选完成，不能直接擦除另一模块的状态。

## 9. 触发链

### 9.1 触发点

至少支持：

- BeforeSettlement；
- AfterDecision；
- BeforeApply；
- AfterApply；
- OnDamage、OnHeal、OnAbsorb；
- OnShieldBreak、OnDeath、OnKill；
- OnCritical、OnBlock、OnDodge；
- OnEffectApplied、OnEffectRemoved；
- OnResourceSpent。

### 9.2 链标识与循环保护

```cpp
struct SettlementChainContext {
    SettlementId current;
    SettlementId root;
    SettlementId parent;
    std::uint32_t depth;
    std::uint32_t emittedCount;
};
```

强制限制：

- 最大深度；
- 单链最大派生结算数；
- `(ruleId, source, target, trigger)` 重入策略；
- 内部冷却；
- 每回合/每 tick/每链次数限制；
- 循环拒绝必须进入 Trace，而不是静默丢弃。

### 9.3 常见派生效果

- 吸血：基于实际生命伤害派生 healing；
- 反伤：交换 source/target 派生 damage；
- 溅射：按稳定目标顺序派生批量结算；
- 连锁闪电：维护已命中集合和剩余跳数；
- 过量治疗转护盾：基于 clamped amount 派生 shield；
- 击杀刷新技能：基于 disposition 和 death transition 派生资源变化。

## 10. Trace、事件与可解释性

Trace 优先扩展现有 `SettlementResult::stages/details`。只有证明现有结构无法同时满足 Summary/Full，并且至少有编辑器与回放两个消费者时，才拆出独立 `SettlementTrace`。概念条目为：

```cpp
struct SettlementTraceEntry {
    StageKind stage;
    std::string ruleId;
    std::string source;
    bool conditionMatched;
    double before;
    double operand;
    double after;
    Value details;
};
```

Trace 应回答：

```text
基础伤害 100
攻击强化 ×1.20 → 120
高地加成 +10 → 130
火焰抗性 −25% → 97.5
护盾吸收 30 → 67.5
生命上限 Clamp 2.5 → 65
最终应用 65
```

提供三档采集：

- Off：生产热路径最小成本；
- Summary：记录规则命中和阶段汇总；
- Full：记录条件结果、每步 before/after 和随机决策。

事件只在状态成功提交后发布；事件日志失败时按事务契约回滚状态。

## 11. 预测、提交和验证

统一入口语义：

```cpp
preview(request, snapshot, decisions)
commit(request, livePolicy, decisions)
verify(request, expectedResult, snapshot, decisions)
```

要求：

- preview 与 commit 走相同编译规则和阶段代码；
- preview 不修改权威状态、不推进 RNG、不发布事件；
- commit 返回完整 owning result；
- verify 返回字段级差异，而不是单一 bool；
- UI、AI、服务器和回放不得自行复制伤害公式。

## 12. 配置、持久化与热重载

### 12.1 Schema

每份规则配置包含：

- `schema`；
- `version`；
- `rules`；
- 未知字段策略；
- 条件语言版本；
- 可选内容哈希。

### 12.2 迁移

- 旧版本先迁移为当前内存模型；
- 迁移失败不得发布部分规则；
- 未知 operation/stage 默认拒绝；
- 可扩展 `extra` 只能存储声明允许的命名空间字段。

### 12.3 热重载

流程：

```text
读取候选
→ Schema 校验
→ AST 编译
→ 字段/函数绑定
→ RuleSet 全量校验
→ 生成版本和哈希
→ 原子替换
```

失败时继续使用旧版本，并返回完整诊断列表。

## 13. 脚本 API

建议的 EveScript 使用方式：

```nut
local result = Settlement.compileCondition(
    "target.hp_ratio < 0.3 && request.has_tag('damage:physical')"
);

if (!result.ok()) {
    // 显示 result.diagnostics
}
```

更常用的批量入口：

```nut
local configured = battle.configureSettlementRules([
    {
        id = "execute",
        stage = "source_modifiers",
        operation = "multiply",
        value = 1.5,
        when = "target.hp_ratio < 0.3"
    }
]);
```

绑定要求：

- 一次性解码并编译整个数组；
- 任一规则失败则不替换旧配置；
- 不允许把闭包作为运行时条件；
- 不向脚本暴露内部 AST 裸指针；
- 条件编译产物由 `SettlementRuleSet` 私有拥有，不向脚本暴露 handle 或建立第二个注册表；
- restore/热重载原子替换整套拥有型规则，失败保留旧规则，外部不存在需要失效的 compiled-condition handle。

## 14. 各玩法接入完成标准

### 14.1 RPG

- Battle 伤害、治疗、护盾和资源变化统一进入 Settlement；
- StatusSystem 周期 tick 通过 `makeStatusTickSettlementRequest` 自动投影请求；拥有稳定主体身份和提交时机的
  宿主可交给 `Battle::settleStatusTick` 执行，StatusSystem 本身不越权修改 Vitals；
- Trait、装备、状态可提供条件字段与规则；
- 保留 VitalsEvent 和现有脚本事件语义；
- Battle preview 与实际执行一致；
- 死亡、复活、吸血、反伤和控制效果有组合测试。

### 14.2 RTS

- 武器、投射物、技能、范围伤害全部进入同一 DamageRuntime；
- incoming multiplier、科技、Veterancy、地形、标签、护盾均在 Settlement 阶段解释；
- 大规模多目标结算采用稳定顺序和批量工作区；
- provider present/absent 均有测试；
- 单位与建筑两类状态共享 contract test；
- 预测、命中事件和实际生命/护盾变化一致。

### 14.3 Tactics

- `useAbility` 继续只负责合法性和行动资源；
- `AbilityReceipt` 通过 `TacticsSettlementRuntime` 进入统一结算；
- 高地、掩体、侧击、距离和阵营关系作为只读条件字段；
- 结算死亡结果通过 `defeatUnit` 原子更新目标和目标条件；
- 回放记录能力声明、决策输入、结算结果和派生触发；
- cell-only、unit-target、AOE 三类能力有组合测试。

### 14.4 Card

- 即时与周期 Damage/Heal/Shield 全部进入 Settlement；
- 数值费用和伤害结果可进入 Settlement；弃牌、抽牌、召唤继续复用现有 resource/container/transaction
  权威路径，Settlement 只携带其确定性触发，不把结构变更伪装成标量资源；
- Barrier 与临时规则消费语义明确；
- 同卡、同来源、唯一光环等堆叠策略可配置；
- 牌序、目标序和触发序确定；
- 快照恢复后 effect handle 明确失效；条件编译产物没有公开 handle，规则集热重载失败保留旧配置。

## 15. 性能设计

### 15.1 热路径原则

- 配置加载时完成字符串解析和名称绑定；
- 运行时使用 FieldId、TagId、RuleId；
- 不在每次结算中调用 `getModInst`、`requireModInst` 或字符串 capability 查询；
- 简单 filter 在 AST 前短路；
- RuleSet 按 kind、tag、stage 预建索引；
- evaluator 使用有界栈或紧凑字节码，避免递归分配；
- 批量结算复用 scratch buffer；
- Trace 关闭时不构造详细 Value 对象。

### 15.2 性能指标

建立基准：

- 10、100、1000 条规则下单目标耗时；
- 1000 个 RTS 单位的批量伤害；
- 条件命中率 0%、50%、100%；
- Trace Off/Summary/Full 成本；
- 触发链深度 1、4、8；
- 冷缓存与热缓存；
- 每次结算分配次数和峰值内存。

性能回归门槛以基准建立后的真实数据确定，不预先编造绝对数字。

当前已有默认空操作、仅在设置 `EVENGINE_SETTLEMENT_BENCHMARK=1` 时执行的无渲染矩阵基准，输出
机器可读的 `SETTLEMENT_BENCHMARK_JSON`。矩阵覆盖 10/100/1000 条已编译规则、0/50/100% 命中率和
Trace Off/Summary/Full、触发链深度 1/4/8，并包含 1000 项 `settleIndependent`。Windows MSVC Debug 的首个完整诊断样本
已经通过：例如 1000 条规则、50% 命中时 Off p50/p95 约 94918/95389 us，Summary 约
130933/131154 us，Full 约 156659/157219 us；10 条规则、50% 命中的 1000 项 Independent 折算每项
约 1509/1510 us；深度 1/4/8 的链 p50 约 3108/7943/14385 us。独立 Windows MSVC Release 全构建也已
完成并通过同一矩阵：1000 条规则、50% 命中时 Off p50/p95 约 112.8/114.8 us，Summary 约
2336/2377 us，Full 约 3672/4083 us；1000 项 Independent 折算每项约 6.52/6.62 us；深度 1/4/8
的链 p50 约 15.08/46.7/85.44 us。Release 的 406 项相关回归全部通过。数据表明当前主要成本来自保留
Trace，而非无 Trace 的规则执行或批处理；尚无依据引入 scratch/cache 类。正式跨机器预算仍待补齐，
不设置未经 CI 参考机校准的武断阈值。

现有 benchmark 现已直接补充观测而未修改运行时 API：各平台记录基准开始/结束时的进程峰值驻留字节数；
MSVC Debug 复用仓库已有的 CRT allocation hook，按矩阵操作、Independent 项和触发链记录分配次数，
不支持该精确计数方式的构建在 JSON 中输出 `null`。首个 Windows Debug 样本的峰值驻留从约 39.9 MiB
增至 53.8 MiB；10 条规则、50% 命中、Trace Off 约 4382 次 CRT 分配/操作，1000 项 Independent 约
4446 次/项。该数据揭示了真实优化空间，但 Debug CRT 与 Release allocator 不可直接比较，因此当前只建立
观测基线，不据单机样本设阈值，也不在没有 profile 证据前引入新的缓存或 arena 类型。

## 16. 安全与确定性

- 条件 AST 有节点数、深度、参数数和字符串长度限制；
- 除法、NaN、Infinity 和数值溢出返回结构化失败；
- 自定义函数必须声明纯度、成本和确定性；
- 不允许条件调用未知脚本或回调；
- 所有集合遍历采用稳定顺序；
- RNG 只通过命名 stream 和显式序号；
- 每次结算记录规则版本/哈希；
- 网络和回放比较使用规范化结果摘要；
- 触发链限制防止恶意或错误配置造成无限递归。

`AbilityReceipt`，经 `TacticsSettlementRuntime` 结算后把死亡结果交给 `defeatUnit`，并验证消灭目标完成；
因此能力合法性、行动点、统一规则和战棋目标状态均处于同一真实调用链中。
旧 `rpg::SettlementPipeline` 仍作为脚本兼容 facade 保留，但其 `run()` 已把回调执行放入 canonical
`settlement::SettlementPipeline` 的阶段/事务协议；正式 Battle 不读取该注册表。这样保留旧项目行为，
同时删除第二套独立执行循环，也没有增加新的公开类型。
Card 还覆盖了活动规则投影在 lifecycle 候选推进后失败时不提交 target、effect 时间或 tick；恢复干净快照后
同一 tick 可正常重试。RPG 覆盖无效活动 Status 规则不修改 Vitals、不发布伤害事件并显式产生
`settlementFailed`。Tactics 覆盖了领域 policy 在实际写入后报告 commit 失败时由 Settlement 回滚权威状态，
以及两目标范围结算任一提交失败时全部恢复。
Card 的即时 Damage/Heal/Shield 和周期 Damage/Heal/Shield 现已共用 `CardEffectExecutor` 管线；即时
Damage/Heal 仅在 period 为零时执行，保留周期效果 apply 时不提前结算的语义，没有新增即时执行器。
规则规模、命中率、Trace 三档、触发深度 1/4/8 与 1000 项 Independent 的可重复矩阵基准已经建立，
当前测量不支持新增 workspace/cache 类型。Windows Release 基线已经建立。现有 Windows、Linux、macOS
Release lane 已直接运行同一个 benchmark case，并分别上传包含单行 `SETTLEMENT_BENCHMARK_JSON` 的原始
日志，用于积累参考机样本；在样本稳定前只采集、不设置武断阈值。benchmark JSON 已加入跨平台峰值驻留
观测和 MSVC Debug 精确 CRT 分配计数；Release lane 会保留峰值字段，其分配字段明确为 `null`。跨平台
连续样本与正式回归阈值仍待 CI 数据校准。

独立 Debug/Release 配置还验证并修复了 Vulkan SDK `shaderc` 库的跨配置缓存污染：构建脚本改为局部
`NO_CACHE` 查找，不增加运行时类型或兼容层；Debug 选择 `shaderc_combinedd.lib`，Release 选择
`shaderc_combined.lib`。

## 18. 测试矩阵

每一阶段至少覆盖：

- 单元测试：parser、type checker、evaluator、规则操作；
- contract test：所有领域 policy 共享；
- composition test：RPG、RTS、Tactics、Card；
- provider present/absent；
- failure injection：prepare、commit、event、trigger；
- restore/hot reload；
- determinism/replay；
- script binding；
- trimmed profile；
- 性能基准；
- fuzz：条件 parser、配置 decoder、触发链。

关键不变量：

1. 失败后权威状态与事件日志均不发生部分变化。
2. Preview 不改变状态、事件、RNG 和 effect 生命周期。
3. 相同输入的规则顺序和结果稳定。
4. 未知字段、规则、版本和 stale handle 显式失败。
5. 所有跨模块状态通过 policy、typed Link/Handle 或明确 adapter 访问。

## 19. API 演进与兼容

- 保留现有单 magnitude API 作为低成本入口；
- 新能力通过显式 builder 或 bundle API 提供；
- 旧 `preview` 明确为 provider-level preview，完整预测使用 `previewSettlement`；
- 兼容 facade 必须注明 compatibility-only，并委托 canonical Result API；
- 持久化格式新增 schema/version 和迁移；
- 不使用第二套规则状态作为过渡方案；
- 废弃 API 给出替代项、移除版本和迁移文档。

## 20. 建议的 PR 拆分

为了减少中间抽象和重复 wiring，默认按 8 个垂直闭环 PR 推进：

1. 条件语言最小闭环：parser、类型检查、evaluator、SettlementRule 接入及测试；
2. 配置闭环：JSON/EveScript 解码、原子替换、错误诊断和热重载；
3. Effect 投影闭环：RPG 与 Card 先在现有 adapter 接入、restore 测试；只在出现重复后提取私有纯函数；
4. RTS/Tactics 的 `context` 快照；仅对真实用例补充最小分组策略；
5. 多资源、多段和多目标事务，保留单值快速路径；
6. Decision、命名 RNG、免疫、驱散和控制递减；
7. 触发链、循环保护以及基于现有 result details 的 Trace；
8. 回放/联网摘要、批处理优化和性能门禁。

每个 PR 必须同时更新接口、所有受影响 provider/consumer、测试、模块依赖和用户文档，不提交中间破坏状态。

若某个 PR 需要新增超过两个公开核心类型，应暂停实现并重新审查是否出现过度设计。
新增一个公开类型也必须逐项回答 1.3 的四个问题。内部 parser 节点和测试夹具不计入该限制，
但必须保持模块私有，且不得通过大量私有类规避代码体积审查。

## 21. 完成定义

只有满足以下条件，才可称为“通用结算系统完整接入”：

- RPG、RTS、Tactics、Card 的正式运行入口均使用 Settlement；
- 活动效果自动投影，无需玩法手工复制 Buff；
- 条件字符串在加载时编译为强类型 AST；
- 多资源、多段、多目标和触发链有正式 API；
- preview、commit、verify、replay 共享规则语义；
- 配置具备 schema、版本、迁移、热重载和精确诊断；
- 状态、事件和触发具备明确原子性；
- 全链路 Trace 能解释最终结果；
- 四玩法 contract/composition/failure/restore 测试完整；
- trimmed builds、架构门禁、跨平台构建和性能预算通过；
- 文档明确所有权、生命周期、线程、重入、确定性和成本契约。

## 23. 最终玩法入口审计（2026-09-21）

审计范围是 `rpg`、`rts`、`tactics`、`card` 模块内所有 health/HP 赋值、伤害、治疗、维修和周期恢复入口。
判定原则是：战斗或效果产生的数值变化必须经过 Settlement；初始化、存档恢复、编辑器直接赋值、最大生命变化时
保持原生命比例，以及明确的销毁/复活状态迁移，不属于一次伤害或治疗交易。

- RPG：`Battle` 的技能伤害、治疗、状态周期结算、吸血和反伤均进入 `Battle::settleRequest`；活动状态规则在执行前
  投影到同一管线。`VitalsSystem::takeDamage/heal` 和 `RPGActor` 同名接口仅保留为 compatibility-only 的低层状态提交
  接口，不是正式 Battle 结算入口；新玩法不得用它们计算或绕过规则。
- RTS：武器命中、投射物、能力伤害原本已统一到 `DamageRuntime`。本次把 facade 主动治疗、能力治疗、建筑维修和
  `healingPerSecond` 周期恢复全部改为调用 `DamageRuntime::heal`，与伤害复用同一个已配置的 Settlement 管线。
- Tactics：模块只负责行动合法性、目标和资源请求，生命权威状态由调用方 policy 持有；单目标和原子多目标入口均调用
  `TacticsSettlementRuntime`，未发现模块内直接写生命值的旁路。
- Card：立即伤害/治疗及周期伤害/治疗均调用 `CardEffectExecutor` 的 Settlement 管线；`CardSettlementPolicy` 内的
  candidate 写入是管线 prepare/commit 的事务实现，不是旁路。

审计中保留的直接写入均属于以下非结算类别：实体/archetype 初始化、快照恢复、定义重建、科技升级时保持生命比例、
明确的比赛结束或容器销毁归零，以及 Settlement policy 内的候选状态提交。除 RPG compatibility-only 状态提交 API 外，
四种玩法的正式伤害/治疗运行入口未发现遗留旁路。
