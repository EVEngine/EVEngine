# 领域短根继承与跨域组合架构
日期：2026-08-26
状态：已确认的架构方向

## 决策

EVEngine 的运行时对象采用以下结构：

> 各领域维护短而稳定的实体继承树；领域内用 `ecs::View<Base, Components...>` 完成类型与组件的联合批处理；正交能力使用组件组合；Scene、Graphics、Physics、UI 等不同领域之间使用强类型 Link/Handle 连接。

不建立统一的 `GameObject`、`GameplaySubject` 或 `GameplayActor` 大根类。公共协议中的 `SubjectRef` 可以引用不同领域对象，但不要求这些对象继承同一个玩法实体基类。

## 为什么适合当前 ECS

EVEngine ECS 同时具有两个正交维度：

- 类型维度：`ENTITY(Derived, Base)` 建立注册表继承树，查询 Base 会包含其子类。
- 组件维度：`COMPONENT` 提供按组件批量访问，`View<Base, A, B>` 联合限制类型家族和组件列。

例如：

```cpp
class RPGActor : public ecs::Entity {
public:
    ENTITY(RPGActor, ecs::Entity)
    COMPONENT(Attributes, attributes)
    COMPONENT(Statuses, statuses)
};

class Monster : public RPGActor {
public:
    ENTITY(Monster, RPGActor)
    COMPONENT(AIState, ai)
};
```

`ecs::View<RPGActor, RPGActor::Attributes>()` 会同时访问 RPGActor、Monster 及其后代；`ecs::View<Monster, RPGActor::Attributes, Monster::AIState>()` 则收窄到 Monster 类型树。

因此继承不仅是代码复用，还决定系统查询闭包、组件承诺和脚本 `eve.view(Base)` 的可见范围。

## 三种关系

### 继承：表达“是什么”

仅当 Derived 在完整生命周期内都能被 Base 系统无条件处理时使用继承。

```text
RPGActor
├── Player
├── Monster
│   └── Boss
└── NPC
```

新增 Base 必须至少有一个真实 `View<Base,...>` consumer。若 Base 系统经常排除某个 Derived，说明继承关系或 Base 契约错误。

### 组件：表达“拥有什么能力或状态”

运行时可批量处理、生命周期依附实体、但不定义对象本质的概念使用组件：

- Attributes、Tags、Effects、Orders、ActionState
- Health、Armor、Sensing、Formation、Production
- SceneLink、RenderLink、PhysicsLink
- Container membership、Selection、Presentation state

不要用子类表达会变化的状态，例如 Selected、Dead、Poisoned、PlayerControlled。

### Link/Handle：表达“在另一领域对应什么”

一个玩法对象可同时对应 SceneObject、Renderable、Physics Body，但 C++ 实体只选择一个主领域继承轴：

```text
VehicleEntity
├── Motion
├── Orders
├── SceneLink   ──→ SceneObject
├── RenderLink  ──→ Renderable3D
└── PhysicsLink ──→ Physics Body
```

跨领域组件不得长期保存裸指针；使用现有 `ecs::EntityHandle` 或对应领域的 generation handle。Link 必须定义 owner、失效检测、销毁联动和重建策略。

## 继承规则

### 领域短根

- 每个领域从 `ecs::Entity` 建立自己的短根，如 RPGActor、VehicleEntity、CardData、Renderable3D、SceneObject、UIHost。
- 通常保持 2–3 层稳定继承；项目可在领域根下继续派生具体类型。
- 不跨越模块层级建立向上的实体继承关系。
- 不因为复用函数或字段而继承。
- 不为纯 definition 差异创建 C++ 子类；只有组件集合、脚本 API 或系统参与方式稳定不同才派生类型。

### 查询闭包

对于 `Derived : Base`，所有合法的 Base View/System 都必须适用于 Derived：

```cpp
ecs::View<Base, BaseComponent>();
```

Derived 自动进入 Base 的类型注册树。评审继承关系时，必须列出 Base 的现有和计划 View，逐项确认替代性。

### 基类组件承诺

基类组件会传播给所有子类。只有所有子类都具有明确语义、生命周期和系统需求的组件才能放到基类。

热组件与冷组件应分离：

- 热组件：Transform、Velocity、SimulationState；紧凑、固定布局、尽量 POD，可用于 GPU 批处理。
- 冷组件：Identity、Tags、DefinitionRef、metadata；允许字符串和容器，但不与热路径大结构混放。

## 身份与句柄

- ECS 实体的运行时身份使用现有 `ecs::EntityHandle` 和 generation/stale 检测，不重新实现一套 ECS RuntimeHandle。
- 跨存档、网络和编辑器边界的对象可另外持有 PersistentId/UUID。
- 非 ECS 的 Physics、GPU、UI 等 registry 可使用同构的 `RuntimeHandle<Tag>{index,generation}`。
- PersistentId 与 runtime handle 是两个不同概念，可以同时存在于一个实体上。

## 各领域建议

### RPG

保留 RPGActor 领域根，Player、Monster、Boss 等在其下短继承。Attributes、Statuses、Skills 继续作为可批量访问的组件，但底层语义分别复用公共 attributes、effects 和 action 协议。

### Card

保留 CardData、Deck、Hand、Zone 等独立 ECS 类型。它们有独立身份、生命周期、脚本 API 和 View 需求。共享 Container/Transfer 协议，但 Hand 布局、拖拽、Deck shuffle/draw 仍属于 Card/presentation 领域。玩法组件保存 AssetRef，不长期保存 Graphics Texture 裸指针。

### Weapon 与 Vehicle

保留 WeaponEntity、WeaponMountEntity、WeaponRigEntity、AmmoPoolEntity 和 VehicleEntity 等领域类型。载具子类可按稳定运动模型追加组件；Orders、Attributes、Effects 等通过共享组件语义复用，而不是继承统一玩法根。

### Dialogue

DialogueParticipant、DialogueTrigger、BarkEmitter 等世界对象可成为领域实体；ConversationAsset、ConversationRunner、call stack、编译器、本地化和 migration 保持普通对象/服务。实体通过 session handle 连接 runner。

### RTS

RTSUnit、RTSBuilding 等建立自己的短根或从项目内稳定领域根派生；Orders、Sensing、Formation、Economy link、Weapon link 通过组件组合。RTS 不成为包办所有玩法机制的大模块。

### Procgen

PointSet、Grid、MeshData 和生成中间点保持紧凑普通数据，不逐点创建 ECS entity。Artifact 发布到运行时世界后，可创建 GeneratedTerrain、GeneratedBuilding、GeneratedResourceNode 等短根实体，并携带 ArtifactRef/BuildKey/Bounds 组件。

### Physics

Physics solver、broadphase、manifold、constraint storage 和 GPU buffer 保持专用后端。若 Body/Shape/Joint 需要独立脚本身份和批量查询，可以有 Physics 领域实体；它们通过 solver handle 连接后端。玩法实体通过 PhysicsLink 连接这些对象，不继承 Physics 类型。

## System 和结构修改

系统优先写出目标 View，再反推类型和组件边界：

```cpp
ecs::View<RPGActor, Attributes>();
ecs::View<VehicleEntity, Motion, Orders>();
ecs::View<CardData, Identity, State>();
```

遍历期间的实体创建、销毁和结构修改使用现有 `ecs::ScopedDefer`；长期引用使用 `ecs::EntityHandle`，不得依赖销毁后裸指针。

跨领域操作采用 Request/Transaction/Command Buffer：

```text
UI / AI request
    → validate / transaction
    → ECS deferred mutation
    → domain systems
    → domain event
```

## 明确不使用 ECS 的对象

- Schema、Definition、Recipe 和 Registry
- Result、Diagnostic、ConditionResult
- Event log、Transaction coordinator、Snapshot
- ConversationRunner/Compiler
- Procgen 中间计算数据与 worker job
- Physics solver 和 Graphics backend
- Asset database、resource loader、module capability

这些普通对象可以创建、查询或修改 ECS 实体，但不因“属于游戏功能”而变成 Entity。

## 评审清单

新增实体类型或继承关系时必须回答：

- [ ] 对象是否需要独立运行时身份、生命周期和直接查询？
- [ ] 候选 Base 的全部 System 是否应无条件看到 Derived？
- [ ] Base 的全部组件对 Derived 是否始终有意义？
- [ ] 这是稳定本质，还是运行时可变化状态？
- [ ] 差异是组件/API 差异，还是仅 definition 数据差异？
- [ ] 该 Base 是否至少有一个真实 `View<Base,...>` consumer？
- [ ] 是否错误跨越了模块依赖层级？
- [ ] 其他 Scene/Render/Physics/UI 身份能否使用 Link 表达？
- [ ] Link 是否有 owner、generation、失效和重建规则？
- [ ] 热组件是否保持紧凑，冷数据是否从热路径分离？

## 结果

最终架构分工如下：

```text
领域内部：短根继承 + View 类型/组件联合批处理
正交能力：Components + Systems
领域之间：强类型 Links/Handles + Capabilities
跨模块一致性：Identity + Value + Result + Event + Transaction + Schema
```
