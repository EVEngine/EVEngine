# TVE primary material import

The native Unity importer now dispatches the supplied TVE 12.6.0 Plant Standard,
Plant Subsurface, Prop Standard and Prop Subsurface shader GUIDs to a primary
material converter. Other shader identities remain unsupported. This is partial
material translation, not complete shader equivalence.

The converter writes `eve.material/3`, preserving material identity from the Unity
GUID/fileID. It binds the original main albedo image and a separate derived ORM
image whose identity is a stable child of the material identity. Main mask pixels
are decoded as data; original texture definitions and source bytes are unchanged.
Derived channels are AO from source G, roughness from source A, zero metallic,
and source B in alpha for RGB mixing. AO/smoothness factors are baked into bytes
with explicit nearest-integer rounding; runtime factors remain one. Missing mask
assignments use the shader-defined white texture. Missing nonzero references fail.

Main color and second color RGB are converted from serialized sRGB to canonical
linear values. Alpha and UV vectors are not color-converted. The target is linear
PBR, matching Unity's documented [linear-workflow color property conversion](https://docs.unity.cn/ru/Manual/SL-PropertiesInPrograms.html).
The implementation uses extended sRGB for HDR values; exact Unity HDR exposure
and legacy gamma-workflow appearance are not certified. Main UV scale/offset is
translated across the existing V-axis conversion: native offset Y is
`1-scaleY-sourceOffsetY`.

The primary conversion includes albedo intensity, RGB dual-color remapping,
opaque/masked/transparent mode, cutoff and both/front-face selection. Back-face-only
rendering is unsupported. Normal processing, alpha ordering/secondary opacity,
subsurface, detail, field/global effects, fades, motion bindings, sampler overrides
and remaining render states are not translated. Every admitted material emits an
explicit unsupported-feature finding alongside the primary translation finding.
Original source is retained by the collection importer.

Parsing rejects duplicate selected properties, invalid numbers/ranges and absent
primary texture sources. Conversion is reentrant and builds an unpublished owning
candidate, with no GPU allocation or retained source pointers. Derived PNG encoding
is bounded and returns checked results. The collection's existing budget and
transaction rules govern publication. Prefab material dependencies use the actual
manifest version instead of a hard-coded v2 type.

## Height-generator candidate rejection

A first empirical candidate was evaluated against all 88 Unity exports. It uses arithmetic RGB height, periodic central differences (or separable Sobel), and a hypothesized strength factor `h * 2^(2*h - 2.5) * sqrt(width*height)`. This is an experiment, not the native conversion contract. Only 41 of 88 cases match every exported X/Y byte. Rectangular inputs differ by up to three bytes, disproving exact compatibility of the candidate.

For the original 1024-square Pine source, Standard at 0.25 matches 2,087,020 of 2,097,152 X/Y channel samples with maximum error one byte; Sobel at 0.25 matches 2,058,485 samples. At strength 1, Standard matches 1,925,511 and Sobel 1,729,580 samples, again with maximum error one byte. These are importer-byte comparisons before lighting or platform compression, not rendered parity. Full per-case measurements are in `build/tve-reference/height-normal-candidate-comparison.json`. Strength scaling, rectangular dimension dependence and quantization remain unresolved; height-map admission remains explicitly unsupported until a validated implementation is available.

The isolated oracle additionally exported the 8x8 ramp as actual RGBAFloat at the same six strengths. The editor terminated and all six format records report RGBAFloat, so these values do not pass through RGBA32 quantization. X remains packed in alpha, Y in green. Inverting the normalized X gives effective central-difference coefficients 0.2142908635, 0.5000523360, 1.3892845705, 2.9705886679 and 5.7825883793 for strengths 0.125, 0.25, 0.5, 0.75 and 1 respectively (height expressed as source byte / 256). The boundary/interior signed slope ratio is -3 within 0.000004, consistent with periodic central differences on this ramp. This isolates the unresolved strength mapping from final eight-bit quantization; it does not establish arbitrary-image or Sobel parity. Reproduction script: build/tve-unity-normal-oracle/Assets/Editor/ExportFloatNormals.cs. Compact evidence: build/tve-reference/height-normal-float-measurement.json.

## Exponential height-strength calibration

A dense 33-point RGBAFloat sweep resolves the strength curve: the central differences of arithmetic RGB height in [0,1] are multiplied by `0.04 * (width + height) * (pow(10, heightmapScale) - 1)` before normalization with Z=1. This supersedes the rejected exponential-times-h / geometric-mean candidate. All synthetic Standard-filter RGBA32 cases match byte for byte using this formula, including rectangular ramps. Across all 88 cases, 71 match exactly and every remaining discrepancy is at most one byte. Evidence is in build/tve-reference/height-normal-exponential-comparison.json.

The original Pine Standard case has 7,487 differing X/Y bytes at strength 0.25 and 10,496 at strength 1 out of 2,097,152 samples each. Of those differences, 7,481 and 10,488 respectively occur where the arithmetic source height gradient is exactly zero: the boundary at neutral 127.5 is sensitive to floating-point RGB accumulation and normalization. Only six and eight nonzero-gradient channels differ, each by one byte. Sobel still needs its own float comparison and operation-order check. The calibrated formula is empirical Unity 6000.0.79f1 importer evidence, not a published Unity algorithm contract; native implementation and regression coverage remain required.

## Next lighting integration: source-confirmed translucency contract

Source inspection of `Core/Runtime/TVEUtils.cs:1280` shows the canonical material controls are mapped to template controls before rendering: scattering power maps to strength, angle maps to exponent, and normal/direct/ambient/shadow map independently. Importing only serialized template defaults would miss the effective source behavior. The Built-in Prop forward pass around line 1423 and Universal 6000 Prop forward pass around line 1520 both form light direction plus normal distortion without renormalizing that sum, then clamp the view dot product before applying the angular exponent.

The Universal path attenuates each light by distance, then interpolates shadow attenuation by the material shadow control. It adds a light-scaled combination of the direct backlight lobe and baked diffuse ambient. The contribution multiplies the final base color, the separately computed subsurface color (itself modulated by wetness-stage albedo), intensity, mask, a factor of ten, and power. These two color stages must remain distinct when detail/wetness/global overlays are integrated; collapsing them into one tint changes the authored result. Built-in differs for shadow interpolation on directional versus local lights and therefore needs a stated backend lighting contract rather than an assumed identical implementation.

Plant's source mask interpolates from one to the remapped blended mask using `_SubsurfaceMaskValue` (Built-in Plant around line 1715); Prop uses one. Global subsurface and overlay subsurface modulate intensity. The current native PbrSurface and Vulkan PBR fragment shader contain no corresponding controls. Integration remains pending across the canonical material reader, source importer, validation, uniform transport, lighting evaluation, and real backlit render fixtures. This source finding is not completion evidence for those consumers.

## Explicit mip integration constraints from current source

Current HEAD (not only the working tree) already ships the eve.image/2 cooker and EVIMG v1, and AssetMigration registers image current=2 with v1-to-v2 migration. Fourteen source/test/catalogue files directly constrain eve.image/2. Consequently this feature must introduce image v3, update the registered N/N-1 window with v2-to-v3 migration, update producer/dependency declarations and readers together, and preserve v2 base-image behavior during migration. No existing EVIMG v1 reserved field can silently acquire mip semantics.

The Vulkan texture creation implementation already uploads a contiguous level-major chain through recordTextureCopies, but the public resource factory accepts only base pixels plus a generic generation option. Explicit imported levels require a checked upload operation; the existing height-normal measurements prohibit replacing them with generic generation. Before GPU allocation, the operation must validate dimensions, full level count, exact per-level/total byte sizes and budgets, and reject unsupported providers observably. recordTextureCopies currently narrows staging offsets to uint32_t, so the admitted upload byte budget must respect that bound or the underlying copy API must be widened as part of the change.

Successful publication must keep the texture and GPU-owner registries consistent under allocation/upload failure. Returned textures remain factory-owned and are released through the same factory. Required composition evidence is a source-produced multilevel image cooked into the new payload, loaded through the image factory, sampled at a nonzero LOD in the real renderer, plus malformed-chain and unsupported-provider cases. Old single-level images must retain their prior upload behavior. These are implementation constraints verified from current source, not a claim that explicit mip upload is implemented.
