# 通用武器系统设计 — `weapon` v2

日期：2026-08-25
状态：已实现（含 v2 核心 + P0 补充：多弹丸/散布 bloom/后坐力/射击模式切换/开镜/伤害类型/共享弹药池）
分支：`codex/weapon-system-v2`
存放：`docs/dev/`

## 背景与问题

现有 `src/modules/weapon/` 是一套**为枪械（热武器）特化的单体模块**，把弹药/装填/
连发直接硬编码进 `WeaponEntity::State` 与 `WeaponSystem::update()`。它无法优雅表达：

| 形态 | 现有系统的障碍 |
|---|---|
| 热武器（步枪/加农炮） | ✅ 当前唯一一等公民（hitscan / projectile / ammo / reload） |
| 冷兵器（剑/斧） | ❌ 没有挥击阶段 / 命中弧，且"装填"对它毫无意义 |
| 法杖武器（法术） | ❌ 没有施法前摇 / 持续引导 / MP 资源 / AoE 落点 |
| 导弹（制导） | ❌ 没有锁定 / 引导 / 发射成本，投射物服务只管"生成" |

`IWeaponLogic` 目前只建模 `fire`（生成投射物 / 直射判定），没有阶段生命周期
（windup / channel / recover），`FireRequest` 也是面向"打一个目标点"的投射物语义。

同时按本仓库自己的约定（`docs/dev/模块编排与裁剪架构.md` §7.3）：
**裁剪粒度到模块为止，模块内不做 feature flag**。但这里"裁剪"的真实需求是
**按武器形态裁剪**——RTS 只要热武器，ARPG 要近战+法杖，RPG 要全都要。所以裁剪轴
应该是"形态（attack form）"，而不是"整个武器模块"。

## 决策（已与使用者确认）

1. **保持单一 `weapon` 模块**（不做 4 个物理子模块的拆建），形态裁剪通过
   **数据驱动的 `kind` + 模块内形态提供者注册表**实现。好处：零构建复杂度、
   不触及 `module_manifest.cmake`；配合现有 `registerLogic` 能力接口，
   游戏侧仍可只链接自己需要的提供者。坏处：形态不各自独立成构建单元。
2. **先写设计稿，评审后再实现。**
3. **首期完整实现：近战 + 热武器**；法杖 + 导弹完成**数据模型与接口**，
   实现列为 Phase 2。

## 目标 / 非目标

### 目标

- 一套通用的**触发管线**（资源门槛 → 阶段机 → 形态提供者），近战/热武/法杖/导弹共用。
- 数据驱动的 `kind` 让同一把武器可用不同"形态"表现。
- 兼容并推广现有能力注入（`IProjectileService`）与事件队列（`fire/reload/empty`）。
- 面向 RPG / RTS / ARPG 三种形态都能裁剪使用。

### 非目标

- 不做伤害结算本身（命中/受击/护甲继续由游戏侧或 `rpg` / `vehicle` 处理）。
- 不做武器模型/动画资源（持有位姿与阶段名由游戏侧驱动渲染）。
- 不做网络同步 / 存档（阶段机与资源状态可序列化，留给游戏侧）。
- 不做真实弹道物理（弹道仍经 `IProjectileService` 交给游戏侧）。
- 不新增物理模块 / 构建单元。

## 数据模型变更

### 1. `WeaponKind` —— 形态分类

```cpp
enum class WeaponKind : uint8_t { Melee, Ranged, Magic, Missile, Custom };
const char* weaponKindName(WeaponKind k);        // "melee" | "ranged" | "magic" | "missile"
WeaponKind weaponKindFromName(const std::string&);
```

写入 `WeaponDefinition::kind`（默认 `Ranged`，等价旧 `logic` 路径）。
`kind` 选择形态提供者；`logic` 保留为"底层效果器"（近战走 `melee`、热武走 `ranged`，
法杖走 `magic`、导弹走 `missile`）。两者分离：`kind` 决定**阶段机怎么跑**，
`logic` 决定**特效/弹道/命中怎么做**。

### 2. `AttackResource` —— 通用触发资源

替换硬编码的 `magAmmo / reserveAmmo` 门槛，用一个通用资源模型：

```cpp
enum class ResourceKind : uint8_t { None, Ammo, Mana, Charges, Stamina };
struct AttackResource {
    ResourceKind kind = ResourceKind::None;
    float value = 0.f, max = 0.f, regen = 0.f;  // regen>0 每秒恢复（法力/体力）
    bool infinite = false;                       // 近战/无消耗
    float cost = 0.f;                            // 每次触发消耗
};
```

`WeaponEntity::State` 由 `magAmmo/reserveAmmo` 收敛为：

```cpp
struct Resource {
    AttackResource def;          // 模板定义（注册表持有，实体只存快照）
    float value = 0.f;           // 当前值
    bool  reloading = false;
    float reloadProgress = 0.f;
};
```

映射关系：
- 热武器：`Ammo`，`value`=弹匣剩余，`cost`=1，`max`=弹匣容量；`regen=0`，
  装填仍是"从备用弹药重填"（保留现有 `reserve`/`reloadTime` 字段以兼容）。
- 法杖：`Mana`，`regen>0`，`cost`=每次施法蓝耗。
- 导弹：`Charges`，`cost=1`，`regen` 可选（装填式 or 自然回复）。
- 近战：`None` 或 `Stamina`，多数情况 `None`（无限）+ 仅受阶段/冷却限制。

### 3. 阶段机 —— `AttackStage`

替换"装填/连发"两条特判路径为一个通用阶段机：

```cpp
enum class AttackStage : uint8_t { Idle, Windup, Active, Recover };
struct AttackStageSpec {
    float windupTime  = 0.f;   // 前摇（挥剑起手 / 施法抬手 / 导弹锁定）
    float activeTime  = 0.f;   // 生效期（命中帧 / 引导节拍 / 发射时刻）
    float recoverTime = 0.f;   // 后摇（收刀 / 施法硬直 / 再装填窗口）
};
```

推进逻辑（`WeaponSystem::update`）：

```
Idle  --tryAttack()--► Windup --windupTime--> Active --activeTime--> Recover --recoverTime--> Idle
                          ▲                                                            │
                          └──────────────────── 打断（cancelAttack）───────────────────┘
```

- `Windup→Active` 时刻调用形态提供者的 `fire()`（近战命中帧 / 热武器出膛 / 法术释放）。
- `Active` 期可选调用 `channel()`（引导法术、导弹飞行引导）。
- `Recover` 期阻挡下一次 `tryAttack`（等价旧的 cooldown）。保留 `State.cooldown`
  字段作为额外全局冷却，兼容旧数据。

事件：新增 `windup_start`、`attack_end` 事件类型，连同现有 `fire`/`reload_start`/
`reload_end`/`empty`。

### 4. `AttackRequest` —— 泛化请求

`FireRequest` 更名/扩展为 `AttackRequest`：

```cpp
struct AttackRequest {
    // 目标
    float targetX = 0.f, targetY = 0.f, targetZ = 0.f;
    bool  hasTarget = false;
    ecs::EntityHandle targetHandle;   // 可选：锁定单位（导弹/法杖单目标）
    // 方向与来源
    float yaw = 0.f, pitch = 0.f;
    float muzzleX = 0.f, muzzleY = 0.f, muzzleZ = 0.f;
    int   shooterId = 0;
    // 形态载荷（近战命中弧 / 法术 AoE 落点），由 kind 提供者解释
    float arcAngle = 0.f;             // 近战挥击角度
    float aoeRadius = 0.f;            // 法术/导弹爆炸半径
};
```

旧字段全部保留，`weapon::fireAt` 脚本 API 不变，仅内部类型换名。

## 模块结构（仍在单一 `weapon` 模块内）

```
src/modules/weapon/
  Weapon.h           模块入口（注册表/工厂/挂点与手持位/事件）——签名基本不变
  WeaponTypes.h      数据模型：kind / resource / stage / request / 实体组件
  WeaponLogic.h      接口：IWeaponLogic v2（阶段生命周期） + 形态提供者注册表
  WeaponSystem.cpp   阶段机推进 + 资源门槛 + 形态提供者调度
  forms/             （新）形态提供者
    MeleeForm.cpp     近战：挥击命中弧 / windup-recover / 可选耐力
    RangedForm.cpp    热武：hitscan / projectile（继承现有 projectile + hitscan）
    MagicForm.cpp     （Phase 2）法杖：引导 / 蓝耗 / AoE 落点
    MissileForm.cpp   （Phase 2）导弹：锁定 / 引导 / 发射成本
```

`IWeaponLogic` 升级（向后兼容：旧实现只有 `fire` 也合法）：

```cpp
class IWeaponLogic {
public:
    virtual ~IWeaponLogic() = default;
    virtual const char* name() const = 0;
    virtual bool canFire(const WeaponEntity&) const = 0;            // 形态级门槛
    virtual void fire(WeaponEntity&, const AttackRequest&) = 0;     // Active 生效时刻
    virtual void update(WeaponEntity&, float dt) = 0;
    // 新增阶段钩子（默认空实现）
    virtual void begin(WeaponEntity&, const AttackRequest&) {}      // Windup 起点
    virtual void channel(WeaponEntity&, const AttackRequest&, float dt) {}  // Active 期
    virtual void end(WeaponEntity&, const AttackRequest&) {}        // Recover 起点
};
```

`IProjectileService` 保持，供热武/导弹经能力接口生成弹道；近战 / 法术命中走事件队列，
由游戏侧读取 `fire` 事件（附带 arc / aoe）做范围判定。

## 手持位 vs 炮塔挂点

现有 `WeaponMountEntity`（限位/转速/射界）保留，专供 **RTS 炮塔 / 载具**。

为 **ARPG / RPG 角色手持**新增轻量 `WeaponRigEntity`（可选，不参与炮塔旋转）：

```cpp
class WeaponRigEntity : public ecs::Entity {
    COMPONENT(Identity, identity);        // id / nodePath（手持节点）
    COMPONENT(Held,      held);           // 持有位姿：position/rotation 偏移 + wield 类型
    COMPONENT(State,     state);          // weapon 指针（不拥有）
};
```

角色近战 / 法杖 / 远程步枪都挂 `WeaponRigEntity`；炮塔/车载武器仍用 `WeaponMountEntity`。
二者互不冲突，`Weapon` 模块分别提供 `newRig()` / `rigAttachWeapon()`。

## 迁移与兼容

- 旧 JSON：无 `kind` 时默认 `Ranged`；`ammo`/`fireMode`/`burst`/`reload` 字段照常解析，
  热武器行为与现在**逐字节一致**（回归基线 = 现状）。
- `WeaponEntity::State` 的 `magAmmo/reserveAmmo` 访问器在脚本层保留
  （`getMagAmmo/getReserveAmmo` 映射到 `Resource.value`），避免破坏 `vehicle` 与现有脚本。
- 旧 `logic` 值 `hitscan`/`projectile` 继续有效；新增 `melee`（Phase 2 加 `magic`/`missile`）。
- 模块 manifest 不改（仍是单一 `weapon`，LAYER 4，GROUP 2d 3d）。

## 脚本 API 摘要

```squirrel
weapon <- eve.Weapon()
weapon.registerWeaponsFromJson(json)

// 热武器：同旧 API
rifle  <- weapon.newWeapon("rifle")
weapon.fireAt(rifle, x, y, z)

// 近战：触发即进入阶段机，事件驱动命中
sword  <- weapon.newWeapon("sword")
weapon.attack(sword, yaw, pitch)          // 触发挥击（资源门槛 + 阶段机）

// 手持位（ARPG/RPG 角色）
rig <- weapon.newRig("right_hand")
weapon.rigAttachWeapon(rig, sword)

// 事件：阶段与命中
weapon.getEventType(i)                    // "windup_start" | "fire" | "attack_end"
weapon.getEventArc(i)                     // 近战命中弧（仅 fire 事件）
weapon.getEventAoe(i)                     // 法术/导弹爆炸半径（仅 fire 事件）
```

## 测试计划（`test/weapon.cpp` 增补）

- **近战阶段机**：windup→active→recover 时长推进、`fire` 事件落在 active 期、recover 期不可再触发。
- **近战资源**：`None` 无限触发（仅受冷却/阶段限制）；`Stamina` 耗尽即被门槛挡住。
- **热武回归**：现有 11 个用例全数通过（fire/cooldown/empty/reload/burst/mount）。
- **手持位**：`newRig` / `rigAttachWeapon` / 位姿组件读写。
- **kind 解析**：`weaponKindFromName` 各值 + 默认回退 `Ranged`。
- **阶段钩子**：自定义 `IWeaponLogic` 实现 `begin/channel/end`，断言调用次序。

## Phase 2（本次仅出数据模型与接口）

- `MagicForm`：引导（channel）多节拍、蓝耗、AoE 落点。
- `MissileForm`：锁定 `targetHandle`、转向制导、发射成本、命中 AoE。

## 取舍

1. **单模块 vs 拆 4 模块**：选单模块（使用者确认）。形态按 `kind` 裁剪，
   靠 `registerLogic` 让游戏侧只注册需要的提供者；若要进一步到构建级裁剪，
   可后续把 `forms/` 拆成子模块，接口已为此留好（`IWeaponLogic` 注册表）。
2. **阶段机替代 cooldown/burst**：burst 由 `cooldown` + 连发参数保留兼容；
   `reload` 语义由 `Resource.kind==Ammo` 触发，近战/法杖自动忽略。
3. **`fire` 事件保留为通用"命中/生效"信号**：近战命中弧、热武器出膛、法术释放、
   导弹爆炸都以 `fire` 事件承载（附带 arc/aoe），游戏侧统一处理渲染与伤害。
