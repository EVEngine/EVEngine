## 1. 目标与判据

**目标**：用户尽量只写脚本、不写 C++，就能新增功能；所有 API 对用户自定义行为有足够扩展性。

| # | 判据（可证伪） | 取证方式 | 状态 |
| --- | --- | --- | --- |
| J-1 | 脚本里注册一个**游戏规则型扩展点**并生效，不改任何 C++ 文件 | 新增 example + 集成测试 | ✅ §9.11 + §9.9 |
| J-2 | 用户对象挂进场景变换/物理同步管线 | 一个脚本 link kind + 集成测试 | ✅ §9.12 |
| J-3 | 用户自定义组件状态能被引擎工具读到（编辑器 / 存档 / 重放） | 三条通路各自取证 | ✅ §9.67、§9.72–§9.76（编辑器 + MCP） |
| J-4 | 扩展点在**提供方缺席**时行为已定义且被测试 | present/absent 双探针 | ✅ 每个插座都有 absent 探针 |

**边界**：J-1..J-4 只覆盖"声明 + 行为 + 数据"三类接入，不含每帧每实体的热逻辑、GPU 内部布局、物理求解器内部（§6）。

## 2. 现状（2026-09-21 复测口径）

### 2.1 两套组件世界，不共享存储

C++ ECS 用编译期 `typeid` 键 + 稠密 `std::deque`；脚本 ECS 用字符串槽名 + 类身份。**脚本组件没有原生存储**，原生 `View<T>` 看不见它们。两者之间有**三条**互操作通路（原生实体对脚本视图可见、脚本实体被逐帧回调、脚本组件字段进 GPU buffer），各自的覆盖用例与断言级别已逐条盘点（§9.48）。

### 2.2 已脚本化的扩展点（插座）

工具报的 15 个"孤儿能力"名字里，**5 个 `IMotion*Sink` 是工具盲区**（真实消费是 `MotionBuilder` 直接注入）；其余逐个人工定性后接入，**本轮全部接上**（不按工具输出开工，CANDIDATE ≠ FAIL）：

| 插座 | 形状 | 条目 |
| --- | --- | --- |
| `IVehicleDamageModifier` | 4 标量、无返回 | §9.9 |
| `IProjectileService` | 2 结构体进、无返回 | §9.53 |
| `IPhotoModeApplySink` | 标量 | §9.69 |
| `IClimbingEventSink` | 标量 | §9.71 |
| `ITileCollisionSink` | **先改接口**：`const void* layer` → 稳定身份 `TileLayerRef` | §9.77 |
| `ISensingCandidateProvider` | `TargetingQuery` 进、候选记录出（先定编组） | §9.79 |
| `IStateQuery` / `IStateMutation` | 记录进 / 出（对话侧消费） | §9.81 |
| `IMotionFloatSink` + `Vec2/Vec3/Color/Quat` | builder 接受脚本 sink 对象（不能做成全局 `cap::provide`） | §9.80、§9.82 |
| 脚本 link kind（`scene::LinkOps`） | 函数指针表 + 按名注册，目标可以是脚本对象 | §9.12 |

### 2.4 脚本 ECS 的四处缺陷（F1–F4）

F2（`destroy()` 不清 `_comps` 与字段）、F3（`eve.view` 返回缓存数组**本体**）已修（§9.13）；F4 的"字段槽位从未接上 / `getComponent` 与打包读到不同对象"被实测**推翻**——两者是同一个对象（§9.14.2 → §9.38）；F1 的"顺序"半边已修（§9.42，`eve.view` = 实体 id 升序），"不 `destroy()` 就泄漏"属设计。

### 2.5 重放/快照的硬失败

已修（§9.41）：不可捕获的值（类实例 / 闭包）改为"跳过 + 记名"写进捕获结果，不再让整次捕获失败。

## 4. 顺序与理由（事后核对）

- **门禁先于一切**：阶段 3 的收敛目标与阶段 4 新增的脚本 `provides`，都只能用 `provides`/`requires` 声明来验收。
- **收敛先于脚本 provider**：脚本 provider 需要"注册 / 撤销 / 热重载 / 线程安全"的单一语义；不收敛就要在 13 个家族注册表上各接一次。
- **阶段 3 是加法不是大迁移**：风险限制在 `Capability.h` 一处，既有调用点零改动，阶段 4 因此不用等家族迁移完。
- **诚实记录**：阶段 1–3 没有用户可见功能。当时允许"阶段 4 首批与阶段 3 并行验证"——实际就是这么做的（`IVehicleDamageModifier` 是第一个 sink），**没有返工**（§10 第 1 条）。

**成本可见性的硬约束**：脚本调用是**解释器代价**，所以脚本 provider 的注册 API 必须让调用者看出冷 / 热路径，**不得**与 C++ 函数指针 sink 形状相同。桥放宽到"对象 / 表参数"后 `@cost` 已重估（§9.68）；登记组件的字段访问实测约 **2.5x**（§9.62.1），已写进契约。

## 6. 非目标（明确不做）

| 不做 | 理由 |
| --- | --- |
| 统一 6 种载体（ECS/capability/event/Link/脚本/协议） | 规范 §8.4：「把这六种收敛成一种是**取消**而非简化」 |
| 统一 `IModuleInterface` 基类 | 无法表达"3 能力 + 2 可选依赖 + 4 事件 + 1 脚本类"而不变成 god-object |
| 合并 provider 策略 | `R-COHESION-4` |
| 每帧每实体的热逻辑脚本化 | 解释器代价；应原生或 GPU |
| GPU 内部（SSBO 布局 / command buffer / descriptor）脚本化 | 引擎内部布局 |
| 物理求解器内部（broadphase / BVH / constraint solver）脚本化 | 重型后端；只做注册式扩展 |
| 改 `external/ECS.hpp` 让脚本类成为原生组件 | 编译期 `typeid` 不可运行时注册；且违反既定决策（脚本类 `extends` 原生注册类会破坏 `eve.view` 子类语义） |
| 把 `Value` 负载上 GPU | `EcsGpu.h` 的 `static_assert(is_trivially_copyable_v)` 编译期排除 |

**判据**：一段逻辑若"每帧执行一遍解释器代价可接受"且"不需要碰引擎内部布局"，它应脚本化；否则原生。
