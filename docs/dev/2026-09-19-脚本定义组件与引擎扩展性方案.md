## 1. 目标与判据

**目标**：用户尽量只写脚本、不写 C++ native 代码，就能新增功能；所有 API 对用户自定义行为有足够扩展性。当前"加功能要改引擎"是主要痛点。

**达标判据**（可证伪，避免目标漂移）：

| # | 判据 | 取证方式 |
| --- | --- | --- |
| J-1 | 用户能在脚本中注册一个**游戏规则型扩展点**并生效，且不改任何 C++ 文件 | 新增一个 example 与其集成测试 |
| J-2 | 用户能把自己的对象挂进场景变换/物理同步管线 | 新增一个脚本 link kind + 集成测试 |
| J-3 | 用户自定义的组件状态能被引擎工具读到（编辑器/存档/重放） | 三条通路各自的集成测试 |
| J-4 | 上述扩展点在**提供方缺席**时行为已定义且被测试 | present/absent 双探针 |

**判据的边界**：J-1..J-4 只覆盖"声明 + 行为 + 数据"三类接入。**不包含**每帧每实体的热逻辑、GPU 内部布局、物理求解器内部——见 §6 非目标。

## 2. 现状诊断（当日复测）

### 2.1 两套组件世界，不共享任何存储

| | C++ ECS（`external/ECS.hpp`） | 脚本 ECS（`src/engine/common/ECS.cpp` 内嵌 `kEcsScript`） |
| --- | --- | --- |
| 组件单位 | `COMPONENT(T,name)` → `ComponentRef<T>`，**编译期类型** | Squirrel 类实例；`eve.Component` 子类 |
| 存储键 | `std::type_index(typeid(T))` | **字符串槽名** `_slots[fieldName]` / `_comps[name]` |
| 实例容器 | `std::deque<T>`，按实体 id 稠密 | `eve._ecsTypes[cls].instances` |
| 查询 | `View<B,Ts...>` 编译期模板 | `eve.view(cls)` 按类身份 |
| 实体身份 | `id` + `generation`，`EntityHandle`/`try_get` 校验 | `eve.allocEntityId()` **裸计数器**，无 generation |

**脚本 `eve.Entity` 不是 ECS 实体**（`ECS.cpp:31-36`、`:313`），所以两侧的 `View` 互相看不见。唯一交集是 `SceneObject::ScriptBindings`（`std::vector<HSQOBJECT>`，无类型键）与 `Scene::updateScripts` 的逐帧驱动。

### 2.2 集成机制并不算多，但**同一机制被重复实现**

6 种载体（ECS / capability / event / Link / 脚本 / 协议）各自语义不可替代，规范 §8.4 已明确**不统一**。问题在机制轴：

| 现象 | 实测 |
| --- | --- |
| provider 家族自造注册表 | 参考实现 1（`editing`）+ 候选 3（`common/ScriptModule`、`physics_backend`、`scene_editing`） |
| 根因 | `common/Capability.h:40-44` 只给裸指针 + "lifetime is the caller's" + 非线程安全 → 需要所有权/租约/代际失效的家族只能自造 |

### 2.3 能力面只有一半（**当日复测，比台账更差**）

口径：`python3 scripts/module_boundary_audit.py --json`，工作树 `f6e657c8c`。

**结论**：能力面在扩张（48→70）而没有闭合（孤儿 11→16）。在这个面上直接叠加"脚本提供方"会把问题相乘。

### 2.4 脚本 ECS 的四处正确性缺陷

| ID | 缺陷 | 位置 |
| --- | --- | --- |
| F1 | 脚本实体被 `eve._ecsTypes` 永久强根引，不显式 `destroy()` 即泄漏 | `ECS.cpp:259-263` |
| F2 | `destroy()` 不清 `_comps`/字段，销毁后仍可读可写且对 view 无影响 | `ECS.cpp:352-356` |
| F3 | `eve.view` 返回缓存数组**本体**（`v1 == v2` 是测试断言），脚本改动污染所有使用者 | `ECS.cpp:737,741` |
| F4 | 组件双写 `_comps[name]` 与 `e[name]`，且吞掉字段赋值异常 → `getComponent` 与 `packEcsFloats` 可读到不同对象 | `ECS.cpp:317-321`；`EcsScriptPack.cpp:165` |

### 2.5 重放/快照的硬失败

`Snapshot.cpp:179-184` 设定错误、`:409-414` **整次捕获失败**：任何被接受的 table/array 根内出现 `OT_CLASS`/`OT_INSTANCE`/closure 成员即失败。而 `resolveRoots`（`:369-374`）**静默过滤**顶层 instance 全局。因此"把实体实例从全局挪进一个列表"会把行为从"被忽略"翻转成"致命错误"——而"维护一份实体列表"正是本方案会鼓励的用法。

## 3. 方案：六个阶段

### 阶段 1 — 门禁 G-1 + G-2（可证伪的边界声明）

| 项 | 内容 |
| --- | --- |
| 做什么 | `check_architecture_contracts.py` 的 `RULES` / `RULE_REQUIRED` 新增 `module-interface` 规则与必需字段（`provides`/`requires`/`emits`/`observes`/`binds`/`trim`）；`lint_contract_coverage` 新增触发器：`cap::provide<X>`/`cap::addListener<X>`/`cap::query<X>`/`cap::forEach<X>` 必须映射到 `module-interface` 条目，且**类型名 X 出现在该条目的 `provides`/`requires` 列表中** |
| 理由 | 规范 §8.2 G-2 原文：「现有触发器只按规则 + scope 匹配，**不校验名字，必须补上**」。台账 §7 判定它是 E1/E2/E3-01/E2-OPT **四类发现共同的前置** |
| 为什么最先 | 它是后续所有阶段的**验收前提**：阶段 3 的收敛目标、阶段 4 新增的脚本 `provides`，都只能靠 `provides`/`requires` 声明来证明 |
| 风险 | 零（source-only，changed-line 语义，不改运行时行为） |
| 验收 | `make check/architecture-contracts` 通过；`scripts/tests/test_architecture_contracts.py` 新增两条 fixture（缺 `provides` 名字 → 拒绝；声明齐备 → 通过）；对 16 个孤儿能力不再新增"够不着"的条目 |

### 阶段 2 — 围栏 G-3 + G-4 与 `ProviderRef<T>`

| 项 | 内容 |
| --- | --- |
| 做什么 | `hot_path` 路径 glob 声明 + 新增行禁用原语门禁（G-3）；runtime profile 源码出现 `getModInst`/`requireModInst` 即失败（G-4）；引入不可拷贝、必须存为成员、**没有每帧可调重载**的 `ProviderRef<T>` |
| 理由 | 规范 §4.3：「**正确的用法必须是最顺手的用法；错误的用法必须编译不过，或需要额外写代码**」。§7 判定只有 §4 围栏与 §5 成本"不依赖使用者自觉" |
| 实测理由 | M3 在 3.6 天内从 111 处升到 204 处——43 提交/天的速度下，自觉不可行 |
| 风险 | 低（G-3/G-4 为 source-only；`ProviderRef<T>` 为新增类型，不迁移存量） |
| 验收 | 两个门禁对 fixtures 生效；存量按 `§8.3 按触碰补齐`，不要求一次性改 42 个模块 |

### 阶段 3 — 机制收敛 R-COHESION-3（**加法式，非大迁移**）

| 项 | 内容 |
| --- | --- |
| 做什么 | 把 `editing::EditingExtension.h` 已验证的模型（`shared_ptr` + generation handle + lease + 线程安全注册）作为**可选所有权模式**加到能力注册表层（`Capability.h`）。**新增模式，不改现有裸指针模式的语义** |
| 理由 | 规范 `R-COHESION-3` 原文即「作为**可选所有权模式**提升到能力注册表层，使每个家族退化为『一个类型名 + 一个生命周期策略选择』」 |
| 关键取舍 | **不做全仓 13 家族一次性迁移**。新增模式后，家族按 `§8.3` 触碰迁移；阶段 4 的脚本 provider 直接建在新模式上，旧家族保持原样继续工作 |
| 风险 | 中，但被"加法式"限制在 `Capability.h`/`Capability.cpp` 一处；`cap::` 有约 114 处注册点，但**现有调用点零改动** |
| 验收 | 新模式有 present/absent + 租约过期 + 撤销时序的独立测试；`module-interface` 的 `absent_behavior` 对新模式唯一为真 |

### 阶段 4 — 脚本 provider 桥（**用户可感收益的起点**）

| 项 | 内容 |
| --- | --- |
| 做什么 | 脚本注册具名 provider + 一组具名方法；C++ 侧一张通用 ops 表，每槽一个 C 函数，从注册表取出被根引的实例并 `sq_call` 对应方法；方法缺失 = `Unsupported` |
| 首批范围 | ① 游戏规则 sink（16 个孤儿中的游戏规则型）；② 脚本 link kind（`registerLinkKind` 的 `LinkOps` 由脚本方法驱动，复用 `TransformSystem` 既有分发） |
| 理由 | 16 个孤儿是**已声明、已被查询、无任何提供方**的插座：消费方调用已写好、无 C++ 实现冲突。是成本最低的落点 |
| 必须处理 | §2.5 的 snapshot 硬失败必须先修（否则脚本 provider 持有的实例会污染捕获）；F1/F2 生命周期必须先修（否则脚本 provider 无法安全退役） |
| 风险 | 中高。`Capability.h:108-115` 的 `forEach` 是**分发前快照**语义，与脚本 provider 的运行时注册/撤销/热重载冲突——这正是阶段 3 存在的原因 |
| 验收 | J-1 + J-2 达成；每个接入的扩展点有 present/absent 双探针（J-4） |

### 阶段 5 — 脚本组件身份与生命周期

| 项 | 内容 |
| --- | --- |
| 做什么 | 修 F1–F4；脚本组件注册表改为**名字 + 版本**为键（对齐 `DefinitionRegistry` 的 `(type,id)` + `SchemaVersion` + `Generation` + tombstone 模式），**不以类对象为键**（热重载会原地替换类对象）；组件句柄用 `RuntimeObjectRegistry` + `ownerEpoch`，替代裸 `_eid` |
| 理由 | 热重载是**原地替换同一 VM**（无 VM 重建路径），`_ecsTypes` 按类对象作键会让旧实例被孤立。引擎已有正确范式可抄：`Runtime::unload` 按类身份比较后才删 root 槽（`Runtime.cpp:1025-1039`）、`scanClasses()` 重检 `SQClass*` 变化的类（`:1099-1147`） |
| 风险 | 中。改的是脚本 ECS 语义，`Scene::updateScripts` 与 `packEcsFloats` 的现有用户受影响，需回归 |

### 阶段 6 — 数据互操作（宿主组件 + 序列化 + 编辑器）

| 项 | 内容 |
| --- | --- |
| 做什么 | `ScriptComponents` 通用 C++ 宿主组件（`Value` 负载 + `active` 标志，符合 `Camera2D::Data::active` 惯用法）让原生 `View` 可见；序列化走 `SnapshotEnvelope`（`schema`/`schemaVersion`/`Value payload`）+ `SnapshotMigrationChain`；编辑器接 `ISceneComponentPayloadProvider` + `IDomainOperationTargetStaging` |
| 复用而不新建 | schema/版本/字段约束/反射读写/变更通知**已存在**：`</ id=…, version=1, min=0 />` 成员属性 + `Schema::registerFromClass`（`Schema.cpp:196-284`）+ `Runtime::reflectInstance` + `ReflectedPropertyModel : IPropertyAccess` |
| 不要复用 | `definitions::RuntimeInstance<State>`——它要求编译期 C++ `State`，且 `RuntimeSnapshot` **拒绝未知字段** |
| 实现约束 | 读组件必须用 `storage->getComponentBuffer<T>()` + `size()` 守卫（`COMPONENT` 访问器是非 const 且会创建+resize）；构造 `View` 前先 `getModule<T>()==nullptr` 守卫（否则给所有实体分配列） |
| 风险 | 中。`Value` 非 trivially copyable，**永久不能上 GPU 路径**（`EcsGpu.h:25-27` 的 `static_assert`） |

## 4. 顺序与理由

```
阶段 1  门禁 G-1/G-2        ── 提供"可证伪的声明"
   │
阶段 2  围栏 G-3/G-4 + ProviderRef
   │
阶段 3  R-COHESION-3（加法式可选所有权模式）
   │                          └─ 提供"一次实现的脚本 provider 生命周期"
阶段 4  脚本 provider 桥 ────── 首个用户可感收益（J-1 / J-2）
   │      └─ 前置：修 §2.5 snapshot 硬失败 + F1/F2
阶段 5  脚本组件身份与生命周期（F1-F4 + 名字键注册表）
   │
阶段 6  数据互操作（宿主组件 + 序列化 + 编辑器）
```

**为什么门禁必须先于一切**：阶段 3 的收敛目标与阶段 4 新增的脚本 `provides`，都只能用 `provides`/`requires` 声明来证明。没有 G-2，这两步都**无法验收**。

**为什么收敛必须先于脚本 provider**：脚本 provider 需要"注册 / 撤销 / 热重载 / 线程安全"的单一语义。现在 `Capability.h` 只有裸指针 + 调用方保证生命周期，13 个家族各自为政——不收敛就要在 13 个注册表上各接一次，且每接一次独立解决热重载与撤销，等于 13 倍工作量与 13 倍出错面。

**为什么阶段 3 是加法而非大迁移**：规范原文要求的是"**可选**所有权模式"。加法式把风险限制在 `Capability.h` 一处，现有约 114 处注册点零改动，且让阶段 4 可以立刻开工，不必等 13 个家族迁移完。

**诚实提示**：阶段 1–3 交付的是治理与前置，**没有用户可见功能**。若希望更早看到用户可感收益，可把阶段 4 的一小部分（例如单个游戏规则 sink，如 `IProjectileService`）与阶段 3 并行验证——但不得跳过阶段 3，否则该 provider 的撤销/热重载语义无据可依。

## 5. 与强制规范的关系

本文各阶段适用规则如下（`AGENTS.md` 要求逐条引用）。

| 阶段 | 适用规则 | 说明 |
| --- | --- | --- |
| 1 | `R-FACE-2`、`R-FACE-3`、G-1、G-2 | 六面声明与可证伪性 |
| 2 | `R-MECH-2`、`R-MECH-3`、`R-MECH-5`、`§4.3` | 热路径声明、便捷原语退出 runtime、围栏 |
| 3 | `R-COHESION-3`、`R-COHESION-4`、`R-FACE-4` | 机制合一、策略分开、缺席语义唯一为真 |
| 4 | `R-MECH-1`（四轴推导）、`R-COHESION-6`（接口所有权跟随提问方）、`R-FACE-1`、`R-COST-1` | 新增跨模块交换必须给出四轴取值；脚本 provider 的成本形状必须声明 |
| 5 | `领域短根继承与跨域组合架构.md`（短根/组件/Link）、`重构代码质量与系统完整性规范.md`（所有权、时间与确定性） | 组件身份与生命周期 |
| 6 | `persistence` 契约（schema/version/migration/unknown_fields/restore_atomicity）、`R-COST-1`、`R-FACE-5` | 持久化五字段与成本可见性 |

**成本可见性的硬约束**：阶段 4 引入的脚本调用是**解释器代价**。规范 §5 要求"成本必须编码在 API 形状里"。因此脚本 provider 的注册 API 必须能让调用者看出它落在冷路径还是热路径；**不得**让一个脚本 sink 与一个 C++ 函数指针 sink 形状相同。

## 6. 非目标（明确不做）

| 不做 | 理由 |
| --- | --- |
| 统一 6 种载体（ECS/capability/event/Link/脚本/协议） | 规范 §8.4：「把这六种收敛成一种是**取消**而非简化」 |
| 建立统一 `IModuleInterface` 基类 | 规范 §8.4：无法表达"3 能力 + 2 可选依赖 + 4 事件 + 1 脚本类"而不变成 god-object |
| 合并 provider 策略 | `R-COHESION-4` |
| 每帧每实体的热逻辑脚本化 | 解释器代价；应原生或 GPU |
| GPU 内部（SSBO 布局 / command buffer / descriptor）脚本化 | 引擎内部布局 |
| 物理求解器内部（broadphase / BVH / constraint solver）脚本化 | 重型后端；只做注册式扩展 |
| 改 `external/ECS.hpp` 让脚本类成为原生组件 | 编译期 `typeid(T)` 不可运行时注册；且违反已知设计决策（`场景节点ECS打通界面设计.md:33`，脚本类 `extends` 原生注册类会破坏 `eve.view` 子类语义） |
| 把 `Value` 负载上 GPU | `EcsGpu.h:25-27` 的 `static_assert(is_trivially_copyable_v)` 编译期排除 |

**判据**：一段逻辑若"每帧执行一遍解释器代价可接受"且"不需要碰引擎内部布局"，它应脚本化；否则原生。

## 7. 验收与取证

**每阶段的取证要求**（沿用本仓"改动行 / 改动面"惯例）：

| 阶段 | 验收命令 | 备注 |
| --- | --- | --- |
| 1 | `make check/architecture-contracts`；`python3 -m unittest scripts.tests.test_architecture_contracts` | source-only，不 configure/不 build |
| 2 | 同上 + `python3 scripts/module_boundary_audit.py --findings` | 取证器只读、不做门禁 |
| 3 | 新模式的独立单测 + `module-interface` 条目 | 需 present/absent 双探针 |
| 4 | 新增 example + 集成测试；**只跑相关过滤，不跑全量** | 见下 |
| 5 | 脚本 ECS 回归 | `FILTER=ScriptECS` / `Scene.script` / `gpgpu.ecsPack` |
| 6 | 序列化往返 + 编辑器 provider + 撤销 | `FILTER=editor.scene.component` |

### 9.2 `hot_path` 的定性结论：审计候选多为假阳性，不得批量声明

清单 §4.8 的 `M1-HOT` 是按**文件名启发式**（`*System`/`*Pump`/`*Update`…）产生的候选，台账已标注为 CANDIDATE。逐个查看源码后：

| 候选 | 实际形态 | 是否每帧路径 |
| --- | --- | --- |
| `particles/ParticleSystem.cpp:186,204,395` | `emitterOffscreen()` 在 `for (auto* emitter : emitters)` 每帧循环内被调用（`:411` 模拟、`:517` 绘制），且每 emitter 做一次字符串键 `getInstance<Graphics>` | **是**——已声明 `hot_path` |
| `weapon/WeaponSystem.cpp:52` | `ProjectileLogic::fire()` 内 `cap::query<IProjectileService>()`，即**每次开火**一次，不是每帧每实体 | **否** |
| `map/TileSystem.cpp:126` | `fileModtime()` 内的模块查找，属**热重载轮询**，不是每帧每瓦片 | **否** |
| 其余 7 个模块（`audio`/`joystick`/`keyboard`/`touch`/`ui`/`window`/`system`） | 多为 `sdl/EventSink.cpp` 的事件回调，属"每事件"而非"每帧" | **未定性** |

**结论**：`hot_path` 的定性需要把调用链追到每帧循环，仅凭文件名不够。按 `R-MECH-5`（"热路径不得为通过声明而排除整个文件……把热代码挪进未声明文件以规避门禁，按违反处理"），**不得**按候选清单批量声明。其余 7 个模块应逐个追调用链后再定；本阶段到此为止，不猜测。

由此也确认：**G-3 目前的 3 处命中是真实违规**，而非启发式噪声。

| 错误语义 | 名字空或非实例 = `InvalidArgument`；未发布或已被取代 = `StaleHandle`；方法缺失 = `Unsupported`；返回值非数值 = `InvalidArgument`；脚本抛错 = `Failed`（含格式化后的脚本错误文本） |

**写测试时发现并修掉的两个真实缺陷**（这是"先写测试"的直接收益，值得记录）：

1. **脚本抛错会让进程段错误。** 第一版 `sq_call` 用 `raiseerror = SQTrue`，脚本层错误会进入 simplesquirrel 的默认错误处理器；在没有 `Runtime`（因而没安装引擎自己的 error hook）的 VM 里，该处理器解引用坏指针 → 访问违例（`0xC0000005`，栈帧 `CallErrorHandler → defaultRuntimeErrorFunc → strlen`）。现在所有 `sq_call` 用 `SQFalse`，失败路径读 `script::takeLastScriptError` 并格式化为诊断。新增用例 `scriptErrorsAreReportedNotRaised` 故意 `throw` 后再调用一次，证明栈已恢复且 provider 仍可用。
2. **Squirrel 取值 API 需要 out 参数**（`sq_getfloat(vm, idx, &value)`），不是返回值；另 `SquirrelOwnership.h` 的类型在 `namespace eve::script`（不是 `eve`）。两处已修正。

| 基数 | 多提供方、**按优先级顺序**全跑 | 与既有 `cap::forEach` 语义一致；脚本规则注册在默认优先级，原生提供方仍可用更低优先级先跑 |

**关停/热重载时序（三处都要成立，缺一即泄漏或悬垂）**：

1. `Vehicle::~Vehicle()` → `withdrawScriptDamageSeam()`：摘掉全部监听并 `removeCapability`，使**接缝寿命等于拥有者寿命**——否则模块已走，接缝仍在广告一个只会失败的绑定。
2. `Runtime::shutdown()` → `ScriptProviderRegistry::clearAll()`（在 `vm_.reset()` 之前）：逐个调用 unbinder。`clearAll` **先摘表再回调**，因为 unbinder 是用户代码、可能再次 publish 从而 rehash 映射表；声明过的接缝**不**随 `clearAll` 消失（它是组合期声明，不是发布态）。
3. `publishForCapability` 的 binder 失败 → 原子回滚（`unload` 该代际，从而也跑 unbinder），调用方**永远看不到"已发布但不服务任何东西"的 provider**。

**§2.5 快照硬失败（阶段 4 前置项）在本片的边界**：provider 实例只由 `script::OwnedSquirrelObject` 做 **VM 引用计数**根引用，不占根表槽位；`Snapshot::resolveRoots` 只枚举根表槽位且只收 `int/float/bool/string/table/array`（`Snapshot.cpp:365-375`），因此 provider 本身**不会**污染捕获。残留项不变：脚本若把 provider 塞进快照会枚举到的全局表，捕获仍会整体中止——那是 §2.5 / 阶段 6 的既有条目，本片未触及也未加重。

**本片测试揭出的第三个真实缺陷（比 §9.8 记录的范围更大，必须记下来）**：

§9.8 记的是"`sq_call` 用 `raiseerror=SQTrue` 会进 simplesquirrel 的默认错误处理器"。**实测更严重：`raiseerror=SQFalse` 并不能覆盖所有情况。**

`SQVM::Execute` 的 `ET_CALL` 分支（`sqvm.cpp:691-697`）在 `StartCall` 失败时**无视 `raiseerror`** 直接调用错误处理器：

```c
if(!StartCall(...)) {
    //call the handler if there are no calls in the stack, if not relies on the previous node
    if(ci == NULL) CallErrorHandler(_lasterror);
    return false;
}
```

而每个 `ssq::VM` 的构造函数都会把 simplesquirrel 的 `defaultRuntimeErrorFunc` 装成 Squirrel 错误处理器（`simplesquirrel/source/vm.cpp:24,87`）。该函数在 `sq_gettop(vm) >= 1` 时读**栈索引 2**，栈形状不符时拿到坏指针 → `strlen` 访问违例（本片实测栈：`sq_call → Execute:695 → CallErrorHandler:1169 → CallNative → defaultRuntimeErrorFunc:213 → RuntimeException → strlen`）。

即：**参数个数写错**（`StartCall` 的 `paramssize != nargs`）这条路径，用 `raiseerror=SQFalse` 也躲不开；只有 VM 上装了安全处理器才躲得开。原实现只有 `Runtime` 装（`Runtime::installErrorHandler`），裸 `ssq::VM` 的嵌入方（以及所有 `ScriptTest` 夹具）没有。

处理方式（不是绕开，而是修掉）：

| 项 | 内容 |
| --- | --- |
| 新增导出 | `script::installScriptErrorHook(HSQUIRRELVM)`（`ScriptError.h`）。把 `Runtime` 里原本私有的四步（`sq_enabledebuginfo` / `sq_notifyallexceptions` / `sq_newclosure(scriptErrorHook)` / `sq_seterrorhandler`）提成唯一实现，`Runtime::installErrorHandler()` 改为调用它 |
| 理由 | `Module.h:98-99` 已经声明支持"直接持有 `ssq::VM` 的嵌入方"；既然支持，就必须给他们安全处理器，否则一次参数写错就是崩溃而不是诊断 |
| 测试侧 | `test/ScriptTest.h` 的 `expose()` 现在先装 hook 再 `ModuleManager::expose`。此前测试跑的是"引擎从不使用的 VM 配置" |
| 回归用例 | `ScriptProvider.callSetupErrorsStayReported`：故意用错参数个数调用 provider，断言拿到 `Failed` 且报文含 `parameters`，并且 provider 之后仍可用（栈已复位） |
| 修复后语义 | 参数个数错误 = `Failed` + `"wrong number of parameters (N passed, M required)"`；脚本层 `throw` = `Failed` + 脚本错误文本与位置。两者都不再是崩溃 |

**这条缺陷不止影响脚本 provider**：任何"原生代码调用用户脚本"的路径（`registerLinkKind` 的 `LinkOps`、`Runtime::createInstance` 之后的调用、未来阶段 5/6 的脚本组件回调）都在同一个 `Execute:695` 上。把它记在此处，阶段 5/6 不必重新发现。

**F3 的取舍（必须写明，因为它动的是性能设计）**：`viewCacheStableAndInvalidated` 的注释原文是"same cached array identity (zero allocation per frame in System.entities())"。改成返回副本后，**`System.entities()` 每帧不再零分配**——代价是每次调用一次数组拷贝（`resize` + 逐元素）。收益是缓存**不再可被外部篡改**：把缓存本体交出去时，"视图"与"缓存"是同一个对象，任何调用方的一次 `pop` 就改变了下一个调用方看到的内容。缓存仍承担贵的那一步（遍历全部注册类型 + 子类过滤），所以复杂度从 O(全部类型 × 全部实例) 降为 O(视图长度)，而不是退化成每次全量收集。这条取舍已同步到 **`docs/dev/2026-08-30-ecs-gpu-efficiency.md`** 的 System 契约（"稳定顺序快照"一条补上"每次返回新数组"）。

**F2 的取舍**：销毁后字段槽位是 `null`，不是"删除槽位"。删除会让 `e.pos` 回落到**类默认值**——而脚本 ECS 的类默认值正是**组件类对象本身**（`class Node extends eve.Entity { pos = Pos }`），于是 `e.pos.x = 1` 会写进类、影响之后所有实例：比"静默 no-op"更糟。置 `null` 使销毁后的访问**显式失败**（脚本错误会被引擎 error hook 记录），符合"不要静默 no-op"。

#### 9.14.1 `CHECK` 是警告级：它不会让用例失败

本仓 `zeroerr`（`external/zeroerr/include/zeroerr/assert.h:111-142`）在 `ZEROERR_NO_ASSERT` 下把断言宏展开为空；而测试目标反掉了这个宏（`test/CMakeLists.txt:199-205` 显式 `/UZEROERR_NO_ASSERT`），所以断言宏是活的——**但 `CHECK` 与 `REQUIRE` 的级别不同**：

| 宏 | 结果 | 退出码 |
| --- | --- | --- |
| `CHECK(false)` | 打印 `WARN Assertion Failed`，汇总 `PASSED 0 / WARNING 1 / FAILED 0` | **0（CTest 报 Passed）** |
| `REQUIRE(false)` | 打印 `ERROR Assertion Failed`，汇总 `FAILED 1` | 1（CTest 报 Failed） |

实测（`test/ScriptECS.cpp` 临时加入两个控制用例，随后删除）：

```
TEST CASE [ScriptECS.cpp:519] zz.control.literalFalseAssertion  ⚠️   WARN Assertion Failed: false
TEST CASE: 0 PASSED | 1 WARNING | 0 FAILED       退出码 0
TEST CASE [ScriptECS.cpp:521] zz.control.literalFalseRequire    ❌   ERROR Assertion Failed: false
TEST CASE: 0 PASSED | 0 WARNING | 1 FAILED       退出码 1
```

**后果（必须写进所有后续取证）**：

1. 本仓大量脚本测试写成 `CHECK(vm.callFunc(vm.findFunc("testX"), vm).toBool())`——**这类断言永远不可能失败**：脚本函数返回 `false` 也只是警告。实测把 `testComponentStorageIsSingle` 的**函数体换成 `return false` 后用例依然 Passed**。
2. 因此本轮与上一轮我报告的"`ScriptECS` 14/14、15/15、16/16 通过"**只等于"没有崩溃/没有超时"**，不等于断言成立。§9.13 的 F2/F3 取证同样如此（当时只改了断言内容，没改级别）。
3. 真正的失败信号只有三种：`REQUIRE`/`ASSERT` 失败、崩溃（`***Exception`）、超时。`bundle/time_subscription_consumers.cpp` 的 Failed 属于这一类。
4. **本片已把受影响的两个用例改成 `REQUIRE`**（`ScriptECS.viewCacheStableAndInvalidated`、`ScriptECS.destroyClearsComponentState`），并做了反向验证（见 9.14.3）。建议后续单独一片把全仓脚本测试的 `CHECK(vm.callFunc(...))` 扫成 `REQUIRE`——这是一个**独立于本方案**的测试有效性问题，量级是全仓性的。

#### 9.14.2 Squirrel 拒绝给 class 实例新建槽位：F4 的真相远比台账严重

`SQVM::NewSlot`（`sqvm.cpp`）对 `OT_INSTANCE` 只有两条路：实例有**带 `MT_NEWSLOT` 元方法的 delegate** → 调用之；否则 `Raise_Error("class instances do not support the new slot operator")`。

而**动态键赋值走的就是 new-slot 操作码**——实测两次：

* `create()` 里若写 `e[name] <- c`：`Node.create()` 立刻抛 `class instances do not support the new slot operator`。
* `destroy()` 里写 `this[name] = null`（`=`，但键是动态的）：同样抛。

于是 F4 的台账描述（"组件双写 `_comps[name]` 与 `e[name]`，两者可能读到不同对象"）**低估了现状**：`try { e[name] = c } catch (ex) {}` **每一次都失败**，字段槽位从未写入过组件实例。实际语义是：

| 路径 | 读到的对象 |
| --- | --- |
| `e.getComponent(Pos)` / `hasComponent` | `_comps[name]` 里的**每实体实例**（正确） |
| `e.pos`（脚本日常写法 `e.pos.x = 1`） | 类的**默认成员值**——对 `pos = Pos` 而言是组件**类对象**本身 |
| `packScriptEntityFloats`（GPU 打包，读字段槽位） | 同上，即组件类对象 |

即 `e.pos.x = 1` 写的是**类级字段**（被所有实例共享），而 `getComponent(Pos).x` 读的是实例字段——两者不只是可能分叉，**字段那条路根本没有接上**。这也解释了为什么此前 F4 的合成实验"无法复现分叉"：我按 `_comps` 打补丁后发现测试仍过，真正原因是断言级别（9.14.1），而不是补丁机制。

**F4 因此不是一行改动**，需要先定方案，两个候选：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A. 给 `eve.Entity` 的实例装带 `MT_NEWSLOT` 的 delegate | `MT_NEWSLOT` 把新槽位路由到 `_comps`；`e.pos = x` 于是写入唯一存储 | 需要给每个实例 `setdelegate`，且 `packScriptEntityFloats` 仍按"读字段槽位"实现，得改成读 `_comps`（否则读不到） |
| B. 让 `_comps` 成为唯一存储 | 保持 `create()` 现状（只写 `_comps`），把 `getComponent` 留在 `_comps`，并**改 `EcsScriptPack` 从 `_comps` 取组件**；脚本侧 `e.pos` 语义改为"经 delegate 转发"或明确废弃 | 改一处 C++（打包）+ 脚本 API 语义决定；`e.pos.x` 写法需保留就必须做 A 的 delegate 部分 |

两者都要碰 GPU 打包侧，且都改变用户可见写法，**属于阶段 6 的"组件数据权威所有者"（§10 第 3 条）同一个决定**。建议把 F4 与 §10 第 3 条合并成一次决策后再动手。本片**不做 F4**。

#### 9.15.1 本片最重要的发现：C++ 默认实参对脚本绑定不可见

| 接口 | C++ 签名 | 脚本写法 | 结果 |
| --- | --- | --- | --- |

### 9.16 阶段 5 第四片：把"默认实参对脚本不可见"变成可证伪的约定

§10 第 7 条要求先决定"脚本面能不能用带默认实参的方法"。本片先把它**量出来**，再决定。

#### 9.16.1 实测规模（决定了方案只能是"约定 + 冻结"，不能是"逐处修"）

| 指标 | 数值 |
| --- | --- |
| `src/**` 里 `addFunc("x", &Class::method)` 形式的脚本绑定 | **7077** |
| `src/**/*.h` 里带默认实参的成员声明 | **729** |
| 绑定目标声明**确实**带默认实参的（按"最内层类名 + 方法名"精确配对，排除同名误报） | **241**，跨约 30 个模块（ui 48、animation 45、graphics 27、physics 20、building 10、ik 10…） |

也就是说这不是三个 API 的疏忽，而是**整个脚本面的一贯形态**：C++ 侧习惯性给尾参默认值，脚本侧因此必须每次都传满。

#### 9.16.2 为什么不做"自动短调用"

默认值**只存在于 C++ 声明里**，运行时拿不到。可行的做法只有两条，都不划算：

| 做法 | 为什么不选 |
| --- | --- |
| 绑定层按 `sq_gettop` 派发、给缺省位补值 | 补什么值只有 C++ 知道。补 `null` 会让 `sq_getfloat`/`sq_getstring` 直接类型报错；要正确补值就得**逐个 API 手写变参编组**（241 处） |
| 支持"少传即用声明默认值" | 需要反射 C++ 默认实参，本仓没有这条通路，为它引入反射的成本远高于收益 |

顺带确认了 Squirrel 的语义（`sqvm.cpp:1204-1209`）：native closure 的 `_nparamscheck > 0` 是**精确**个数，`< 0` 是**最少**个数——后者允许多传，**不允许少传**，所以它也解决不了这个问题。

#### 9.16.3 决定：绑定精确 + 短形式归脚本封装层

写进 `docs/dev/模块接口契约与机制选型规范.md`（§3.1 六面里的 script bindings 面，新增 §3.4 与 **R-FACE-6**）：

1. **绑定即完整签名**：`addFunc` 发布完整形参个数，脚本调用方传满每一个实参；
2. **短形式属于脚本封装层**，不属于绑定层——需要 `addNode("id")` 就在脚本面（如场景的 NodeRef 封装）提供包装，而不是给绑定加魔法；
3. **想省掉实参就改 C++ 声明**：对 C++ 调用方也不再可选的参数，把默认实参删掉，让两侧要求一致且编译期可见；
4. **冻结而非禁止存量**：存量 241 处登记为依赖该约定，新增必须显式决定。

#### 9.16.4 机械校验（本片的可证伪部分）

### 9.17 阶段 5 第五片：`SceneEntity` 节点桥的读写路径不一致（定性 §9.15.3 的 6 个 Scene 用例）

**机制**（`src/modules/scene/Scene.cpp`）：写路径与读路径都经过"节点的 `objectId` → `SceneObject::scriptBindings()->instances`"，但两者对同一个节点的观察不一致：

### 9.19 阶段 5 第七片：§9.17 的定性被推翻一半——真正根因是三个独立缺陷

#### 9.19.1 已修：`SceneNode::objectId` 的哨兵值与真实实体 id 0 撞车

ECS 的 `RegistryComponentBuffer::add()` 返回 `container.size()`（`external/ECS.hpp:438-443`），所以**进程内第一个** `SceneObject` 的 id 就是 **0**；而 `SceneNode::objectId` 当时用 `0` 表示"没有 SceneObject"。写路径把 0 存进去，读路径 `if (id == 0) return nullptr` 一律当"没挂"。

#### 9.19.2 已修：`Scene::callCallback` 少传一个参数（真正的首因）

`sq_call` 的参数个数**包含 receiver 槽**（对照同文件的 `callMethod`：压 `this`+1 个实参后调 `sq_call(vm_, 2, ...)`）。`callCallback` 压了 `fn, inst, index` 却按 `params = 2` 调用，等价于 **`this = inst`、唯一实参 = `index`**。于是脚本回调里的 `e` 收到的是**整数下标**而不是实体：

| 脚本回调 | 现象 |
| --- | --- |
| `function(e, index)`（`detachEntityAt`） | 参数个数 3≠2 → `sq_throwerror`，静默失败 → `idx` 恒为 -1 → 实体根本没 detach（`entityViewCacheAfterDetach` 首因） |
| `function(e)`（`getEntityAt`/`entitiesOfAt`） | 调用"成功"，但 `e` 是整数 → `e instanceof cls` 恒假 → `hasEntity`/`getEntity` 恒空、`entitiesOf` 返回下标（`entityLifecycle` 首因） |

- 修法：`callCallback` 改为压 `fn, inst(this), inst(实体), index` 并按 `sq_call(vm_, 3, ...)` 调用；两个只声明了一个形参的回调补成 `function(e, index)`。

- 为什么它藏了这么久：`raiseerror=SQTrue` 只是把错误留在 VM 里，`callCallback` 又丢弃返回值；而 6 个用例当时都是 `CHECK`（警告级），所以"实体查不到"从来没让任何用例变红。**约定**：给脚本的回调调用必须能被观察到失败，不能只 `return false`（登记为待办，见 §10.8）。

#### 9.19.3 已修：`updateScripts(dt)` 之后世界矩阵是陈旧的

| 探针 | 结果 |
| --- | --- |
| `n[k] = 5`（动态键 + `=`） | **成功**（`dyn-set=5`） |
| `n[k] <- 5`（动态键 + `<-`） | `class instances do not support the new slot operator` |
| `n.level = 5`（静态键） | 成功 |
| `n.rawset(k, 5)` | 成功（`rawset` 是实例 delegate 方法） |
| `getclass(old)`（全局调用形式） | `the index 'getclass' does not exist` |
| `old.getclass()`（**方法**形式） | 成功，class 对象**可枚举**（`n=2`） |
| `foreach (k, v in old)`（枚举**实例**） | `_nexti failed` |

1. **`n[k] <- v` 对动态键永远抛错**，而 `catch` 把每一次都吞掉 → `migrate_instance` **静默地什么都没拷**，重载后 class 实例状态全部退回新类默认值。这正是注释"Not assignable on the new class; keep the default"想处理的**另一种**情况：`n[k] = v` 才是对的——对新类**声明过**的成员赋值成功，对没声明的成员抛错并被 `catch` 接住（这才是 catch 的本意）。
2. **实例不可 `foreach`**（`_nexti failed`），所以"拷贝实例的可枚举字段"这句注释在这台 VM 上不成立；`getclass()` 是**实例方法**（没有同名全局函数），class 对象才可枚举。

修法（`src/scripts/load.nut`）：按 `typeof` 分支——table 走 `foreach (k, v in old)` + `n[k] = v`；instance 走 `foreach (k, v in old.getclass())`、跳过 `function` 槽（方法保持新类定义）+ `n[k] = old[k]`。测试镜像（`test/reload_script.cpp` 的 `migrate_inst`）同步改成同一机制，并把 3 个用例从 `CHECK` 改回 `REQUIRE`。

### 9.22 阶段 5 第十片：`eve.SceneEntity` 的惰性解析顺序（§9.18.2 修完）+ `sq_call` 全仓核对（§10.11）

#### 9.22.1 已修：惰性解析在"放弃"之前从不注入脚本 ECS 基类

链路：`eve` 表有一个 delegate getter（`Module.cpp eveTableGet`），未命中的名字走 `bindOnDemand`：

1. 名字是脚本 ECS 名（`Component`/`Entity`/`System`/`view`/…）→ `ensureScriptEcsInTable` → 注入脚本 ECS；
2. 否则 `bindNamedModule(name)`（按模块名找 exposer）；
3. 仍没有且是 PascalCase → `bindUntilKeyExists`：按名字排序把**所有尚未 expose 的模块**依次 expose，每步后检查名字是否出现。

而 `eve.SceneEntity` 不属于任何模块名——它由 Scene 模块在**静态初始化**时注册的 post-ECS 钩子创建。`flushPostEcsHooks` 有一条前置条件：`if (!ecsScriptInjected()) return;`（钩子必须建立在 `eve.Entity`/`eve.Component` 之上）。于是"第一个 ECS 名字恰好是 `SceneEntity`"时：扫描把每个模块都 expose 了一遍，`flushPostEcsHooks` 每次都因 `ecsScriptInjected() == false` 直接返回，**扫描结束时脚本 ECS 从未被注入**，最后抛 `the index 'SceneEntity' does not exist`。现有用例之所以没踩到，是因为 `testAttachRejectsPlainEntity` 里先写了一句 `class Marker extends eve.Component` 来"垫"一次 ECS 访问（本片把那句注释改成了历史说明）。

修法（`Module.cpp bindUntilKeyExists` 末尾）：扫描完仍没有该名字时，调一次 `ensureScriptEcsInTable(table)`。此时**所有模块都已 expose 过**，所以 `ensureScriptEcsInTable` 的优先级规则（它会把模块提供的 `eve.System` 删掉、换成规范的脚本 `System`）正好在正确的顺序上生效；而钩子会在 `exposeECS` 末尾被 flush，`eve.SceneEntity` 随之出现。

> 为什么不直接在 `flushPostEcsHooks` 里注入基类：那会让**任何**模块的首次惰性绑定都提前注入脚本 ECS，可能在宿主信息模块绑定 `System` **之前**就把规范 `System` 建好，反而制造 §9.22.1 注释里描述的那个命名冲突。放在"扫描全部模块之后"是唯一既修复顺序、又不改变优先级的位置。

### 9.23 阶段 5 第十一片：`glm::eulerAngles` 逐处清出引擎（§10.10 决策落地）

§9.20.3 只统一了 SceneNode 自身的权威转换路径，并登记了"仓里两种欧拉约定并存"。本片把**剩余 7 处**全部改完——`src` 里现在除了注释再无 `glm::eulerAngles`。

#### 9.23.1 根因重述（为什么单轴能过、多轴必错）

引擎组合变换的顺序是 `T · Ry(yaw) · Rx(pitch) · Rz(roll) · S`：`TransformSystem::localMatrix()`、`RenderSystem3D::modelFromTransform()`、`physics/SceneLinks.cpp pushBody3D()` 三处**逐字一致**。而 `glm::eulerAngles()` 返回的是**另一族**欧拉角（`gtc/quaternion.inl:10-38`，`pitch/yaw/roll` 用的是另一种组合）。逆错族 ⇒ 多轴姿态被改写；单轴时两族数值恰好相同 ⇒ 一直没暴露。

#### 9.23.2 新增唯一权威：`src/engine/common/TransformEuler.h`

```cpp
template <typename T> void eulerYxzFromMatrix(const glm::mat<4,4,T,defaultp>&, T& yaw, T& pitch, T& roll);
template <typename T> void eulerYxzFromQuat  (const glm::qua<T,defaultp>&,    T& yaw, T& pitch, T& roll);
```

两点设计约束写在头文件注释里，且都是这次踩出来的：

1. **模板化**：编辑器那条链是双精度（`glm::dmat4`/`glm::dquat` → `double` 字段），只给 float 版本会逼调用方降精度。

#### 9.23.3 七处调用点（都朝"矩阵/四元数 → 引擎 yaw/pitch/roll"这一个方向）

### 9.26 阶段 5 第十四片：`Profiler.begin` 的 binding 形状与名字生命周期

#### 9.26.1 两个叠加的缺陷

登记写的是"binding 要实例、脚本给字符串"。修掉第一层后露出了第二层，两层都是真实缺陷：

| 层 | 现象 | 原因 |
| --- | --- | --- |
| ① 参数类型 | `bad cast expected: INSTANCE got: STRING` | `Profiler::begin(const char*)` 被**直接** `addFunc` 绑定；绑定层把 `const char*` 当作不透明指针类型，于是要求传实例，字符串无法转换 |
| ② 名字生命周期 | ①修好后脚本仍返回 `false`，插桩定位到 `test/profiler.nut:18`（`if (!found)`，即捕获结果里没有 `scriptScope`） | `ZoneRecord::name` 是 `const char*`，注释写明 "*pointer is static storage, never freed*"；而 `frameMark()` 才真正读取它（聚合在帧边界做，`Profile.cpp:132+`）。把临时 `std::string` 的 `c_str()` 传进去 → 悬垂指针 → 采样名字对不上 |

#### 9.26.2 修法

绑定层改成 `[](Profiler* self, const std::string& name)`，并把名字**驻留**在模块自己的名字池里：

```cpp
const char* Profiler::internScopeName(const std::string& name) {
    const auto inserted = scopeNames_.insert(name.empty() ? std::string("scope") : name);
    return inserted.first->c_str();   // unordered_set 节点地址在 rehash 后仍稳定
}
```

即"由调用方满足核心的静态存储契约"，而不是去改采集器。选择这个位置的理由：`Profile.cpp` 是每帧热路径，若在核心里对每个 zone 做一次字符串键查找（或让 `ZoneRecord::name` 变成 `std::string` 从而每 zone 一次分配），都要动热路径的成本模型；模块侧的名字池只在**脚本面**（主线程、名字集合天然有限）承担这点开销。名字池的线程/重入约定写在头文件注释里。

#### 9.26.3 顺带发现：同一契约在 C++ 路径上也**被违反**（未修，登记 §10.16）

排查时发现 `RenderTrace.h` 的 `RenderPassScope` **复制**调用方的名字到成员 `name_`，再把 `name_.c_str()` 交给采集器：

```cpp
explicit RenderPassScope(const char* name) : name_(name ? name : "") { rtPassBegin(name_.c_str()); }
```

而两个调用点传的**本来就是字符串字面量**（`"RenderSystem2D"` / `"RenderSystem3D"`，静态存储）。也就是说这份拷贝不是"保护"，而是**把生命周期从"静态"缩短到"作用域结束"**：

| 证据 | 位置 |
| --- | --- |
| 2D pass 作用域在 `drawItems()` 栈上，函数返回即析构 | `RenderSystem.cpp:348`（`drawItems` 由 `render` 在 487 行调用） |
| `frameMark()`（真正读名字的地方）在**之后**才发生 | `RenderSystem.cpp:488` 的 `rtFrameEnd()` |
| 3D 同理：`RenderSystem3D::render` 的作用域先析构，`rtFrameEnd()` 后发生 | `RenderSystem3D.cpp:636`、`Graphics.cpp:198-199` |

所以内置 pass 的 zone 名字在 `frameMark()` 时指向已析构的 `std::string`（短名字走 SSO，字节就在栈上），读到什么取决于栈是否被覆盖——非确定性，因此长期无人发现。**本片不动它**：两条候选修法（①核心里在 `zoneBegin` 驻留名字，让契约对所有调用方成立；②`RenderPassScope` 直接转发调用方的字面量并把这个要求写进契约）都要改变采集器/热路径的成本模型或契约措辞，值得你定调后再改。

### 9.27 阶段 5 第十五片：§9.15.3 最后一处（两处都是**测试自己的错**）→ **清单清零**

`schema.module.reflectFromClass` 登记的原因是"反射不匹配"。逐个证伪后确认：**引擎侧没有缺陷**，是两个叠加的测试缺陷。这也是"把断言变成真的"最后一次收获——它们此前被 `CHECK` 掩护着，看不出问题在哪一层。

#### 9.27.1 缺陷一：脚本假设字段枚举顺序 == 声明顺序

先打印真实反射结果（临时探针）：

```
0=attack:integer  1=health:integer  2=name:string  3=id:string  4=kind:string  5=cost:integer
```

类型全部推断正确（`cost` 就是 `integer`），**错的只是下标**：`getFieldType(id, 3)` 拿到的是 `id:string` 而不是 `cost`。原因在 `Schema::registerFromClass`：它用 `sq_next` 遍历**类对象**（`Schema.cpp:241`），而 Squirrel 的 `SQClass` 把成员存成 `SQTable *_members`（`sqclass.h:74`）——表的遍历顺序，不是声明顺序。（声明顺序其实存在 `_defaultvalues` 这个按 slot 索引的 vector 里，但 `SQClass::Get` 会把索引解析成值，没有导出槽位号的 API，取它要伸进 Squirrel 内部。）

而 API 文档只说 `getFieldName` 是"stable"、`getSchemaId` 的索引是"deterministic"，**没有承诺声明顺序**——所以"错"的是测试的假设。修法：脚本改用 `getFieldName` 按名字解析下标（顺带断言 6 个字段都真的被反射出来了，比原来的下标断言更强）。**顺序本身该不该改成声明顺序，登记为 §10.17**（有设计文档要求"保存输出字段顺序稳定，便于 Git diff"，见 §9.27.3）。

#### 9.27.2 缺陷二：把 Result 投影表当 bool 用

改完下标后失败点前移到校验段：

```squirrel
local bad = @"{""id"":""x"",""name"":""y"",""kind"":""air"",""cost"":25}";
if (s.validateJson("card.definition", bad)) return "invalid";   // ← 永远返回 "invalid"
```

探针把每一类约束跑了一遍，打印**返回值类型 + 错误个数**：

```
type=(table)/3  enum=(table)/3  max=(table)/3  addl=(table)/3  wrongtype=(table)/2
```

即：校验**完全正常**（那个坏载荷报了 3 条错：enum、maximum 等），而 `validateJson` 返回的是**投影后的 Result 表** `{ok, code, status, diagnostics, …}`——不是 bool（Result 规范本就禁止把 Result 塌缩成 bool）。Squirrel 里**表恒为真**，所以 `if (s.validateJson(bad))` 永远成立 → 用例永远返回 `"invalid"`。原写法里"合法载荷"那条之所以看起来通过，也只是同一个错觉：`!table` 恒为假。

修法：读 `.ok`；末尾那条"第一个错误码必须是 enum"也改成**按类断言**（遍历错误码，要求同时出现 `enum` 与 `maximum`），因为错误顺序同样取决于字段遍历顺序。两处都比原写法更强。

#### 9.27.3 顺带记录的契约问题（登记 §10.17）

`docs/dev/游戏内容编辑器组件设计分析.md:91` 要求"保存输出字段顺序稳定，便于 Git diff 和合并"。当前顺序是 Squirrel 成员表的哈希/插入顺序：同一份 schema 内可复现，但**增删字段会牵动无关字段的相对次序**，对 diff 不友好，也不是作者书写顺序。要不要（以及如何）改成声明顺序，已作为决策项登记，并注明两种实现路径的代价（伸进 `_defaultvalues`/`_members` 取槽位号 vs. 保持现状只把"顺序未定义"写进文档）。

#### 9.27.4 取证（窄范围）

| --- | --- |
| 字段顺序探针 | `0=attack 1=health 2=name 3=id 4=kind 5=cost`（类型全对）；证明是顺序而非类型问题 |
| 约束探针 | 五类违规全部被拒绝（3/3/3/3/2 条错误）；证明校验无缺陷 |
