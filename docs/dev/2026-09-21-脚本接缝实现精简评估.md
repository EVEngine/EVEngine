## 3. 与上游设施的关系

- **(a) `editing/SceneComponentPayload.h` 的 `SceneComponentPropertyBindings`（`已核`：确实实现了 `ISceneComponentPayloadProvider`，已有 `components`/`payloadOperationTarget`/`validateComponent`/`translate`）→ 建议复用。** 我们重写了其中约 100 行。两个真实阻碍：① `translate()` 要求一次选择里的所有绑定共用同一个 `properties`/`operations` 指针，而我们目前直接拒绝多选——要么支持多选，要么在绑定层就拒绝；② 脚本组件消失/热重载时，我们现在靠 `resolve()` 里现查，改成绑定表就需要显式的 `unbind()` 刷新路径。净效果约 −100 行 + 40 行胶水 + 一次多选契约变更。
- **(b) `common/CapabilityOwned.h` 的 `OwnedProviderRegistry` → 不建议复用。** 三条硬理由：它要 `shared_ptr<I>`（我们持有的是**根引用**的脚本对象，必须在 VM 线程、VM 销毁前释放，`shared_ptr` 的删除器保证不了）；它在重复 id 上返回 `Conflict`（我们需要**顶替**并执行被顶替代际的 unbinder）；`provide` 会顺手 `provideRaw`（我们不希望脚本对象出现在 `cap::query<I>` 里）。可共享的只有 handle/代际那约 15 行身份记账。
- **(c) `SquirrelBinding.h` 的 `callFunctionResult`（`已核`：`:248` 硬编码 `raiseerror = SQTrue`）→ 可复用，但要加一个 `bool raiseError = true` 参数**（我们需要 `SQFalse` 才能把抛异常的脚本方法变成 `Failed` 结果而不是 VM 抛出）。可省约 25 行手写的压栈/推导/恢复。所有权侧已经在用上游 `script::OwnedSquirrelObject`，没有重复。`projectResult` 是反向（C++→脚本），不重叠。

## 4. 建议顺序

1. **低风险先做**（不动语义，约 180 行）：D4、D5、D8、D3，以及第 2 节里的 `erase_if` / 分组 / `to_vector`。
2. **再做 D1（`ScriptSeamHost`）**：一次消掉约 200 行，7 个接缝同时受益；风险中等，需要逐接缝确认 `provide` vs `addListener` 与 animation 的按名索引。
3. D2 / D6 / D7 随手带上。
4. (a)(c) 是两个独立增量，各自需要动上游头文件与一个契约（多选；raise 语义）。
