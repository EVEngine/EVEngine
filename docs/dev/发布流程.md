# 发布流程

`main` 是最新正式版（GitHub 默认分支，克隆即可编译）。日常开发在 `dev`。一次发布用隔离分支 `vMAJOR.MINOR.PATCH`。设计见 [release-branch-model spec](superpowers/specs/2026-08-19-release-branch-model-design.md)。

## 一次性仓库设置

由维护者在 GitHub 上执行，脚本不会改默认分支或保护规则：

```sh
git fetch origin
git branch dev origin/main && git push -u origin dev
```

默认分支保持 `main`。

### 保护 `main`（建议）

Rulesets → New ruleset，目标 `main`：

1. **Require a pull request before merging**（不必要求 review，除非你想多点一次 Approve）。
2. **Require status checks to pass**：检查名填 `main-gate`。
3. **Block force pushes** / **Restrict deletions**（现有 NoForcePushMain 可保留）。
4. **不要**加 Bypass（不用 GitHub App，也不用管理员 PAT）。

`main-gate` 只放行两类 PR：文档白名单，或 `promote/vX.X.X`（发布脚本开的正式版 PR）。从 `dev` 把引擎代码合进 `main` 会被挡住。

`dev` 可以要求走 PR；不要给它开「必须 status check 才能合」，否则 `GITHUB_TOKEN`
开出的 rebase / sync-docs PR 可能一直转圈。`sync-docs` 也只开 PR，不直推 `dev`。

## 发一次正式版

1. 保证要发布的提交已在 `dev`。
2. 在 GitHub 上对当时的 `dev` HEAD 创建一个 **Pre-release**，tag 形如 `v0.1.0`（必须是 `vMAJOR.MINOR.PATCH`）。此时树上仍是 `0.1.0-dev`。
3. `Release` workflow 会：
   - `scripts/release.py start`：建 `v0.1.0`、去掉 `-dev`、把 tag 挪到正式版 commit；
   - 跑严测（现有 Debug CI + 桌面 Release 构建 / `make test/<plat>` + 移动端 Release 构建）；
   - 打五平台 SDK 并挂到该 Release；
   - `scripts/release.py finish`：升正式版；在 `v0.1.0` 上写回 `0.1.0-dev`；**开两个 PR，不直推 `main` / `dev`**：
     - `promote/v0.1.0` → `main`（正式版 commit，不含 `-dev`）
     - `rebase/v0.1.0` → `dev`（rebase 成功或冲突说明）
4. 人点 Merge：先合 `promote/v0.1.0` → `main`，再合 `rebase/v0.1.0` → `dev`。

rebase 冲突时 PR 正文有本地续做命令。把修好的结果推到 `rebase/v0.1.0`，不要 force-push `dev`。

下一正式号以**新的** Pre-release tag 为准（允许比树上数字高，禁止降级）。`finish` 回写的永远是刚发布的同一组数字加 `-dev`。

## 版本一致性

除 `CMakeLists.txt` 外，还有几处对外暴露版本号，发布时必须同步为同一组数字，
否则 SDK / Android 模板 / MCP / 示例会各说各的：

- `platform/android/apk/app/build.gradle.kts`（`versionName`；`versionCode` 由
  `major*10000 + minor*100 + patch` 推导，当前 0.1.0 → 100）
- `src/engine/devtools/McpServer.cpp`（MCP `serverInfo.version`）
- `examples/basic/root.nut`、`platform/ios/game-shell/root.nut`、
  `platform/android/game-shell/root.nut`（`EVEngine vX.Y.Z` 打印）
- `docs/CMakeLists.txt`（Doxygen 版本号）

`release.py start` 会把以上 **required** 触点随正式版一起改写并提交进 `vX.X.X`；
日常 CI 的 layering 作业跑 `python3 scripts/release.py check-versions` 兜底，任一失配
都会失败。独立发布的工具（`tools/*/package.json`、Python 包 `__version__`）只报
WARN，不自动改写。

## SDK 打包

- **许可证**：SDK 的 `share/eve/licenses/` 包含引擎的 `LICENSE*` 与 vendored
  第三方源树（`external/*`、`third-party/`）里的 `LICENSE*`/`COPYING*`/`NOTICE*`
  （best-effort，保留相对路径便于溯源）。
- **模块头文件**：按 `cmake/module_manifest.cmake` 的 `EVE_ENABLED_MODULES` 自动导出
  当前构建启用的模块，SDK API 面与目标运行时一致，不再手维护白名单。
- **可用性测试**（`test-sdk.sh`，桌面三端硬门槛）：SDK 布局 + 精确版本断言 +
  `eve zip`/`eve package` + **C++ 插件编译**（`find_package(EVEngine)` +
  `add_eve_plugin()`）；Android 额外跑模板 APK 组装冒烟
  （`gradlew :app:assembleDebug`）。
- **完整性**：publish 前逐个校验 zip 的 `share/eve/VERSION` == tag，并生成
  `SHA256SUMS` 随 SDK 一起上传（可选开启 Artifact Attestations）。

## 消费侧全链路验证（release 时强制）

SDK 上传到 Release 之后，`sdk-release.yml` 继续以“用户机器上什么都没有”的
身份跑完整消费链路（`consumer-test.sh`），只用真实 release 产物：

- **consumer-win32 / consumer-linux / consumer-macosx**（硬门槛）：下载对应
  `eve-sdk-<host>-<tag>.zip` → `eve -v` 版本断言 → `eve get android`
  （下载官方 android SDK + 工具链，SHA256 校验）→ `eve build android`
  （断言 APK 含 `lib/arm64-v8a/libmain.so`、`assets/game/*`，且 launcher 是
  `EVEngineActivity`）→ `eve package <host>` 出包 → **真实启动打包游戏**，
  grep `EVE_CI_GAME_OK` 启动标记。
- **交叉编译矩阵**（硬门槛，按承诺的组合执行，不能交叉的平台不进矩阵）：
  linux 主机出 win32 包，macosx 主机出 win32 + linux 包；产物上传后由
  `run-win32-cross` / `run-linux-cross` 在**目标平台**（SwiftShader /
  Lavapipe 软件 Vulkan）真实运行并 grep 标记。
- **Android 模拟器**（`run-android`，软门槛，best-effort）：APK 装进 arm64
  模拟器（macOS arm64 runner）启动 `EVEngineActivity`，logcat grep 标记；
  连续稳定后再转硬门槛。
- **iOS 模拟器**（`ios-sim`，软门槛，best-effort）：从 release 源码构建
  iphonesimulator 游戏 app（`make build/ios-sim-debug`，无需签名），simctl
  安装启动后 grep 标记。发布版 iOS SDK 是 device app，无法在模拟器跑，
  因此这步是“引擎在 iOS 上能跑游戏”的源码级验证。

消费侧依赖的产物特性：win32 SDK 的 `bin/` 内置 `vulkan-1.dll` + VC 运行库
（`cmake/win32_bundle_runtime.cmake`），所以任意主机都能打出自包含的 win32
包；`eve package` 按目标 SDK 的 `TARGET_PLATFORM` 选运行时名（跨平台出包）；
`eve` 启动时 stdout 无缓冲，启动标记才能实时进 CI 日志。

## 分支清理

发布 PR 合并后，`vX.X.X` / `promote/*` / `rebase/*` 分支由
`release.py cleanup-branches` 自动删除（每周一 02:00 UTC 定时，或
`workflow_dispatch` 手动触发）。删除条件是分支已并入 `main`/`dev`；同名 tag
永不删除，`main`/`dev` 永不删除。

## 失败与重跑

| 阶段 | 留下什么 | 怎么继续 |
|---|---|---|
| `start` | 可能已有 `vX.X.X` 或已挪 tag | 对同一 tag 重跑 `Release`（`start` 幂等） |
| 严测 / SDK | 正式版 commit 与 tag 在，Release 仍为 pre | 修复后对同一 tag `workflow_dispatch` 重跑 `Release` |
| `finish` | zip 可能已挂上；可能已开 promote / rebase PR | 同一 tag 重跑；已正式 / 已开的 PR 幂等（复用） |
| rebase 冲突 | 不改写 `dev` | 合入 `rebase/vX.X.X` PR |

## 只改 main 上的展示文档

对 `main` 开 PR，且只改：

- `README.md` / `Readme.md` / `Readme.en.md`
- `docs/**`
- `Doxyfile`

`main-gate` 会放行。合并后 `Sync docs` workflow 会把这些文档改动同步到 `dev`：
以 `merge-base` 到 `main` 的路径差为准，只同步文档路径，开 `sync-docs/from-main` →
`dev` 的 PR（**不直推 `dev`**）。release 的版本触点（`CMakeLists.txt` 等）不算
非文档改动，会走发布管线自己的 rebase PR。混入白名单外文件会失败，应改走 `dev`。

## 本地脚本

需要 [GitHub CLI](https://cli.github.com/)（`gh`）。不在 PATH 会报错退出。

```sh
python scripts/release.py --dry-run start --tag v0.1.0
python scripts/release.py start --tag v0.1.0
python scripts/release.py finish --tag v0.1.0
python scripts/release.py sync-docs
python scripts/release.py check-main-pr
python scripts/release.py check-versions
python scripts/release.py cleanup-branches
```

单测（不访问网络）：

```sh
python -m unittest discover -s scripts/tests -p "test_*.py" -v
```
