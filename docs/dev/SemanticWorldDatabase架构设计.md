## 背景与结论

当 Agent 只能通过脚本、场景文件或 MCP 逐步操作引擎时，它必须反复重建对象含义、依赖与修改范围。多个 Agent 同时修改不同文件，也可能破坏同一个玩法约束。单纯增加工具数量不能解决身份漂移、并发修改、状态可见性和重载影响范围的问题。

设计目标是让世界从底层拥有可查询、可验证、可事务化修改的语义结构：**Semantic World Database（语义世界数据库）**。它借鉴数据库的身份、Schema、查询、索引和事务能力，同时保持游戏运行时的数据布局与调度方式。

核心决策是：**ECS 保存权威运行时状态；稳定身份、Schema 和关系描述世界；空间、属性与向量索引是可重建的查询投影；Agent 提交结构化修改意图，由引擎验证并应用。** 向量相似度用于找到候选对象，不能决定对象是否存在、字段值、引用是否合法或修改是否冲突。

本文以需求中的讨论要点为设计输入。引用聊天的助手正文未能读取到，因而不将本稿称为原文转录；关于其他引擎的不足也不作为未经核实的事实结论。

## 1. 目标、范围与现状

### 1.1 设计目标

1. 用稳定 Entity ID 跨编辑、存档、热重载和 Agent 会话定位同一个对象。
2. 显式表达组件字段、关系、约束和依赖，避免由名称或代码片段猜测世界结构。
3. 提供空间 / 属性 / 关系 / 语义混合查询，返回可解释的实体与版本证据。
4. 在一致快照上规划变更，检测字段冲突及跨对象语义冲突，再原子提交。
5. 通过依赖分析缩小重载范围，失败时保持已发布世界可用。
6. 让游戏系统也能使用结构化运行时查询，同时把推理与高成本检索隔离在帧关键路径之外。

非目标：把每帧 ECS 读写改成 SQL；用 embedding 取代组件；引入分布式共识或承诺任意 C++ 代码在线替换；用自然语言隐式批准修改；通过这层架构直接补齐渲染、物理等模块功能。

### 1.2 已有基础与尚未实现的边界

以下是基线源码可核对的基础，未在本次文档修改中重新执行运行时测试：

- [Identity.h](../../src/engine/common/Identity.h)已有 PersistentId、SceneObjectId、TransactionId 等强类型身份；其契约明确区分持久身份与本地运行时句柄。[SceneObject](../../src/modules/scene/SceneObject.h)已有 `persistentId` 字段。不能因此推断全世界实体身份映射已经完成。
- [空间索引](空间索引模块设计.md)已有独立整数 ID / AABB 查询结构；[数据库模块](数据库模块设计.md)提供 POCO Data / SQLite 与 ECS 导出。数据库事务不等于运行时世界事务。

本文提出的统一世界版本、Schema 注册、混合查询规划、向量投影、世界 MVCC、语义冲突规则与依赖驱动的原子发布，均为**待设计和实施**能力。现有 tensor embedding 运算也不等于世界语义向量索引。

## 2. 权威状态与分层

```text
人类编辑器 / Agent / 游戏系统
        │ 结构化查询、预览、修改命令
        ▼
World Query / Transaction Service（拟议）
        ├─ Identity + Schema + Relation Catalog
        ├─ 版本、约束、读写集、审计日志
        └─ 查询规划与索引水位检查
        │ 模块接口 / owner 线程安全点
        ▼
ECS + 领域 owner（权威运行时状态）
        │ 有版本的变更记录
        ├─ 属性 / 关系投影
        ├─ 空间投影
        └─ 向量投影（异步、可缺席、可重建）
```

作者文档保存可持久化的初始状态和编辑意图；运行中的位置、生命值等由 ECS / 领域 owner 决定。运行时修改是否写回作者文档必须显式选择，不能由查询服务自动同步。GPU 资源、物理后端与场景 arena 保留各自 owner，通过组件或 Link 提供可查询的逻辑状态，避免复制出第二份权威状态。

投影只能读版本化事件或一致快照，不得扫描正在并发修改的裸 ECS 指针。事务协调器不能绕过模块生命周期直接改物理或渲染内部数据。接口、provider 和裁剪遵循[模块接口契约与机制选型规范](模块接口契约与机制选型规范.md)及[模块编排与裁剪架构](模块编排与裁剪架构.md)；向量后端可裁剪，基础世界读写不能依赖 LLM 服务。

## 3. 稳定 Entity ID

拟议逻辑 Entity ID 复用现有强类型身份体系，不另外发明裸字符串主键；具体采用 PersistentId 还是增加领域 tag，留待身份契约评审。

- 持久 ID 不随改名、移动、arena 重建或进程重启改变；名称和路径只是定位属性。
- 运行时使用紧凑句柄及其生命周期校验。映射带 world/session 域，禁止把上次会话的句柄当作持久 ID。
- 一个持久 ID 在同一世界中最多映射到一个活对象。创建检查碰撞；销毁留下有版本的 tombstone，过期查询不能解析到复用槽位的新实体。
- 实例化生成新 ID，并显式记录 prefab/source 关系；复制对象不能复制其身份。导入旧场景需持久保存映射和迁移版本，不能依赖可变名称反复推导。
- 场景对象、资源、文档采用各自 ID 域；关联通过带类型引用表达。多 Agent 的离线创建也必须验证唯一性。

## 4. Schema 与关系图

Schema 是可验证契约，至少描述组件类型 ID、字段 ID、类型、单位、默认值、范围、序列化版本、读写权限、owner、变更通知与迁移函数。区分作者字段、运行时字段与派生字段；派生字段不可被 Agent 当作独立状态写入。字段重命名保留稳定字段 ID，类型改变需要显式迁移。

关系以 `source ID + relation type + target ID` 表达，例如 parent、owns、usesAsset、targets、dependsOn。每类关系声明方向、基数、是否允许环、删除策略和强弱引用。parent 无环、唯一所有者、目标类型等属于提交时约束；不能只在编辑器界面检查。

世界关系图与热重载依赖图职责不同：空间邻近或敌对关系不必触发重载；只有声明具有失效传播语义的依赖边参与重载规划。Schema 与依赖元数据自身也有版本；事务读过的 Schema 改变后必须重新验证。

优先复用[Eve-Schema 子集与绑定契约](Eve-Schema子集与绑定契约.md)能够表达的部分；世界约束和字段迁移不能仅因已有绑定描述就视为完成。最初只覆盖一个领域，通过 adapter 注册，避免一次反射全部组件。

## 5. 空间 / 属性 / 向量混合索引

空间索引负责 AABB 宽相候选；属性索引负责类型、标签、枚举、数值范围等确定性筛选；关系索引负责受限图遍历；向量索引负责描述、用途、视觉风格等相似候选。精确几何仍交给领域系统。

每份向量记录保存 Entity ID、输入字段 hash、源版本、embedding 模型及版本、维度、索引版本。模型升级建立新索引后切换，禁止混用向量空间。只在语义输入改变时重算，动态坐标与每帧数值不默认进入 embedding。对象删除必须过滤旧候选。

例如“门口 20 米内，可交互、未锁定，风格像废弃矿场的门”：

1. 解析为受限查询计划，确认米制、坐标域、类型、状态与权限；自然语言只生成计划。
2. 根据选择率选择属性或空间起点，再进行关系过滤；不能固定所有查询都先向量 top-k。
3. 对候选做语义排序，回到同一快照读取精确属性与存在性；返回匹配理由和新鲜度。
4. ANN 检索不保证全集；后过滤不足 k 时可扩大候选或返回不足，禁止承诺找到了“所有门”。要求全集的操作必须使用确定性查询。

强一致查询要求所有参与索引达到指定世界版本，否则等待到预算上限、使用准确扫描或明确返回暂不可用。最终一致检索可返回旧向量分数，但必须披露各索引水位，并在权威快照上校验候选；不能把旧语义排序伪装成快照一致。向量系统离线时仍可运行结构化查询。

## 6. 事务化修改与 MVCC

建议首先实现编辑 / Agent 平面的 MVCC，而不是复制每帧全部 ECS 数据。世界提交序号与 simulation tick 分开；游戏系统的直接写入必须产生字段版本或使相关编辑事务失效，不能成为绕过冲突检测的隐藏写者。

拟议事务包含 transaction ID、actor、world/session、base revision、Schema revision、读集、写集、查询谓词依赖、前置条件与预算。读集记录参与决策的实体字段和关系；范围查询还需记录谓词或范围版本，防止新增对象造成 phantom 冲突。

```text
读取一致快照 → 构造命令 → dry-run / diff / 影响范围
    → 提交时验证版本与权限 → 检查关系和领域约束
    → owner 安全点应用 → 发布新版本及变更事件
    → 更新派生索引 / 记录审计与可逆操作
```

快照可以采用按组件块 copy-on-write 或版本化编辑投影，具体布局需压测。提交先验证完整读写集，再暂存所有 owner 的变更；发布前任何读者都不能看到一半修改。涉及不可回滚资源操作时，先 prepare 资源，再切换可见版本，最后延迟释放旧资源。无法做到原子参与的 owner 必须拒绝该事务，不能借用“事务”名称默许部分成功。

幂等 transaction ID 防止重试重复创建对象。失败返回结构化原因、冲突字段、当前版本与重试建议；成功返回最终 diff 和新版本。undo 是带当前前置条件的新事务，不能把整个世界倒回旧快照并覆盖其他 Agent 的修改。

快照设置 TTL、内存上限和并发数；历史版本由最老活跃读者约束回收，超限明确中止快照。索引更新失败不回滚已提交权威状态：标记投影落后，重放事件或重建。崩溃持久化、WAL 与 ECS 发布顺序需要单独设计；内存原子性不等于磁盘耐久性。

## 7. 多 Agent 语义冲突检测

字段冲突只覆盖“改了同一个值”。语义冲突还包括：Agent A 移门、B 调整路径，两者共同堵死出口；A 删除目标、B 新增引用；两个事务分别创建不同 ID，但违反区域内唯一出生点约束。

按三级处理：

1. **硬冲突**：版本不匹配、悬空强引用、Schema 不兼容、同字段写入；拒绝并返回证据。
2. **领域约束**：唯一性、所有权、预算、连接性、碰撞 / 可达性等。规则声明依赖范围，在最新候选世界检查；昂贵验证安排到准备阶段，并在提交时校验其输入版本。
3. **意图风险**：风格、叙事或用途互相抵触但无法形式化。LLM 可以解释风险，不能据向量距离自动判定可安全合并；按项目策略交由人类或指定协调者处理。

不相交字段也只有在读集、关系与领域约束均兼容时才能自动合并。数值加法等操作仅在 Schema 明确声明可交换且满足约束时允许。短期实体 / 区域租约可降低重复工作，但不能替代版本验证；租约过期后仍需 CAS。

返回内容应包含 actor、对象 ID、规则 ID、冲突 diff 与最小相关子图，使 Agent 能重新规划。事务日志只记录世界修改；代码文件合并、构建兼容性仍由版本控制和 CI 处理。

## 8. 热重载依赖分析

依赖节点包括资源版本、Schema、脚本定义、实体、组件和系统；边描述 uses、instantiates、derivedFrom 等失效传播。文件 watcher 只提供变化起点，不能推断全部依赖。动态脚本引用需注册或进入保守扩大重载范围。

重载流程：计算反向依赖闭包 → 合并环为强连通分量 → 暂存新资源 / 定义 → 检查兼容性与迁移 → 迁移受影响状态 → 在安全点发布 → 失效索引和派生缓存 → 观察诊断。固定实例 ID，重新解析句柄；运行中的事务若依赖被更新定义则失效。

纹理内容变化、脚本函数变化、组件布局变化分别采用不同策略。无法迁移的布局 / ABI 改变提示受控重启，不能承诺一切热重载。失败保留旧版本与可诊断错误；provider 回退默认值必须显式报告，不能称作无损回滚。GPU 旧资源等到 fence 完成后释放。

## 9. 运行时查询契约

游戏系统优先使用预编译的类型 / 属性 / 空间查询；Agent 使用受限查询 AST 和分页结果。输出至少包含 ID、字段投影、world revision、tick、索引水位、截断标志、预算消耗与匹配解释。订阅以有序增量和 resume token 工作；断流或日志缺口后要求重新取快照。

以下仅为接口语义示意，**不是已存在的 API**：

```text
query(snapshot, type=Door, within=Sphere(origin, 20m),
      where={interactable:true, locked:false},
      similarTo="废弃矿场", limit=20, consistency=eventual)

commit(baseRevision=42, readSet=..., commands=[SetField(id, fieldId, value)],
       preconditions=[Exists(id), FieldVersion(id, fieldId, 7)])
```

查询返回稳定 ID 或快照值，不泄漏跨帧裸指针。可见字段按 actor 权限过滤；查询预算涵盖图深度、结果数、扫描量与时间。把查询结果用于修改时，必须把相关谓词及字段加入事务读集；“搜索到了”不代表获得写权限。

## 10. 性能边界与验证方法

- 渲染、物理和高频 ECS 循环保持数据局部性；embedding、ANN 构建、自然语言解析和磁盘事务不能阻塞帧关键路径。
- 高频位置更新只更新空间投影或批量 dirty 集；属性索引只覆盖声明可索引字段，防止写放大。事件队列需上限、背压和可恢复的索引重建策略。
- 向量原始存储约为 `N × d × bytesPerScalar`。100 万条 768 维 float32 仅原始向量约 3.07 GB（约 2.86 GiB），还未计 ANN 图、元数据与多版本；默认不能为全部组件建立向量。
- MVCC 成本随写入量、保留时间和快照读者增加。用分块快照、短 TTL 和域级版本降低成本，不能以无限历史换“无锁”。
- 预算数值待实测，本文不承诺吞吐或时延。首轮基准覆盖 1 万 / 10 万 / 100 万对象、静态及高频移动、长快照、多 Agent 同域修改和重载风暴；记录硬件、构建、数据分布、p50/p95/p99、帧时间、峰值内存、索引延迟、冲突率与恢复时间。
- 对照组为原生 ECS view 与现有空间查询。ANN 测 recall@k，确定性查询与准确扫描核对全集；事务验证无部分可见、无丢失更新、无 phantom 漏检及失败恢复。性能门槛由阶段评审确定后才能成为验收承诺。

## 11. 分阶段实施路线图

各阶段均为拟议，进入下一阶段前需要真实可复现的验证结果；不与发布版本号自动绑定。

### P0：身份与契约闭合

选取一个场景领域，核对 owner、持久 ID、句柄映射、Schema 和迁移规则；补齐生命周期与变更事件。验收：改名、重载、保存 / 加载保持身份，复制产生新身份，重复 ID 和过期句柄被拒绝。先记录当前基础性能。

### P1：确定性世界查询

实现类型 / 属性 / 关系 / 空间投影及只读快照接口，接入一个运行时 MCP 查询入口。验收：同版本查询与权威扫描一致；删除、移动、索引落后和裁剪后降级行为可验证。此阶段无需向量后端。

### P2：事务与多 Agent 竖切

实现版本化命令、dry-run、读写 / 谓词冲突、有限 MVCC、审计和条件 undo；覆盖一个跨对象领域约束。验收：两个 Agent 并发修改可复现成功合并、拒绝和重试，运行时写入参与检测；注入 owner 失败时无部分发布。

### P3：语义混合检索

加入可选 embedding provider 与向量索引，记录输入来源、版本和解释。验收：语义候选经结构化条件复核，模型切换、删除、离线降级与 recall 基准可复现；证明它改善发现效率且不改变事务正确性。

### P4：依赖驱动重载与规模化

扩展资源 / Schema / 脚本依赖图，接入 prepare / migrate / publish；压测历史回收、事件背压和大世界分区。验收：局部重载影响范围有证据、失败保留旧世界、身份与引用不漂移，并完成运行时帧时间和内存门槛评审。

## 12. 待决问题

1. Entity ID 采用何种领域 tag？怎样兼容现有 SceneObjectId、旧 nodeId 与世界分区？
2. Schema 的单一来源和 adapter 生成方式是什么？如何避免绑定描述、序列化和组件注册三份定义漂移？
3. 哪些字段进入世界 MVCC，哪些高频状态只暴露 tick 快照？运行时写者如何低成本发布版本？
4. 多 owner 原子发布、安全点和资源失败恢复由谁协调？现有 reload provider 哪些必须升级契约？
5. 查询谓词依赖采用域级 epoch 还是更细范围版本？误冲突与漏冲突的权衡如何量化？
6. 哪些领域约束能确定性验证，哪些只作为提示？验证超预算时拒绝还是转离线准备？
7. 日志耐久性、崩溃恢复、作者文档写回及网络同步分别需要什么保证？是否有真正的离线合并需求？
8. embedding 采用本地还是远程 provider，授权、隐私、模型再分发和版本固定如何管理？

评审优先顺序：身份与 owner → 一致性及原子发布 → Schema / 查询 → 领域约束 → 向量与性能扩展。先完成不依赖 AI 推理的正确性基础，再评估语义检索收益。

## 13. 面向 AI 自动设计开发大型游戏的配套结构

本节扩展前述世界数据库的应用目标，涵盖俯视动作、策略、战棋、RPG，以及它们的组合。**以下全部为设计目标与建议，不代表这些配套结构已经实现。** Semantic World Database 负责世界如何被理解、查询和修改；完整开发闭环还需要表达设计目标、组合玩法、生产内容和判断完成质量。

### 13.1 组织原则：通用底座、类型领域包与项目规则

通用底座提供身份、时间、命令、事件、查询、依赖、版本和验证。类型领域包表达不同玩法的领域语义；项目规则决定某个游戏的体验。不能把动作角色、连续实时循环或空间关卡当作所有类型的默认模型，也不追求一个能表达全部玩法的万能角色类。

```text
设计目标与约束
    → 可验收功能规格
    → 领域规则、内容资产与实现
    → 构建 / 模拟 / 实际游玩
    → 运行证据与体验评估
    → 修订设计或实现

Semantic World Database：提供身份、状态、关系、查询及世界修改契约
工程与内容管线：管理代码、资源、构建和交付
验证系统：判断功能正确性、可完成性、成本和体验目标
```

### 13.2 可执行的游戏设计模型

以版本化设计对象记录核心循环、玩家选择、胜负条件、资源流、进度、难度目标和限制条件。每个目标关联设计理由、规则、依赖和验收方法。例如策略游戏的“扩张有风险”需要落实为补给成本、领土收益、暴露程度与反制机会；“缩短回合时间”需要追踪行动点、动画时长、地图规模和单位数量。

区分可自动检查条件与体验假设：每回合存在合法行动可以验证，战棋是否有趣需要实验和人类体验。目标与实现可以多对多关联；自动检查通过不能直接将体验目标标记为完成。设计发生变化时，沿追踪关系使相关规格与验收证据失效，避免旧结果证明新设计。

### 13.3 多种时间与推进方式

模拟底座应支持实时连续更新、固定 tick、离散回合、规划 / 结算 / 执行阶段，以及暂停下令后继续。通过明确的命令、事件、阶段状态和调度依赖表达推进方式，而非把全部规则塞入逐帧 update。

不同时间域可以组合，例如世界地图按天推进、局部战斗按回合推进。跨域交接需定义状态归属、命令何时生效、事件时间戳和存档边界。提供可控随机数、重放与状态校验，允许快速模拟和稳定复现；确定性范围需明确，不能默认 GPU、物理后端或跨平台浮点结果逐位一致。

作者状态、模拟状态与派生状态沿用本文的一致性分工。Agent 对正在变化的对象提交带条件及有效期的领域命令，不要求为每次规划冻结整个世界。

### 13.4 可组合的玩法领域模型

ECS 承载状态；合法行动、结算和领域不变量由领域契约表达。建议按玩法职责提供可组合领域包：

- 俯视动作：移动、瞄准、命中、伤害、状态和交互。
- 策略：单位、编队、命令、视野、补给、生产和经济。
- 战棋：棋盘拓扑、回合、行动点、占位、攻击范围和结算。
- RPG：属性、装备、技能、任务、对话、阵营和成长。

共享命令、事件与规则机制，保留各领域语义。例如攻击先查询目标资格，再执行命中与伤害规则；任务订阅战斗结果，不读取某种角色类内部字段。领域包声明输入、输出、owner、时间域、约束与可选依赖，按项目组合和裁剪。地形、导航、视野及 UI 等能力可跨类型复用，但不同玩法不必共享同一内部算法。

### 13.5 不完整信息与决策接口

明确区分世界真实状态、玩家观察、NPC 观察和设计 Agent 的调试权限。观察包含可见对象、记忆及信息时间；不能让自动对战或 NPC 隐式读取全图真值，否则平衡评估与行为都可能失真。

决策接口以观察、合法行动和目标为输入，以领域命令为输出，使脚本 AI、行为树、搜索算法与学习策略可替换、可测试。非法或过期命令仍由运行时验证器拒绝。LLM 优先参与低频规划、内容设计和解释；高频行为由有预算且可控的运行时系统执行，不能把远程推理延迟放入帧关键路径。

### 13.6 内容生产与依赖管理

地图、敌人、装备、任务、对话、资源和本地化作为有 Schema、版本、来源和验证规则的内容资产，采用以下流程：

```text
设计规格 → 生成候选 → 静态与领域检查
    → 游戏内验证 → 审阅 → 发布
```

生成 RPG 任务时同时检查前置条件、角色存在性、奖励经济、地图可达性和剧情时间线。模板、变体与覆盖规则必须有明确合成顺序和迁移策略，避免大量内容变成相互漂移的独立脚本。记录生成输入、工具版本、资源来源与使用授权，使失败能复现、资产能追溯。

内容依赖图接入世界查询及热重载，但代码、内容与世界状态各自保留版本及提交机制。跨产物发布使用一致的版本清单和集成验收，不能用一个世界事务假装已经原子更新代码、磁盘资源和运行时。

### 13.7 体验验证与自动实验

验证至少区分程序正确性、游戏可完成性、系统平衡和表现质量：崩溃 / 引用 / 存档 / 规则；可达性 / 任务链 / 软锁 / 胜负；经济膨胀 / 优势策略 / 无效技能 / 难度曲线；画面 / 音效 / 动画 / UI / 输入反馈。

提供快速无头模拟、可视化运行、自动玩家、场景夹具、指标与错误复现包。不同类型使用不同验收：策略关注经济与决策，战棋关注行动空间，动作关注操作与反馈，RPG 关注成长和内容连贯性。测试数据、随机种子、构建、规则及内容版本必须进入证据，失败保存最小可复现场景或命令轨迹。

使用不同策略与能力层级的自动玩家，并保留人类体验评估。防止系统只适配某个测试机器人或单一代理指标；修改优化目标之后，重新检查体验和行为副作用。正确、可完成、指标达标与有趣是不同结论，报告必须分别说明。

### 13.8 多 Agent 工程协调与追踪关系

每个工作单元声明输入、输出、依赖、允许修改范围、版本和验收条件。优先按可验收功能组织，如“单位受攻击中断采集，逃跑完成后恢复”，而不是仅按“编写采集模块”分派。工作单元关联设计目标、领域规则、实现、内容、测试场景和运行证据。

代码变化由版本控制、接口检查与构建管理；内容变化由资源契约和生产管线管理；世界变化由本文的事务管理。三者通过集成验收协调，不能互相替代。Agent 的完成声明应指向证据；证据过期、依赖改变或检查未运行时，保留待验证状态。

### 13.9 大型项目分区与质量预算

除了空间分区，还需按阵营、经济、任务、战斗实例与存档域划分逻辑状态。声明跨分区引用、加载策略、状态生命周期和卸载后的查询语义；暂未加载对象不能被误判为已删除。跨域操作明确协调范围和失败策略。

将单位模拟、资源内存、地图流送、内容规模、构建和验证成本作为可查询预算。设计提案说明预期成本和测量方法，预算超限触发缩减、分批或重新规划。预算目标由项目与目标平台决定；本文不设未经测量的统一性能承诺。

### 13.10 配套实施顺序与跨类型验收

以下是产品闭环的推进顺序，与 §11 的数据库 P0–P4 相互配合，不替代其身份、一致性及事务前置条件：

1. 设计模型、多模式模拟和领域命令：明确要完成的功能，以及执行与验证方法。
2. 内容管线和自动实验：持续生产内容，并通过运行证据评估结果。
3. 多 Agent 工程协调、分区和预算：支持项目规模增长和持续集成。
4. 按实际需求扩展语义检索，衡量探索效率收益，保留无需推理的正确性基础。

首轮选择一个俯视实时动作和一个回合制战棋完整切片，共同验证身份、内容、存档、命令和测试底座，并暴露时间模型、目标选择、棋盘规则与交互差异。随后以策略经济和 RPG 任务链检验长期状态、复杂依赖与内容规模。切片是验证架构的阶段，不作为缩减最终支持范围的理由。

跨类型验收应记录定位错误、事务重试、开发等待、玩法规则失败、帧开销和验证成本，同时检验实际交互表现。最重要的共同产物是**“设计目标—领域规则—实现—运行证据”追踪关系**：它使 Agent 能判断是否完成游戏功能，而非仅统计执行了多少操作。

### 13.11 配套待决问题

1. 设计规格使用什么 Schema，哪些可从现有契约生成，哪些需要人工维护？怎样避免多份定义漂移？
2. 时间域与领域包的最小公共接口是什么？跨实时、回合和阶段的交接如何保存及重放？
3. 观察与权限由谁生成，怎样验证自动玩家和 NPC 没有读取隐藏信息？
4. 哪些规则能自动检查，体验目标采用什么实验、人类审阅与证据有效期？
5. 工作单元和追踪关系如何接入仓库、资源版本及 CI，怎样管理集成后失效的验收结果？
6. 跨分区状态、离线模拟、内容发布与存档迁移分别需要哪些一致性保证？
