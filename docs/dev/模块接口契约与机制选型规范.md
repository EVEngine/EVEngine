# 模块接口契约与机制选型规范

日期：2026-09-15
状态：已确认的架构要求。门禁落地状态逐条标注于 §8；标注「待实施」的条目自本文合并之日起约束新增与改动的代码，但在对应门禁落地前不产生 CI 失败。
适用范围：新增模块与公共 API、跨模块接线、ECS/事件/provider/Link 选型、性能敏感路径，以及所有 agent 实施工作。

## 目的

本规范解决三类此前只能靠经验与个人判断决定的问题：

1. **一个模块与外界交换什么** —— 今天没有任何一份产物描述模块边界，只能靠检索与人工重构反推。
2. **这些交换该用哪种机制** —— ECS、capability、event、Link、直接调用并存，选型没有判据。
3. **交换的代价如何被调用者看见** —— 成本信息不在接口上，昂贵操作与廉价操作形状相同。

本规范与以下强制文档的分工（互不重复）：

| 文档 | 负责 |
| --- | --- |
| `重构代码质量与系统完整性规范.md` | 返回值语义、所有权与 Link、ECS 使用、时间与确定性、持久化、测试与 CI 门禁 |
| `领域短根继承与跨域组合架构.md` | 实体建模：短根继承、组件、Link/Handle |
| `Result检查与不得丢弃返回值规范.md` | `Result` / `[[nodiscard]]` / 未观察检查 |
| `模块编排与裁剪架构.md` | 实测依赖分层、能力注册表、裁剪 profile 与清单 |
| **本文** | **模块对外契约的声明、连接机制选型、API 成本可见性** |

规则编号（`R-BOUND-n`、`R-MECH-n` 等）是稳定引用标识。评审意见与 agent 交付报告必须逐条引用编号。新增规则只追加编号，不重排已有编号。

## 0. 问题清单

本文各条规则都来自下面这六个已确认的问题。规则不是设计偏好，而是这些问题的闭合手段。

| # | 问题 | 证据 | 规则 |
| --- | --- | --- | --- |
| **P-1** | 把「include 了 B」直接当成「链接期依赖 B」，据此判断可裁剪性 | 两者不互相蕴含：只出现类型、枚举、前置声明、纯虚接口指针调用都不产生符号引用 | `R-BOUND-1..2` |
| **P-2** | `#include` 图被当作可裁剪性判据，但它只度量重编译半径与分层方向 | `scripts/module_depgraph.py` 只扫描 `#include`，从不读取目标文件、`EVELIBS`、链接行或 profile 产物；其 `isolated (trimmable with no graph impact)` 是图上的陈述 | `R-BOUND-3` |
| **P-3** | provider 家族各自实现注册/派发/租约，缺席语义不一致 | 全仓至少 13 个 provider 家族；`editing::EditingExtension.h` 是唯一做全生命周期（`shared_ptr` + generation + lease + 线程安全）的实现，其余多为自造 | `R-COHESION-3`、`R-FACE-4` |
| **P-4** | 没有一份产物描述模块边界，接口的定义位置即唯一真相源 | 现有审查产物只覆盖 Link（5 条）与 ECS System（7 条），能力面与脚本面完全没有 | `R-FACE-1..3` |
| **P-5** | 机制选型无判据；便捷但不适合 runtime 的写法就在手边 | `common/Module.h:43-44` 的 `getModInst` / `requireModInst` 是字符串键懒取单例的一行宏，比正确写法更省力 | `R-MECH-1..4` |
| **P-6** | 成本不在接口上，昂贵与廉价 API 形状相同 | `@cost` 类 Doxygen 标签在全仓公共头文件中 0 命中。`src/modules/graphics/Graphics.h:1273` 的成本说明是孤例，而且**挂在 `setScreenReadbackEnabled`（setter）上，不是挂在真正付代价的 `saveFramePng`（:1282）上**；后者只有「Enables screen readback if needed」且返回 `bool`，形状与廉价 setter 无异 | `R-COST-1..4` |

## 1. 模块边界与可裁剪性判据

### 1.1 一个模块对外有两张图

| 图 | 边 | 度量 | 现有工具 |
| --- | --- | --- | --- |
| **include 图** | A 的源文件 `#include` 了 B 的头 | 重编译半径、分层方向、公共头依赖泄漏 | `scripts/module_depgraph.py`（已接入 CI） |
| **符号引用图** | A 的目标文件对 B 有未定义符号 | **链接期依赖，即真正的可裁剪性** | **无** |

两张图必须分别对待。用 include 出度回答「能不能裁」是口径错误（P-2）。

### 1.2 哪些用法真正产生链接期依赖

判据表。左列是 A 引用 B 的形态，右列是链接 B 是否必需：

| A 对 B 的用法 | 需要 B 的符号 | 不链接 B 时 |
| --- | --- | --- |
| 只出现类型、枚举、常量、前置声明、指针/引用**声明** | 否 | 链接通过 |
| 通过**纯虚接口指针**调用虚函数（接口声明在头里） | 否（vtable 槽间接调用） | 链接通过 |
| 头里的 `inline` / 模板，且从未被 odr-use | 否 | 链接通过 |
| 整个 translation unit 被排除（如 `EVENGINE_EXCLUDED_MODULE_FILES`） | 否 | 链接通过 |
| 调 B 的**非虚、非 inline** 成员函数或自由函数 | **是** | 未解析外部符号 |
| 构造/析构 B 对象、取 B 静态成员地址、实例化定义在 `B.cpp` 的模板 | **是** | 未解析外部符号 |
| 对 B 派生类型做 `dynamic_cast` / `typeid` | **是**（需 `type_info`） | 未解析外部符号 |

两个会改变结果、因此**只能实测不能静态推断**的变量：

- 本仓模块是 OBJECT library（`EV<Name>`），所有 TU 的目标文件都进入最终链接输入，所以「没人调用的代码」在无 `/OPT:REF` 的构建下同样参与符号解析。
- 反过来，静态库 + 被丢弃的 COMDAT 可能让某些引用逃过报错。

### 1.3 裁剪的四个层次

「裁剪」在本文中一律指下列四层之一，不允许不加限定地使用该词。四层判据、失败表现和验证手段各不相同：

| 层 | 定义 | 判据 | 失败表现 |
| --- | --- | --- | --- |
| **L1 编译期剪裁** | B 的源文件不参与编译 | A 的 TU 仍能编译 | 头文件找不到；类型不完整 |
| **L2 链接期剪裁** | B 的目标文件不在链接行 | **符号引用图为空** | 未解析外部符号 |
| **L3 运行期剪裁** | B 的实例不被创建/注册 | 能力查询返回 `nullptr` 且被显式处理 | 空指针解引用 |
| **L4 可观察剪裁** | 缺席是**被测试的状态** | present/absent 两个 profile 都跑通 | 静默跳过 |

`scripts/module_depgraph.py` 量的是 **L1 的重编译半径 + 分层方向**。它不能判定 L2/L3/L4。

### 规则

- **R-BOUND-1** 禁止用 include 关系推断链接期依赖。要断言「A 可以不链接 B」，必须给出符号引用证据（目标文件符号表）或一次真实的裁剪构建结果；不得以「代码里没人调用它」作为理由，因为编译期无法证明运行期不可达。
- **R-BOUND-2** 新增跨模块调用时，必须明确它落在 §1.2 判据表的哪一行。落在右三行（产生符号引用）的调用，必须在模块契约条目中登记为**硬依赖**（见 `R-FACE-2`）。
- **R-BOUND-3** 讨论裁剪时必须指明层次（L1/L2/L3/L4）。禁止用 `module_depgraph.py` 的输出作为 L2 或 L3 的验收证据。
- **R-BOUND-4** 增量步骤：**新增与改动的模块**需要登记 L2 依赖；存量模块按 §8.3 的强度策略渐进补齐。若符号引用图工具尚未落地（§8.2），以「该模块被关掉后 configure/编译/链接/启动四连测的结果」作为替代证据，并在交付报告中写明跑了哪个 profile。

## 2. 模块划分与内聚

### 2.1 内聚是变更的属性，不是代码的属性

两块代码内聚，当且仅当它们**因为同一个原因、由同一个 owner、在同一时刻变更**。「长得像」是**偶然相似**，不构成内聚理由。评审时按序回答三个问题：

| 判据 | 通过的含义 | 不通过的含义 |
| --- | --- | --- |
| **不变式判据**：是否存在一条规则，必须到处都成立，且违反即 bug？ | 是同一个**知识**，重复即债务 | 只是形状巧合 |
| **变更理由判据**：新需求到来时，所有副本会一起改吗？ | 同一个轴 → 应合一 | 不同轴 → 必须分开 |
| **Owner 判据**：这条不变式有唯一 owner 吗？ | 可追责、可测试 | 多头 owner 即无人 owner |

### 2.2 机制与策略是两个轴

这是本仓 provider 家族判断的核心。同一个 API 形状（接口 + 注册 + 查找 + 生命周期）背后有两条完全不同的轴：

- **机制轴（mechanism）**：注册、优先级、派发快照、租约、代际失效、线程亲和、撤销时序。
- **策略轴（policy）**：解析什么、返回什么数据、缺席是致命还是可回退、谁拥有实现。

按 §2.1 的判据：

- 机制在**不变式判据**上全部通过 —— 所有家族都必须遵守同一套派发与撤销语义，违反即崩溃。因此机制**必须合一**。
- 策略在**变更理由判据**上全部不通过 —— 属性编辑 UX、图编辑语义、脚本 URI 解析、生成物发布事务各自由不同 owner 因不同原因变更。因此策略**必须分开**。

### 2.3 本仓 provider 家族现状

至少 13 个家族（完整清单见附录 A）。它们的策略轴差异是真实的，机制轴的重复也是真实的：

| 家族 | 机制来源 | 生命周期能力 |
| --- | --- | --- |
| `eve::cap::provide/query/addListener/forEach(Until)` | 通用能力注册表 | 裸指针；`Lifetime is the caller's`；注册非线程安全 |
| `editing::IEditingExtensionProvider` + `ExtensionProviderRegistry` | **自造，机制超集** | `shared_ptr` + `ProviderHandle{id,generation}` + `ProviderLease` + 线程安全 |
| `eve::script::IScriptModuleProvider` + `ScriptModuleResolver::registerProvider` | **自造** | `shared_ptr` + `ProviderId`；链式「未处理则试下一个」 |
| `scene::ISceneComponentPayloadProvider` + 自造按名注册表 | **自造** | 裸指针 + 自建 `std::map` |
| 其余 9 个（`IPropertyProvider`、`IGraphDomainProvider`、`IGameplayControlProvider`、`ISensingCandidateProvider`、`IAcceleratorBackendProvider` 等） | 部分走 `cap::`，部分与既有机制绑定 | 随宿主而定 |

根因：`src/engine/common/Capability.h:40-44` 只提供裸指针并声明「lifetime is the caller's」「registration is not thread-safe」。任何需要所有权、租约、代际失效或线程安全的家族只能自造注册表，于是缺席语义在各家族之间不一致。

> **实测修订（2026-09-15，见 `docs/dev/2026-09-15-模块边界审查台账.md` §5.1）。** 全仓扫描 194 个模块、48 个具名能力后，P-3 证据列中「其余多为自造」**不成立**，此处记录实测结论：
>
> - `editing::IPropertyProvider` / `IGraphDomainProvider` / `IEditingSnapshotProvider` 经 `editingCapabilityId()` 由 `editing::IEditingExtensionProvider`（上表的机制超集）分发，是**同一机制的类型化子面**；
> - `audio_editing` / `physics_editing` / `editor` 直接复用 `editing::ExtensionProviderRegistry` 与 `editing::ProviderHandle`；
> - `INavigationProvider`（`npc_ai/Navigation.h:105`）与 `IActionResourceProvider`（`action/Action.h:347`）是**消费方持有的注入接口**，不参与任何注册表，属 `R-COHESION-6` 的正面例子；
> - 真正的自造注册表实测**只有 2 处**：`common/ScriptModule` 与 `scene/editing/SceneComponentPayload`。
>
> 规则 `R-COHESION-3`（机制必须收敛到单一实现）与 `R-COHESION-4` 不受影响；受影响的是附录 A「机制来源」列的措辞，应改为「随宿主 / 类型化子面 / 消费方注入 / cap:: 通用机制」，与上表最后一行的分类一致。

### 2.4 同时属于 A 和 B 的概念

这类概念**通常不是一个概念，而是一个交点**。正确的产物不是合并的类型，而是**有方向的协议 + 两侧绑定**。

本仓已经有的正解是 `src/engine/common/ArtifactPublication.h`：生成物发布同时属于 procgen（生产者）与 scene/graphics/physics/map（消费者）。它的三分解是：

| 成分 | 归属 | 理由 |
| --- | --- | --- |
| `ProviderContract`（prepare/commit/rollback 机制） | `common/` | 机制轴，跨域不变 |
| `ISceneArtifactAdapter` 等**类型名**（`eve.procgen.*`） | **消费者**（procgen 提问） | 接口所有权跟随提问方 |
| 实现（`SceneArtifactProvider` 等） | 提供者模块 | 实现所有权跟随回答方 |

处理交点的三条路径，按优先级排序。**必须从上往下选，不得为了「更干净」跳级**：

1. **类型化句柄/Link**：关系是数据，单侧拥有，有显式失效检测（`ProviderHandle` + generation，或 `领域短根继承与跨域组合架构.md` 定义的 Link/Handle）。
2. **低层契约 + 每消费者一个类型名**：交点是「能力」而非「关系」，即提供者可能有很多时使用。即 artifact 模型。
3. **提升为新领域**：仅当交点有**自己的不变式、自己的生命周期、自己的 owner**，且 A、B 都无法拥有它。这是稀缺情况 —— **说不出第三个领域独立的不变式，它就不是领域，不得创建**。

要明确点名的反模式，正是「全放一起」会造成的两种损伤：

- **机制侧的 god-registry**：一个知道所有 provider 策略的中心注册表，等于让 `common/` 反向依赖所有域。
- **类型侧的共享基类**：把 A 和 B 的字段塞进一个类型，即本仓明令禁止的 universal `GameObject` / `GameplaySubject` / `GameplayActor`。

### 规则

- **R-COHESION-1** 合并代码前必须通过 §2.1 的三条判据，并在交付报告中写出变更理由与 owner。不得以「DRY」「看起来一样」为合并理由。
- **R-COHESION-2** 禁止按 include 出度或 provider 数量评价耦合度或灵活性。「能不能换、能不能删」必须用 `R-BOUND-1` 的证据回答。
- **R-COHESION-3** provider **机制**必须收敛到单一实现。收敛目标是把 `editing::EditingExtension.h` 已验证的模型（`shared_ptr` + generation handle + lease + 线程安全注册）作为**可选所有权模式**提升到能力注册表层，使每个家族退化为「一个类型名 + 一个生命周期策略选择」。在此之前，新增 provider 家族必须复用已有的机制之一，不得第三次自造注册表。
- **R-COHESION-4** provider **策略**禁止合并。不同 provider 家族的数据、缺席语义与 owner 必须保持独立，不得为了统一而合并为通用 provider。
- **R-COHESION-5** 新增跨域概念时按 §2.4 的三条路径排序选择；选择路径 2 或 3 必须在交付报告中说明为什么路径 1 不成立。
- **R-COHESION-6** 接口所有权跟随**提问方**：消费方要问的问题，声明在消费方一侧（或其模块内）；提供方实现该接口，不得反向拥有它。

## 3. 模块对外接口的六个面

### 3.1 六个面

一个模块的对外边界由且仅由下面六个面构成。任何跨模块交换都落在其中之一；**说出不落在其中之一的交换，就是缺了一条面定义**。

| 面 | 方向 | 载体 | 必须声明 |
| --- | --- | --- | --- |
| **E1 能力面** | 出 | `cap::provide` / `cap::addListener` | 能力名、实现类、**缺席时消费者看到什么** |
| **E2 依赖面** | 入 | `cap::query` / `cap::forEach` / `ModuleManager` 查找 | 能力名、必需或可选、**缺席时的显式回退** |
| **E3 数据面** | 双向 | ECS 组件 / `scene` Link | 类型、owner、失效检测、双向析构顺序 |
| **E4 事件面** | 出/入 | `Observer` / `Subscription` / 状态 provider / 事件队列 | 事件类型、顺序语义、派发时机、重入性 |
| **E5 脚本面** | 出 | `expose(ssq::Table&)` / `SSQ_REG` | `eve.*` 类名、方法、所有权语义 |
| **E6 协议面** | 出 | MCP / LSP / DAP | 工具方法名与返回形状（仅对有工具面的模块） |

E3 与 E4 的一部分**已经**有强制契约：`scripts/architecture_contracts.json` 的 `link`（5 条）与 `ecs-system`（7 条）规则已经要求 `create`/`ownership`/`destroy_order`/`restore`/`stale` 与 `entity_scope`/`view`/`read_set`/`write_set`/`structural_changes`/`events`/`services`/`phase`，并有符号交叉校验。**E1、E2、E5、E6 完全没有。**

### 3.2 声明的必需字段

新增一条 `module-interface` 规则，逐模块声明。字段沿用现有 catalogue 的信封（`id`、`rule`、`scope`、`owner`、`issue`、`reason`、`expiry`、`evidence`、`tests`），加上：

```json
{
  "id": "physics-module-interface",
  "rule": "module-interface",
  "scope": "src/modules/physics/**",
  "provides":    [ { "capability": "...", "impl": "...", "absent_behavior": "..." } ],
  "requires":    [ { "capability": "...", "required": false, "fallback": "..." } ],
  "emits":       [ { "event": "...", "ordering": "...", "dispatch_phase": "..." } ],
  "observes":    [ "..." ],
  "binds":       [ { "script_class": "...", "methods": [ "..." ] } ],
  "protocol":    [ { "method": "...", "shape": "..." } ],
  "thread_affinity": "...",
  "trim":        { "absent_profile": "..." },
  "cost_notes":  [ { "api": "...", "shape": "two-step|owned-result|builder", "why": "..." } ]
}
```

`link` 与 `ecs-system` 的已有条目按 `scope` 归并入同一模块的边界，不重复声明。

### 3.3 交叉校验要求

声明的价值不在于写下来，而在于**能被证伪**。`module-interface` 条目必须支持下列机械校验（机制见 §8.2）：

| 校验方向 | 规则 |
| --- | --- |
| 源码 → 声明 | 模块内出现的每个 `cap::provide<X>` / `cap::addListener<X>` 必须在 `provides` 中 |
| 源码 → 声明 | 模块内出现的每个 `cap::query<X>` / `cap::forEach<X>` 必须在 `requires` 中 |
| 源码 → 声明 | 每个 `SSQ_REG` / `expose(ssq::Table&)` 的类必须在 `binds` 中 |
| 源码 → 声明 | 每个 `Observer<...>` 成员必须在 `emits` 或 `observes` 中 |
| 声明 → 构建 | `trim.absent_profile` 必须与 `cmake/module_manifest.cmake` 的 DEPS 一致，且该档能 configure |
| 声明 → 测试 | 可选依赖必须同时有 present 与 absent 探针（沿用 `optional-capability` 的既有字段与语义） |

**只写不查的清单一定会腐化。** 缺少「源码 → 声明」方向的校验，`module-interface` 就退化成又一份无人维护的文档。

### 规则

- **R-FACE-1** 每个模块的对外边界必须能由 §3.1 的六个面完整枚举。新增跨模块交换时，必须指明它属于哪个面。
- **R-FACE-2** 新增或改动的模块必须有一条 `module-interface` 条目，字段见 §3.2，并通过 §3.3 的交叉校验。存量模块按 §8.3 渐进补齐。
- **R-FACE-3** 声明必须可证伪。禁止只写摘要性描述（「提供若干渲染能力」）；每个字段都必须能被 §3.3 的某一项机械校验覆盖。
- **R-FACE-4** 能力（E1/E2）的声明要唯一为真，前提是缺席语义在所有家族一致。因此在 `R-COHESION-3` 收敛完成前，`provides` / `requires` 的 `absent_behavior` / `fallback` 描述的是**该家族当前的实测语义**，并必须标注是否为预期语义。
- **R-FACE-5** 禁止用 `common/` 承载具体领域的接口或状态（沿用既有规则）；`common/` 只承载机制、无领域语义的值类型与信封套。

## 4. 连接机制选型

### 4.1 四轴判据

机制不是被「选择」的，是由四个数值**推导**出来的：

| 轴 | 取值 |
| --- | --- |
| **基数** | 1（单例） / 已知少数 / 随实体数增长 |
| **频率** | 每帧每实体 / 每帧 / 每次状态变化 / 每次编辑或加载 / 单次 |
| **关注者可知性** | 编译期已知 / 运行期未知或会增长 |
| **原子性** | 需要全成或全不成 / 单步即可 |

| 四轴特征 | 正确机制 | 用其它机制错在哪 |
| --- | --- | --- |
| 基数随实体数增长 + 每帧 | **ECS 视图** | `cap::query` 每实体每帧查表 = O(N·log M) 字符串比较，且阻断批处理 |
| 每帧 + 单提供方 + 进程级 | **启动期 resolve 一次，缓存为成员** | 每帧查询是纯浪费；反向也不能硬 include（破坏裁剪） |
| 低频 + 多提供方 + 按序尝试 | **`cap::addListener` + `forEachUntil`** | 硬编码 provider 列表 = 不可裁剪、不可扩展 |
| 状态变化 + 关注者未知 | **`Observer` / 事件** | 直接调用 = 反向依赖；用 ECS 系统 = 把 push 退化成每帧全表扫描 |
| 关系**持续存在**且存在性本身是数据 | **`scene` Link / 类型化句柄** | 用事件表达持久关系 = 丢状态、不可查询、无失效检测 |
| 多步不能部分生效 | **`ProviderContract` prepare/commit** | 用事件 = 无法回滚 |
| 游戏侧要调用 | **`expose` / `eve.*`** | — |
| **只在调试 / 工具 / 热重载里用一次** | 便捷直取 —— **但必须被限定在非 runtime profile** | 见 §4.3 |

### 4.2 热路径

热路径必须**可声明**，否则性能判断只能靠直觉。声明粒度是**文件作用域**（`fnmatch` glob），不是函数体 —— 因为现有门禁是逐行正则、没有 C++ 解析器，函数体扫描不可靠（§8.2）。

`module-interface` 条目中的 `hot_path` 是一个路径 glob 列表。落在其中的文件，其**新增行**不得出现下列原语：

- `ModuleManager::getInstance` / `getModInst` / `requireModInst`
- `cap::query<` / `cap::forEach<` / `cap::forEachUntil<`
- 逐行进行的字符串键查找

正确形态是启动期解析一次并缓存成员，或使用 S4 开放式 Link 已验证的**函数指针表 + 预取指针**（`src/modules/scene/SceneLink.h`）。

### 4.3 便捷路径必须退出便利位置

这是唯一不依赖使用者自觉的杠杆。原则：

> **正确的用法必须是最顺手的用法；错误的用法必须编译不过，或需要额外写代码。**

具体要求：

- `getModInst` / `requireModInst`（`src/engine/common/Module.h:43-44`）只允许出现在**非 runtime profile**（工具 / 编辑器 / 调试）。runtime profile 不提供它们。
- runtime profile 只提供不可拷贝、必须存为成员、**没有每帧可调重载**的提供方引用类型（本文以 `ProviderRef<T>` 指代该待引入形态），使「每帧重新查找」这一写法根本不存在。
- 一个「方便」的实现，如果指认不出它属于哪个非 runtime profile，那它**不是调试代码，是错误代码**。

### 规则

- **R-MECH-1** 新增跨模块交换前，必须按 §4.1 的四轴给出取值并推导机制。任何以「调用方便」为由的选择都不进入该流程。
- **R-MECH-2** 热路径文件必须在 `module-interface` 条目中声明为 `hot_path`；其新增行不得出现 §4.2 列出的原语（§8.2 门禁落地后强制执行）。
- **R-MECH-3** 便捷查找原语（`getModInst` / `requireModInst` 及同类）不得出现在 runtime profile 的模块代码中。它们只属于非 runtime profile。
- **R-MECH-4** 能力查询必须集中在 composition root、adapter 或明确边界；业务逻辑中不得散落 `if (capability != nullptr)` 分支（沿用既有规则，此处明确其判据来源是四轴中的「频率」）。
- **R-MECH-5** 热路径不得为通过声明而排除整个文件。`hot_path` 的 glob 必须指向真实承担每帧工作的文件；把热代码挪进未声明文件以规避门禁，按违反处理。
- **R-MECH-6** 模块内部的 feature flag 禁止新增（沿用 `模块编排与裁剪架构.md` §七.3）；裁剪粒度到模块为止，粒度不够说明该拆模块而不是加宏。

## 5. 形状即成本

### 5.1 原则

**成本必须编码在 API 形状里。** 调用者从签名与步骤数就能读出成本量级，无需读实现、无需文档、无需问人。三个推论：

1. 便宜的操作 → 直接 API，零仪式。
2. 昂贵的操作 → **在步骤上可见**（两步 / 令牌 / builder）。
3. **步骤数即成本量级。**

「性能逻辑与使用逻辑一致」的可测试形式是：**对同一个操作，代码里不应存在第二种更便宜的写法。** 存在即是一种应被消灭的状态 —— 这是「不得建立第二真相源」在性能维度上的推广。

### 5.2 本仓已有的正例

原则已在仓里存在，只是被局部遵守：

| 形态 | 位置 | 说明 |
| --- | --- | --- |
| Builder 已是昂贵构造的既定形态 | 16 个 `*Builder` 类（`PipelineBuilder`、`SamplerBuilder`、`BindGroupLayoutBuilder`、`TerrainMeshBuilder`、`VirtualGeometryBuilder`、`AnimationStateGraphRuntimeBuilder` 等） | 分布本身标注了哪些操作昂贵 |
| 借用与拥有编码在类型里 | `src/engine/common/GpuResidentBufferView.h`（非拥有 view）对 `tensor::OnnxDeviceStorage::readback()` 返回 `Result<std::vector<uint8_t>>`（拥有 = 一次拷贝，`src/modules/tensor/OnnxStorage.h:14`） | — |
| 零拷贝返回 view 而非容器 | `climbing::ClimbingTelemetry::samples()` 返回 `std::span<const ...>`（`src/modules/climbing/ClimbingTelemetry.h`） | 比「先返回 buffer 再取数据」更优：连 buffer 都不返回 |
| 昂贵前提被强制承认 | `src/modules/graphics/vulkan/Canvas.cpp`：`if (hdr) throw Exception("HDR Canvas pixel readback requires an explicit tone-map pass")` | 不返回错数据，也不静默降级 |
| 昂贵操作无法被一步调用 | `Graphics::beginFrameReadback(path)` → 轮询 `frameReadbackStatus()`（`src/modules/graphics/Graphics.h`） | 三段式 |
| 廉价路径与昂贵路径各有名字 | `src/modules/tensor/OnnxCompute.h:33`：「no readback is required」的 queue 路径对 `readback()` | — |
| 契约已是可读的 C++ 数据 | `src/modules/climbing/ClimbingECS.h` 的 `ClimbingSystemContract` + `climbingSystemContracts()` | `ecs-system` 规则的已落地先例 |

### 5.3 `@cost` 标签

本仓公共头文件已经有一套自定义 Doxygen 标签并被门禁使用：`@ownership`（462 处）、`@lifetime`（500）、`@thread`（548）、`@reentrancy`（377）、`@nullable`（64）。成本标签沿用同一形态：**`@cost`**，不使用 `@par Cost`（`@par` 在全仓 0 命中）。

写法要求：

- 写**相对于什么**的量级与摊销维度，不写绝对数字（绝对数字会过期，相对量级不会）。
- 必须写清副作用（例如「开启 readback 并在此后每帧持续拷贝，直到显式关闭」）。
- 必须写清应当在哪里调用（每帧 / 每次编辑 / 单次）。

```cpp
/** @brief Save the last presented frame to a PNG at @p path.
 *  @cost One full-frame GPU->CPU readback plus PNG encode; enables screen
 *        readback as a side effect (a persistent per-frame copy until
 *        disabled). Call once per capture, never per frame.
 */
```

**写不出 `@cost` 的 API，通常意味着作者没想清楚它的成本** —— 这一步本身就是设计审查。

### 5.4 命名动词对与令牌形状

当一个操作同时存在便宜与昂贵两种实现时，**不得用默认参数区分**（`getPixels(copy = true)` 让不看默认值的调用者不知道自己在付什么）。用两个名字，并让昂贵的名字读起来就昂贵：

- `pixels()` / `pixelsOwned()`
- `read()` / `readOwned()`
- 已有正例：`samples()`（span）对 `readback()`（`Result<vector>`）

更强的手段是**令牌形状**：声明为昂贵的操作，其返回值必须是不可直接读的令牌，取数据必须再调一次 —— 让「一步拿数据」这个写法不存在。已有的令牌类型是 `GpuResidentBufferView`；本规范不规定具体命名，只要求「昂贵 → 不可一步取数据」这一形状。

**builder 与 options 的使用判据**不是「昂贵就加 builder」，而是：**调用者有没有可能误以为它便宜？** 若名字已含成本（`readAllFiles`、`loadModel`），不必加仪式。`PipelineBuilder` 该有；仓里那批 `*Options` / `*Desc` 需要逐个审，其中一部分可能是纯仪式。

本仓现成的一个反例：`Graphics::saveFramePng` 返回 `bool` 并带一个昂贵副作用（启用全帧 readback，且此后每帧持续拷贝直到显式关闭）。它的形状与隔壁的 `setBackgroundColor` 无法区分。这正是 `R-COST-1` 要消除的形态 —— 至少应返回可判别结果的 `Result`，并把成本写在**这个** API 自己的 `@cost` 上。

### 5.5 两个反面

**反面一：便宜的操作装成昂贵。** 这才是真正的风险。如果每个 getter 都要 builder，所有人都会绕路 —— **这是我们自己在生产「顺手的选择」需求**，直接对抗 §4.3。

**反面二：成本不确定的 API。** 同一个 API 有时便宜（cache hit）有时昂贵（miss），必然误导。规则：**成本不确定就必须拆开** —— 拆成两个名字，或让第一步返回一个成本已确定的东西（`prepare()` 返回令牌）。「不确定」比「昂贵」严重得多，它是错误调用的真正根源。

### 规则

- **R-COST-1** 新增公共 API 必须判断其成本档位。昂贵档位必须按 §5.3 给出 `@cost`，并按 §5.4 选择命名动词对、令牌形状或 builder 之一。
- **R-COST-2** 禁止用默认参数区分成本档位。同一操作的便宜与昂贵路径必须有不同名字或不同返回类型。
- **R-COST-3** 成本不确定的 API 必须拆分，不得保留「有时拷贝、有时借用」的单一入口。
- **R-COST-4** 不得为便宜操作添加仪式（builder / `*Options` / `*Desc`）。判据是「调用者有没有可能误以为它便宜」，不是「实现是否复杂」。
- **R-COST-5** `@cost` 描述的是**该 API 当前的实测成本**。修订实现改变了量级或摊销维度时必须同步修改 `@cost`；把 `@cost` 写成不会过期的模糊话（「可能较慢」）按未声明处理。

## 7. 与「自说明代码」的关系

本文五组规则不是五件独立的事，而是同一目标的五层，按有效性递增：

| 层 | 作用 | 手段 | 是否需要使用者先知道规则 |
| --- | --- | --- | --- |
| §1 边界层 | 让「能裁」**可验证** | 符号引用图 vs include 图 | 是 |
| §2 划分层 | 让重复机制**收敛** | 单一 provider 运行时 | 是 |
| §3 声明层 | 让边界**有声明** | 六面模型 + `module-interface` | 是 |
| §4 围栏层 | 让错误选择**不可达** | 便捷原语退出 runtime profile | 否 |
| §5 成本层 | 让成本**可见** | `@cost` + 令牌形状 + 命名动词对 | **否** |

**§5 是最根本的一层**：另外四层都要求使用者先知道一条规则，而 §5 不要求。如果 `saveFramePng` 的签名、文档与返回形状都在说「我很贵」，那么一个从没读过任何文档、只看当前调用点的 agent 也不会误用它。**这就是「自说明代码」比文档和门禁更根本的原因** —— 它把约束从「需要被记住」变成「无法被忽略」。

§4 层（围栏）与 §5 层（成本）合起来还有一个推论：**这是唯一不依赖 agent 自觉的防线**。文档与门禁可以阻止违规合并，但只有形状与围栏能阻止违规**书写**。

### 8.3 强度与渐进策略

沿用本仓「门禁只查改动行 / 改动面」的既有传统（format gate、API-shape lint 都是 changed-line 语义）：

- **新增模块与被改动的模块必须满足本文全部规则。**
- **存量模块按触碰补齐**：改动某个模块时顺带补它的 `module-interface` 条目，不要求一次性补齐 56 个模块。
- **不新增第二真相源**：`module-interface` 条目的 `link` / `ecs-system` 部分必须归并既有条目，不得重复声明同一契约。
- **`full` 档保持零行为变化**（沿用既有约束）：本文任何门禁的落地都不得改变默认构建的行为或产物。

### 8.4 明确的非目标

- **不统一连接机制。** ECS、capability、event、Link、脚本、协议六种载体各自有不可替代的语义（批量类型化视图、优先级链、push/未知关注者、持久关系、游戏侧调用、外部协议）。把这六种收敛成一种是**取消**而非简化。
- **不建立统一 `IModuleInterface` 基类。** 它无法表达「提供 3 个能力 + 可选依赖 2 个 + 发 4 个事件 + 绑 1 个脚本类」而不变成 god-object，且会强制链接期耦合，抵消能力注册表存在的全部意义。
- **不把 provider 策略合并。** 见 `R-COHESION-4`。
- **不做模块内 feature flag。** 见 `R-MECH-6`。
- **不把全仓一次改完。** 见 §8.3。
