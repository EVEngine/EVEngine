## 目标与既定约束

在保留当前 ECS 类型模型的前提下，提高大批量原生数据处理能力，并打通按需场景表示。
不为对齐 UE Mass 引入 Tag、通用 GameObject 根类或全量 Archetype 迁移。
领域类型描述稳定的“是什么”；组件描述可变化的状态和正交能力；跨领域使用带代际的 Handle。
死亡、选中等动态状态仍应由组件字段表达，不通过运行时改实体 C++ 类型实现。

本文继承[领域短根继承与跨域组合架构](领域短根继承与跨域组合架构.md)的决策，不建立第二套
权威接口目录。实施公共 API、存储或跨域生命周期变更之前，必须按根 AGENTS.md 阅读相关
重构规范、Result 规范、模块契约和边界审查文件，完成 `make check` 与受影响模块契约测试。

## 当前事实

| 位置 | 已有能力 | 实施时注意 |
| --- | --- | --- |
| `external/ECS.hpp/src/ECS.hpp` | 每实体类型 Manager、分列 deque、继承 View、位图、代际 Handle、defer/commit | View 已缓存 Buffer 并按索引同步前进，不能当作逐实体类型查找 |
| `View::engageSlots` | 可默认构造组件会在建 View 时补槽 | 当前查询具有初始化效果；不能无声更换为纯过滤语义 |
| `src/modules/scene/SceneObject.h` | 节点按需创建 ECS companion | companion 不是所有仿真实体必须拥有的场景对象 |
| `SceneHost` / `SceneNode` | arena 层级、TRS、索引、dirty、reconcile | append/remove/rebuild 可使节点裸指针失效 |
| `SceneLink` / `TransformSystem` | 模块注册变换同步与存活检查 | 不等于已有批量表示选择、对象池和生命周期编排 |
| `NpcAiECS.h` | 模块自有 AI 状态、代际连接与阶段契约 | 可复用边界模式，避免再复制一份 AI 权威状态 |
| `Crowd.h` | 批量仿真、稳定逻辑 ID、紧凑槽位 | 删除后槽位改变，不能当长期实体身份 |
| `EcsGpu.h` / `Graphics.h` | 打包、范围传输、GPU resident 实例提交 | GPU 权威字段与 CPU 投影需显式同步 |

Mass 提供可借鉴的紧凑存储、预绑定数组和批处理组织；其 Tag/Archetype 分组不构成我们的
功能缺口。deque 已提供分段连续存储，但当前公开 View 没有可直接借用的整段组件 span，且
逐槽检查 dead/staging 与组件位图。是否值得优化这些成本，以配套测量为依据。

## 第一步：建立可复现的原生 ECS 基线

操作入口：[benchmark README](../../benchmarks/ecs/README.md)。构建 Release，先用 1001 个实体
跑所有场景检查奇数边界，再测 1万、10万、100万、300万。每场景独立进程，正式比较至少三轮。
同时保存 CSV、stderr、CPU/OS/配额、编译参数、引擎/ECS revision、源码 hash 和修改状态。

依次检查 dense/dense4/cold、holes50/holes90/refill、inheritance/deferred/vector。
原始 N、live 和扫描范围必须一起报告；p95 批次均值不能称为单帧 p95。
先给目标硬件定义实际阶段预算，再判定是否达标，禁止凭“创建了百万对象”宣称百万完整 NPC
可达到 60 FPS。初始创建与大批结构变化可以超出稳态预算，但需明确装载/生成的单独预算。

交付物：原始测量、同机参考、一个按预算排序的瓶颈列表；保留所有结果校验。没有预算或硬件
数据时，只报告规模增长曲线，不作生产达标承诺。

## 第二步：选择最小的存储优化

按证据选择一个方向单独实施，避免同时变更存储、查询语义和场景桥接：

| 测量现象 | 优先操作 | 验收 |
| --- | --- | --- |
| 稠密两列更新已在预算内 | 保留 View；优化实际业务计算 | 原生基线无回退，业务阶段预算下降 |
| 空洞场景成本随历史槽位增长 | 研究联合位图按 machine word 跳过无效槽位 | 稀疏场景改善，稠密/继承/生命周期无回退 |
| 创建/销毁抖动较大 | 先批量化业务操作并复用槽位，分析分配和提交成本 | 独立多进程生命周期测量及 burst 延迟达预算 |
| 稠密扫描明显落后于产品预算 | 评估显式连续页及对齐的列范围 | 相同工作量下改善，不靠跳过实体或去掉校验 |
| View 每帧准备成本较高 | 单独 profile `engageUpTo` 的全槽位补建检查，再研究不改变语义的快速路径 | 已初始化稠密列加速，空洞/补槽行为仍正确 |
| Scene 桥接耗时占主导 | 直接进入第四步 | 不为场景字符串查找成本重做 ECS 存储 |

连续页方案必须先写出与当前契约的差异：每组件的物理页边界未必对齐，应输出共同连续
区间，遇到空洞再切分；不能把 `&deque[i]` 与总剩余长度直接包装成 span。也不能在访问
热路径把整个 View 复制到 vector 后将其称为零拷贝块处理。

当前 registry 使用 deque/freelist，已有地址与 Handle 语义。若压实会移动实体/组件，先盘点
所有跨帧指针消费者，使用 Handle 重解析，并提供迁移契约测试；不默认为性能可牺牲地址稳定性。
上游 ECS 子模块的修改遵循仓库既有依赖固定与补丁流程，不复制一份新 ECS 实现。

## 第三步：收紧查询和 System 契约

先盘点真实调用点，区分“确保组件存在”与“只查询已有组件”的需求。当前默认构造组件补槽行为
已有消费者依赖；若需要纯查询，应提交具体 API 提案、成本、兼容迁移和契约测试，一次更新
实现与消费者。本文不预先引入未实现的查询方法名。

每个 System 在其代码旁记录实体家族、View、读写组件、结构修改、事件、服务、阶段与确定性。
优先显式阶段编排：输入/决策 → 仿真 → 物理结果同步 → 表示选择/同步 → Scene 变换 → 渲染。
dt、仿真 tick 和 RNG 流由调用方注入。依赖契约明确前，保持单线程所有者模型。
thread_local current Table、defer 和只读 View 都不自动提供线程安全。

若基线支持再引入批任务，需为每个任务提供不重叠写入范围、只读集合和提交边界；工作线程不
创建/销毁实体、不调用 VM、不查场景字符串索引、不回调未知代码。位图、Manager 创建、View
构造的补槽及 defer 深度也可能写共享状态，不能只证明组件行不重叠就宣布并发安全。

验收：继承查询闭包、无基类实例时的派生查询、多 Table 隔离、非默认构造组件、删除复用、
staging 可见性、嵌套 defer、失败路径和既有场景组合测试继续通过。新增并行能力另需竞争检测
和任务取消/异常/提交顺序测试。

## 第四步：仿真实体按需获得场景表示

先以一个真实领域（例如士兵）落地，不建立横跨全部模块的新对象基类。

1. 画出字段权威表。位置由 ECS、Crowd、物理或 GPU 中选定一个 owner；Scene TRS 和渲染矩阵
   是投影。物理驱动对象采用相反同步方向，同一阶段不允许双向写同一事实。
2. 沿用 `ecs::EntityHandle`、领域 generation handle 与现有持久 ID；Crowd compact index
   仅作当前批次定位，结构变化后重解析。Scene 节点地址不跨 reconcile/append/remove 保存。
3. 建立领域内表示策略：远处仅实例、近处场景表示，必要时激活物理/交互。用距离迟滞、每帧
   激活/回收预算避免边界抖动；仿真频率与显示精度分别控制。
4. 缓存经过存活验证的运行时连接，在明确阶段收集变换并批量同步；字符串 ID 用于装配、恢复
   和诊断，不逐实体逐帧查找。是否需要新的批量 API，由桥接测量证明。
5. 实例路径优先复用 `gpuDrivenSubmitOpaque` / `gpuDrivenSubmitResident`；能力缺失要返回
   明确状态并遵循已声明的产品策略，不能静默退化为海量逐对象调用。

表示连接的实施提案必须逐项定义：owner、是否拥有目标、代际失效检测、实体先销毁、表示先
销毁、对象池释放、模块卸载、热重载、存档恢复、GPU 提交完成前的资源寿命。SceneLink 当前
通用 void* 连接不能直接替代这些领域所有权契约，也不能未经盘点整体改写它。

验收：数量可控的近处表示、远处批量显示、无重复权威状态；两种销毁顺序及场景重建可恢复。
分别验证 provider 存在/缺失，以及 CPU/GPU 各自权威时的同步边界。

## 第五步：端到端预算和发布

原生微基准通过后，再新增项目级场景基准，记录 ECS、AI/Crowd、Physics、Scene、上传、渲染
各阶段 CPU/GPU 时间、p50/p95/p99、活体数量、可见数量和实际表示数量。场景图规模独立于
仿真规模。空间网格用于邻居/范围查询，与 ECS 内存页或 Chunk 分开管理。

每个变更拆成可回滚的 PR：先测量，再单项优化，再领域表示接入。比较性能时使用相同硬件、
构建和输入，不设共享 CI VM 的固定毫秒门禁；CI 先执行小规模结果校验，受控性能机器再做
预算与同机回归。实施存储/API/跨域改动时执行 `make check`、对应模块契约与组合测试，并
按根规范验证相关裁剪构建。微基准不能替代引擎 SHARED/OBJECT 和多平台契约验证。

每次交付填写：目标硬件与预算、实际基线、选择的优化、接口与生命周期影响、验证命令及结果、
未覆盖边界、回滚方式。未通过的检查明确说明，不以功能测试通过代替性能证据。
