# 感知与目标选择系统设计

日期：2026-09-14  
状态：提案（对照 UE5 GameplayTargetingSystem，基于现有 `sensing` / `Targeting*` 协议演进）  
适用范围：`sensing`、`action` 组合、RTS/武器/AI 等消费者；不含编辑器 `EditableTarget`、动画 retarget。

## 1. 结论

EVEngine **已经有**与 UE5 Targeting System 同层的协议骨架，而不是“完全没有对应功能”：

| 层 | 现状 | 对标 UE5 |
|---|---|---|
| 候选事实镜像 | `SensingWorld`（2D circle/box + tag/faction/visibleTo） | Selection 粗查的一部分 |
| 坐标安全约束解析 | `TargetingSpec` / `TargetingQuery` / `TargetingResolver` + `TargetSet` | Filter 管线的一部分 |
| 能力注入 | `ISensingCandidateProvider`、`ILineOfSightQuery` | Task 依赖的 World/Subsystem 服务 |
| Action 组合 | `TargetingMode::{None,Explicit,Query}` + `SensingTargetingAdapter` | GA `PerformTargetingRequest` 的薄适配 |

真正缺的是 UE5 最有用的那一层：**可数据驱动的 Select → Filter → Sort 任务管线 + Preset + 带分数的排序结果**，以及把现有双轨 API、`spatial` 后端、更多查询形状和消费者桥接补齐。

**不要**照搬 UE5 的 Actor/`FHitResult` 中心模型，也不要把“谁最值得打”写死进 `sensing` 核心。架构已明确：`sensing` 只返回候选与可解释分数；技能 / 武器 / 卡牌 / RTS 命令保留最终选择语义（见 checklist §23、`组合式游戏机制架构.md` §5.7）。

## 2. UE5 GameplayTargetingSystem 要点

插件提供数据驱动请求：

1. **`UTargetingPreset`**：有序 Task 列表（Selection → Filter → Sort）。
2. **`FTargetingSourceContext`**：源 Actor / 位置 / Instigator / Socket。
3. **`UTargetingSubsystem`**：同步 `Execute*` 或异步 `StartAsync*`，用 `FTargetingRequestHandle` 取结果并释放。
4. **内置任务**：AOE 选择、基础过滤、按距离排序等；可扩展自定义 Filter/Sort。
5. **结果**：候选列表 +（Sort 后）每项 `Score`；Gameplay Ability 可走 `PerformTargetingRequest` / `PerformFilteringRequest`。

价值不在“能查到附近单位”（我们已有），而在：

- 同一套 Preset 可被技能、AI、投射物、UI 复用；
- 选择 / 过滤 / 打分可插拔，不改调用方；
- 排序分数可调试、可解释。

## 3. 现状与差距

### 3.1 已具备（保留）

- 强类型坐标空间：`World2D/3D`、`Grid2D/3D`，禁止隐式混用。
- `TargetingSpec`：domain、min/maxCount、range、required/excluded tags、zone、world/grid area、LOS 模式。
- `TargetSet`：subjects + 可选 primary / point / area（resolver **从不**隐式设 primary）。
- Capability：缺 provider → `Unsupported`，不假装空成功。
- Physics LOS adapter（World3D）；Action Query 模式已接入。
- RTS `CombatFireSystem` 用 `SensingWorld.circle` + 局内 priority 表做自动索敌（策略在 RTS，不在 sensing）。

### 3.2 主要缺口

| 缺口 | 说明 |
|---|---|
| 双轨未统一 | `SensingWorld` 与 `ISensingCandidateProvider` / `TargetingResolver` 无生产桥；RTS 走前者，Action 走后者 |
| 无 Preset / Task 管线 | 约束写死在 `TargetingSpec` + resolver 硬编码过滤；无法像 UE5 那样组合 Selection/Filter/Sort |
| 无排序分数 | `maxCount` 是硬失败（`PreconditionViolation`），不是 “取 top-K”；`setPrimary` API 在但 resolver 不用 |
| 查询形状偏少 | `SensingWorld` 仅 2D circle/box；`WorldArea` 有 sphere/box3D，但无 cone/sector/capsule/sweep；无朝向 |
| 未用 `spatial` | 模块 `DEPS spatial`，实现仍是 `std::map` 线性扫描 |
| 无脚本 Targeting 绑定 | 仅 `Sensing`/`SensingWorld`；`Targeting*` 无 Squirrel API |
| 无异步请求 | 与当前确定性同步仿真一致；异步可后置，不必第一期跟 UE5 |
| 周边未接满 | 武器 lock-on、aim assist、npc_ai PerceptionMemory、Zone→sensing 绑定仍在各自 gap 文档中 |

### 3.3 明确不放进 sensing 核心

以下保持**游戏侧 / 领域模块**策略（可用 Sort Task 或 policy 表达，但不内置题材语义）：

- Soft-lock / sticky aim / magnet / 手柄吸附
- 威胁表、仇恨、职业克制
- 导弹制导轨迹（武器模块已有数据模型草案）
- UI 卡牌拖拽合法性（`card` 只管手势）

## 4. 目标架构

在现有协议之上增加一层 **Targeting Pipeline**，语义对齐 UE5，形状对齐 EVEngine：

```text
SourceContext + TargetingPreset
        │
        ▼
┌───────────────────┐
│ Selection tasks   │  → 候选集合（可多源合并）
├───────────────────┤
│ Filter tasks      │  → 剔除 / 约束（domain、tag、LOS、cone…）
├───────────────────┤
│ Sort / Score tasks│  → 稳定排序 + 可解释分数；可选 truncate top-K
└───────────────────┘
        │
        ▼
RankedTargetSet  (subjects + optional scores + optional primary)
```

### 4.1 核心类型（拟新增，仍在 `eve::sensing`）

```cpp
/** @brief Who/where the request starts; never an ECS entity pointer. */
struct TargetingSourceContext {
    SubjectRef origin;                 // required, non-nil
    TargetLocation originLocation;     // space must match preset/spec
    std::optional<SubjectRef> instigator;
    std::optional<std::string> socketOrBone; // opaque token for adapters
    // no Actor*, no SceneObject*, no UI handles
};

enum class TargetingTaskKind : std::uint8_t { Selection, Filter, Sort };

/** @brief One ordered step in a preset. Implementations are capability-backed or pure functions. */
class ITargetingTask {
public:
    static constexpr const char* capabilityName = "eve.sensing.ITargetingTask";
    virtual ~ITargetingTask() = default;
    [[nodiscard]] virtual TargetingTaskKind kind() const noexcept = 0;
    [[nodiscard]] virtual LogicalId taskId() const noexcept = 0;
    [[nodiscard]] virtual Result<void> execute(TargetingRequestState& state) const = 0;
};

/** @brief Data-driven ordered task list; owned as Definition or runtime value. */
struct TargetingPreset {
    LogicalId id;
    std::uint32_t schemaVersion = 1;
    std::vector<LogicalId> taskIds; // resolved via registry / Definition
};

struct ScoredTarget {
    SubjectRef subject;
    float score = 0.f;               // higher is better unless Sort says otherwise
    std::string scoreReason;         // stable diagnostic token, not free-form essay
};

class RankedTargetSet {
public:
    [[nodiscard]] Result<void> add(ScoredTarget item);
    [[nodiscard]] Result<void> setPrimary(SubjectRef subject); // still explicit
    [[nodiscard]] std::span<const ScoredTarget> ranked() const noexcept;
    [[nodiscard]] TargetSet asTargetSet() const; // strips scores for Action compatibility
};
```

`TargetingResolver::resolve` **保留**为“单 Spec 硬过滤”路径（现有测试与 Action 不破）。新入口：

```cpp
class TargetingPipeline {
public:
    [[nodiscard]] Result<RankedTargetSet> execute(const TargetingSourceContext& source,
                                                  const TargetingPreset& preset) const;
};
```

### 4.2 内置任务（第一期最小集）

| Kind | Task id（稳定） | 行为 |
|---|---|---|
| Selection | `sensing.select.provider` | 调 `ISensingCandidateProvider`（或 `SensingWorld` 桥） |
| Selection | `sensing.select.area` | 按 `WorldArea`/`GridArea` 广相 |
| Filter | `sensing.filter.spec` | 复用现有 `TargetingSpec` 匹配 |
| Filter | `sensing.filter.los` | 调 `ILineOfSightQuery` |
| Filter | `sensing.filter.cone` | 朝向 + 半角 + 距离（新增几何） |
| Sort | `sensing.sort.distance` | 近→远；score = −distance 或 `1/(1+d)`（文档固定一种） |
| Sort | `sensing.sort.score_key` | 读候选自定义 float 属性键（由 provider 投影） |
| Sort | `sensing.sort.truncate` | top-K；**替代**当前 maxCount 硬失败的“选取”语义 |

自定义任务通过 `ITargetingTask` + registry / Definition 注册；题材策略（威胁、职业）落在游戏模块，不进核心。

### 4.3 统一候选源：桥接双轨

```text
SensingWorld  ──adapter──▶  ISensingCandidateProvider
ECS View 镜像 ──adapter──▶  ISensingCandidateProvider
测试 fixture   SensingCandidateProvider（已有）
```

- `SensingWorldCandidateProvider`：把 `SensingWorld` 的 subject 事实投影为 `TargetCandidate`（faction→domain 映射由 adapter 参数给出，不写死 RTS）。
- RTS `CombatFireSystem` 逐步改为：镜像仍可写 `SensingWorld`，索敌走 `TargetingPipeline` + preset（priority 表变成 Sort task 或 RTS 侧 post-pass）。
- Action `SensingTargetingAdapter` 可增加 `resolvePreset(...)` 而不删除现有 `resolve(query)`。

### 4.4 几何与空间后端

- 扩展 `WorldArea`：`cone2D` / `sector3D`（origin + forward + halfAngle + radius）；可选后续 capsule。
- Selection 广相走 `spatial`（hash/quad/octree），Filter 再精筛；保持 sensing header 不 include physics/scene。
- `SensingWorld` 保留脚本友好 API；内部可改为 provider 前端，避免两套真相。

### 4.5 异步

第一期 **只做同步**（与确定性仿真、现有 Action/RTS tick 一致）。若后续需要：

- `TargetingRequestHandle` + 显式 `release`；
- 完成回调禁止在持锁时调未知脚本；
- 异步结果不得隐式写 ECS；只交付 owning `RankedTargetSet`。

对标 UE5 的 async 是可选增强，不是对等必要条件。

### 4.6 脚本与 Definition

- Definition：`eve.targeting.preset` schema（task id 列表 + 参数表）。
- Squirrel：`sensing.executePreset(source, presetId) → RankedTargetSet`；保留现有 `circle`/`box`。
- 分数与 reason 暴露给调试 / MCP，便于对标 UE5 draw-debug。

## 5. 与现有架构规则的对齐

| 规则 | 本设计如何满足 |
|---|---|
| sensing 不决定目标价值 | Sort 只产生分数与顺序；primary 仍显式；题材权重在游戏 Sort task / policy |
| 短根 + Link，无 GameObject | `SubjectRef` / `ZoneRef`；无 Actor 大根 |
| Capability 注入，无向上 include | LOS / spatial / 自定义 task 均 capability 或 registry |
| `Result` + `[[nodiscard]]` | Pipeline、task、preset 加载全部结构化失败 |
| 可选依赖可观测 | 缺 provider / LOS / task → `Unsupported`，不空成功 |
| 持久化 | Preset schema id + version + unknown-field 策略；`RankedTargetSet` 本身通常不入档 |
| 确定性 | 同步路径；同分 tie-break 用 `SubjectRef` 字典序（与现 `SensingWorld` distance+id 一致） |

## 6. 分阶段实施

### Phase 0 — 文档与契约（本提案）

- 固定词汇：`SourceContext` / `Preset` / `Task` / `RankedTargetSet`。
- 标明 `TargetingResolver` 为兼容路径；新功能走 Pipeline。

### Phase 1 — 统一候选源 + top-K（高杠杆、侵入小）

1. `SensingWorldCandidateProvider` 实现 `ISensingCandidateProvider`。
2. `TargetingSpec` 增加可选 `SelectionPolicy::{FailIfOutOfRange, TruncateToMax}`（默认保持 Fail，不破现有测试）。
3. Sort-by-distance + truncate 作为 resolver 可选后处理，或最小 `TargetingPipeline` 只含 `filter.spec` + `sort.distance` + `truncate`。
4. 测试：桥接、top-K、同分 id 稳定序；Action Query 回归。

### Phase 2 — Preset / Task 注册表

1. `ITargetingTask` + 进程内 registry（Definition 热重载 generation）。
2. 内置 Selection/Filter/Sort 任务表（§4.2）。
3. `cone` 几何 + Filter task。
4. 用户文档 `docs/usr/modules/sensing.md`。

### Phase 3 — 消费者迁移

1. RTS 索敌 preset 化（priority 表 → sort 参数或 RTS Sort task）。
2. Weapon lock 目标获取改走 Pipeline；aim assist 仍游戏侧。
3. npc_ai：sensing 变化 → PerceptionMemory adapter（已有 spec）。
4. Zone 编辑器绑定 → runtime zone membership 投影到 candidate.zones。

### Phase 4 — 性能与调试

1. `spatial` 广相；大数据量基准。
2. MCP / debug overlay：画出 area、cone、ranked scores。
3. 评估异步请求是否值得（多数确定性玩法可能永不需要）。

## 7. API 草图（脚本）

```squirrel
local sensing = eve.Sensing();
local world = sensing.newWorld().value;
// 现有路径仍可用
local n = world.circle(x, y, 12.0, "enemy", "", "", "", "player", 8).value;

// 新路径：数据驱动
local ranked = sensing.executePreset({
    origin = "unit.hero",
    x = x, y = y, space = "world2d"
}, "preset.melee_cleave").value;

local primary = ranked.primary;      // 显式策略设好才有
local best = ranked.at(0);           // score + subject + reason
```

C++ Action：

```cpp
definition.targetingMode = TargetingMode::Preset; // 新增，与 Query 并存
definition.targetingPresetId = LogicalId::parse("preset.skill.fireball").value();
```

## 8. 测试与验收

- 合同测试：同一 Preset 在 fixture provider 上确定性输出（含 score、tie-break）。
- 缺 capability：`Unsupported` 可观测。
- 坐标混用：`Rejected` / `InvalidArgument`。
- `TruncateToMax` vs `FailIfOutOfRange` 行为对照。
- RTS / Action 回归：旧路径默认行为不变。
- 架构门：`ARCHITECTURE_BASE=HEAD make check/architecture-contracts`；`module_depgraph --check` 无 sensing→physics/scene 泄漏。

## 9. 非目标

- 复制 UE5 `FHitResult` / Actor 数组作为一等结果。
- 在 sensing 内实现完整瞄准辅助或摄像机 soft-lock。
- 用一个 `gameplay` 大模块吞掉 sensing/action/weapon。
- 把 `EditableTarget` / 动画 retarget 混进本协议。

## 10. 建议落地顺序（工程判断）

若只做一个 PR 的增量，优先 **Phase 1**：`SensingWorld`→provider 桥 + `TruncateToMax`/`sort.distance`。这能立刻让 Action 与 RTS 共用一套候选事实，并消除 “maxCount 只能整组失败、不能取最近 N 个” 的协议尴尬——这正是 UE5 Sort+结果列表日常在做的事，又完全符合 “sensing 不决定价值、只提供有序候选” 的现有宪章。

Preset/Task 完整化放 Phase 2，避免一次性把 Definition、脚本、RTS、武器全扯进同一 PR。
