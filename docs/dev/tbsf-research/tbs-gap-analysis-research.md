## READ FIRST — retrieval limitation that governs every claim in this document

This research ran in an environment with **no working page retrieval**:

- `web_fetch` failed on **every** URL attempted — `github.com`, `assetstore.unity.com`, `discussions.unity.com`, `www.redblobgames.com`, `en.wikipedia.org`, `raw.githubusercontent.com` — always with `URL hostname "..." resolves to a non-public IP address`.
- Direct HTTP from the shell also failed: `curl` returned `schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS`; `Invoke-WebRequest` returned a connection closed on receive.

**The only working channel was the `web_search` tool, which returns result titles and URLs but not page bodies.** Roughly **80 search calls / ~270 queries** were spent across the two targets and three parallel workstreams.

**Consequence:** *no cited page was opened.* Almost nothing below about what a vendor or author actually says is verified content. What is attested is (a) that a page exists at that URL, (b) its title/slug, and (c) in some cases a sentence or code fragment the search index surfaced in the title field, quoted verbatim.

Every claim carries a tag:

| Tag | Meaning |
|---|---|
| **SNIPPET** | Body text (a sentence, rule number, or code fragment) appeared verbatim in a search result for that URL. Closest to readable evidence. Context still unknown. |
| **TITLE** | The URL and its title/slug confirm the page covers this topic. The *detail* is my summary and may not match the author's wording. |
| **WEAK** | Title-level only **and** the source is weak (forum post, SEO farm, aggregator, marketplace listing, AI-generated repo). Treat as a lead, never as authority. |
| **INFER** | My own reasoning or domain knowledge. **Not sourced in this session.** |
| **UNVERIFIED** | Could not confirm at all. Recorded so the gap is visible rather than silently filled. |

**Do not encode any numeric or behavioural mechanic from this document into engine requirements without re-reading the cited page with a working fetch path.** The "Confidence and gaps" section lists the highest-value unread primaries.

## 2.1 Turn scheduling patterns

### The design space

- The Chalmers/ITU **game design patterns** catalogue has a dedicated **"Turn Taking"** pattern — **TITLE** — [virt10 — Turn Taking](http://virt10.itu.chalmers.se/index.php?title=Turn_Taking&direction=next&oldid=973&printable=yes), a mirror at [few.vu.nl](http://few.vu.nl/~eliens/papers/media/@s5-pattern-turntaking.html), plus the named consequences **First Player Advantages** — [virt10](http://virt10.itu.chalmers.se/index.php?title=First_Player_Advantages&direction=prev&oldid=11112&printable=yes) — and **Analysis Paralysis** — [virt10](http://virt10.itu.chalmers.se/index.php?title=Analysis_Paralysis&direction=next&oldid=10213&printable=yes) — with an accessible restatement at [League of Gamemakers](https://www.leagueofgamemakers.com/designing-games-to-prevent-analysis-paralysis-part-2/).

### Side-alternating / IGOUGO
- **INFER** — the default model: a player takes all their units' actions, then the opponent does. *Advance Wars*/*Nintendo Wars* and *Fire Emblem* (player phase / enemy phase) are the archetypes; *Civilization* is IGOUGO at the empire level.
- *Advance Wars* / *Nintendo Wars* structure — **TITLE** — [Nintendo Wars (pt.wikipedia)](https://pt.m.wikipedia.org/wiki/Nintendo_Wars), [Advance Wars: Dual Strike (Giant Bomb)](https://giantbomb.com/wiki/Games/Advance_Wars_Dual_Strike), [archived Wikipedia article](https://webarchiveweb.wayback.bac-lac.canada.ca/web/20051215000000/http://en.wikipedia.org/wiki/Advance_Wars).
- *Fire Emblem* player/enemy phases are documented on dedicated "Turn" pages — **TITLE** — [Fire Emblem Wiki](https://fireemblemwiki.org/w/index.php?title=Turn&diff=269503&oldid=255190), [Fire Emblem Fandom](https://fireemblem.fandom.com/wiki/Turn).
- *Wargroove* is the modern Advance-Wars-lineage exemplar; Chucklefish discussed its development — **TITLE** — [Game Developer](https://www.gamedeveloper.com/design/watch-chucklefish-s-ceo-and-tech-director-discuss-i-wargroove-s-i-development).
- **INFER** — the structural cost of IGOUGO is that the non-active side has no agency during the opponent's turn, so "reaction" must be modelled as pre-committed state (overwatch) — see §2.2.

### Initiative / CTB (Charge Time Battle)
- **SNIPPET** — *Final Fantasy X* "uses a turn-based battle system called the Conditional Turn-Based Battle, or CTB for short" — [Gamer Guides — FFX HD battle system](https://www.gamerguides.com/final-fantasy-x-hd/guide/introduction/gameplay/battle-system). Corroborating concept page: [Conditional Turn-Based Battle (Giant Bomb)](https://giantbomb.com/wiki/Concepts/Conditional_Turn_Based_Battle).
- *Final Fantasy X* has a per-action priority stat with its own reference page, **"Rank"** — **TITLE** — [Final Fantasy Wiki — Rank (FFX)](https://finalfantasy.fandom.com/wiki/Rank_(Final_Fantasy_X)); main system page [Final Fantasy X battle system](https://finalfantasy.fandom.com/wiki/Final_Fantasy_X_battle_system).
- *Final Fantasy Tactics* has a stat literally named **Charge Time (CT)** — **SNIPPET** — [Game8 — CT (Charge Time) Explained](https://game8.co/games/Final-Fantasy-Tactics/archives/543470). Corroboration: [altema FFT battle system](https://altema.jp/fft/battlesystem). The reverse-engineering community has derived the *actual accumulation behaviour* in [FFHacktics — "Charge Times (Average Turn Time)"](https://ffhacktics.com/smf/index.php?topic=4384.0) — **TITLE**.
- **INFER** — the shared mechanism (formulas **UNVERIFIED**): each combatant accumulates a "time until next turn" value derived from a speed stat; the scheduler repeatedly picks the smallest and advances the clock; acting also sets that unit's next arrival. ### ATB (Active Time Battle)
- **SNIPPET** — the design origin is documented in a press headline: *"Final Fantasy's ATB battle system was originally inspired by race cars"*, slug naming FFIV — [Rock Paper Shotgun](https://www.rockpapershotgun.com/final-fantasy-ivs-active-time-battle-system-was-inspired-by-race-cars).

- **INFER** — **ATB vs CTB is the architecturally important distinction:** ATB is a *real-time accumulator* whose gauges fill against wall-clock time, with Active/Wait sub-modes deciding whether gauges freeze while menus are open. ### What scheduling implies for the runtime
- A **turn/initiative queue** with deterministic tie-breaks — not just a "current player" field.
- A **pluggable ordering policy** behind one interface, because shipped games change their model (Civ exposes **Simultaneous Turns vs Dynamic Turns** as a user-selectable mode — **SNIPPET** — [Arqade](https://gaming.stackexchange.com/feeds/question/347352); BattleTech has a long-running *official alternatives* thread, i.e. initiative is a tunable rules module — **TITLE** — [battletech.com forums](https://battletech.com/forums/index.php/topic,54827.msg1267177.html)).
- A **phase/segment state machine** over subsets of units, with per-unit **per-phase** "already acted" flags.
- A re-derivable **queue projection exposed to the UI** (FFX's displayed turn list is the classic case).
- An **ordered command buffer** that can be executed, replayed, and (WEGO) previewed.
- **Interrupt/entry points** in the schedule (§2.2), including **out-of-band group insertion** (pods).
- Sources: [Turn Order and Structure](https://www.taylorfrancis.com/chapters/mono/10.1201/9780429430701-2/turn-order-structure-geoffrey-engelstein-isaac-shalev) — **TITLE**; [virt10 Turn Taking](http://virt10.itu.chalmers.se/index.php?title=Turn_Taking&direction=next&oldid=973&printable=yes) — **TITLE**; [DTIC AD1161430](https://apps.dtic.mil/sti/trecms/pdf/AD1161430.pdf) — **SNIPPET**; [BGA "why a game state machine" (PDF)](http://en.doc.boardgamearena.com/images/9/98/4-gamestates.pdf) — **TITLE**.

- (b) XCOM 2's action-point ambiguity is documented above (§2.1.6) and in [XCOM Wiki — Turn (XCOM 2)](https://xcom.fandom.com/wiki/Turn_(XCOM_2)) — **TITLE**.

### Reactions, interrupts and opportunity attacks
- **INFER** — a reaction system needs three things the base turn loop does not provide: (1) a **trigger** evaluated on state changes; (2) an **interrupt window** inside another actor's action where the trigger's owner may pre-empt; (3) an **ordering policy** when several triggers fire at once.
- **The most rigorously specified public model of (3) is Magic: The Gathering's stack + priority.** **SNIPPET** — retrieved rule text includes *"117.3b The active player receives priority after a spell or ability (other than a mana ability) resolves"* — [Magic Comprehensive Rules 2025-06-06 (PDF)](https://media.wizards.com/2025/downloads/MagicCompRules%2020250606.pdf). Other retrieved CR fragments: *"116.2c Turn-based actions happen automatically when certain steps or phases begin"* — [MagicCompRules 2018-07-13](https://media.wizards.com/2018/downloads/MagicCompRules%2020180713.pdf) — **SNIPPET**.
- **SNIPPET** — MTG separates **three** resolution mechanisms, not one event bus: **replacement/prevention effects** (ordered by an explicit affected-party choice procedure — CR 616.1, [MagicCompRules 2015-01-23 CS](https://wiki.mtgjudge.cn/_media/magiccomprules_20150123_cs.pdf#41#20)), **state-based actions** performed as a single uninterruptible event (CR 116.5, [MagicCompRules 2014-07-18](https://media.wizards.com/images/magic/tcg/resources/rules/MagicCompRules_20140718.pdf#11#6)), and **triggered abilities on a LIFO stack** (CR 603.x). Special actions bypass the stack (CR 405.6d, [MagicCompRules 2019-05-03](https://media.wizards.com/2019/downloads/MagicCompRules%2020190503.docx#51#14)). **INFER** — that "three mechanisms" synthesis is the architectural takeaway.
- **SNIPPET** — MTG's triggers key on **state transitions**, so a continuously-true predicate cannot retrigger — *"becomes tapped"* fires only on an actual untapped→tapped change ([MagicCompRules 2016-01-16 CS](https://wiki.mtgjudge.cn/_media/magiccomprules_20160116_cs.docx?rev=1453179506#48#18)).
- **SNIPPET** — **delayed triggers are first-class objects with provenance** — CR 603.7d (a delayed triggered ability's source) ([MagicCompRules 2019-05-03](https://media.wizards.com/2019/downloads/MagicCompRules%2020190503.docx#51#19)); and CR 403.4: a permanent that leaves and re-enters is a **new object** with no relation to the previous one ([MagicCompRules 2014-07-18](https://media.wizards.com/images/magic/tcg/resources/rules/MagicCompRules_20140718.docx#45#13)).
- **SNIPPET** — **target/choice legality is re-validated at resolution time**, and choices may be made *during* resolution — CR 608.2b ([MagicCompRules 2014-02-01](https://media.wizards.com/images/magic/tcg/resources/rules/MagicCompRules_20140201.pdf#21#17)), CR 608.2d ([MagicCompRules IT 2019-01-25](https://blogs.magicjudges.org/translatedrules/files/2019/01/MagicCompRules_2020190125_IT.pdf#31#27)).
- **Overwatch / reaction fire / return fire is a common shipped-game pain point.** **SNIPPET** — the Phoenix Point forums contain a thread literally titled *"Return fire fail"* — [forums.snapshotgames.com](https://forums.snapshotgames.com/t/return-fire-fail/11434/22) — and longer design arguments at ["BB3 Some thoughts on Return Fire"](https://forums.snapshotgames.com/t/bb3-some-thoughts-on-return-fire/2207/16) and ["That return fire"](https://forums.snapshotgames.com/t/that-return-fire/429/23) — **WEAK**. ### Determinism and non-reentrancy of reactions
- **INFER** — rules that keep a reaction system deterministic (only the *ordering/priority* half is sourced, via MTG CR above):
  1. **Single trigger queue** — reactions are *enqueued*, never executed inline from inside another reaction.
  2. **Total order on simultaneous triggers** — fixed by (phase, initiative index, side, stable content ordinal). Never map/pointer iteration order, never timestamps.
  3. **Once-per-window guards** and a **depth cap**.
  4. **Resolve after the triggering step completes**, so the world is never observed half-mutated.
  5. **No RNG inside trigger ordering**; if RNG is needed it comes from a named, seeded stream drawn in the fixed scheduled order.
  6. **Loop/non-termination detection** with a defined resolution (cap, flag, or draw) rather than a stack overflow.
- **SNIPPET** — deferred-event design exists as a named pattern in a mainstream engine: [Roblox — Deferred engine events](https://raw.githubusercontent.com/Roblox/creator-docs/refs/heads/main/content/en-us/scripting/events/deferred.md). A shipped library tracked *"improved event recursion solution"* as an issue: [ModiBuff issue #13](https://github.com/Chillu1/ModiBuff/issues/13) — **WEAK**.
- **SNIPPET** — a tactical-game project tracked a **stack resolution system** as an explicit work item: [anchapin/planar-nexus issue #8](https://github.com/anchapin/planar-nexus/issues/8) — **WEAK**.
- **INFER — the single most important structural finding of Target 2:** **a reaction/interrupt system is the most architecturally invasive requirement in the whole survey.** It forces the scheduler to *suspend an actor mid-action, run a nested resolution, then resume or invalidate*. A plain "for each unit, run its turn" loop cannot express it, and nearly every scheduling model above needs it (opportunity attacks, reaction fire, overwatch, snap-to-action, counterattacks).

## 2.3 Determinism, replay and rollback

### Lockstep determinism
- **TITLE** — the classic primary-engineering write-up is the Age of Empires piece **"1500 Archers on a 28.8k Modem"**, describing deterministic lockstep, command turns, and why all clients must produce identical results — [PDF mirror (WPI course copy)](http://web.cs.wpi.edu/~claypool/courses/4513-B03/papers/games/aoe.pdf).
- **TITLE** — a practitioner reference dedicated to the technique: [Gaffer On Games — Deterministic Lockstep](https://www.gafferongames.com/post/deterministic_lockstep/) (Fiedler), plus **WEAK** a Spanish-language thesis that names the technique explicitly (*"Es aquí cuando nació el Deterministic Lockstep…"*) — [burjcdigital.urjc.es](https://burjcdigital.urjc.es/server/api/core/bitstreams/6de759e4-0ebf-4d11-bb5b-12f4614d8d17/content).
- **TITLE** — a shipped-game GDC talk on cross-platform determinism: [GDC Vault — Cross-Platform Determinism in Warhammer Age of Sigmar: Realms of Ruin](https://gdcvault.com/play/1034229/Cross-Platform-Determinism-in-Warhammer); related determinism talks on [For Honor](https://www.gdcvault.com/play/1026322/) and [For Honor's deterministic vs replicated AI](https://www.gdcvault.com/play/1024454/).

### Fixed-point vs floating point
- **INFER** — floating-point results are not guaranteed identical across compilers/CPUs/SIMD paths, which breaks bit-exact lockstep and exact replays. TBS engines that want either use **(a)** fixed-point/integer math for all simulation arithmetic, or **(b)** strictly constrained FP (no fast-math, fixed op order, no x87 excess precision) and accept a narrower platform matrix **with a written policy**.
- **TITLE** — evidence that this is a real, acknowledged blocker: a UE5 library marketed specifically as a **fixed-point math library for determinism** ([Parad0x84/DeterministicMath](https://github.com/Parad0x84/DeterministicMath)); Photon **Quantum** documents fixed-point math as a core ECS feature ([Photon Quantum — Fixed Point Math](https://doc.photonengine.com/zh-cn/quantum/v3/manual/quantum-ecs/fixed-point)); a platform-divergence write-up ([Microsoft — Sinus-Berechnung auf der XBox](https://learn.microsoft.com/bg-bg/archive/blogs/twendel/sinus-berechnung-auf-der-xbox-edt-120909)); a float non-associativity paper ([arXiv 2104.06262](https://export.arxiv.org/pdf/2104.06262#5#2)); and a project that keeps a **float-parity policy document** in-repo ([crimson float-parity-policy.md](https://github.com/banteg/crimson/blob/master/docs/rewrite/float-parity-policy.md#1)).
- **SNIPPET** — a UE5 rollback implementation states its approach in its own blurb: *"fixed-step simulation, SaveGame-reflection state capture, UDP transport with input redundancy and reliable ACKs"* — [gregorik/Rollback-Core](https://github.com/gregorik/Rollback-Core).

### Seeded RNG streams
- **INFER** — one global RNG shared by everything is the standard source of desyncs and irreproducible replays. The robust pattern is **named, independently seeded streams** (combat, AI, mapgen, cosmetic/FX), each serialised into save/replay state, with cosmetic streams explicitly excluded from simulation state.
- **TITLE** — multiple streams/sequences as a first-class RNG feature: [PCG — Useful Features: multiple streams, sequences](https://pcg-random.org/useful-features.html#multiple-streams-sequences). **WEAK** — a stream-isolation pattern doc: [tachyon-beep rng-isolation-patterns.md](https://github.com/tachyon-beep/skillpacks/blob/c284720d484f61e7399699c53f566746f289e1c6/plugins/axiom-determinism-and-replay/skills/using-determinism-and-replay/rng-isolation-patterns.md#1).

### Commands, event sourcing, snapshots
- **INFER** — two persistence models. **Command log**: store the ordered commands, re-simulate to reconstruct state — tiny, replayable, spectatable, but *any* simulation-semantics change invalidates every old log. **Full-state snapshot**: store the state — robust, undo-friendly, survives refactors, but large and schema-fragile. **Hybrid (snapshot + recent command log) is the reference architecture.**

### Undo
- **INFER** — undo is cheap *only* if you already have one of: (a) full state snapshots per command (memory-heavy, trivially correct); (b) command log + re-simulation (cheap in memory, requires determinism); (c) exact inverse commands (smallest, hardest — every command must define a perfect inverse). **Undo is therefore a determinism forcing function: it is the earliest feature that makes you commit to a determinism story.**
- **SNIPPET — the best concrete evidence for (a) over (c):** a *shipped* Into the Breach bug where the **"[Undo move] button can make smoke disappear"** — [Subset Games forum](https://subsetgames.com/forum/viewtopic.php?p=118198). **INFER** — this is precisely the failure mode of inverse-command undo: a *stateful derived subsystem* (smoke/fire/LOS cache) was not restored. Undo must restore **state**, including derived caches, not just invert commands.
- **TITLE** — related: [GDC Vault — Into the Breach Design Postmortem](https://gdcvault.com/play/1026333/-Into-the-Breach-Design).

### Rollback netcode and its applicability to TBS
- GGPO is the reference rollback implementation — **TITLE** — [ggpo.net](https://www.ggpo.net/), [GGPO README](https://raw.githubusercontent.com/pond3r/ggpo/master/doc/README.md#1). Tuning/configuration docs: [rollback-netcode/docs/configuration-tuning.md](https://github.com/someusername6/rollback-netcode/blob/HEAD/docs/configuration-tuning.md) — **TITLE**; prediction as a separately configurable layer: [lightyear PredictionConfig](https://docs.rs/lightyear/0.17.0/lightyear/client/prediction/plugin/struct.PredictionConfig.html#1) — **TITLE**.
- **INFER** — rollback exists to hide *latency* in games where input must be applied immediately (fighters, RTS). In a **turn-based** game the opponent is not acting during your turn, so latency is absorbed by the turn structure itself; rollback buys almost nothing and costs save/restore of the entire tactical state. **No source found that argues "TBS doesn't need rollback" — this conclusion is my inference only.** The defensible recommendation is: *document the decision not to implement rollback, but still build the determinism/snapshot prerequisites, because undo, replay and desync detection need them anyway.*
- **SNIPPET** — desync detection and recovery tracked as an explicit milestone: [freeciv-nostr issue #18 "Phase 3.4: Desync Detection & Recovery"](https://github.com/average-gary/freeciv-nostr/issues/18) — **WEAK**.

### What determinism implies for the runtime
- Injected simulation clock; fixed-step turn advance; no wall-clock reads inside simulation.
- A deterministic numeric substrate (fixed-point/integer) with a written float-parity policy.
- A **simulation-only RNG API** with named streams, serialised in saves/replays, plus a stored match seed.
- Canonical, order-stable serialisation and a **state hash** for desync detection and replay verification.
- An ordered command pipeline with a stable total order.
- A published **determinism contract** stating what is bit-exact and what is tolerant.
- Sources: [1500 Archers](http://web.cs.wpi.edu/~claypool/courses/4513-B03/papers/games/aoe.pdf), [Gaffer On Games](https://www.gafferongames.com/post/deterministic_lockstep/), [PCG streams](https://pcg-random.org/useful-features.html#multiple-streams-sequences), [GDC — Warhammer AoS determinism](https://gdcvault.com/play/1034229/Cross-Platform-Determinism-in-Warhammer), [opencombatengine ADR-0059](https://github.com/jamesplotts/opencombatengine/blob/main/docs/adr/0059-combat-serialization.md) — all **TITLE**.

## 2.4 AI for TBS

### Choosing a technique by scale
- **INFER** — rough guidance:
  - **FSM / simple rules** — few unit types, no planning.
  - **Behaviour trees** — reactive, readable, designer-authored unit behaviour; weak at long-horizon goals.
  - **Utility AI** — many heterogeneous considerations scored into one number; scales to "many units, many options", easy to tune; poor at multi-step plans.
  - **HTN** — hierarchical, hand-authored decomposition; cheap and predictable; brittle when the world deviates.
  - **GOAP** — planner over action preconditions/effects; flexible and emergent; cost grows with the action graph.
  - **Minimax / alpha-beta** — strongest in small, well-defined tactical spaces.
  - **MCTS** — strong where branching is large and playouts are affordable; usually too slow for a whole TBS turn, viable for local sub-problems.
  - **Influence maps** — the standard *spatial* layer under any of the above; lets hundreds of units share one cheap evaluation.

### Making TBS AI fast enough for many units
- **INFER** — two-tier architecture is the defensible reading of the evidence: **a cheap global tier** (influence/threat/control fields computed once per turn and read by everyone) **plus a per-unit tier** (utility scoring over a small candidate action set). The expensive part is shared, not repeated. Expensive reasoning (MCTS, GOAP search, alpha-beta) must be **budgeted and amortised** — reserved for a small "command" set of units, a few high-stakes decisions per turn, or abstracted action groups. Hierarchical decomposition is the recurring answer to scale (HTN decomposition, node grouping, squad-level plans are three names for one idea: decide coarsely, refine locally).
- **TITLE** — the best source for time-sliced/async work in the AI/nav pipeline: [Havok — Asynchronous Navigation Processing: Stable AI Pathfinding in Games](https://www.havok.com/blog/asynchronous-navigation-processing/).
- **TITLE** — terrain/spatial analysis for game AI: [Northwestern EECS 395 — Terrain Analysis](https://users.cs.northwestern.edu/~forbus/395gai/lectures/L5_Terrain_Analysis.pdf).
- **TITLE** — the Old World postmortem is the best public case study of a turn-based 4X AI under a human-visible turn budget: [GDC Vault — "My Elephant in the Room: An 'Old World' Postmortem"](https://www.gdcvault.com/play/1028038/). Soren Johnson's classic on AI quality expectations: [Game Developer — "Analysis: AI Fallibility And The Chick Parabola"](https://www.gamedeveloper.com/game-platforms/analysis-ai-fallibility-and-the-chick-parabola).
- **TITLE** — *Into the Breach* is the notable counter-example: rather than strong search, the AI telegraphs a small set of deterministic attacks the player can reason about — [GDC Vault postmortem](https://gdcvault.com/play/1026333/-Into-the-Breach-Design).
- **INFER** — **AI planning horizon is a function of the scheduling model.** IGOUGO lets the AI plan one contiguous side-turn; interleaved/CTB forces incremental/reactive planning; WEGO forces plan-under-uncertainty with a devalidation pass; ITB-style telegraphed phases let the AI be a deterministic, fully-searchable component. **A TBS engine cannot treat "AI" and "scheduler" as independent modules** — the AI needs a contract with the scheduler (who acts next, when may it think, what may it assume).

### AI honesty — what the AI is allowed to know

## 2.8 Persistence

### Save vs replay — the real decision
- **INFER** — the engineering ledger (only the pieces cited below are sourced):
  - **Full-state snapshot** — pros: load is O(state); works with arbitrary code (no re-simulatable model required); trivially supports *undo* and *mid-battle save*; does not require bit-exact determinism. Cons: save size grows with world size; every new field is a compatibility event; it captures state you may not be able to *reconstruct* correctly (cached plans, RNG state, AI blackboards) unless you deliberately serialise them.
  - **Command-log replay** — pros: tiny saves (log + seed); self-documenting history; gives replays and undo almost for free; enables desync detection. Cons: requires a *deterministic* simulation (fixed-point or strictly controlled float, seeded RNG streams, stable iteration order); load time grows with log length; it breaks the moment gameplay code changes semantics; fragile against "same input, different state" bugs; does not restore *presentation* state.
  - **Hybrid** — snapshot + recent command log (the rollback pattern) buys cheap save and fast recovery at the cost of keeping *both* paths correct.
- **SNIPPET** — concrete evidence of the **snapshot** strategy: *"Deterministic GGPO-style rollback netcode for Unreal Engine 5: fixed-step simulation, **SaveGame-reflection state capture**, UDP transport with input redundancy and reliable ACKs"* — [gregorik/Rollback-Core](https://github.com/gregorik/Rollback-Core).
- **TITLE** — a real TBS project weighing exactly this: [opencombatengine ADR-0059 "Combat Serialization Strategy"](https://github.com/jamesplotts/opencombatengine/blob/main/docs/adr/0059-combat-serialization.md), alongside [ADR-0058](https://github.com/jamesplotts/opencombatengine/blob/main/docs/adr/0058-combat-loop-refinement.md).
- **TITLE** — productised command model: [Deterministic Command Engine – Undo, Redo & Replayable Gameplay](https://assetstore-fallback.unity.com/packages/tools/game-toolkits/deterministic-command-engine-undo-redo-replayable-gameplay-368060). Snapshot/ECS-archive tooling: [chengts95/bevy_archive](https://github.com/chengts95/bevy_archive) — **WEAK**; [ryo_storage](https://docs.rs/ryo-storage/0.1.0/ryo_storage/storage/) — **WEAK**.
- **UNVERIFIED** — no source found that lays out this snapshot-vs-replay tradeoff as a *design article or GDC talk*. **The claim "there is a GDC talk on save/load architecture" was not verified** — multiple queries returned only vendor blogs, GitHub issues, patents and lecture notes.

### Mid-battle save
- **INFER** — a "save in the middle of a tactical battle" requirement immediately forces the engine to **suspend and resume an in-flight action sequence**: the pending command queue, the reaction queue, animation state and any partially-resolved action must all be representable as data. Engines that resolve actions as a synchronous, non-interruptible call stack cannot do this without leaking.
- **TITLE** — the best available source that mid-battle saves are a **balance decision, not just a filesystem feature**: [RPS — "XCOM Expansion Grudgingly Acknowledges Save Scummers"](https://www.rockpapershotgun.com/xcom-expansion-grudgingly-acknowledges-save-scummers).

### Schema versioning and migration
- **INFER** — for a live game every save needs a **schema id + monotonic version**, an explicit **unknown-field policy** (ignore / preserve / reject), and a **one-way migration chain** (v1→v2→v3, applied in order, tested) so the number of migration paths stays linear. Migration must be **atomic**: a failed migration must not leave partially loaded observable state.
- **TITLE** — practitioner write-up of the same problem in another engine: [StraySpark — "UE5 Save System Versioning: How to Not Break Save Files on Update"](https://www.strayspark.studio/blog/ue5-save-system-versioning-2026), with companions [Complete Guide to Save Systems in Unreal Engine 5](https://www.strayspark.studio/blog/complete-guide-save-systems-unreal-engine) and [Save Systems That Actually Work: Godot vs Unreal vs Custom Serialization](https://www.strayspark.studio/blog/save-systems-godot-vs-unreal-vs-custom-serialization) — **WEAK**.

A productised migration framework: [SavePatch Pro (Unity Asset Store)](https://assetstore.unity.com/packages/tools/utilities/savepatch-pro-save-migration-data-versioning-framework-361268) — **WEAK**.
- **TITLE** — concrete cases of the problem tracked as work: [asgardtech/archer #662 — "Add save format versioning and migration framework"](https://github.com/asgardtech/archer/issues/662) — **WEAK**; [hydralauncher/hydra PR #2652 — legacy save management](https://github.com/hydralauncher/hydra/pull/2652) — **WEAK**; [cooneycw/unicorn-game #64 — Save File Resilience & Backup System](https://github.com/cooneycw/unicorn-game/issues/64) — **WEAK**; and **SNIPPET** a save format changing numeric representation: [spencerduncan/balatro-rs #243 — "Update serialization format for f64 values"](https://github.com/spencerduncan/balatro-rs/issues/243) — **WEAK** — *exactly the migration hazard*.
