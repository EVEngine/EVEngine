## 5. 实测推翻了哪些先前判断

审查的价值一半在确认，一半在**否证**。以下四条是首轮实测推翻或降级的先前判断：

### 5.1 规范 `P-3` 的「其余多为自造」不成立

`模块接口契约与机制选型规范.md` §2.3 / P-3 的证据列写「全仓至少 13 个 provider 家族 …… 其余多为自造」。实测：

- `editing::IPropertyProvider`、`IGraphDomainProvider`、`IEditingSnapshotProvider` 通过 `editingCapabilityId()` 经 `editing::IEditingExtensionProvider`（**规范机制**）分发——`audio/editing/AudioTarget.cpp:43`、`animation/editing/AnimationClip.cpp:163` 等。它们是同一机制的类型化子面，不是独立注册表。
- `audio_editing`、`physics_editing`、`editor` 使用 `editing::ExtensionProviderRegistry` / `editing::ProviderHandle`（`audio/editing/AudioEditingProvider.h:34-35`）——**机制复用者**。
- `INavigationProvider` 是**消费方拥有的构造注入接口**（`npc_ai/Navigation.h:105` 的 `unique_ptr<INavigationProvider>`），根本不参与任何注册表——正是 `R-COHESION-6`「接口所有权跟随提问方」的正面例子。
- `IActionResourceProvider` 同样是直接注入的裸指针成员（`action/Action.h:347`）。

真实的自造注册表**只有 2 个**（§4.5）。**建议修订 P-3 的证据表述**，把「其余多为自造」改为「其余为类型化子面、消费方注入或 `cap::` 通用机制；自造注册表实测 2 处」。规范状态为「已确认的架构要求」，因此本台账只提出建议，不擅自改动。

### 5.2 成本**形状**无法用于存量判别（C 组只能在改动行上判定）

首轮尝试过两个全量代理，都不判别：

| 代理 | 全量命中 | 结论 |
| --- | --- | --- |
| 函数名匹配昂贵动词（`Readback|Load|Save|Build|Compile|…`） | 500+ 条 | 命中大量普通 setter/resolver（`resolve`、`commit`、`prepare`、`sync`、`build`）。**只适用于改动行门禁**（规范 §8.2 G-5 的 changed-line 语义是对的） |
| 公共 API 按值返回拥有型容器且无 `@cost` | 1446 条 | `std::string getQuality()`（`graphics/AmbientOcclusion.h:37`）这类短字符串按值返回是常态，不是「昂贵」 |

## E. `B-03` 裁剪证据：从「工具不存在」变为「有解但首轮方法会误判」

## F. `B-02` 模块职责：一对一耦合不成立，但发现两个更大的问题

**F1. 清单的 FAIL 条件（「总是同开同关、一对一耦合」）不成立。**
- **manifest 层面：0 / 194。** 没有任何模块在「恰好一个 `DEPS`」的同时是该依赖的唯一依赖方。
- **能力层面：20 处命中，16 处是注册表形态**——9 个 `IEditorAutomationTargetFactory` 供 `editor`、5 个 `IPlatformEventSink` 供 `platform_event`、2 个 `IStateProvider` 供 `devtools`。真正的 1:1 只有 4 处：`common`→filesystem（`IAssetReloader`）、`platform_event`→thread（`IMainThreadPost`）、`procgen`→devtools（`IProcgenQuery`）、`pixelworld`→devtools（`IPixelWorldAutomation`）。
- **拆分家族不是伪模块，证据是它们位于不同层**：`asset_import` L1、`asset_scene` L2、`asset_graphics` L4、`asset_physics`/`asset_stylize` L5、`asset_procgen` L6。每个是把 `asset` 与**另一个域**集成的跨域适配器，层号跟随那个域。`physics_softbody`(L3)/`_cook`(L4)/`_graphics`(L4)/`_editing`(L5) 与 `pixelworld_*` 同理。合并它们会迫使宿主依赖它集成的每一个域。这是**正确形态**。

**F2. 声明式接口层只覆盖 28%。**
**140 / 194 个模块既不提供也不消费任何能力。** 对它们，跨模块reach 靠直接 `#include`/`DEPS` 或脚本层。这是「如何拥有明确统一的外部接口」的量化答案：六面模型的 E1/E2 面只对 54 个模块落地。

**F3. 创作卫星存在系统性的「不可达」形态（工单清单，非结论）。**
`*_editor` 模块中 **24 / 28 的主 TU 是 4~6 行空锚点**，例如 `building/editor/building_editor.cpp` 全文 7 行：

```cpp
#include "building/editor/EditorBuildingTarget.h"
namespace eve::editor {
namespace { constexpr int buildingeditorModuleAnchor = 0; }
}
```

锚点未被使用。**82 个创作卫星中 42 个匹配不上仓内 13 种注册机制中的任何一种**（`ExtensionProviderRegistry`/`IEditingExtensionProvider`/`editingCapabilityId`/`ProviderHandle`/`IPropertyProvider`/`IGraphDomainProvider`/`IEditingSnapshotProvider`/`EditorAutomationTargetFactory`/`registerLinkKind`/`cap::provide`/`cap::addListener`/`addClass(`/`addFunc(`）。
端到端核实 2 个（非外推）：`building_editor`（3 文件）与 `camera_editor`（2 文件）——主 TU 是空锚点，`Editor*Target.h` **只被自己目录 include**，不注册任何东西。它们编译进二进制但无人可达。
**诚实边界**：24/28 的锚点计数与上述 2 个端到端核实是硬的；「42/82」是**工单清单不是判决**——注册词汇表有限，可能不全。
相关：`GROUP` 在 194 个模块上只给出约 6 种不同配置（`2d,3d,minimal,web` 一个桶就有 38 个模块），模块级可开关性比 194 个声明粗。

## G. 修正后的结论与下一步

首轮 §7 的三条规模性结论中，两条需修正：M3 的真实规模是 **27 处 R-MECH-4 违规（约 19 处每帧）**，不是 111 处；能力面的「1/3 只有一半」需改为 **`IStateQuery`/`IStateMutation` 是接线断裂（0 个 provide，非缺实现）**，且 `ITimeSource` 应从 E1-DEAD 移出。

按「能同时消掉多个已有问题」排序的建议：

1. **修取证工具 A1–A9，再重跑台账。** 在工具修正前，任何基于它的数字都不可引用。A1（词边界 + 只在 `*System.cpp` 上生效）与 A4（教会 `*SystemContract` 家族）是单行级；A3 需改为**逐 link 种类**判断；A5/A6 需把 `systems`/`symbols` 校验改成双向且区分定义/前向声明。

3. **把 `E3-ECS`/`E3-LINK` 的作用域判据写进规范**，否则 43 + 13 个已有条目模块内的缺口的定性无法固化，约 19 个无条目模块的判定也无据可依。
4. **为 E5-01 的 859 条豁免清单补 owner/issue/expiry**，并把「C++ 公共面与脚本面语义一致」纳入门禁——目前无任何机械覆盖。
5. **落地三面裁剪工具**（C++ 符号 ∪ 能力边 ∪ 脚本绑定）——三个输入都已存在，替代 `B-03` 目前「靠 include 图或不测」的状态。
6. **为创作卫星（F3）定 owner 决定**：未完成迁移，还是有意占位。
7. 首轮 §7 的第 1、2、5 项仍然有效。
