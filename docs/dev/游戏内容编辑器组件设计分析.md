# EVEngine 游戏内容编辑器组件设计分析

日期：2026-08-24
状态：设计提案
范围：场景、资产、材质、完整内容生产编辑器及玩家创造/建造玩法体系
设计依据：EVEngine 当前模块、工具链、内容生产需求与玩家创造玩法需求

配套落地设计：[`编辑器具体 API 与组件设计`](编辑器具体API与组件设计.md)

## 1. 结论先行

EVEngine 不应继续停留在“由每个游戏自行拼装若干 Toolbar/Inspector 状态”的阶段。推荐建设一套 **可选安装、可裁剪、数据驱动、编辑器/游戏/Agent 三端同构** 的官方内容编辑器：

- `editor-core` 提供文档、命令、选择、焦点、事务、撤销、属性描述和扩展注册，不依赖渲染、场景、材质等业务模块；
- `editor-shell` 提供窗口、Dock、布局、菜单、命令面板、状态栏和工作区，不拥有业务数据；
- 场景、资产、材质、动画、粒子、UI、地图等模块各自通过 capability 和 descriptor 提供编辑能力，禁止编辑器核心向上包含模块头文件；
- 资产使用稳定 GUID、可异步查询的元数据索引、依赖图和导入产物；源文件、可编辑文档、平台产物三者分离；
- 所有写操作统一走 `Command -> Transaction -> Validation -> Document/Asset mutation -> Journal`，菜单、快捷键、拖放、MCP 和脚本不得各自实现修改逻辑；
- 官方编辑器只是一种宿主。相同工具、命令、事务与描述符还可供玩家建造模式、游戏内编辑器、CLI、测试和 `eve-mcp` 使用；
- “开发编辑器”和“玩家建造玩法”不分叉业务实现：二者只替换 Shell、权限策略、数据目标和持久化后端；过山车、公园、城市、房屋、载具等搭建玩法应直接复用场景编辑能力；
- 游戏玩法模块可以反向注册专用工具、Inspector、Overlay、验证规则与模拟模式，使官方编辑器自动成为该游戏的专用编辑器；
- 第一阶段优先实现编辑器内核、资产数据库、反射属性和场景文档，而不是先堆 UI 面板。

这套方案建立在 EVEngine 的模块裁剪、capability、Squirrel 生产接口和 AI 工具优势之上，以稳定身份、文档事务、完整内容工作流和运行时可裁剪性补齐当前能力，同时避免引入全局对象模型和重型二进制包体系。

## 2. 设计边界与需求归纳

### 2.1 内容编辑内核需求

内容编辑能力需要形成以下统一机制：

1. `DocumentKey` 以资产 GUID、资源路径或会话 ID 表示稳定文档身份；文档记录 revision、saved revision、外部 revision、脏状态、冲突和保存票据。
2. 一个文档允许多个 View，脏状态属于文档而不是面板；View 关闭后，历史记录仍能通过稳定 locator 找回文档。
3. `EditorCommandRegistry` 将菜单、快捷键、工具栏、上下文菜单、拖放、自动化和 API 统一为带焦点与选择快照的命令上下文。
4. 命令执行自动进入用户动作事务；Undo 不只恢复属性，还恢复选择、焦点、层级、Prefab、组件顺序和文档 revision。
5. Panel 类型先声明交互契约再注册到窗口系统，防止 UI 类成为业务权威。
6. 资产 GUID、依赖图、导入设置、导入产物、删除预检、外部文件冲突和原子保存形成完整闭环。
7. 通用 Node Graph 被材质、粒子、动画状态机等复用，而非各写一套节点画布。
8. MCP 使用同一公开命令/资产/场景接口，Agent 并不模拟鼠标点击 UI。

实现应避免过多细颗粒代理、全局 singleton 服务和 UI 驱动的运行时约定。EVEngine 更适合用 C++ 小接口、值类型描述符和 Squirrel 扩展保持边界清晰。

### 2.2 完整内容生产工作流需求

官方内容编辑器不能只提供局部控件，还应覆盖完整工作流：主工作区组合 Viewport、Outliner、Details、Content Browser 和编辑模式；不同资产按类型进入专用编辑器；资产索引在不加载资产的情况下异步提供元数据；Cook 将编辑源格式转换为平台运行格式；数据验证、源代码管理和协作状态在内容工作流中可见。

相关能力按当前项目阶段分三类处理：

- **首期必需**：主工作区、资产浏览/搜索、统一 Details、专用资产编辑器、预览场景、导入/Cook、验证、引用审计、Play In Editor；
- **适度简化**：世界分区、地形植被、建模、Sequencer、视觉脚本、行为树、动画蓝图；先提供扩展框架，再随运行时能力落地；
- **暂不建设**：全局对象反射体系、重型二进制 Package、专用多人事务服务器和完整视觉脚本编译器；它们的工程规模不符合当前 EVEngine。

### 2.3 EVEngine 当前基础

EVEngine 已有可复用基础：

- `editor` 模块：`IEditorTool`、`IEditableTarget`、笔刷、约束、Overlay、Inspector、Gizmo、History；
- `scene` / `entity` / `sceneloader`：场景树、实体及场景加载能力；
- `filesystem`：资源访问、HotReload、压缩与虚拟路径；
- `graphics` / `model3d` / `animation` / `particles` / `ui`：内容运行时；
- `Capability.h`：可选模块跨层能力注册；
- `module_manifest.cmake`：单一模块声明与裁剪；
- DevTools、MCP、`creative-brain`、`scene-qc-agent`、`story-scene-agent`：自动化、场景构建和视觉质检；
- JSON View + Squirrel ViewModel 的 editor host：适合快速生成项目专用工具。

当前缺口是“构件之上的内容生产协议”：缺少统一资产身份与索引、通用属性元数据、正式文档模型、跨面板事务、专用资产编辑器注册、导入产物状态以及官方完整工作区。现有 `EditorHistory` 适合局部工具，不能单独承担整个编辑器的一致性。

## 3. 设计原则

### 3.1 开发编辑器是可选产品，编辑能力是运行时可复用内核

发布游戏默认不携带开发者 Dock Shell、源文件导入器、缩略图生成、项目设置、Cook、源控和无限制资产浏览等生产工具；但 Tool、EditableTarget、Command、Transaction、Selection、Property、Overlay 等 **运行时安全的编辑协议** 必须可独立裁剪进游戏。模拟经营、建造和沙盒游戏可以把它们作为核心玩法，而不是复制一套“游戏版编辑器”。

因此应拆成两种构建能力：

- `editing-runtime`：可发布，提供工具、目标、命令、事务、约束、选择和运行时属性；
- `authoring`：仅开发环境，增加项目文档、源资产导入、Cook、源控、开发诊断和官方桌面 Shell。

`3d`/`2d` 运行组不自动包含二者，游戏在 manifest 中按需选择 `editing-runtime`。Cook 必须移除未被游戏授权的开发者命令和 EditorOnly 元数据，而不能简单假设所有编辑功能都不进入发布包。

### 3.2 数据模型先于 UI

面板只投影文档和服务状态。按钮不得直接写 SceneNode 或材质；它触发命令，命令在事务里操作明确的文档或编辑目标。这样同一动作才能被快捷键、脚本、MCP、测试和未来协作系统复用。

### 3.3 跨模块只走接口

遵循仓库 layering 规则：低层编辑器核心不包含 `scene`、`graphics`、`animation` 等模块头。消费者在 `common/` 或自己模块声明接口，提供者通过 `eve::cap::provide/query` 注册。模块是否存在必须可查询，缺失时相关工具和资产类型自然消失。

### 3.4 文本友好与稳定引用

场景、Prefab、材质图和导入设置优先采用有 schema/version 的确定性文本格式；大二进制源文件与 Cook 产物单独保存。引用使用 GUID，不把可变路径作为身份。保存输出字段顺序稳定，便于 Git diff 和合并。

### 3.5 人类与 Agent 同构

MCP 工具调用命令服务和查询服务，不控制 ImGui。每个编辑能力都应同时定义：人类入口、命令 ID、参数 schema、查询快照、校验结果和可撤销语义。

### 3.6 渐进复杂度

默认界面只暴露常用属性；高级、调试和平台特定项可折叠。专用编辑器复用统一 Viewport、Property、Graph、Timeline 等组件，避免形成多个风格不一致的孤岛。

### 3.7 编辑器与游戏同构

编辑行为不得以 Dock、菜单、ImGui 控件或桌面文件为前提。一项能力只有同时满足下列条件，才算正式进入编辑器体系：

1. 业务操作由 presentation-neutral 的 Tool/Command 表达；
2. 操作目标通过 capability 暴露，而不是绑定开发编辑器对象类型；
3. UI 由描述符投影，桌面 Editor UI 和游戏 UI 可以采用不同布局与视觉；
4. 持久化由上下文注入，可写项目文档、关卡草稿、SaveGame、服务器世界状态或用户蓝图；
5. 权限、成本、解锁条件、地图边界等由 Policy/Constraint 决定，不散落在按钮回调中；
6. 同一操作在两个宿主中具有一致的预览、提交、取消和撤销语义。

这里的“同构”不是要求游戏显示开发者界面，而是要求 **模型与行为同源、呈现与权限可换**。例如开发编辑器的“放置过山车轨道”可以显示坐标、曲率和碰撞调试；玩家界面则显示造价、满意度影响和解锁状态，两者仍调用同一个轨道放置工具和轨道网络命令。

## 4. 总体架构

```text
Developer Shell                     Game Shell
(Dock/Menu/Project/Source UI)        (HUD/Radial/Palette/Touch UI)
            \                         /
             Presentation Descriptors
                       |
Editing Runtime (Tool / Command / Selection / Transaction / Constraint)
                       |
Target & Gameplay Capabilities ---------------------------------+
   |             |              |            |          |        |
 Scene target   Asset target   Material     Animation   UI     Game systems
   |             |              |            |          |        |
 Runtime modules: scene, filesystem, graphics, model3d, animation, ui, ...
                       |
          Persistence / Authority Adapter
      Project Document | SaveGame | Server World | User Creation

Developer-only Authoring Services:
Document Registry / Asset Import / Cook / Source Control / Project Validation
```

推荐模块拆分：

| 模块 | 层级/依赖 | 职责 |
|---|---|---|
| `editor`（扩展现有，发布安全） | 纯协议和值类型 | Tool、Target、Command、Transaction、Selection、Constraint、Property descriptor |
| `editing_runtime`（可与 editor 合并） | 可选运行时组 | 编辑会话、Undo、运行时 palette/schema、SaveGame/服务器提交适配 |
| `assetdb` | L0，依赖 filesystem/data | GUID、元数据索引、依赖图、导入状态、查询；运行时可裁剪为只读 manifest |
| `authoring` | authoring 组 | DocumentRegistry、UndoJournal、Validation、ImportCoordinator、Cook orchestration |
| `editorui` | authoring，依赖 ui/window/input | Dock shell、通用面板、PropertyGrid、GraphView、TimelineView |
| `editor_scene` | authoring adapter | 场景文档、Outliner、Viewport、Prefab、Play session |
| `editor_render` | authoring adapter | 材质、纹理、网格、RenderGraph/后处理预览 |
| 各业务编辑适配 | 可选 | animation/particles/map/ui/audio 等专用编辑器与描述符 |

不建议建立一个依赖所有模块的巨型 `EVEditor`。模块清单派生编辑器功能，编辑器启动时从 registry 构造可用菜单与资产类型。

同一注册表允许多个 host profile：`developer`、`runtime-builder`、`runtime-admin`、`automation`。Profile 只决定某个 descriptor 是否可见、用哪种 presenter、允许哪些命令以及连接哪个持久化后端，不改变工具实现。

## 5. 编辑器基础组件

### 5.1 Workspace 与 Dock Shell

职责：多窗口、多显示器、Dock/浮动、文档标签、工具面板、布局保存和工作区切换。

预置工作区：

- Level：场景视口 + Outliner + Inspector + Content Browser；
- Material/VFX：图画布 + Preview + Details + Palette + Compile Results；
- Animation：骨骼树 + Preview + Timeline/Curve + Details；
- UI：Canvas + Hierarchy + Inspector + Anchors/Layout；
- Debug：Game View + Console + Profiler + Render/Physics inspectors。

布局保存为用户级配置，不能污染项目内容。项目可提供推荐布局，但用户布局优先。面板缺失时保留占位记录，插件恢复后可重新装载。

核心接口：`IPanelFactory`、`PanelDescriptor`、`WorkspaceLayout`、`IWorkspaceService`。Descriptor 至少包含稳定 type ID、显示名、菜单路径、单例策略、所需 capability、默认停靠区和交互上下文。

### 5.2 Command、Shortcut、Focus 与 Selection

所有用户意图注册为稳定命令 ID，例如：

```text
scene.object.create
scene.selection.frame
asset.import
asset.rename
material.graph.connect
edit.undo
play.start
build.cook
```

`CommandContext` 固化触发时的 source、active document、focused panel、selection snapshot、input context、payload。延迟菜单必须保存原上下文，不能执行时重新读取选择，否则会修改错误对象。

Selection 使用带类型 item：`SceneObjectSelection`、`AssetSelection`、`GraphNodeSelection`、`TimelineKeySelection`。主选择和集合分离；支持 selection channel，使 Scene View、Outliner、Inspector 联动，同时不覆盖 Material Graph 的内部选择。

快捷键按 input context 分层解析：模态框 > 文本输入 > 当前工具 > 当前文档 > 全局。支持用户配置、冲突检查和可搜索命令面板。

### 5.3 Document Registry

文档是可保存内容的唯一编辑权威。建议模型：

```cpp
struct DocumentKey { AssetTypeId type; Guid asset; };
struct DocumentRevision { uint64_t edit, saved, disk, preview; };
enum class DocumentState { Loading, Ready, Saving, Conflict, Failed, Closed };
struct DocumentLocator { Guid stableViewlessId; DocumentKey key; };
```

一个 Scene 文档可以同时被 Scene View、Outliner、Inspector 投影；材质文档可以被图、预览和参数面板投影。面板关闭不等于文档关闭。文档管理：

- 打开去重和最近文档；
- revision 与 dirty；
- Save、Save As、Save All、Discard；
- 异步保存 ticket，保存期间继续编辑不会错误清除 dirty；
- 外部文件变化检测与 Reload/Keep/Merge；
- 关闭项目/编辑器的统一未保存协调；
- 会话恢复与崩溃恢复草稿；
- 文档 schema migration。

保存采用 compare-and-swap 文件状态与临时文件原子替换，避免外部修改或并发保存被静默覆盖。

### 5.4 Transaction 与 Undo Journal

事务是所有变更的边界。`IEditCommand` 提供 `apply/revert/merge/describe/affectedDocuments`。连续拖动在开始时捕获 before，更新 preview，结束时提交一个合并命令；取消则恢复 before。禁止每个鼠标像素生成一条历史。

历史需要覆盖：

- 属性修改与多选批改；
- 创建、删除、复制、重父级和重排；
- 组件增删与顺序；
- Prefab override/apply/revert/unpack；
- 资产创建、移动、重命名、删除、导入设置；
- 图节点与连线；
- 时间轴 key/curve；
- 选择和焦点的合理恢复；
- 文档 revision 同步。

每个动作记录 origin（User、Script、Automation、Importer）、命令 ID、时间、影响文档和简短摘要。History 面板可查看、跳转和复制诊断信息。导入器后台刷新不应混入用户 Undo，但必须可通过 reimport 恢复确定状态。

### 5.5 Property/Reflection 系统

这是 Inspector、序列化、资产元数据和自动化共同依赖的关键设施。避免引入宏驱动的全局对象模型，采用显式注册和值访问器：

```cpp
PropertyDescriptor {
  id, displayName, category, type, flags,
  getter, setter, defaultValue,
  range, step, units, enumItems,
  assetTypeFilter, visibilityPredicate,
  validator, customEditorFactory
}
```

支持 bool、整数、浮点、字符串、枚举、颜色、向量、矩阵/TRS、数组、结构、Variant、对象引用、资产引用和只读统计。元数据支持 tooltip、单位、范围、滑块、角度、颜色空间、文件过滤、可见条件、ReadOnly、Advanced、EditorOnly、Transient。

Inspector 必须支持：搜索、分类折叠、混合值、多选交集、恢复默认、复制/粘贴属性、锁定选择、资产拖放、错误/警告内联显示和属性级 Undo。属性 descriptor 同时导出为 MCP/JSON schema。

### 5.6 Validation 与 Diagnostics

验证是独立服务，不属于 Inspector。规则可针对 Asset、Document、Selection、Scene、Project、BuildTarget；结果包括 severity、稳定 rule ID、对象定位、说明和可选 quick fix 命令。

基础规则：命名、丢失引用、循环依赖、非法层级、Prefab override 失效、纹理/网格预算、材质编译、碰撞缺失、场景无主相机、脚本错误、Cook 不支持格式。支持保存前轻量验证、手动全项目扫描和 CI headless 扫描。

## 6. 资产系统与 Content Browser

### 6.1 三层资产模型

```text
Source       原始 PSD/PNG/FBX/WAV/GLTF 等，可在项目内或外部源目录
Authoring    .eveasset/.evscene/.evmat 等可编辑文档 + .meta GUID/导入设置
Artifact     缓存中的平台/配置产物，内容寻址，可删除重建
```

不要让运行时直接依赖原始源文件，也不要把派生产物提交为业务权威。`AssetRecord` 至少包含 GUID、逻辑路径、类型、schema、source URI、content hash、importer ID/version、settings hash、artifact keys、tags、dependencies、status 和 diagnostics。

### 6.2 Asset Database

AssetDB 启动时异步扫描元数据；Content Browser 查询未加载资产，不为显示一张列表而加载模型或材质。功能包括：

- GUID <-> path 与移动/重命名保持引用；
- 类型、标签、路径、修改状态和全文字段查询；
- hard/soft/editor-only/build 依赖边；
- 正向 References 与反向 Referencers；
- 文件监听、增量索引、重复 GUID 检测；
- 缩略图 key 与导入状态；
- 资产删除预检、重定向/修复引用；
- 缓存可重建，索引损坏不丢业务数据。

建议项目布局：

```text
Content/                 可编辑资产
SourceAssets/            可选原始文件
.eve/meta/               若不使用同目录 sidecar，可集中存 GUID 元数据
.eve/cache/<platform>/   导入/Cook 产物（忽略提交）
.eve/editor/             用户无关的项目编辑设置
Saved/                   日志、草稿、自动保存、崩溃恢复
```

### 6.3 Content Browser 组件

组成：Sources Tree、Breadcrumb、Search、Filters、Collections、Asset View、Preview/Details、Import Queue。提供网格、列表、列三种视图，支持多实例和保存查询。

操作：创建、导入、打开、拖入场景、重命名、移动、复制、复制引用、重新导入、Reveal Source、验证、引用查看、迁移、删除预检。集合是对 GUID 的软组织，不改变目录；支持本地和项目共享集合。

搜索语法建议：

```text
type:material tag:environment path:/Content/World has:error
ref:/Content/Characters/Hero size>10MB modified:true
```

缩略图由 `IAssetPreviewProvider` 异步生成，使用固定预览场景与内容哈希缓存。列表滚动不得同步创建 GPU 资源。

### 6.4 Import、Reimport 与 Cook

`IAssetImporter` 声明扩展名、目标类型、设置 schema、版本和 headless 能力。导入流程：候选识别 -> 设置草稿 -> 后台解析 -> 临时产物 -> 验证 -> 原子发布 -> 更新依赖/缩略图 -> 通知热重载。失败保留上一份可用产物。

Reimport 使用保存的 source URI 与 settings；Importer 版本或设置 hash 变化使资产变为 stale。批量导入显示队列、阶段、耗时、取消和诊断。

Cook 从显式入口场景/Primary Asset 出发遍历依赖，剔除 EditorOnly，按 target 生成 manifest 和内容包。支持 dry-run、缺失引用报告、体积统计、chunk/标签规则和增量 Cook。编辑器 Build 面板只是 CLI pipeline 的前端，CI 使用完全相同命令。

## 7. 场景与 Prefab 编辑器

### 7.1 场景文档

场景源格式应包含稳定 object/component ID、父子关系、local TRS、组件类型与属性、Prefab 来源与 override、外部子场景引用、编辑器标签/层。序列化顺序确定，运行时句柄不写入文档。

场景修改先落在 `SceneDocument`，再由 adapter 同步到预览运行时；不要把正在运行的 SceneNode 指针当作持久文档。文档可在无 GPU/headless 环境加载、验证和变换。

### 7.2 Level Workspace 组件

默认布局：中央 Scene View；左侧 Place/Tools；右侧 Outliner + Inspector；底部 Content Browser；状态栏含 Console、任务、源控和 Cook 状态。

Scene View：

- 透视、顶/前/侧正交、多视口；
- 编辑相机书签、聚焦选择、飞行/轨道导航；
- 选择轮廓、框选、多选、遮挡选择策略；
- Translate/Rotate/Scale/Bounds gizmo，local/world/pivot，网格/角度/表面/顶点吸附；
- Lit、Unlit、Wireframe、Normals、UV density、Overdraw、Lighting-only、Collision、Navigation 等可注册视图模式；
- Grid、坐标轴、相机、灯光、音频范围、碰撞、路径、物理约束等 overlay；
- 资产拖放预览，确认时形成单个事务；
- 工具模式：选择、放置、地形、植被、瓦片、样条/道路、体素、测量；模式来自 registry。

Outliner：

- 层级、搜索、类型/标签/层过滤；
- 多选、重命名、拖拽重父级和顺序调整；
- 可见、锁定、EditorOnly、Prefab 状态列；
- Folder/Collection 只组织编辑器视图，不必改变运行时层级；
- 多实例、保存过滤器和列配置；
- 大场景虚拟化列表和增量 diff，避免每帧重建整棵树。

Place Palette：按类别显示可创建对象、组件模板、Prefab 和常用资产；拖放或点击进入 placement tool。项目可注册自己的 archetype。

### 7.3 Prefab

Prefab 是独立资产文档，实例保存 Prefab GUID、内部对象稳定 ID 映射和最小 override 集。功能：

- 从选择创建、嵌套 Prefab、隔离编辑；
- override 可视化、Apply、Revert、Unpack；
- 丢失/重命名字段迁移；
- 实例结构冲突诊断；
- 变体通过父 Prefab + override 实现，不复制整份数据。

Prefab 修改向所有预览实例传播，但必须保留实例 override。场景历史引用稳定 ID，传播后仍可恢复。

### 7.4 Play In Editor

提供 Edit、Simulate、Play 三态：

- Play 从场景文档快照创建隔离运行世界；
- Stop 丢弃运行态变化并恢复编辑选择/相机；
- 可选 Keep Changes 只生成可审查的属性差异事务，不能直接把整个运行世界覆盖回文档；
- Pause、Step Frame、Time Scale、输入焦点切换；
- Game View 与 Scene View 分开，相机和 overlay 状态互不污染；
- 脚本热重载失败保留上一可运行版本，并显示诊断。

未来大型世界可通过 `IScenePartitionProvider` 增加 cell/streaming、Data Layer、HLOD 和世界原点工具；核心场景编辑器只理解可加载区域接口，不内置 UE World Partition 模型。

## 8. 材质、Shader 与渲染编辑器

### 8.1 材质资产模型

分为：

- Material Graph：可编译图，定义 shading model、render state、参数和输出；
- Material Function：可复用子图；
- Material Instance：父材质 + 参数 override，不复制图；
- Render Effect/Render Pipeline：后处理或 RenderGraph 资产，使用同一通用图基础设施但不同节点域。

图文档使用稳定 node/pin ID、类型化 pin、默认值、位置/注释、schema version；编译结果和生成 shader 不写回业务文档。

### 8.2 Material Editor 布局

Graph Canvas、Preview Viewport、Details、Node Palette、Parameters、Compile Results、Stats。支持：

- 搜索创建节点、拖线创建兼容节点、reroute、comment、group、对齐；
- 类型检查、隐式转换规则、循环检测、死节点提示；
- 实时预览开关和 debounce，编辑期间取消过时编译；
- 球/平面/立方体/自定义网格、HDRI/灯光环境、背景和曝光；
- 编译错误定位到节点/pin；
- shader instruction、sampler、uniform、variant 和 pass 统计；
- 参数分组、默认值、instance hierarchy 和查找使用者；
- Apply/Save 语义明确：预览可用草稿，运行场景只接收成功编译版本。

### 8.3 通用 Graph Framework

Material、Particle、Animation FSM、Behavior Tree、RenderGraph 不共享业务节点，却共享画布和文档操作：pan/zoom、选择、节点布局、连线、复制粘贴、搜索、注释、minimap、Undo、diff。定义 `GraphDomainDescriptor` 提供节点目录、pin 类型系统、连接规则、编译器、Details provider 和调试 overlay。

这避免不同资产编辑器重复实现 graph core，也为 EVEngine 未来可视化玩法逻辑保留入口，而不承诺立即实现完整视觉脚本系统。

## 10. 编辑器与游戏双向复用

### 10.1 一份能力，四种可替换部件

任意可复用编辑功能必须拆成以下四部分：

| 部件 | 例：铺设过山车轨道 | 开发编辑器 | 玩家游戏 |
|---|---|---|---|
| Tool/Command | 放置控制点、连接轨道、调整坡度 | 工具栏、快捷键、数值输入 | 建造菜单、手柄/触摸、引导提示 |
| EditableTarget | 轨道网络与地形能力 | SceneDocument 预览目标 | 权威游戏世界/服务器目标 |
| Policy/Constraint | 曲率、碰撞、边界、连接规则 | 可警告或调试绕过 | 强制规则、造价、科技、领地权限 |
| Presenter | palette、properties、overlay 意图 | Dock/Inspector/debug overlay | HUD、径向菜单、世界空间 UI |

Tool 不查询“当前是不是编辑器”，而是查询上下文提供的 capability。例如 `ICurrencyBudget` 缺失时不显示造价；存在时提交前执行预算预留。这样开发工具可以完整调试几何，玩家工具可以叠加玩法规则，核心轨道生成逻辑仍只有一份。

### 10.2 Host、Session、Target 与 Authority

建议明确四个不同概念：

- **Host**：输入和 UI 容器，例如桌面编辑器、游戏 HUD、触屏建造界面、VR 手柄或 MCP；
- **EditorSession**：当前工具、选择、指针捕获、事务和局部历史；
- **EditableTarget**：实际被改的能力集合，例如 SceneDocument、运行世界、地图存档、Prefab 草稿；
- **Authority**：谁能接受提交，例如本地项目、单机 SaveGame、多人服务器或创意工坊草稿。

`EditorSession` 不拥有目标，也不假设文件存在。一次事务先在目标上 preview，经 Constraint/Authority 预检后 commit。多人游戏中客户端可预测预览，服务器复验命令并返回 authoritative transaction ID；拒绝时恢复预览。开发编辑器则由 Document Authority 校验 revision 并写入文档历史。

### 10.3 持久化策略

同一命令产生领域差异或操作描述，不直接打开文件：

```text
SceneDocumentPersistence  -> .evscene/.evprefab，支持 Save/Save As/Git
SaveGamePersistence       -> 玩家存档，记录世界状态或玩家蓝图
ServerWorldPersistence    -> 服务端事件/快照，带权限和并发版本
UserCreationPersistence   -> 沙盒作品/关卡分享包，经过白名单 Cook
TransientPersistence      -> 教程、预览、规划模式，不落盘
```

开发文档可以保存源资产 GUID、EditorOnly 注释和精确浮点；玩家作品只能引用运行时白名单资产和参数，不能夹带任意路径、脚本、shader 或开发命令。用户创作内容导出前运行独立验证和安全 Cook。

### 10.4 UI 描述符而非 UI 复用

不要直接把开发编辑器 Inspector 嵌进游戏。Tool/Property/Action descriptor 提供语义：类别、图标语义、字段类型、单位、范围、危险级别、适用条件、快捷 action 和帮助文本。不同 presenter 决定具体控件、信息密度和美术风格。

例如同一个 `TrackSlope` 属性：

- 开发 Inspector：精确角度输入、曲率图、碰撞与切线诊断；
- PC 游戏：滑杆、造价变化、有效/无效颜色；
- 主机游戏：左右肩键分档调整；
- 移动端：世界空间拖柄和大尺寸确认按钮；
- Agent：JSON schema 中的 number、范围、单位与 validation rule。

共享的是属性路径、读写命令、约束和 Undo，不是像素布局。

### 10.5 游戏玩法注入开发编辑器

游戏模块应提供 `IGameEditorExtension` 或等价注册入口，在项目加载后注册：

- 自定义 Tool 与 placement archetype；
- 领域 Property provider 和 Inspector section；
- 场景 Overlay、Gizmo 与 debug visualization；
- 资产类型、预览器和创建菜单；
- Validation/Quick Fix；
- 自定义 Workspace/Panel；
- Play/Simulate 模式和领域 profiler；
- 命令、MCP schema 和自动化 fixture。

示例：城市建造游戏注入道路、分区、公共交通、人口热力图和经济模拟时间控制；塔防游戏注入路径波次、射程 Overlay 和关卡合法性检查；过山车经营游戏注入轨道编辑、列车测试、G-force 曲线、游客可达性和造价预算。它们进入官方编辑器后仍调用游戏正式运行系统，不能维护一套“仅编辑器近似模拟”。

扩展注册必须由模块 manifest/插件派生，不能手改中央菜单和 boot list。游戏模块卸载时，对应面板和工具优雅消失，未知组件/数据仍可保真保存。

### 10.6 玩家建造模式的产品级要求

运行时编辑不是开发工具的阉割开关，还需要正式玩法能力：

- 规划/预览、确认/取消和批量连续建造；
- 造价、退款、资源预留和原子扣款；
- 解锁、领地、角色权限和多人所有权；
- 网格、道路、表面、连接点和语义吸附；
- 拆除、升级、复制、蓝图/模板和作品分享；
- 手柄、触摸、键鼠及可访问性输入；
- 操作教学、失败原因和建议修复；
- 大规模增量重建与后台派生数据更新；
- 多人预测、服务器验证、冲突与恶意 payload 限制；
- 存档迁移和旧版本玩家作品兼容。

这些能力通过 Policy、Authority、Persistence 和 Presenter 扩展通用编辑协议，不应污染几何工具本身。

### 10.7 同构验收矩阵

每个计划进入游戏的编辑组件至少通过：

1. 同一个 Tool 在 developer host 和 runtime host 上操作同一种目标 capability；
2. 两端对相同输入生成等价领域命令/差异；
3. 两端都支持 preview、cancel、commit、undo；
4. 更换 UI presenter 不修改 Tool 或 Target；
5. 更换 Document/SaveGame/Server persistence 不修改 UI 或领域命令；
6. 运行时 profile 无法发现或调用被裁剪的开发者命令；
7. 游戏扩展能在不修改 editor-core/editor-shell 的情况下注册完整专用工作区；
8. Headless 测试可直接执行相同命令验证确定性。

## 11. 协作、源控与外部变化

第一版不建设实时多人编辑服务器，但现在就要保证协议可演进：

- 每个事务记录稳定对象/属性路径和 base revision；
- 文档保存检测 disk revision/content hash；
- Git 状态在 Content Browser、文档 Tab 和状态栏显示；
- Source Control provider 为接口，首个实现调用 Git，不把 Git 命令写入 UI；
- 支持 diff、reveal、stage/commit 可后置，第一期至少有 modified/conflict/ignored/read-only；
- 文本资产提供结构化 diff，场景按对象/组件/属性显示，不只展示 JSON 行差异；
- 外部变化：干净文档自动重载；脏文档进入 conflict，提供 compare/reload/keep/save-as；
- 文件锁仅是 provider 能力，不作为核心假设。

未来多人协作可传输同一事务 journal，在本地文档快照上形成会话层；“会话内先不写磁盘、显式 persist”是可选上层，不进入一期。

## 12. Agent、脚本与自动化

EVEngine 在这一点可以优于传统编辑器。建议为每个服务提供 Query 与 Command 两面：

```text
query: editor.documents, asset.search, scene.snapshot, material.compile_status
command: asset.import, scene.object.create, property.set, build.cook
```

规则：

- MCP/Squirrel 通过命令 ID 执行，自动进入同一事务与验证；
- 查询返回稳定 ID、revision 和分页数据，不暴露裸指针；
- 写命令带 expected revision，防止 Agent 根据过期场景修改；
- 支持 dry-run，返回影响对象、验证警告和预估产物；
- 批量操作在一个 compound transaction 中，要么完整成功，要么回滚；
- Agent 动作在 History 标记 origin，可人工 Undo；
- screenshot/视觉检查作为补充，语义状态是主要控制回路；
- `creative-brain` 生成的项目专用 editor JSON 可以作为 Workspace 中的 Tool Panel，但业务修改仍调用命令。

应补充的 MCP 能力：资产查询与引用图、通用属性 schema、文档脏状态/保存、场景批量事务、材质图 CRUD/编译、验证运行、Cook dry-run、任务进度和诊断定位。

## 13. 性能、可靠性与测试指标

目标规模（初始工程预算）：

- 100k 资产索引，启动扫描异步，Content Browser 首屏不等待完整扫描；
- 50k 场景对象 Outliner 虚拟化，筛选和选择不遍历/重绘所有行；
- 属性连续编辑 60 Hz preview，Undo 只生成一条记录；
- 缩略图、导入、shader compile、Cook 均为可取消任务；
- UI 线程不做模型解析、hash 大文件或同步 shader compile；
- 崩溃后可发现自动保存草稿，原文件保持原子一致。

测试分层：

1. 纯单元：GUID、索引、查询、descriptor、命令路由、事务合并、schema migration；
2. 文档契约：save ticket race、外部冲突、关闭协调、Undo 后 revision；
3. 导入 golden：相同 source/settings/version 得到相同 artifact key；
4. Headless 集成：打开场景、修改、保存、重载、Cook、依赖闭包；
5. UI 交互：选择联动、拖放、快捷键上下文、面板恢复；
6. GPU 预览：在现有 Vulkan/Xvfb/Lavapipe 环境做短测试；
7. MCP 合同：Agent 与 UI 对同一命令得到相同文档结果；
8. 性能门：10k/100k 资产查询、50k Outliner diff、大图编辑和批量导入。

每个业务编辑器的新测试放在独立 `test/editor_<domain>.cpp`，不扩张共享 test main。UI 截图测试不代替文档/命令层断言。

## 14. 分阶段开发路线

### Phase 0：冻结协议与样例（2–3 周）

- 用一个小型样例项目定义 scene/material/texture 的预期目录和格式；
- 决定 GUID sidecar 位置、URI 规范、schema/version 规则；
- 写出 Tool、Target、Command、Transaction、Property、Policy、Authority、Document、AssetType 最小接口和依赖图检查；
- 将现有 `EditorSession`/Gizmo/Brush 明确定位为 Tool 层，不破坏兼容 API。
- 建立最小 developer host 与 runtime host：不同 UI presenter 操作同一个测试目标；
- 建立 SceneDocument 与 SaveGame 两种 persistence adapter 的契约测试。

退出条件：无 UI 也能 headless 做一个属性事务、Undo 和持久化；同一 Tool 在开发宿主与游戏宿主产生等价领域差异。

### Phase 1：内容编辑内核（4–6 周，最高优先级）

- `assetdb`：GUID、索引、查询、依赖、文件监听；
- `authoring`：DocumentRegistry、Transaction/Undo、Command/Selection/Focus；
- PropertyDescriptor 与通用序列化 adapter；
- 原子保存、外部冲突、自动保存；
- Validation 和 Task/Diagnostic 服务；
- 对外 Squirrel/MCP API。
- 发布安全的 `editing-runtime` profile、命令白名单和运行时 schema 裁剪；
- GameEditorExtension 注册入口与至少一个样例游戏专用工具。

退出条件：100k synthetic asset 索引测试通过；所有写操作经命令与事务；MCP 可执行并 Undo 属性修改；发布 profile 无法调用 authoring-only 命令。

### Phase 2：官方 Level Workspace（5–8 周）

- Dock Shell、布局、命令面板、Content Browser、Inspector、Outliner；
- SceneDocument adapter、Scene/Game View、Gizmo、多选、拖放；
- Place Palette、Prefab 基础、Edit/Play/Stop；
- Console、任务、History、Project Settings。
- 使用同一场景 Tool 构建一个游戏内建造模式示例，改用游戏 HUD、Constraint 和 SaveGame persistence；
- 从样例玩法模块向官方编辑器注入专用 Tool、Overlay、Inspector section 和 Validation。

退出条件：可从导入模型开始，创建场景、放置/编辑/Prefab、保存、Play、重开无数据差异；相同放置/变换工具在游戏建造模式可用，玩法扩展无需修改 editor-core/editor-shell。

### Phase 3：渲染资产生产（5–8 周）

- 通用 Graph Framework；
- Material/Function/Instance 编辑器；
- Texture/Static Mesh importer settings 与预览；
- shader compile diagnostics、统计、缩略图；
- Render Effect/Render Pipeline 视图。

退出条件：材质图修改只发布成功编译版本；场景实例热更新；Cook 包含正确依赖。

### Phase 4：动画、VFX、UI、地图（按产品需求并行）

- Animation Clip/FSM/Skeleton/Physics Asset；
- Particle Graph；
- UI Canvas；
- Tile/Terrain/Voxel 工具；
- Timeline/Sequencer。

各域复用 Graph/Timeline/Property/Preview，不允许自建第二套文档与撤销。

### Phase 5：规模化生产

- 结构化 diff、源控 provider、变更列表；
- 包体/内存/依赖审计、chunk；
- 世界分区、Data Layer、HLOD；
- 远程设备 deploy/profile；
- 可选多用户事务会话。

## 15. 关键接口草案

```cpp
class IEditorCommandService {
public:
    virtual CommandResult execute(CommandId, const CommandContext&) = 0;
    virtual bool canExecute(CommandId, const CommandContext&) const = 0;
};

class IEditingHost {
public:
    virtual HostProfile profile() const = 0;
    virtual IInputRouter& input() = 0;
    virtual IPresentationService& presentation() = 0;
};

class IEditableTarget {
public:
    virtual TargetRevision revision() const = 0;
    virtual void* queryCapability(CapabilityId) = 0;
    virtual PreviewResult preview(const DomainCommand&) = 0;
};

class IEditAuthority {
public:
    virtual PreflightResult preflight(const DomainCommand&, const EditContext&) = 0;
    virtual CommitResult commit(const DomainCommand&, ExpectedRevision) = 0;
};

class IEditPersistence {
public:
    virtual PersistenceKind kind() const = 0;
    virtual SaveResult persist(const CommittedTransaction&) = 0;
    virtual RestoreResult restore(PersistenceKey) = 0;
};

class IDocumentController {
public:
    virtual DocumentSnapshot snapshot() const = 0;
    virtual SaveResult save(const SaveTicket&) = 0;
    virtual void discard() = 0;
    virtual ReloadResult reload(const DiskRevision&) = 0;
};

class IAssetDatabase {
public:
    virtual AssetQueryResult query(const AssetQuery&, PageToken) const = 0;
    virtual std::optional<AssetRecord> find(Guid) const = 0;
    virtual DependencyResult dependencies(Guid, DependencyDirection) const = 0;
};

class IAssetTypeProvider {
public:
    virtual AssetTypeDescriptor describe() const = 0;
    virtual std::unique_ptr<IDocumentController> open(Guid) = 0;
    virtual IAssetEditorFactory* editorFactory() = 0;
};

class IPropertyProvider {
public:
    virtual PropertySchema schema(const SelectionSnapshot&) const = 0;
    virtual PropertyValue read(PropertyPath) const = 0;
    virtual std::unique_ptr<IEditCommand> makeSetCommand(
        PropertyPath, PropertyValue, ExpectedRevision) = 0;
};

class IGameEditorExtension {
public:
    virtual void registerTools(IToolRegistry&) = 0;
    virtual void registerPresentation(IPresentationRegistry&) = 0;
    virtual void registerValidation(IValidationRegistry&) = 0;
};
```

接口放置遵循消费者声明原则。`editor` 核心定义通用协议；Scene adapter 所需的场景修改接口由 adapter/`common` 以最小值类型表达，`scene` 模块注册实现。Host、Target、Authority 与 Persistence 彼此不包含具体类型，使同一 Session 能在项目文档和游戏世界间切换。不得为了 Inspector 方便直接把所有模块类暴露给 `editorui`，也不得让游戏 HUD 直接调用 authoring-only 服务。

## 16. 风险与明确取舍

| 风险 | 对策 |
|---|---|
| 先做 UI 导致业务写死在面板 | Phase 1 headless 验收；UI 只调用命令 |
| 反射系统膨胀成全局对象体系 | 显式 descriptor + adapter，不要求所有运行时对象继承基类 |
| 文本场景在大规模下慢 | authoring 文本 + 增量/分区文档；Cook 为紧凑二进制 |
| GUID sidecar 丢失/复制冲突 | 重复 GUID 扫描、明确复制命令、修复向导，CI 验证 |
| 异步任务覆盖新编辑 | revision/ticket/CAS；过时结果丢弃，成功产物原子发布 |
| Undo 恢复到无效裸指针 | 只记录稳定文档/对象/组件/属性 ID |
| 各专用编辑器重复造轮子 | Graph/Timeline/Preview/Property 作为共享组件和契约测试 |
| 巨型 editor 模块破坏裁剪 | manifest 生成注册，业务模块提供 capability |
| Agent 与 UI 行为分叉 | 同一 CommandService，MCP 不直接写文件或对象 |
| 开发编辑器与游戏建造模式各写一套 | 将双 Host/双 Persistence 契约测试作为 Phase 0/1 退出条件 |
| 为复用而把开发权限带进发布包 | Build profile + 命令白名单 + schema 裁剪 + 服务端复验 |
| 游戏规则侵入通用几何工具 | 成本、解锁、权限和玩法限制只进入 Policy/Constraint/Authority |
| 追求 UE 全功能拖垮项目 | 先闭环基本内容生产；高级工具按运行时成熟度插件化 |

## 17. 最小可交付产品（MVP）

MVP 不以面板数量衡量，而以一条完整内容链衡量：

1. 导入 PNG/glTF，生成 GUID、元数据、缓存产物和缩略图；
2. 在 Content Browser 搜索并拖入场景；
3. Outliner 选择对象，Inspector 修改 TRS、mesh、material；
4. Scene View 使用 gizmo、多选、吸附，所有动作可 Undo/Redo；
5. 从对象创建 Prefab，并显示 override；
6. 打开 Material，修改参数或简单图，编译成功后更新场景预览；
7. 保存、关闭、重开保持稳定引用；外部修改能检测冲突；
8. Play/Stop 不污染编辑场景；
9. Validate 与 Cook 能从 CLI、UI、MCP 三处得到一致结果；
10. 同一放置/变换 Tool 可切换到游戏 HUD、SaveGame persistence 和玩法 Constraint，形成可发布建造模式；
11. 一个样例游戏模块可向官方编辑器注入自己的 Tool、Overlay、Inspector 和 Validation，而无需修改编辑器核心；
12. 发布构建不含源文件、EditorOnly 数据和 authoring-only 模块，只包含项目明确选择的 `editing-runtime` 能力。

达到上述闭环后，再增加更多专用编辑器才会形成复利；在此之前添加粒子、行为树或大型地形面板只会扩大基础设施债务。

## 18. 与现有文档的关系

现有 `docs/dev/编辑器模块设计.md` 描述的“可组合构件而非封闭 Editor App”仍然成立，但需要更新解释：

- 引擎核心继续只提供可组合协议与工具；
- 仓库可以额外提供一个由这些协议组装的 **官方参考内容编辑器**；
- 游戏作者仍可替换 Shell、裁剪专用编辑器或把同一 Tool 作为正式玩法；
- 游戏玩法通过 extension/capability 注入工具和领域信息，使官方编辑器自然成为项目专用编辑器；
- 官方编辑器不是业务模块反向耦合的理由。

因此，本提案不是推翻现有设计，而是补齐“构件 -> 内容协议 -> 可替换宿主 -> 官方工作流/玩家玩法”中缺失的中间层。最终目标是让 EVEngine 的轻量模块化、脚本化与 Agent 工作流，拥有足以支撑真实游戏生产和玩家创造玩法的同一套编辑底座。
