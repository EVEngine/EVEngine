核心游戏代码模型
====================

为了实现游戏函数的热重载，要对游戏模型进行仔细设计，尤其对数据、依赖、控制、操作等进行系统性的设计来实现。

# 设计思考

## 游戏是什么

游戏可以看做一个有限自动机，根据输入，状态机发生转移，显示新的内容，如此反复。
那么游戏中的代码函数是什么，是转移规则，是状态转移的转到哪里的逻辑，用户通过编写函数来实现状态的转移，从而使得状态机发生改变，显示内容发生改变。

游戏的原始数据可以看做是初始状态集合，而游戏的存档可以看做是运行期间某个状态的副本，并且可以下次恢复到此处。这样，只要把核心状态维护好，那么是可以实现代码热更新的。

## 对象是什么

object作为把数据和方法打包在一起的结构，可以看做一个小的状态机，所有调用此对象的方法都在依赖此状态机的状态

## ECS的理解

ECS则可以看做是一张大的稀疏的表，横向entity，纵向component，每个entity可以任意组合已有的数据类型，那么只要知道了所支持的component，就可以批量地筛出要处理的数据
使用ECS可以看做是DOD设计中，将各种状态统一放到一张大表中，可以根据需要筛出内容进行处理，我们对状态的管理要参考ECS的设计，将状态整合起来进行管理，脚本中要明确划分功能，数据结构定义时确定entity和component的关系，
而System部分对应脚本中的方法，提供对数据的操作


## 纯OO的思考

在一组互相引用的对象上，假设每个对象都是一个状态机，各自有一些依赖的对象，有的内部包含，有的是多个共享，如果我们修改了一个对象的某个方法，那么可以分情况讨论：
1. 修改的方法没有进行状态转移，是一个只读取的方法（const），那么修改该方法当然是安全的
2. 修改的方法会将初始化的数据以不同方式改变，这时修改方法后，还需要根据外部环境，同步更新当前对象的状态
3. 修改的方法会同时影响其依赖项的状态，这时其依赖项必须也重新刷新构建，为了避免游戏整体状态更新（直接重启），必须对状态间的影响进行一定程度的隔离

## snapshot的作用

在游戏的运行中，如果有一个方法写错了，将游戏状态转移到了错误的状态，那么我们就需要恢复到之前的某个状态，修改方法后重新执行，那么游戏状态就可以继续。
游戏存档也有类似的功能，但游戏存档在很多游戏设计中读取也很费时间，并且一些运行中的场景可能没有设计或不能设计成存档

## 可达状态和不可达状态

在状态表示时，很多状态其实是为了便捷性，而没有压缩储存，比如一些游戏中事件的flag，比如每一章中的flag都是相互独立的，当前一章的某些状态会影响后一章，那么就有状态的可达与不可达，有些状态组合是无论如何都无法到达的。
那么在状态设计时，就可以添加一系列约束条件，来检测状态是否合法，如果一旦进入不合法状态，就会对相关代码发出警告
对于有范围的状态，也一定要对范围进行约束，尽可能保证以下两点：
1. 可达状态都在约束中，不在约束中的一定不可达
2. 约束中的不可达状态尽可能可以通过某些途径变成可达状态

## 脚本中定义的数据结构

脚本中定义数据结构是非常常见的，而这种定义数据后的实例，同样是状态的一部分，如果我们把引擎做成无状态的，那么我们只需要对所有squirrel中内存对象建立有效管理，就可以对游戏状态进行维护，实现snapshot等功能。
当然，脚本中的数据结构也有很多是根据当前核心状态派生出来用来显示的，那么我们可以对核心的状态让用户进行标记（比如添加attribute），之后就可以跟踪并对其进行维护，用户需要保证其他状态是在




# 设计草案

## 多层级模型方案

我想避免单一设计模式对系统的局限，要在恰当的部分组合实现对不同设计模式和模型的整合。

基础架构分为4层：
1. 模型 - 脚本定义的数据结构，这部分采用ECS模式，把数据作为核心
2. 逻辑 - 游戏的核心逻辑，update函数中对状态更新逻辑，采用传统OOP的方式组织，但也有抽象出来的逻辑作为ECS的一部分
3. 渲染 - 无状态的渲染类，可以有内部数据和状态，但所有数据在每帧会根据核心模型状态而刷新，不能影响模型，模型改变时，其内部状态也要下一帧自动改变
4. 交互 - UI和用户输入，这里的核心是一个View Model，通过对UI建模，来实现对显示位置，显示数据，用户操作的绑定，这里把用户的操作抽象成了对UI数据的操作，进一步绑定成为了对模型数据的操作


## 模型层设计

模型是游戏的核心，也是游戏脚本中要定义的最重要数据结构，我们可以认为数据的状态机的状态，每个数据的更新规则都是根据上一帧的状态和input，来更新下一帧的状态，每个更新规则都是不依赖当前帧的计算结果的，所以我们可以开一个滚动数组，来反复用上一帧的数据来并行地更新下一帧的数据，同时把这些数据的变化用渲染器部分渲染到屏幕上。

ECS的模型可以定义成以下模式：

#include <MapPosition.h>

class Monster {

    struct Status {
        // 用户自己定义当前状态
    };
 
    struct Porperty {
        // 自己定义当前属性
    };

    component<Monster::Status>  status;
    component<MapPosition> position;
    component<Monster::Porperty> porperty;
}

component定义为一个id, 是数据表中的一个值，所有相关属性的直接访问都定义为对不同数据表的操作

component<Template> 会创建一个static的表，用来存储所有的实例


这个用户创建的类也可以被放到component里面，用作其他类的属性
同时你也可以使用继承，将类派生出来，这时，component将采用块状链表的形式在处理父类对象时，把继承的子类对象也一并放入迭代器处理。

class Goblin : public Monster{
    struct Status {
        // 额外的特殊状态
    };
    component<Goblin::Status> status;
}

这时每个属性会给Goblin类也同时开一张表，但会向Monster类创建访问指针，使其能够同时迭代子类的对象
