# 原生 ECS 容量试验记录：2026-10-22

这是共享云 VM 上的初始测量，不是产品硬件验收。内核为原生 ECS 的两列/四列更新，未运行 Scene、脚本、AI、物理或渲染。

环境：Intel Xeon Platinum 8573C，x86-64 Linux，GCC 14.2.0，Release / `-O3 -DNDEBUG`，单线程；容器 CPU 配额 4 核、内存上限 16 GiB。每个 sample 是 3 次完整更新的平均耗时，warmup=5、samples=21。RSS 包含辅助 Handle 数组和进程开销。

## 可以据此采取的行动

- 300 万实体的数据更新与删除/复用/defer 生命周期校验均能完成；这是容量与正确性证据，不是实时帧预算达标。
- 本机百万稠密两列更新的实测时间超过 16.67ms，即使不计其他阶段也无法据此宣称 60 FPS 百万活体全量更新。须在目标硬件复测，并制定 ECS 阶段预算。
- holes90 只剩 10% 活体，时间仍接近原始槽位规模的扫描。优先 profile View 准备、位图检查及空槽扫描；不要先引入 Tag/Archetype 或整体压实。
- 连续 vector 参考明显更快，提示有优化空间，但它没有实体身份、位图、继承和生命周期成本，不能把全部差额归因于 deque。
- cold 场景保留的 256B/实体数据确实被分配、触及并校验，RSS 明显增长；更新不读取冷列。共享 VM 下的时间差不能单独证明热冷隔离效果。
