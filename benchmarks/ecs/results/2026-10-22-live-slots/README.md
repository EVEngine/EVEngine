# View 死槽准备与稳态缓存优化

日期：2026-10-22。范围：原生 ECS 的 View 准备；不改变实体类型分类、继承查询、Handle 或组件列的存储方式。

## 修改与语义

旧实现按历史槽位前缀补建所有默认组件：创建 130 个实体、初始化组件、销毁 129 个后，下一次
View 会额外默认构造 129 个组件。现在只为非 dead 实体补建，staging 实体仍准备组件但暂不参与
遍历。原始 `ComponentBuffer::engageUpTo` 与公开 `View::engageSlots` 的前缀构造语义保留。
复现输入见 [计数程序](dead-slot-probe.cpp)，输出见 [修改前](before-probe.txt) 与
[修改后](after-probe.txt)：存活均为 1，额外默认构造从 129 降为 0。

仅逐槽判断 dead 的初版导致稀疏稳态反复检查空槽，耗时明显回退，因此未采用该版本。
最终实现保留完整组件位图 word 的快速跳过，并按具体类型 Manager 的实体修订号、组件列
presence 修订号及准备范围缓存一次无构造回调的完整检查。稳定且未变化的列直接复用检查结果。

实体创建（包括旧 staging 发布）和销毁使 Manager 修订号变化；组件 mark/unmark 使列修订号
变化，覆盖补建、显式移除和迁移。修订号和缓存只是内部失效索引，实体 flags 和现有 presence
位图继续是权威状态。通过正式创建/销毁/组件 API 修改状态；直接改 flags、container 或位图
不属于缓存契约。一次准备调用了构造函数或抛异常时不保存缓存，避免构造回调清空早先槽位后
被错误地认为已完整准备。之后一次无回调检查才缓存结果。

缓存成本为每 Manager 一个修订号、每组件列一组固定元数据，不增加逐实体或逐组件槽位开销。
不压实 deque，不释放历史原始槽位容量；不能把构造次数下降表述为 RSS 必然下降或扫描范围缩短。
View 的遍历阶段仍需沿历史槽位检查可见性。

## 测量方法

GCC Release，同一工作树、同一百万实体输入，三轮独立进程，奇数轮 before→after，偶数轮
反向。before 包含前两批已完成修改；after 增加本次补丁。每轮 11 个样本、3 次预热，样本为
连续 3 tick 的平均。prepare 测 View 构建/析构，其余测完整 update tick。原始 CSV 和校验
stderr 保存在同目录；只有进程成功退出且 `validation=passed` 的记录参与比较。

环境与源文件/二进制哈希见 [environment.json](environment.json)。最终对照在编译结束后固定 CPU 4
进行，源码检查仍在运行；共享 VM 结果不能作为独占硬件的加速承诺。此前与编译重叠的
[探索数据](contended/README.md) 单独保留。p95/p99 是批次均值分位数，
不是单帧尾延迟。构造计数和契约验证不依赖计时噪声。

| 场景 | 修改前 p50 中位数（ms） | 修改后（ms） | 三轮 after/before |
| --- | ---: | ---: | --- |
| prepare | 0.135827 | 0.000061 | 0.000862×, 0.000449×, 0.000419× |
| dense | 72.948366 | 52.830649 | 0.581×, 1.01×, 0.904× |
| holes90 | 31.640215 | 32.506491 | 0.896×, 1.54×, 0.881× |
| refill | 53.378724 | 44.657810 | 0.614×, 1.08×, 0.974× |
| deferred | 47.269972 | 51.098405 | 1.03×, 1.18×, 1.08× |

最终三轮中 deferred 的 update_tick 比值均高于 1，其他更新场景也存在双向波动。
因此只确认死槽构造消除及稳态准备成本下降，不宣称整体更新全面加速；deferred 的性能趋势
需要在受控机器上继续确认。缓存未改变遍历阶段随历史槽位增长的复杂度。

## 验证与边界

新增用例覆盖跨 64 槽组的销毁、全部销毁、继承、槽位复用和 stale handle、staging 发布/取消、
构造期间销毁、缓存后的组件移除，以及构造回调清空早先槽位后的重试。
原有抛异常、非默认构造、Table 隔离及 defer 契约继续运行。

原生与 OBJECT/SHARED foundation 组合测试、严格 C++17 fixture 由 standalone CTest 执行；
这不是完整图形引擎或 Windows DLL 验证。ASan/UBSan 使用 `detect_leaks=0`，不声称完成泄漏检测。

验证结果：14/14 CTest 通过；原生契约 18 用例、1164 断言通过，ASan/UBSan 同样通过。
日志见 [CTest](ctest.txt)、[契约](contracts.txt)、[ASan/UBSan](asan.txt)。
三轮五场景共 30 个百万实体进程均通过完整结果校验。
`make check` 通过，包含 313 个脚本测试；[完整门禁日志](source-quality.txt)。
补丁初次应用、重复应用和全序列重放通过。

此次遵循领域短根、组件所有权、Handle 代际、单一权威状态和 defer 约束，无架构例外。
Manager/组件列布局变化，需要 engine/SDK、静态库、DLL 和插件一致完整重编译。
补丁通过主工程及 standalone CMake 同时应用，不更改子模块 pin。
回滚时从两处补丁列表移除 `ecs-view-live-slots`，还原对应 vendor 补丁并完整重编译。
