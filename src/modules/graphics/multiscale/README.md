# Explicit multiscale view queries

Default-OFF L4 graphics satellite depending on graphics and spatial_multiscale.
The first boundary is an owning sphere-to-NDC query, not a replacement camera or
completed rendering mode. Old camera, depth, postprocessing and module defaults
are untouched. Actual rendering requires a separately validated depth/occlusion
path; these rectangles alone do not authorize compositing independent layers.

One known view owner calls a constant-cost pure query for each active candidate.
Known observer, per-candidate frequency, single consumer and value-only atomic
return select direct calls. Six boundary faces: C++ queries and explicit script factories, no capability
registration, ECS/Link, events or tool protocol. Headers forward-declare
spatial values. There is no saved format, retained pointer, ownership transfer to
a renderer, implicit time or RNG. Restored scene values are queried afresh.

The caller supplies one common dyadic lattice and an orthonormal camera basis.
Sphere radii have mantissa/exponent physical units. Address subtraction happens
before double conversion; calculation remains in lattice units, so physical
distances beyond binary64 are never constructed. The query has no far plane.
Measured basis norms inflate radius, center errors propagate through the basis,
and interval division yields conservative screen rectangles. Rectangle width is
an upper bound for screen occupancy, not the exact silhouette or an LOD error.

Bounds wholly behind the camera or outside the viewport can reject geometrically.
A bound that intersects the camera plane returns the whole viewport and requires
the caller to refine; it is never dropped because projection is singular. Invalid
inputs and numerical range limits return structured failures. Radius underflow
rounds conservatively upward; enormous enclosing radii remain visible candidates.
Total traversal, final emissive compositing, shape approximation, depth, shadows,
transparency, picking and temporal stability remain separate acceptance work.

`FarFluxFrame` is a separate, explicit CPU point-emitter preparation path. It projects
positions in the same dyadic lattice and accumulates inverse-square linear RGB flux
into a bounded image in O(emitters + pixels) work. A bright source can remain
representable at the far end of the finite lattice without a far clip. An uncertain
direction may span at most two rows and columns; its flux is shared among those
pixels, while larger ambiguity, singular distance and numeric over/underflow fail
with a Result. The frame owns its pixels and does not change legacy camera behavior.
It has no GPU presentation, exposure, occlusion or PSF integration yet, so this CPU
image alone is not visual proof of a visible distant star.

No universal O(pixel count) traversal claim is made. This query is O(1) per active
bound and allocates no success-path containers; scene traversal must bound its own
work explicitly. Numerical contract assumes IEEE arithmetic with gradual underflow
and no fast-math. Replay is tolerance-based, not bitwise across backends.

## Dedicated opaque sphere reference view

SphereFrame validates and owns a complete render snapshot before GPU work.
SphereView owns a fixed quad and shader through Graphics' weak resource lifetime.
Consumer-first destruction releases GPU storage and deletes the transferred CPU
facades; provider-first destruction revokes access without dereferencing handles.
Frames keep no scene/provider pointer and must be rebuilt by the authoritative
scene owner after changes. Rendering borrows the frame synchronously.

render owns begin3DFrame/present and requires a fresh frame boundary. draw begins
the same dedicated pass but leaves present to the host, including the normal
engine render callback. Neither entry point may follow another open 3D pass.
Do not interleave old-scene draws or postprocessing that assumes the legacy depth.
It is an unlit opaque sphere reference renderer, currently Vulkan only; other
backends reject explicitly. No module boot, camera defaults or old shader changes
are made. The checked-in shader arrays are generated by
scripts/compile_multiscale_shaders.py from the adjacent GLSL sources.

Centers/radii are normalized by a per-sphere power of two. The fragment shader
intersects the view ray with that sphere and writes
`(log2(rayDistanceInNormalizedUnits) + physicalExponent + 2048) / 4096`.
All spheres share this encoding, so relative visibility is depth-tested within
the view, independently of draw order. This is not two independent color layers.
Preparation rejects normalization overflow, physical exponents outside [-2000,2000],
radius/distance below 1e-5, and camera-on-surface uncertainty within 1e-5 relative.
These are explicit reference-path limits, not silent distance culling. Ordinary
depth-buffer quantization and float ray-intersection error remain; close surfaces
can have indistinguishable encoded depths. A certified total pixel/depth error
budget is not yet provided.

Frame preparation is O(N), with an explicit input count limit. Rendering currently
submits a projected rectangle for each visible sphere: worst-case O(visible N * viewport pixels)
fragment work. This is a correctness reference, not the million-state performance
path. Subpixel flux, detailed meshes, transparency, shadows, picking and temporal
history are not implemented by it. A provider exception during GPU submission
returns Failed but is not an atomic rollback of GPU commands; the host must recover
the graphics frame/provider rather than assuming a partially submitted pass can
be retried unchanged. Input validation and moved/stale checks happen before drawing.

Rectangle preparation unions the mathematical AngularBounds with a bound of the
represented float GPU sphere. The latter inflates radius by
128 * float epsilon * (center distance + radius), and rectangle endpoints round
outward before viewport clipping. This float guard is not a certified complete
shader-error proof. Camera-plane-intersecting or guarded-near-plane spheres keep
the full viewport. The fragment ray and common depth equation are unchanged.

## Explicit GPU batch preparation and updates

SphereBatch::prepare(Graphics&, SphereFrame const&) copies the validated visible
records into an RGBA32Float texture and uploads valid identity instance matrices
through the existing resource-program interface. It returns an owning Result;
no frame pointer is retained. Preparation costs O(visible N) plus pipeline creation,
and is outside render passes. It admits at most 1,000,000 visible records; device
limits or missing SPIR-V validation return explicit failures. Empty frames still
validate resource support. There is no silent fallback to a slower renderer.

SphereBatch::draw() begins the dedicated pass and submits one instanced draw for
a nonempty batch. The host presents afterward. CPU frame destruction does not affect the upload. Graphics
destruction revokes access through its weak lifetime. Both reference and batch
draw reject headless providers before attempting swapchain presentation.

The script factory exposes prepareSphereBatch(gfx, frame); the returned owned
MultiscaleSphereBatch has draw() and update(frame). These operations use the common Result table,
strict native type checks, and the existing VM ownership bridge. Preparation and
drawing are graphics/VM-thread-only and non-reentrant. Reload rebuilds snapshots;
this API introduces no persistent format, ECS owner, event or capability registry.

At least 128 bytes per visible instance are uploaded before padding and CPU mirrors.
One submission does not bound fragment overdraw, nor eliminate upload, rebuild or
memory costs. This is not evidence of million-object whole-frame 60 FPS acceptance.

`SphereBatch::update(frame)` consumes an already built CPU frame synchronously, without retaining it.
Capacity is fixed to max(1, initial visible count); updates may shrink to zero and grow back within
that capacity. The existing pipelines, instance matrices, image and descriptors are retained.
The graphics-owned `ShaderImageUpdate` token validates and copies the complete numeric image;
application waits for prior resource use, then uploads it with explicit image barriers. This is a
synchronous update, not an asynchronous streaming or zero-stall guarantee. Shape mismatch, shared
image identity, moved frames, excess counts and stale providers reject before writes. Device failure
after GPU submission requires recovery; it is not an atomic rollback of submitted image writes.
The old immutable resource-replacement API and deduplicated images keep their existing semantics.
